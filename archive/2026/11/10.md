![Mac 上开着终端，屏幕里是磁盘清理工具的预演清单](https://imgs.huluohu.com:443/2026/11/10/20261108-0600-mole-cover-v2-cover-long.jpg)

> 同一台 Mac，同一条清理命令，隔夜报出的可清理空间从 412.7MB 变成 10.40GB，差的 7GB 藏在 169 个被记成 0B 的目录里。

周一早上六点，这台 Mac mini 的系统盘只剩 8.8Gi 可用。机器是 Apple M4，16GB 内存，228.3GB 的 APFS 系统盘，跑着 [macOS](https://www.huluohu.com/posts/tag/macos/ "macOS") 27.2；`df -h /System/Volumes/Data` 报 `228Gi 190Gi 8.8Gi 96%`。

11 月 8 日傍晚 17:57，这台机器上跑过一遍 `mo clean --dry-run`，结尾报 `Potential space: 412.7MB+ · 442 items`。四百来兆，清不清两可。第二天下午 06:07，同一条命令原样再跑一遍，同一版本 V1.69.0，结尾变成 `Potential space: 10.40GB+ · 468 items`。第三天早上 06:12 再跑，同一台机器同一版本，是 `9.88GB+ · 437 items`。

差了 25 倍。硬盘上并没有多出 7GB 垃圾，变化出在清单本身。

![两天里同一条清理命令报出的空间数，0B 目录数从 169 条掉到 34 条](https://imgs.huluohu.com:443/2026/11/10/20261108-0600-mole-v2-fig1-clean-vs-real.jpg)

## 169 个目录被记成 0B

`mo clean --dry-run` 会把明细写进 `~/.config/mole/clean-list.txt`，每行是路径加体积。11 月 8 日那份清单捞出来数：`grep -c "# 0B"` 返回 169。第二天的清单用同一条 grep，只剩 35。第三天 34。

11 月 8 日那 169 条，今天用 `du -skP` 逐条重新量：155 条现在读得出来，合计 7.49 GiB；剩下 14 条已经不存在了，多半是系统轮转掉的日志。11 月 8 日清单合计 0.40 GiB，加上这 7.49 GiB，和第三天清单 9.79 GiB 的量级正好对上。

为什么第二天量不到？Mole 的源码写得很直白。`lib/core/file_ops.sh` 第 2112 行附近，它用 `du -skP` 量每个目录，紧接着一行 `[[ $size_rc -eq 0 ]] || size_kb=0`：du 一旦失败或超时，体积直接记成 0，不报错也不提示。`lib/clean/user.sh` 第 2606 行还给 Application Support 路径下的每个目录只留 0.4 秒体积预算（`local size_timeout_seconds=0.4`），超时同样按失败处理。

量不到的目录和真空目录，在清单里都写成 `# 0B`，长得一模一样。

## 手动复现了一遍

光读源码不够，在 /tmp 下造了个目录，里面放一个锁死的子目录：
    
    
    mkdir -p /tmp/zero-test2/locked
    dd if=/dev/zero of=/tmp/zero-test2/locked/f bs=1m count=200
    chmod 000 /tmp/zero-test2/locked
    du -skP /tmp/zero-test2   # 返回 rc=1，输出 0
    

du 返回 rc=1，输出 0。同一个父目录下的另一个可读子目录，同一条 `du -skP` 照常报出 51200 KB。一个能读一个不能读，两者在 Mole 的清单里写法相同。

那 7GB 差额的机关就在这里：11 月 8 日那 169 个 0B 条目里，大部分是当时没量出来的真东西。

## 数字对上了，再看这个工具本身

Mole 是 GitHub 上 tw93 开源的[命令行](https://www.huluohu.com/posts/tag/%e5%91%bd%e4%bb%a4%e8%a1%8c/ "命令行")工具 `mo`，2026-11-10 实拉是 74405 颗星、2675 个 fork、2 个未关闭 issue、149 个订阅者，GPL-3.0 许可，主语言 Shell，2025-09-23T06:38:40Z 建仓，仓库 archived 字段是 False，最后一次提交在 2026-11-09T16:22:10Z。仓库最新 release 是 V1.70.0，发布于 2026-11-08T09:55:08Z，本文装的是上一版 V1.69.0；平均 0.4 天一个版本，最近 30 次提交只跨了 1 天，7 位作者在维护，贡献者名单 API 返回 100 人。这台机器上是拿仓库里的 `install.sh` 装到用户目录的，`~/.local/bin/mo` 只是个转发脚本，真正的实现放在 `~/.config/mole` 下；仓库也提供 `brew install mole`，但 brew 那份只装 CLI。

今早这次完整预演跑了 38.60 秒，面板报 `Free space: 9.29GB`，`Whitelist: 22 core patterns active`。清单里用户缓存 46 项合计 7.84GB，Homebrew 能省 114MB，应用残留只找到 1 项 0.1MB，用 `--debug` 追出来是 `com.tencent.LemonUpdate` 的缓存。白名单里的默认规则 `$HOME/Library/Caches/ms-playwright*` 把 2.67 GiB 的 Playwright 缓存拦在清单外，今天清单里 grep 不到它。内置保护还有 gradle caches、ollama models 和 JetBrains 等一批，用户也能往 `~/.config/mole/whitelist` 里自己加路径。仓库与 App 是两回事，README 里写明这个仓库是命令行工具那一半，想用图形界面得单独下载 Mole for Mac，图形版才有「删除前逐项确认」。

大块的东西它只标记不动手，标个 `⊙` 让你自己确认（同一分钟预演出来的读数）：Docker 四个子项合计 13.036GB（镜像 5.033GB，Docker 那份 build cache 8.002GB，其中 7.611GB 可回收），Gradle 缓存 1.22GB，安卓虚拟设备 6.26GB，JetBrains 旧版本数据 2.45GB，加起来 22.97GB。这些跟 `docker system df` 和 `du -sh` 复算的结果一致，差别只在 GiB 和 GB 的单位口径。

![终端里逐层展开的磁盘目录树，每个目录右侧直接标着体积](https://imgs.huluohu.com:443/2026/11/10/20261108-0600-mole-v2-shot-analyze-horizontal.jpg)

`mo analyze` 是另一路本事：扫 `~/Library/Caches` 只用 0.16 秒，136 个条目合计 15.44 GiB，终端里目录树逐层展开，每个目录右侧标着体积。

![终端里扫完整个缓存目录，十五点四 GB 总量逐条列出](https://imgs.huluohu.com:443/2026/11/10/20261108-0600-mole-v2-shot-analyze-vertical.jpg)

`mo installer --dry-run` 专盯 Downloads 目录里下完就忘的安装包（本机这次预演的结果）：Clash.Verge 的 dmg 80.8MB，Manus 安装包 187.8MB，sidecar-monitor 123.5MB，Ottr 9.3MB，还有 ChatGPT 安装器 849KB 和 Homebrew 留下的 Squirrel 25.5MB，逐个标出体积。每次操作都留档，`mo history --json` 能翻，日志写在 `~/Library/Logs/mole/operations.log`。

`mo status` 给个健康分。源码里写着从 100 分往下扣，磁盘权重 20，已用超过 93% 时按 `20 × (已用 − 80) ÷ 20` 扣。这台机器已用 95.99%，磁盘一项扣掉 15.99 分；内存 79.48% 扣 5.20 分，开机 8 天 6 小时没重启再扣 1 分，CPU 占用 13.20% 还在 50% 的警戒线以下没扣分，最后 76 分落在 Good 档，评语是 `Good: Disk Almost Full`。跑 `mo status --watch` 时顺手用 lsof 查了同一时刻的出网，对外连接 0 条。

![工具的健康分从一百分往下扣，每一项扣多少都标在图上](https://imgs.huluohu.com:443/2026/11/10/20261108-0600-mole-v2-fig3-health-score.jpg)

磁盘数字本身也有三种口径。同一分钟里 Mole 面板报 9.29GB，`df -h /` 报 `Avail 8.8Gi`，Mole 自己算的已用是 95.99%。三个数都对，算法不同。按同一分钟 status JSON 里的数复算一遍：total 245107195904 减 used 235289829376 得 9.82GB，扣掉可清除的 0.25GB = 9.57GB，和面板那个数对得上。

## 同类对比：同扫一个目录

`~/Library/Caches` 这一个目录，三个工具各跑一遍（2026-11-10 早上，同一台 Mac mini）：

工具 | 报的总量 | 耗时  
---|---|---  
`mo analyze --json`（Mole V1.69.0） | 15.44 GiB，136 个条目 | 0.16 秒  
`dust -d 1`（v1.2.7） | 17 GiB | 0.12 秒  
`du -sh` | 16G | —  
  
前两者的前五大完全对得上：JetBrains 和 ms-playwright 排前二，后面依次是 WhisperModels、Microsoft Edge 和 pip，连排序都一致。

要注意 dust 也会撞权限墙。它扫同一目录时明确提示 `Did not have permissions for all directories`，被挡的 CloudKit、Safari 等 10 个目录一律显示 0B。静默记 0 这件事 du 系工具多少都有，Mole 的问题在于清理清单里没有任何标记区分。

同一个量不到的机制，在 Mole 的另一条路上换个写法。issue #1956 里有人报告 `mo analyze` 概览把 `Applications` 和 `User Library` 的体积写成 `unknown`，报告人自己量的耗时是 33.64 秒和 22.49 秒，卡在 30 秒上限上；维护者把上限放宽到 5 分钟。另一条 issue #1960 说的是：Mole 跟 DaisyDisk 有同样的磁盘访问权限，却比 DaisyDisk 少看到约 70GB 存储，得靠 DaisyDisk 才能定位系统数据和隐藏数据。

这三条摆在一起是同一件事：Mole 少看的部分，正是它读不出来的部分。`analyze` 那次报 15.44 GiB 也不代表它扫全了，同一份 JSON 里 `scan_status` 字段写的是 `partial`。

## 踩到的五个坑

**坑一：量不到的目录被记成 0B，和真空目录混在一起。** 这是全文最硬的一条。du 失败或超时，源码直接 `size_kb=0`，清单上写 `# 0B`，没有任何标记，隔夜两次 dry-run 的总数能差 25 倍。解法：同事要是打算真删，先别信总数：把这些条目 grep 出来用 `du -skP` 逐条复量，或者换个时间再跑一遍 dry-run 对比。

**坑二：浏览器测试工具的二进制被当成缓存删掉。** issue #1945 里有人报告 `mo clean` 删了 `~/Library/Caches/Cypress`，那是 Cypress 运行器二进制的全局安装位置，删完要重新下载约 1.5 到 2.5GB 才能跑测试。#1941 是 Camoufox，清理后要重下约 1.3GB（解压后 2.4GB），而且「Most people won't connect the failure to their last mo clean」。这两条已经关掉了：维护者在评论里说已在 main 修好，还专门装 Cypress 16.2.1 验证过，旧的 main 删完 `cypress verify` 失败，修好的分支跑得通；Puppeteer 的 `~/.cache/puppeteer` 也一并保护起来了。解法：项目里用了 Cypress 或 Puppeteer 的读者，升级前先往 `~/.config/mole/whitelist` 里手动加上这两处路径。

**坑三：默认永久删除，不进废纸篓，CLI 也没有逐项确认。** 缓存清理底层是 `rm -rf`，卸载残留的 `MOLE_DELETE_MODE` 默认取 `permanent`，「删除前逐项确认」是图形版 Mole for Mac 的能力，CLI 没有。设成 `trash` 后如果废纸篓不可用，它会拒绝执行并报错，不会偷偷降级成永久删除；每次删除都写一行到 `~/Library/Logs/mole/deletions.log`。解法：先 `mo clean --dry-run` 看清单，确认无误再跑真删，介意就设 `MOLE_DELETE_MODE=trash`。

**坑四：系统缓存和废纸篓默认扫不到。** 预演输出里明写 `System caches need sudo` 和 `Trash · skipped, grant Full Disk Access to your terminal`。这台机器 sudo 要密码，`sudo -n` 不可用，这两块直接缺席。解法：想要完整预演就先 `sudo -v`，并给终端授予完全磁盘访问权限。

**坑五：`mo purge` 会重复列目录。** 同一个编译产物目录在 `/Volumes/ssd` 挂载下会被列两遍，软链和挂载各算一次，预演体积虚高。解法：看 purge 清单时留意重复路径，去重后再估算。

## 局限：还有哪些没测

  * 没跑 `mo uninstall` 的完整交互流程，只做了源码级核实和受控函数级验证。
  * 系统缓存部分要 sudo，这台机器 `sudo -n` 不可用，没测。
  * Windows 和 Linux 版没测，图形版 Mole for Mac 是另一个下载，也没测。
  * Time Machine 清理因本机有备份任务在跑被跳过，`mo purge` 只做了预演。
  * 11 月 8 日那 169 个 0B 条目具体是被权限还是超时挡住的，没有逐条定位，只证明了「du 读不到就记 0」这条机制成立，以及其中 155 条今天能读出 7.49 GiB。
  * issue #1960 说的「比 DaisyDisk 少 70GB」没有逐项对上，这台机器没装 DaisyDisk，那 70GB 落在哪些目录上没有核实。
  * issue #1956 说的超时上限已放宽到 5 分钟，但只验证了 `analyze --json` 的 0.16 秒路径，没造一个超过 30 秒的大目录去触发新上限。
  * 磁盘剩余空间在这台机器上每过一阵就变一次（8.8Gi 到 9.4GB 之间波动），正文所有磁盘数字都锚定在 2026-11-10 06:11 那次采样。

## 装完之后先做这三件事

  1. 装上：仓库里的 `install.sh` 装到用户目录，或者 `brew install mole`；装完 `mo --version` 确认版本。
  2. 先跑 `mo clean --dry-run`，再打开 `~/.config/mole/clean-list.txt`，把 `# 0B` 的行 grep 出来逐条复量。
  3. 用 `mo analyze ~/Library/Caches` 看清空间分布，确认白名单拦住的东西没问题，再决定真删。

今晚就能试的第一件事，是把清单里 `0B` 那几行数一遍。

这台 Mac mini 的硬盘最后还剩 8GB 上下，清单里的 9.88GB 一个字节没动。清理工具报的数字，只代表它量到了多少；你真正有多少，得自己再量一遍。

清单里那 169 行 0B，多数目录里实实在在有东西，只是没量出来。下回清理工具报出一个诱人的总数，先把 0B 条目数一遍再动手；适合转给那种同事：Mac 上常年腾不出空间、装完清理工具就以为已经清干净，多半没翻过自己清单里那几行 0B。

什么是阿里云 ESA 

阿里云 ESA（Edge Security Acceleration，边缘安全加速）是集 CDN 加速、边缘安全防护、边缘计算和 HTTPS 管理于一体的边缘云服务。相比传统 CDN，ESA 在国内节点覆盖、边缘安全能力、易用性和前端部署（ESA Pages）上都有更出色的体验，是面向国内用户业务的省心之选。

折腾域名和站点这几年，换过不少加速方案，最后留在手边的还是[阿里云 ESA](http://s.tb.cn/e6.0Fu67m)。以前用 CF，最头疼的就是国内访问不太稳定，网络状况差的时候图片常常要转圈好一会儿；换成 ESA 后，国内节点的体验明显顺畅了不少。再加上 ESA Pages 的前端部署也很省心——托管、证书、防护基本一套就理顺了，少折腾一点，多留点时间给正事。

## 想要一个自己的右键菜单 

起因很朴素：看别人的博客右击有自定义菜单，觉得挺帅。

第一版我写得很干脆，在 `document` 上挂 `contextmenu`，上来就 `preventDefault()`，然后弹自己的菜单。全站接管，一步到位，感觉自己赢麻了。

结果用起来处处别扭。在搜索框里想粘贴，弹的是我的菜单；在评论区想检查文字，弹的是我的菜单；想在新标签页打开个链接，还得先在菜单里找一圈。最要命的是手机上，长按也归我管了，那我到底是给人用还是给爬虫用。

后来一点点改，改到最后发现：**这个需求的难点根本不在 "画一个菜单"，而在"决定哪些位置不该归我管"**。

## 全站接管的三个陷阱 

一开始的问题可以归成三条，都是"过度接管"带来的。

**第一，输入框被抢了。** `input`、`textarea`、`contenteditable` 这些地方，浏览器原生菜单里有"粘贴"、“撤销”、“检查拼写”、“输入法开关”，这些能力我根本没法复刻。抢了之后就只剩一排没用的自定义项。

**第二，链接和图片的操作被吞了。** 原生菜单在 `<a>` 上会给你"在新标签页中打开链接"、“复制链接地址”，在 `<img>` 上会给你"图片另存为"、“复制图片”。这些功能我的菜单里没有，等于我白抢了一个位置还没补上。

**第三，移动端长按。** 手机上 `contextmenu` 事件和长按选择是绑在一起的。拦掉之后，用户长按想选个字都做不到。这个体验破坏得最彻底，因为没有替代方案。

所以我后来的判断标准变成了一句话：**能不接管就不接管，必须接管的地方要把原生的能力补回来** 。

## 分层放行：按目标元素决定 

实现上其实很简单，就是开一个白名单，命中就 `return`，放行给浏览器。

    document.addEventListener('contextmenu', function (e) {
      // 触屏设备交给系统长按菜单
      if (window.matchMedia && window.matchMedia('(hover: none)').matches) return;
    
      var t = e.target;
      if (!t || !t.closest) return;
    
      // 让原生菜单继续工作的地方

`matchMedia('(hover: none)')` 这一行是分水岭。它判断的是"这台设备有没有精确的悬停指针"，触屏设备命中，直接放行。比起用 `touchstart` 去猜，这个判断更稳，因为笔记本插了鼠标时它不会误判。

`closest()` 比 `tagName` 判断靠谱得多。因为 `e.target` 往往是深层的 `span` 或者 `code`，真正的输入框在好几层外面。写成 `t.tagName === 'INPUT'` 会漏掉一大半情况。

## 光标位置会被菜单吃掉 

输入区里的剪切、复制、粘贴，绕不开一个具体问题：**点菜单会把焦点拿走** 。

正常流程是：鼠标在输入框里选中一段文字 → 右键 → 点"复制"。但你点菜单的那一下，`focus` 已经从输入框移到了菜单上，选区也可能被清掉。这时候去执行 `execCommand('copy')`，复制的是空字符串。

修法是右键的瞬间先把选区记下来，执行动作之前再恢复。

    function saveEditSel(el) {
      if (typeof el.selectionStart === 'number') {
        ctx.ss = el.selectionStart;
        ctx.se = el.selectionEnd;
      } else {
        var s = window.getSelection();
        ctx.range = (s && s.rangeCount) ? s.getRangeAt(0).cloneRange() : null;
      }
    }
    
    function restoreEditSel() {
      var el = ctx.el;
      el.focus({ preventScroll: true });
      if (typeof el.setSelectionRange === 'function' && ctx.ss != null) {
        el.setSelectionRange(ctx.ss, ctx.se);
      } else if (ctx.range) {

        s.removeAllRanges();
        s.addRange(ctx.range);
      }

`{ preventScroll: true }` 这个参数别省。不加的话，`focus()` 可能会把页面滚动到输入框位置，右键菜单位置就飘了。

`Range` 的 `cloneRange()` 也值得说一句。如果不克隆，直接存 `getRangeAt(0)`，后续 DOM 变化会让这个 Range 失效或者位置跑偏。克隆一份是保留快照。

## 菜单里的"粘贴"不可能百分百成功 

这是我最想单独拿出来讲的一段，因为**这是浏览器的硬限制，不是代码写得不好** 。

复制好办。`navigator.clipboard.writeText()` 在 HTTPS 下直接可用，失败就降级到 `document.execCommand('copy')` 加一个临时 textarea。

粘贴是另一回事。**浏览器不允许脚本主动往页面里写入剪贴板内容** ，因为这是个安全漏洞——想象一个网页能在你不知情的时候把你剪贴板里的密码填进表单。

所以正确姿势是分层降级：

    function paste() {
      // 一、先试 execCommand('paste')，现代浏览器基本都已禁用
      var ok = false;
      try { ok = document.execCommand('paste'); } catch (e) {}
      if (ok) return;
    
      // 二、读剪贴板，需要用户授予 clipboard-read 权限
      navigator.clipboard.readText().then(function (text) {
        // 三、拿到文字后自己插入，还是得靠 execCommand('insertText')
        //    不行就手动切字符串插进 value
      }).catch(function () {
        toast('浏览器不给读剪贴板，请按 Ctrl+V');
      });
    }
      
  
---|---  
  
三层降级，每一层都可能失败。`execCommand('paste')` 在 Chrome 里早就返回 `false` 了；`readText()` 会弹权限请求，用户点了拒绝就没戏；就算拿到文字，往 `contenteditable` 里插还得靠 `insertText`，而这个命令也在被逐步废弃。

对 `input` / `textarea` 我加了最后一道保险：直接操作 `value` 和 `selectionStart`。这个一定能成，但只对原生表单元素有效，`contenteditable` 没法这么干。

**结论是：菜单里的 "粘贴"是个尽力而为的功能，键盘 `Ctrl+V` 才永远可靠。** 我在菜单项的失败提示里就写"请按 Ctrl+V"，不装作能成。

## 键盘和右键不能互相打架 

这一点是我最初差点搞砸的地方。

自定义菜单做出来之后，很自然的一个念头是：“我把 `Ctrl+C` 也接管一下吧，统一走我的复制逻辑，这样提示也统一。” 这是个坏主意。

因为**键盘复制比菜单复制重要得多** ，而且原生行为已经足够好。一旦 `preventDefault()`，你就得自己处理富文本选区、图片复制、表格结构，全是坑。为了一个"提示文案统一"，代价太大。

我的处理方式是：**不拦截，只旁听** 。
    
    
    1
    2
    3
    4
    5
    6
    7
    8
    9
    

| 
    
    
    document.addEventListener('copy', function () {
      if (isEditable(document.activeElement)) return;  // 输入区不打扰
      if (!selText()) return;
      toast('已复制');
    });
    document.addEventListener('paste', function (e) {
      if (!isEditable(e.target)) return;
      toast('已粘贴');
    });
      
  
---|---  
  
这两个监听里没有一行 `preventDefault()`。浏览器该做的事一件不少，我只是在旁边看一眼，顺手弹一个"已复制"的小提示。

这样做的效果反而更好：用户按 `Ctrl+C` 和点菜单里的"复制"，看到的反馈是一样的，但底层走的是完全不同的两条路——一条是浏览器原生的，一条是我自己实现的。**表面统一，底层各管各的，互不牵连** 。

输入区里我特意跳过不提示，因为系统自带的光标反馈已经足够，再叠一个 toast 就吵了。

## 位置计算：越界自动翻转 

菜单弹出来之后有个必须处理的问题：**靠近屏幕右边或者底部右键，菜单会跑出可视区域** 。

做法很简单，先显示出来量尺寸，再决定位置。

    function place(m, x, y) {
      m.hidden = false;
      m.style.left = '0px';
      m.style.top = '0px';
      var r = m.getBoundingClientRect();   // 先量
      var pad = 8;
      var left = x, top = y;
      if (left + r.width + pad > window.innerWidth)  left = window.innerWidth - r.width - pad;
      if (top + r.height + pad > window.innerHeight) top = window.innerHeight - r.height - pad;
      if (left < pad) left = pad;
      if (top < pad)  top  = pad;
      m.style.left = left + 'px';
      m.style.top = top + 'px';
    }
      
  
---|---  
  
关键在 `hidden = false` 必须在量尺寸之前。`display: none` 的元素 `getBoundingClientRect()` 全是 0，量出来没用。

先把 `left/top` 归零再量，是为了避开上一次定位留下的残留，否则量到的尺寸可能受旧位置影响。这个细节踩过一次就知道了。

## 顺手踩的坑：jsonify 把引号带进了 URL 

菜单里有个"随机看一篇"，数据由模板注入：
    
    
    1
    

| 
    
    
    window.__POSTS__ = [{{ range $i, $p := $posts }}{{ if $i }},{{ end }}{{ $p.RelPermalink | jsonify }}{{ end }}];
      
  
---|---  
  
看着没问题，实际跳转全是 404。看地址栏才发现，跳到了 `/p/站点名/` 加上 `"/p/另一篇/"`——**多了一层引号，浏览器把`"` 编码成 `%22` 拼进了路径**。

原因是 `jsonify` 输出的字符串自带双引号，而我又在外面手写了逗号拼接，于是数组元素变成了 `"/p/a/","/p/b/"` 这种形式被当成纯文本，`location.href` 赋值时整串都进了 URL。

修法有两种。要么模板里不加引号，让 `jsonify` 自己负责：
    
    
    1
    

| 
    
    
    window.__POSTS__ = [{{ range $i, $p := $posts }}{{ if $i }},{{ end }}{{ $p.RelPermalink | jsonify }}{{ end }}];
      
  
---|---  
  
要么外面写好引号，里面不用 `jsonify`：
    
    
    1
    

| 
    
    
    window.__POSTS__ = [{{ range $i, $p := $posts }}{{ if $i }},{{ end }}"{{ $p.RelPermalink }}"{{ end }}];
      
  
---|---  
  
我选了后者，看着更清楚。另外在 JS 里加了一道清洗，防止以后有别的地方再灌进脏数据：

    function cleanUrl(u) {
      return String(u == null ? '' : u)
        .trim()
        .replace(/^["'\s]+|["'\s]+$/g, '')   // 去掉首尾引号
        .replace(/\\\//g, '/');              // 还原被转义的斜杠
    }
      
  
---|---  
  
这个坑挺有代表性：**模板里拼接字符串，引号要么全交给模板函数，要么全靠手写，混着来必然出事** 。

## PJAX 站点要额外处理 

这个站开了无刷新跳转，所以还得考虑换页之后的状态。

菜单元素是动态创建的，挂在 `body` 上。PJAX 换页时 `body` 不重建，菜单还在，但它里面缓存的 `dataset.url`、`dataset.title` 全是旧页面的。如果在旧菜单还没关的情况下换页，点"复制本页链接"复制到的是上一页地址。

处理很简单，换页时把菜单关掉、引用清空：
    
    
    1
    2
    

| 
    
    
    document.addEventListener('pjax:send', close);
    document.addEventListener('pjax:complete', function () { menu = null; });
      
  
---|---  
  
`menu = null` 而不是只 `close()`，是为了让下次 `ensureMenu()` 重新创建。这样连 `dataset` 里的旧值也一起丢了，不会残留。

`ensureMenu()` 里那句 `document.body.contains(menu)` 也重要。PJAX 如果整体替换了 `body` 内容，旧节点就脱离文档了，这时候直接往旧的 `menu` 变量上操作是没有效果的——它还在内存里，但页面上看不见。

## 几个没写进去的东西 

写完之后想过一些加分项，最后都没做，记录一下理由。

**没做 "分享到 XX"。** 静态博客没什么可分享的渠道，加了纯摆设。

**没做 "复制 Markdown 源码"。** 需要 `fetch` 当前页面再解析 HTML，遇到代码块和表格要特殊处理，成本明显不成比例。

**没做移动端适配菜单。** 前面已经放行给系统长按了，再做一套触屏菜单等于两套逻辑，维护成本翻倍，收益可疑。

**没做菜单动画。** 加了一个 0.12s 的淡入，就这个程度。再多就开始拖慢手感了。

我的判断是：**这类 "锦上添花"的功能，功能项的数量要克制，交互的细节要讲究**。五个用着顺手的菜单项，好过十五个看着齐全但一半不好用的。

## 小结 

把整篇的问题和解法压成一张表：

现象 | 根因 | 修法  
---|---|---  
输入框没法粘贴 | 全站接管了 contextmenu | 输入区放行给原生  
链接没法新标签打开 | 右键被吞，菜单没补对应项 | 按落点动态生成菜单项  
手机长按不能选字 | 触屏 contextmenu 被拦 | `(hover: none)` 直接放行  
点菜单后复制为空 | 焦点移走，选区丢失 | 右键时存 Range，执行前恢复  
菜单里的粘贴偶尔没反应 | 浏览器不让脚本写剪贴板 | 三层降级，失败就提示按 Ctrl+V  
靠近边缘菜单出界 | 位置没做边界检测 | 先显示量尺寸，再翻转  
随机跳转 404 | `jsonify` 的引号被拼进 URL | 模板统一引号来源 + JS 清洗  
换页后复制到旧链接 | 菜单 cache 未失效 | `pjax:complete` 时置 `menu = null`  
  
真正花时间的不是菜单本身，而是"什么时候该让路"这个判断。全站接管写起来最快，但用起来最难受；分层放行要多写几十行 `closest()` 判断，可每个位置的行为都符合直觉。

如果你也想给自己的站点加一个，我的建议是先从最小可用开始：只在正文区域接管，菜单里就四五项，跑通了再考虑往外扩。往外扩之前，先把"输入框要不要放行"、“链接和图片补不补"这两个问题想清楚，能省掉后面很多返工。

介绍一下：DGCU-Net-Portal <https://github.com/miaoermua/DGCU-Net-Portal> 是我做的一款东莞城市学院校园网的认证客户端，且完全免费开源使用 GPL-3.0-only 的自由软件。

首先要考虑跨平台，因为我是 Windows 和 Mac 双持，而且学校里面大部分人都应该是用的 Windows，并且我在上学之前使用的 Archlinux 所以考虑。

程序核心使用 Rust，考虑到用户和我个人我选择使用 Tauri 2 作为 GUI，Rust 下的原生界面也不太完善，而且我看上了一个叫 Miuix 的主题，恰好他有有前端 Miuix-vue <https://yukonga.github.io/miuix-vue/> 。

## 最初和骨架

最初的想法我只想做一个很简单的界面，就像点一下就连接的软件一样（不可言传），然后配一个设置界面设置账号密码什么的，然后还要能满足我的需求，能够跳过我长期打开的 Proxy。

也好久没用中转站了，当时刚刚好发布了 GPT 6 Astra 这应该是目前最强的大模型，但可能不是 coding 最好，而是他越来越全能了，想着他应该能胜任这个任务，而我美美在后面玩手机偶尔提出几个需求让他帮忙实现。

还是骚扰了神秘 api 商人核桃，花了点时间搞上中转站，折腾客户端就搞了半天，最后发现是他每一次对话都锁定一个配置，而新建全新一个对话就没事了。

这里为了双开，另外下了个 codebuddy 他设置的则是 deepseek v4.1 flash 这个模型响应很快，基本上可以在 GPT 卡住的时候让他把其他功能做起来，并发处理。（有点烧心）

最开始的 portal 界面是完完全全符合刻板印象的 AI 味，一个菜单黑底再加上一个彩色渐变图标，我不喜欢这样的风格，太冲了，底线还是在的。

还是又花时间摸摸打磨了，当时最慢的就是 GPT 6 Astra，经常就是重试很多次，最多一个小时都在重试。

## 认证协议

这里处理 Portal 协议本来想着能让 Agent 开个浏览器自己摸索，但是这样的话会没有网络给他尝试，好在浏览器开发者里面可以导出 Har，里面包含完整的认证细节，当然也有敏感信息，密码后续可以改但是学号是真真实实报了上去了。

我手动按照原来的方式在后台登录完成了所有需要登录的流程，交给 AI 处理，发现好像和平时少了一步，就是代播。

开始找资料，在认证页面发现服务提供商的信息，发现服务商还挺用心专门有个文档介绍，我将文档内容让 AI 分析，AI 甚至以为我要把整个后端啃下来。

我认为如果他提供文档说不定可以让结构化更好，而不是四处碰壁，他甚至以为我要做服务端，确实是少了一步“代播”。

账号还没到期释放，时间紧任务重，这里经得允许借了个普本 xdx 的号，手动在浏览器中按照流程登录采集 Har。

这次终于出现了代播接着让 AI 分析，至写出了完整的认证协议后面再也没碰过认证协议了。很强，非常强，这下不得不服 Astra。

## 系统差异和服务

在处理好 Portal 协议以后就开始处理烂摊子，协议既然能跑了现有的结构不一定是最好的，代码结构是可以调的，至少我觉得还可以，开始重构代码结构……

最后选择调一下 CLI 的参数命令和代码结构，我觉得已经不是人能够脱离 GUI 能用的，起码得更便捷，后续能够使用在纯 CLI 使用的场景例如 OpenWRT。

## 用户体验优化

将体验贯彻到底，从用户中来到用户中去。作为首席用户，第一关注是软件够不够傻瓜，默认选项是否合理，软件随便操作不会崩溃（鲁棒性），要将核心功能做到足够冗余足够的傻瓜，即便这个问题可能 100 次会遇到一次问的，绝大多数可能就将就打开“自适应模式”亦或者放弃使用这个软件了。

一开始软件需要手动保存，遇到问题还需要关掉认证重新开一遍才能进行保存，到现在非 portal-cli 运行的配置都可以实时保存，且支持自动保存不需要手动点击保存。

Windows 原本没有 installer 的需要自行解包 zip 安装到自定义目录，到 actions 打包好 setup 安装，使用的 NSIS 安装程序制作工具。

macOS 版本是比 Windows 早做到安装器，这里没用 pkg 安装，是抄的 [canmi/rdm](https://github.com/canmi21/rdm/tree/main/pkgs/macos) 的 DMG 安装模版。

这个项目花费了我大量时间和 Token，也从中学习到跨平台、Rust、系统服务，算是一个不错的开发经历，所以这个工程版是面对开发者或者使用 Vibe Coding 但是没有方向的小白。

目前项目基本上开发完毕，如果没有大变动未来就是维护模式，不再添加随意新功能，最多优化一下代码潜在问题，用户反馈以及后续发版引来的各种用户问题优化，这些都需要时间证明。

## 凭什么是 dsh-quirekit-md-editor?

说实话，并不是我一个人注意到了 dsh 无法编辑 md，我看到社区也存在 Marktext，Better Sidebar 等产品，但为什么我还要做，以及做完后凭什么让大家选择我，而不是其他？这对于 quirekit 的 md-editor 来说，并不算是什么困扰，因为我们本身就有很多目前其他方案给不了的东西，这些差异化就是让别人选择我们的理由。

### 1\. 独特的多模式编辑

市面上大多数编辑器，要么提供类似 vscode md-editor 一样的半富文本编辑器状态，要么提供左输入右预览的形态，还有人提供 tiptap 负责富文本，codemirror 负责源码模式的重型形态（存在 pm json 转换，md 源码一定会被格式化）。

但我一直在想，为什么编辑器必须是左右结构？或者富文本模式为什么必须是 tiptap 这种富文本编辑器实现？因此我们基于 codemirror 设计了一套 tiptap api style 的 msfe（markdown 源码优先的编辑器框架）。在这套模式下，我们实现了纯源码编辑、半源码半富文本编辑（选中目标会展示为 md 源码格式）、以及全富文本模式（隐藏 md 围栏与标记，体验与 飞书文档、notion 类似，但实际的修改永远都是 md 字符串）。

在这种体系下，所有模式的菜单、操作等各个模式都是共享的，例如评论：

![](https://cdn.jsdelivr.net/gh/kingshuaishuai/ys-imgs@main/quirepub/019992fb3ba139b548fbfa75795d3757.png)

![](https://cdn.jsdelivr.net/gh/kingshuaishuai/ys-imgs@main/quirepub/1bffcd22e95cdc7a1f8d272c82085d2c.png)

这种体验，我几乎没在市面上的其他编辑器中体验过。

### 2\. 惊人的性能

quirekit 的 codemirror 是拉了源码使用 vendor 版本的，这就给了我们很多机会去改造源码。

改造最大的是 lezer 的算法，lezer 本身其实也是增量的，改完一个字，它只重新解析改动附近的几块，其余的块直接从上一次的语法树里拿过来用。但问题是它拿的时候是一块一块拿的，如果改动点后面有一千个段落，就要逐个检查、逐个接回新树，文档越长，每敲一个字要做的事就越多。 

Lezer 自身有个优化：它为了让编辑器按位置查找节点更快，在建对象树的时候，会自动把相邻的块打包成组，组再打包成更大的组，只是复用旧树时没有用上这层结构。

**我们的优化策略是** ：如果整组都没变，那就一次把整组接回来，不再逐块处理，只有组是个复杂结构，例如代码或者列表，才按原来的方式逐块判断，因为在 markdown 中，这些内容本身就是一个整体，对 md 的拆分如果不正确就会造成一些结构的变化。改完后，300 万字的文档和 10 万字的文档，敲一个字的解析开销基本一样。

以下是之前做的一个优化对比：

工作量| 优化前| 优化后  
---|---|---  
语法树访问| 107,760| 1,380（少了 98.7%）  
语法树比较| 153,940| 660（少了 99.6%）  
  
不过为了保证正确性，对于例如超大的列表，可能还是会在列表这一部分的修改上回退到原来的 lezer 逻辑，不过也就只是这一小块，这个优化我也提取成了新版的 incremark。在此之前，我还开源过一个不太成熟的方案，基于断行实现的 increamrk，处理过程中就遇到了很多拆分导致的坑。 

在 dsh 插件实现过程中，我顺便还优化了一下 UI 层更新导致的性能开销，对比已有的 Marktext，Better Sidebar 产品，也让 claude 做了实测性能比较：

## 安装方法：

需要 DSH 0.2.2-rc.1 及以上（低版本没测过），Web 版执行：
    
    
    dsh plugin --profile web add dsh-quirekit-md-editor

重启 `dsh web`，再从“文件”标签打开 Markdown 文件就行。桌面版在“插件”页点“添加插件”，输入 `dsh-quirekit-md-editor` 安装并启用。完整的演示视频在 GitHub 仓库的 README 里。

## 起因

10月30日，负责监控 NAS 服务的程序突然提示我，所有服务都掉线了。于是我打开 NAS 管理界面看了一眼，发现 Docker 卡死了。当时压根没往被黑的方面想，顺手就点了个重启。这下坏了，等重启完成后，界面竟然直接显示需要重新安装系统。

![重装界面](https://pic.pinaland.cn/uploads/2026/11/10/6af2b6687c66b.webp#vwid=1136&vhei=660) 重装界面

这时才意识到事情可能没那么简单，于是赶紧在社交媒体上搜索相关信息。搜索结果中，几乎都是群晖漏洞导致文件被加密的案例，当时心里还抱着一丝侥幸。随后去群晖官网查了一下，得知重装系统并不影响原有资料的恢复。于是按照系统提示一步步完成重装，进入登录界面后，打开文件夹一看，结果可想而知，我并不是那个幸运儿，近 1.5TB 的照片资料几乎全部被锁。

![被锁](https://pic.pinaland.cn/uploads/2026/11/10/6af2b6bba50a4.webp#vwid=752&vhei=527) 被锁

## 补救措施

当下先检查了一下，发现并不是所有文件都被锁了。在目录层级超过三层的文件夹中，只发现了一份名为 **read-me3.txt** 的勒索信，里面的文件却完好无损，这也算是不幸中的万幸了，之前拍摄的一些视频文件几乎都还在。虽然当时还不清楚其中的原理，但第一时间还是先把 NAS 断网并关机，随后下单了一块大容量硬盘（现在才真正意识到 3-2-1 备份原则的重要性了！）。等硬盘到手后，便先把一些重要且不可再生的资料保存下来。

搜索了相关资料，发现这种会将文件后缀改为 **.L0CK3D** 的勒索病毒被称为 **C3RB3R** ，属于 Cerber-like 勒索程序。这一轮公开案例中，攻击者主要通过利用公网可访问的群晖 DSM 漏洞获取系统访问权限，随后在 NAS 上运行加密程序。从公开案例来看，攻击者可以利用漏洞绕过正常的身份验证流程，在无需获取用户账号密码的情况下获得 root 权限，随后遍历具有写入权限的文件，并对其内容进行加密或改写。

如果当时没有重启，可以参考[这个案例](https://github.com/Benjamin-zlt/c3rb3r-baremetal-rescue)。大致思路是通过特定方式找到勒索进程并将其冻结，随后导出相关数据，再从内存中提取密钥，用来解锁文件。当然，我已经重启过 NAS 了，所以这个方法对我来说已经行不通了。估计大部分看到这篇博文的人，可能也和我一样，发现问题时已经重启过设备了。当时其实已经做好了文件全部无法恢复的心理准备，好在后来事情出现了转机。下面就来看看我是如何一步步恢复这些文件的。

## 解锁过程

巧合在一篇公众号上看到有这么一个[开源项目](https://github.com/crt106/c3rb3r-btrfs-recovery)，按照项目所说

> C3RB3R 只**原地改写** 文件的几段：小文件整体加密，1–5MB 加密前 1MiB，大文件加密头、中、尾三段共约 12%。Btrfs 写时复制会把改写的内容写到新位置，而**原 extent 只要还被文件中没被加密的部分引用，就整块保留在盘上** 。所以只需按 extent 树把被改写的字节映射回旧 extent，就能拿回原始字节；在开启了数据校验和的共享上，还能用 Btrfs 自带的 CRC32C 逐块证实。

群晖 NAS 使用的是 Btrfs 文件系统，而这种文件系统的写时复制（CoW）机制，也让恢复原始数据成为了可能。发现文件被加密后，我第一时间关机，避免进一步写入对原始数据造成影响，这也为后续的数据恢复保留了一线希望。巧合的是，我在寻找解决办法时发现了一个开源项目，它还是一个 AI Agent Skill。既然如此，不妨让 AI 帮忙试试。下面就是我和 AI 的实际对话过程。以下对话中的“我”代表本人，“Codex”则代表当时使用的 Codex。

>

>

前段时间跟公司另一个部门的负责人闲聊，他顺口提了一句，说咱们现在这套产品用起来有些地方不太顺手。我当时很自然地接了句，那欢迎随时提意见，看看哪里能调。结果他摆了摆手，半开玩笑地说他不会吐槽的，因为我的「职场前任」是他关系很好的哥们儿。

我听了第一反应是好笑，但马上意识到他误会我的意思了。我赶紧补了一句，不合理的地方该改就改，这事儿是对事不对人，也不存在针对谁。

所谓的「职场前任」，定义起来很简单。我去一家公司接手 A 职位，只要这不是一个从 0 到 1 新设的坑位，而是替补前一个做 A 职位的人，那个人就是我的职场前任。只要还在换工作，大概率就会遇到这么一号人。有的前任是内部转岗，大家还在一个屋檐下，抬头不见低头见；有的则是彻底离职，除了交接文档和历史群聊记录里的名字，你压根没机会认识他。

刚才那个部门负责人的本能防御，其实挺耐人寻味的。他默认了我邀请他「提意见」，是在收集前任的「罪证」，或者觉得只要否定了现有的产品逻辑，就等于否定了他朋友的能力。

他会有这种戒备心也不奇怪。稍微留意一下就会发现，职场上很多人不管嘴上怎么客套，身体都是很诚实地排斥前任的。不少人刚入职还没把业务摸透，第一件事就是先把前任定下的规章制度、跨部门协作流程改个遍；要是放在产品和研发岗位上，更是恨不得立刻推翻历史代码和原有逻辑，立马立项搞一套重构或者新功能。

大家之所以热衷于干这种「去前任化」的活儿，往深了想，往往是因为对自己的不可替代性缺乏安全感。

一个新人刚进场，最怕别人觉得自己只是个按部就班的维护者。怎么在最短时间内证明公司招自己来是物超所值的？最省力、最显眼的办法，就是把过去的东西定义为「烂摊子」，然后把自己塑造成那个力挽狂澜的拯救者。只要前任的方案是有缺陷的，自己改方案的动作就天然带上了建设性。这种通过踩低前人来垫高自己的做法，本质上是一种低成本的向上管理。但这往往会导致大量的无效折腾，把本该花在解决实际业务问题上的精力，全消耗在了证明「我比上一个强」的姿态上。

如果非要问我怎么看待自己的职场前任，我的态度其实挺冷淡的。倒不是因为我觉得前任不如我，或者觉得对方的东西有多 low，而是我从心底里对自己的业务能力有底气，不太需要靠否定别人来刷存在感。

在我看来，每个人都有他自己的经历、视野和当时的处境。同样的业务命题，交到不同人手里，做事的风格和最终落地的结果肯定是不一样的。更何况，很多看起来别扭的流程和产品逻辑，放在当时的时间节点、资源限制或者老板的强意志下，可能已经是那个阶段能拿出的最优解了。后人站在现在的视角去挑刺，本身就不太公平。

而且，对一份历史遗留结果的评判，绝大多数时候都是主观的。当然，如果一个结果烂到了一定程度，确实会形成某种客观意义上的共识，但即便如此，那个好坏也轮不到我来操心，更不需要我亲自下场去给前任打分。

把人的归人，把事的归事，工作会轻松很多。我接手的是一个岗位和一摊具体的业务，不是接手前任的人际关系，也不是来给他的职业生涯写鉴定报告的。之前的流程如果跑得通、逻辑顺，我就留着用，没必要为了显得自己有动作去硬改一套新词儿；如果确实卡手、阻碍了现在的效率，那不管是谁定的、背后是谁的朋友，该推翻就推翻。

至于前任留下的底子到底是好是坏，其实怎么算我都不亏。前任做得好，基础打得牢，我接手起来自然更顺手，能省下大把填坑的力气去干点新东西；要是前任留下的真是个千疮百孔的烂摊子，那正好，我把它收拾利索了，反而更能衬托出我的业务水平。既然横竖都能把活儿干出来，又何必在前任的影子里较劲呢。

Fable 5.2 上线后，Addy Osmani 在 claude.dev 上发了一篇 [Which Claude model should you build with?](https://claude.dev/blog/which-claude-model-should-you-build-with/)，讲不同任务该用哪个 Claude 模型、effort 怎么调。这篇按我的理解整理文章要点，数字都来自原文。

这是我自己的小记，模型、价格和默认设置都以 2026-11-10 为准。模型随时可能升级或调整，用之前请以官方文档的最新信息为准。

现在正式可用（GA）的 Claude 模型有四个：Haiku 5.5、Sonnet 5.5、Opus 5.5、Fable 5.2。另外还有一个 Mythos 5.2，是网络安全和生命科学研究方向能力最强的模型，要通过 Anthropic 的验证计划才能用，原文没有展开。

## 一句话结论[](https://blog.cosine.ren/post/which-claude-model-to-build-with#一句话结论)

**大部分工作从 Opus 5.5 开始，effort 用默认的`medium`。** Claude Code 默认就是它，输入和输出的单价都只有 Fable 5.2 的一半，官方也推荐大多数编码和知识工作从它起步。

只在下面三种情况换模型：

  * **降到 Sonnet 5.5** ：范围明确的日常活，比如修 bug、按 spec 做功能。spec 写得清楚，也不代表 Sonnet 一定够用。难的迁移或性能优化，可能还是要 Opus，规模大的要 Fable。
  * **降到 Haiku 5.5** ：简单、量大的活，比如分类、路由、信息抽取，也适合给 subagent 做大模型的旁支任务。
  * **升到 Fable 5.2** ：最难的编码、金融、科研项目，Opus 开到 `high` 还不够的时候，或者要长时间无人值守地跑（长时间跑不会贵一倍，原因见下文「长会话的花费主要在上下文」）。

还有一条很重要：换模型之前先调 effort。[effort](https://platform.claude.com/docs/en/build-with-claude/effort) 是同时调成本和能力的细旋钮：

  * 提高 effort，模型会想得更久、多调用工具、多检查自己的结果，代价是延迟。
  * 超过 `high` 以后，再升一档的花费可能和换大一号的模型差不多，两种方案要在自己的任务上比一比。已经开到 `high` 以上的话，原文建议改试大一号的模型，从更低的 effort 起步。
  * 反过来，降一档 effort 也许就能用更低的价格拿到想要的结果。
  * 模型本身没有的知识和能力，effort 补不出来，这时才需要换更强的模型。

## 几组取舍[](https://blog.cosine.ren/post/which-claude-model-to-build-with#几组取舍)

选模型本质上是在做取舍，比如选更大的模型，就是拿延迟换能力。原文讲了三组。

### 能力和每个任务的成本[](https://blog.cosine.ren/post/which-claude-model-to-build-with#能力和每个任务的成本)

大模型每个 token 更贵、能力更强，但落到单个任务上，这个规律不一定成立。单价高不等于每个任务花得多，也不等于结果更好：

  * Terminal-Bench 3.0 上，上一代的 Fable 5.1 开 `max` 得 58.0%，Opus 5.5 开 `high` 得 58.9%，token 只用了一半（数据来自 [Spending your effort](https://claude.dev/blog/spending-your-effort/)）。
  * 在最难的题上，价差会缩小。FrontierCode 2.0 上，Fable 5.2 开 `high` 得 45.3%，Opus 5.5 开 `max` 得 45.5%，前者每个任务的成本大约只有一半。所以在难题上，把 Opus 开到超过 `high` 之前，先试一下 Fable 5.2。日常工作还是从 Opus 5.5 `medium` 开始。更多基准结果见 [Fable 5.2 发布文章](https://www.anthropic.com/claude-fable-and-mythos-5-2)。
  * 小模型也有局限。Claude 平台的[成本与能力测量](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)显示，小模型适合量大、输出能核对的活，不太适合长 Agent 循环。
  * 比较两个模型时，不光要算典型任务，也要算任务集里最难的那几个，因为它们占了大部分花费。在一个 20 道题的搜索基准上，两道题就占了 43% 的花费。

### 延迟和准确率[](https://blog.cosine.ren/post/which-claude-model-to-build-with#延迟和准确率)

配置越快，完成得越早，也越容易出错。先想清楚用户能等多久，再选模型和 effort。用户在等回复的场景，从 Sonnet 5.5 `low` 或 `medium` 开始。

新一代模型通常比上一代快：Fable 5.2 的输出速度比 Fable 5.1 快最多 30%，Sonnet 5.5 比 Sonnet 5 快 30%。

effort 和延迟大致成正比，要判断多出来的准确率值不值得多等。SWE-bench Pro 上的 Opus 5.5，以 `high` 为基准：

  * `medium` 低约 2.5 分，成本约为 70%；
  * `low` 低约 8 分，成本约为三分之一；
  * `xhigh` 高约 1.4 分，成本是 2.5 倍。

    
    
    xychart-beta
      title "Opus 5.5 在 SWE-bench Pro 上的相对成本（high = 100%）"
      x-axis ["low（-8 分）", "medium（-2.5 分）", "high（基准）", "xhigh（+1.4 分）"]
      y-axis "相对成本 %" 0 --> 260
      bar [33, 70, 100, 250]

从 `high` 升到 `xhigh`，成本翻了 2.5 倍，只多 1.4 分。

给模型一个自我验证的手段，往往比调 effort 更省钱，增加的延迟也更少。模型不够好时，按这个顺序升级：
    
    
    flowchart TD
      A[模型结果不够好] --> B{能自己验证结果吗？<br/>测试、构建、调用接口的脚本}
      B -- 不能 --> C[先补上自我验证]
      C --> D
      B -- 能 --> D{还不够好？}
      D -- 是 --> E[effort 升一级]
      E --> F{还不够好？}
      F -- 是 --> G[换上一级模型<br/>从更低的 effort 起步]
      D -- 否 --> H[就用当前配置]
      F -- 否 --> H

能自动判断对错的任务还有一个省钱的办法：全部先用 `low` 跑，只把失败的用 `high` 重跑。在同一个 SWE-bench Pro 子集上，这样大约 97% 通过，每个任务约 $0.17；全部用 `high` 跑是 95.3%，每个任务 $0.29。

如果想让同一个模型回得更快，可以花钱买速度，不用降能力：Claude API 上 Opus 5.5 和 Fable 5.2 都有 [fast mode](https://platform.claude.com/docs/en/build-with-claude/fast-mode)，输出更快，价格更高。

### 长会话的花费主要在上下文[](https://blog.cosine.ren/post/which-claude-model-to-build-with#长会话的花费主要在上下文)

四个模型都有 1M 上下文。上下文大能帮模型完成任务，但每一轮都要把它重新发一遍，每一轮都要付钱。好在[长会话里大部分输入都按缓存读取计费](https://claude.com/blog/claude-opus-5-5-built-for-coding-sessions-that-use-more-context)。Fable 5.2 的缓存读取价格和 Opus 一样，都是 $0.20/M（Sonnet 5.5 是 $0.10），所以在缓存命中多的长会话里，两者的差价主要来自没命中缓存的输入和输出。

换句话说，长时间跑 Fable，总花费不会是 Opus 的两倍。单价翻倍的只有没命中缓存的输入（$8 vs $4）和输出（$40 vs $20），占输入大头的缓存读取两边同价。具体贵多少，要看这两部分在你的会话里占多少。

原文引用了 [What a task costs on Opus 5.5](https://claude.dev/blog/what-a-task-costs-on-opus-5-5/) 里的数：Opus 5.5 一轮的缓存读取，上下文 150K 时约 $0.03，20K 时约 $0.004。所以主模型越大，主上下文越要保持精简：贵模型只负责做决定，大段的阅读交给便宜的 subagent。

Haiku 5.5 是唯一一个单价随 prompt 长度变化的模型：

  * prompt 不超过 100K 按低档计费，超过 100K 的价格是低档的 5 倍；
  * 高档也只有 Sonnet 5.5 单价的四分之一；
  * 短 prompt 最划算，输入价只有 Sonnet 5.5 的二十分之一。

如果每次调用都要带很长的 prompt，Haiku 5.5 和 Sonnet 5.5 要按每个完成任务的成本比，别只看标价。

## 混用模型[](https://blog.cosine.ren/post/which-claude-model-to-build-with#混用模型)

原文有个演示：一个项目里四个模型各管一类活。Fable 5.2 把网店从 JavaScript 迁到 TypeScript，Opus 5.5 做月度订阅功能，Sonnet 5.5 写商品页，Haiku 5.5 给客户消息分类。下面是混用时要注意的几件事。

### 在自然断点切换[](https://blog.cosine.ren/post/which-claude-model-to-build-with#在自然断点切换)

prompt 缓存属于写入它的模型。换模型后的第一轮，要为整段对话重新付缓存写入的钱。想让这一轮小一点：

  * Claude Code 里先 `/compact`，或者带一份简短的书面计划开新会话；
  * 直接调 API 的话，新模型的对话用一份「目前进展」的总结开头，别带完整历史。

思考块（thinking block）会记录是哪个模型生成的，而每个模型只能读一部分其他模型的思考块。在 Claude API 和 Google Cloud 上由 Google 托管的 Claude 模型上：

模型| 能读谁的思考块  
---|---  
Fable 5.2| Opus 5.5、Sonnet 5.5、Haiku 5.5  
Opus 5.5| Sonnet 5.5、Haiku 5.5  
Sonnet 5.5| Haiku 5.5  
Fable 5.1（仅 Claude API）| Opus 5.5  
  
按这张表，往低一级切换一定会丢掉之前的推理，因为模型读不了比自己高档的模型的思考块；从 Fable 5.2 切到其他任何正式版模型，它的推理都会被丢掉。其他方向的切换也可能丢：新模型读不了旧模型的思考块时，API 会直接丢弃它们，请求照样成功，新模型就在没有这段推理的情况下继续干活，不会报错提醒你。

完整的规则见文档 [Preserved thinking](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking)。

### subagent 用小模型[](https://blog.cosine.ren/post/which-claude-model-to-build-with#subagent-用小模型)

[subagent](https://code.claude.com/docs/en/sub-agents) 在自己的上下文里运行，只把总结交回来，按它自己的模型计费。在 Claude Code 里，可以在 subagent 定义里写 `model: haiku` 或 `model: sonnet`；没指定模型的 subagent，默认值由环境变量 `CLAUDE_CODE_SUBAGENT_MODEL` 决定。原文的例子，保存为 `.claude/agents/log-reader.md`：
    
    
    ---
    name: log-reader
    description: Reads test output and logs, and reports each failing case. Use after a test run.
    tools: Read, Grep, Glob, Bash
    model: haiku
    ---
    
    Read the logs you're given. For each failure, report the file, the test name and the first error line. Don't edit any files.

分工原则：小模型只做出错代价低、容易发现的活，比如找文件、跑测试、读日志；改代码和做判断留给主模型。小模型读错一个搜索结果，主模型就会去打开错误的文件，白白花掉 token。

几个容易忽略的配置细节：

  * **内置的 Explore subagent 会使用会话的模型** ，不再固定用 Haiku（在 Claude API 上最高用到 Opus）。想让探索便宜一点，可以自己定义一个名叫 `Explore`、写了 `model: haiku` 的 subagent。
  * `haiku` 别名指向哪个模型可以用 `ANTHROPIC_DEFAULT_HAIKU_MODEL` 固定。
  * 在 Anthropic API 上，`haiku` 别名现在指向 Haiku 5.5，需要 Claude Code v2.1.293 或更新版本。在 Amazon Bedrock、Google Cloud、Microsoft Foundry 和 Claude Platform on AWS 上，它仍然指向 Haiku 4.5。细节见 [Claude Code 模型配置文档](https://code.claude.com/docs/en/model-config)。
  * `opusplan` 别名是在 plan mode 里用 Opus 规划，再用 Sonnet 执行，等于把改代码交给了 Sonnet，正好和上面「改代码留给主模型」的建议反过来。原文建议先在自己的任务上测一下，再决定要不要把它设为默认。

### advisor 的收益还没被证实[](https://blog.cosine.ren/post/which-claude-model-to-build-with#advisor-的收益还没被证实)

[advisor 工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool)（beta）是让一个更快更便宜的执行模型，搭配一个更强的顾问模型。执行模型负责干活，中途可以向顾问求助。大部分 token 按执行模型的价格计费。只有执行模型主动求助、而且顾问能补上执行模型没有的能力时，顾问才有用；effort 越低，执行模型求助得越少。

  * **可能划算的场景** ：大部分轮次都是常规操作的 Agent 工作。
  * **原文的态度很谨慎** ：平台成本指南的 advisor 表格里有四组搭配，没有一组明显胜过执行模型单干。所以要先测一下执行模型的求助频率。
  * **不是任意搭配都行** ：比如 Sonnet 5.5 当执行者，可以配 Fable 5.2、Opus 5.5、Opus 5 或 Sonnet 5.5 当顾问；Fable 5.2 当执行者，只能配 Fable 5.2 或 Mythos 5.2。
  * **收益不大的例子** ：在一个内部编码基准上，Opus 5.5 开 `high` 当执行者、Fable 5.1 当顾问，得 90.1%，每次尝试 $2.92。比 Opus 5.5 `high` 单干高 1.7 分，花费约 2.1 倍。这个差距已经接近两次运行之间的正常波动，和直接提高 effort 能换来的提升差不多。

### 批量的活才值得拆给多个 worker[](https://blog.cosine.ren/post/which-claude-model-to-build-with#批量的活才值得拆给多个-worker)

上面的 subagent 是在一个主模型掌控全局时处理旁支任务。这一节说的是另一种模式：工作量超出一个上下文窗口时，让顶级模型当负责人，把任务拆给很多便宜的 worker 并行做，再汇总结果。

在一个约 2200 万 token 源码的内部找缺陷基准上，Opus 5.5 带最多 25 个并行的 Sonnet 5.5 worker，比 Opus 5.5 默认 effort 单干便宜约三分之一，分数差不多。

Claude 平台上，Claude Managed Agents 的 [multiagent orchestration](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration) 提供了一个协调者 agent 和一组 worker。但如果只是一条有先后依赖的任务链，或者一个上下文就装得下，就别拆了：规划和合并的开销会比省下的还多。什么时候一个 agent 循环比一队 subagent 好，可以看 [When to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)。

## 迁移前检查兼容性[](https://blog.cosine.ren/post/which-claude-model-to-build-with#迁移前检查兼容性)

选模型主要看能力和成本，但换模型不一定只改个模型名就行。现在所有模型都支持工具调用和图片输入，下面这些差异要在切换前测一下：

  * **Fable 5.2 会保留思考** ：所有 API 账号都开启了 [preserved thinking](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking)。Fable 5.2 思考块之前的任何内容（system prompt、工具、更早的消息）变了，API 就返回 400，除非你明确选择丢弃受影响的思考。通过 Claude Code、Claude Agent SDK 或 Claude Managed Agents 发请求的话，不用改任何东西。自己的代码会改历史的话，要改成只追加，切换前先测。
  * **思考** ：Opus 5.5 和 Fable 5.2 始终思考，请求里关掉思考会报错。Sonnet 5.5 默认思考，`between_tools` 把思考限制在工具调用之间。Haiku 5.5 默认思考，effort 在 `high` 及以下时可以关掉。所有模型都要按 `type` 读内容块，因为响应可能以思考块开头。
  * **强制工具调用** ：在 Sonnet 5.5、Opus 5.5、Fable 5.2 上，`tool_choice` 设为 `any` 或 `tool` 会返回 400。要用 `auto`，把工具标记为 `strict: true`，并在 prompt 里写清楚什么时候该用。
  * **Computer use** ：Opus 5.5、Sonnet 5.5、Haiku 5.5、Fable 5.2 只能通过 `computer_toolset_20260801` 工具集使用 computer use，仅限 Claude API 和 Google 托管的 Claude 模型。
  * **从 Haiku 4.5 升到 5.5** ：`budget_tokens` 换成 effort；非默认的 `temperature`、`top_p`、`top_k` 会返回 400；消息必须以用户消息结尾，最后一条是 assistant 消息让模型接着写也会返回 400。
  * **安全回退** ：Opus 5.5、Sonnet 5.5、Fable 5.2 都有安全分类器，最常拦截网络安全和生物类内容。Claude Code 里被拦截的请求可能改用旧模型重跑，记录里会标明用的是哪个。Fable 5.2 沿用 Fable 5.1 的回退模型：网络安全类回退到 Opus 4.8，生物类回退到 Opus 5。

一个系统里用多个模型时，原文建议按最严格的模型来写每一个请求：历史只追加、`tool_choice: auto` 配严格工具、按类型读内容块，prompt 和工具描述写到最「死板」的模型也不会误解的程度。这样任何一步换上换下一档模型都不用改代码。路由规则简单的话（比如每种步骤固定一个模型），就让代码来选模型，别让模型来选。

## 换模型前先跑一次对比[](https://blog.cosine.ren/post/which-claude-model-to-build-with#换模型前先跑一次对比)

SWE-bench Pro、Terminal-Bench 这些公开分数只能帮你选个起点。在 Claude Code 里想知道换模型值不值，最省事的办法是拿手头的一个任务，用 `/model` 换两个模型各跑一次，再看 `/usage` 比较花费。

要在 API 上大量调用的团队，原文给了一套完整的评测流程：真实任务样本、多档 effort、「分数 vs 花费」图和影子流量，见原文的 [Measure on your own work](https://claude.dev/blog/which-claude-model-should-you-build-with/#measure-on-your-own-work)。

我的童年，是从一台彩色电视机开始的。

很小的时候，家里先是一台老旧的黑白电视，屏幕小小的，画面灰蒙蒙一片。两三岁的我总觉得不够好看，那台旧电视只有一个旋钮，咔嗒咔嗒转动着搜台，满屏的雪花杂音是独属于旧时光的背景音。只是年岁太小，那时播放的内容我全然记不清了，真正扎根在记忆里的温暖画面，都来自后来那台崭新的彩色电视。

那台彩电，是父母最辛苦的时光换来的珍宝。小时候爸妈摆摊做小吃、卖凉拌菜（上次写过），起早贪黑忙活副业，一点点攒下的收入，在我四岁左右，换回了一台崭新的彩色电视机。我至今记得那天的模样，大大的纸箱被拆开，崭新的电视机静静立在眼前，好看得让年幼的我满心欢喜。

它和老旧的黑白电视截然不同，机身侧边排布着整齐的按键，还有一方可以掀开的小门，里面藏着拨杆调台的按钮，在我眼里，是无比新奇高级的设计。电视机稳稳摆在家里的写字台上，成了整个家里最亮眼的物件。爸妈格外爱惜这来之不易的大件，特意裁了柔软的灯芯绒布料，缝制了精致的电视机罩，不看的时候便细心盖好，生怕落一点灰尘。

那时候看电视需要架设室外天线，爸爸在屋外装好天线接收器，总要反复调整角度，屏幕的画面才能清晰稳定。后来厂区通了闭路信号，再也不用费力摆弄天线，随时随地都能看电视，成了我们儿时莫大的欢喜。

这台电视机，陪我从四岁走到十五岁，完整盛装了我的童年与少年时光。记忆里还有一段温柔又奇妙的小事，儿时一次发高烧，我昏昏沉沉坠入梦境，梦里的电视正在播放温柔的海景，沙滩上散落着细碎的贝壳，一只可爱的小哈巴狗追着我奔跑。那场温柔的梦，时隔多年，依旧清晰如初。

盛夏的暑假，是属于偷偷看电视的时光。老式显像管电视开机久了，后背会烫得灼热。妈妈下班回家的第一件事，就是伸手触摸电视后盖，以此判断我有没有偷偷看电视。摸清规律的我，总会赶在妈妈回家前，拿着吹风机对着电视后盖吹风降温，小心翼翼藏起自己的小秘密。现在回想起来只觉天真又可爱，也庆幸那台结实的老电视，从未被我折腾坏。

守着这台电视机，我看完了一整个时代的经典，岁岁年年，皆是欢喜。

童年的动画片，是最纯粹的快乐。我最痴迷的便是《圣斗士星矢》，星矢、冰河、雅典娜鲜活明媚，一句“天马流星拳”，刻进了我的童年骨血。当时总有频道反复播放，我一集不落全程追完，这部动画深深影响了年少的我。小学一二年级选书包，我执拗地只想要印着星矢与冰河图案的款式。除此之外，能变形的机器人动画《变形金刚》让我满心惦记，只是播出时间不固定，常常错过，看得断断续续。《黑猫警长》《舒克和贝塔》是反复翻看的经典，偶尔偶遇播出的《哆啦A梦》，零零散散的片段，也足够让我开心许久。

除了动画片，两部儿童剧藏着我童年最柔软的情绪。《小龙人》是我念念不忘的白月光，小小龙人身负秘密，跨越山海苦苦寻找远在雪山的妈妈。“头上有犄角，身后有尾巴，谁也不知道，我有许多秘密”，熟悉的旋律张口即来。故事里北京四合院的孩童生活，对彼时的我而言新鲜又美好，小龙人寻母的执着与心酸，总能让年幼的我看得泪流满面。还有《好爸爸坏爸爸》，朗朗上口的歌词记忆犹新，剧中孩童贪玩不写作业、被父亲责罚的画面，让小小的我看得又紧张又好笑，朴素的日常，满是人间烟火。

年岁渐长，我开始跟着大人追看古装经典，一部部老剧，惊艳了整个童年。

四岁左右追看的傅艺伟版1991年《封神榜》，是我心中最惊艳的经典，无可替代。那时候剧集播出极晚，常常深夜十二点才落幕，我依旧执着守在电视机前。傅艺伟饰演的妲己，是我童年认知里最美的女子，眉眼风华，无人能及。剧中的天宫殿宇、仙袂霓裳、歌舞造型，都和寻常古装剧截然不同，奇幻又雅致。杨戬三眼通神、可化万物，哪吒自肉球降生、脚踏风火轮，姜子牙运筹帷幄，申公豹狡黠阴诡，矮小灵动的土行孙，还有比干挖心、姜皇后蒙难等经典桥段，各路妖精鬼怪、天兵天将、道法仙术，为我打开了一个恢弘瑰丽的神话天地。片尾曲《独占潇洒》悠扬绵长，“愿生命化作那朵莲花，功名利禄全抛下”，儿时不解词中深意，只觉曲调清雅动人，岁岁难忘。

而后热播的《新白娘子传奇》，更是让我深陷其中。白素贞神通广大、温柔善良，小青赤诚忠义、不离不弃，忠厚善良的五鬼默默相伴。她们腾云而起、化光形变，万般法术奇妙绝伦。温柔善良的许仙，执着渡妖的法海，编织出一段缠绵婉转的爱恨痴缠。剧集独有的戏曲唱腔婉转悠扬，亦古亦今，韵味悠长，是独属于那个年代的浪漫。

每年暑假循环重播的《西游记》，是几代人的集体童年记忆。我很少能赶上开篇第一集，偶然一次窥见孙悟空花果称王、跨海求师的片段，便记了许多年。那时不知这部剧仅有二十集，岁岁夏天反复翻看，各路神魔妖鬼、九九八十一难，百看不厌，怎么看都觉得新鲜精彩。

印象深刻的还有1995年播出的刘晓庆版《武则天》，堪称古装剧的审美巅峰。彼时四十岁的刘晓庆，依旧将少女武媚娘的灵动娇憨、帝王的雍容霸气演绎得淋漓尽致，丰润端庄的容貌，完美契合盛唐美人的风骨。整部剧集由毛戈平操刀妆造，审美雅致惊艳，李建群老师饰演的徐才人，剧中每一位女子都风姿各异、容貌倾城。一众演员皆是戏骨，李世民沉稳睿智，陈宝国饰演的李治，将帝王的隐忍、温柔与怯懦刻画得入木三分。盛唐的华服头饰、妆容气韵，恢弘完整的剧情，将大唐风华展现得淋漓尽致，时至今日，依旧是我心中无可超越的经典，是人生最珍贵的童年回忆。

一台老旧的彩色电视机，静静伫立在方寸书桌之上，装下了天马流星拳的热血、小龙人的纯粹赤诚、封神神话的恢弘奇幻，装下了白娘子的柔情、西游记的浪漫恣意，也装下了盛唐风月的绝代风华。

那些守在电视机前的岁岁年年，那些天真欢喜、感动落泪、偷偷窃喜的瞬间，拼成了我最温柔、最滚烫的童年。旧电视早已落幕尘封，可那些光影故事，永远留在岁月里，温暖如初。

如果电视是指television，那我现在已经基本不看了，好多年。

已经记不起家里有没有买过老式黑白电视机了，但对第一台彩电记忆还是比较清晰的。那台电视挺大的，放在爸妈房间的一个大木箱子上面，斜对着他们的床。总之躺着看视角倾斜，坐床上看还好些。

那是高年级小学到初中，作业好像不是很多。好吧，印象里不多，因为从来没有感觉做作业有多辛苦。 但还是能记起我房间桌子上台灯的烫手感觉，以及恶作剧的我把蜡烛放在铁质灯罩上看它慢慢划掉打发时间。

作业不多，嘿嘿，意思就是其实还是有时间可以看电视的。晚饭过后，洗漱完毕，一般是我和爸妈一起看。但看一会儿妈妈就困了，困了也就顺势躺下。

只剩我和老爸。我们一般看古装电视剧。若不努力回想，除了那些经典名剧，已经记不起其他的电视剧了，不过还记得《上错花轿嫁对郎》，也是难得的三个人都喜欢看的电视剧。

其实看电视也没有多么好玩，只是可能奇奇怪怪的电视节目和电视剧会给平淡生活增添些色彩，还有可能是真舍不得那么早去睡觉，觉得睡得太早好像有点亏了。

看没多久，老妈一般已经睡着了，偶尔还说梦话。老妈睡觉很轻，被电视机的声音或光亮一晃可能就醒了。在她看来，都睡了老长一觉，你们俩还在看。

我跟老爸也很冤啊，真的才看几分钟，十几分钟啊。但老妈不觉得，通常会吼我们一声，睡啦。然后真的又睡过去。等到第二次的时候，吼声就大些了。我和老爸才不情不愿地关掉电视，纷纷听话躺回各自的床上。

我们的电视时间一般都在晚饭洗漱过后，所以，电视记忆里面并没有什么动画片儿童节目，都是电视剧。但那时的电视剧每天播两集，一部电视剧通常看不到开头和结尾。总是从中间某一集开始看起。然后觉得电视剧好长啊，例如《新白娘子传奇》和《西游记》，总觉得哪儿看得完啊。结果也才没多少集。

对，说到电视剧还想起一部《蜀山奇侠》，里面的反派入魔~~正派也入过魔~~ ，那可怕表演，没有点定力很容易被留下阴影的。《还珠格格》我不怎么爱看，总是谈情说爱，要死要活的。但抵不住人家就是火啊，火得奇奇怪怪。《三国演义》我看不下去，跟看书一样，一页都没看完过。对，我到现在还没有分析出为什么那么不爱看。

94年好像成都下了雪。下雪时，我在外婆家，外婆家在打井，挺热闹。我说，这都下雪了，好久没播《雪山飞狐》了，今天应该播了吧。结果下午打开电视，我的天，《雪山飞狐》第一集。~~好吧，仔细想想，也有可能是《蜀山奇侠》，记忆真奇怪，我以为我记得，但已经不敢断言了。~~ 总之，看到了某部电视剧的第一集，而且是自己预言中的。记忆是很深刻的吧。

读研之后还是要看的，但像我说的一样，那个时候已经不叫television了，不是别人放什么我看什么，而是我爱看什么播什么，在电脑上。

我看的多的是美剧，每天可以看几集。看得多了就不看字幕了，如果美剧不是那种太多专业词汇的话，大约能懂95%以上的对话。现在不行了，大约还是看少了啊。

现在每周周末看两次四集，不是电视节目，也不在电脑上，而是投屏到电视屏幕上。妻子则看她的言情，也是投屏到电视上，但我和儿子一般不会加入，只偶尔瞟两眼。我们算各看各的了，偶尔还能一起看电影。

当然，儿子每天一集的动画片，我时不时还是会蹭着看。儿子也已经基本不看television了，只在住宾馆，电视投不了屏时看看。但他显然不喜欢被迫看别人播的东西，因此在宾馆里，他按遥控器就像按游戏机手柄一样，每个频道停留时间都不到一秒钟。直到偶尔转到一个疑似比较精彩的电影。

# 当我的 Mac 里塞进 50 个 MCP 和 70 个 Skill：用“元工具”把上下文砍掉 90%

## 中文版

### 先看结论与实测战果

不讲宏大叙事，先摆在这台 Mac 上的真实运行数字：

  * **System Prompt 底座常驻开销** ：从 **14,500 Tokens** 骤降至 **~1,200 Tokens** （降幅 **91.7%** ）。
  * **工具调用冲突与模型选错率** ：由原本 50+ 工具平铺时的 ~18% 错选/幻觉，降为 **0 次错选** 。
  * **Prompt Cache（前缀缓存）命中率** ：从过去“增删一个工具或修改一行技能全盘失效”，提升至日常长对话 **92% 以上稳定缓存命中** ，模型响应首字延迟降低约 60%，API 费用省下大半。
  * **单机 RTK 截流收益** ：针对终端输出膨胀，联动 RTK 智能截流，本机累计 25,558 次命令已从源头挡掉 **530 万 Tokens** （平均每次截流 35.7%）。

一句话：**我们把 50 多个 MCP 工具（含 Apple 官方 54 个 Xcode 工具）和 70 多个本地 Agent Skills，全部抽象进了两层“元工具 (Meta-Tools)”，让 AI 在需要时自己去查、去调，用完即走。**

* * *

### 一、 惨剧：工具与技能是怎么撑爆模型的？

在日常深度用 AI 辅助全栈开发和 macOS 原生开发的过程中，我们本地的环境很快膨胀成了这样：

  1. **MCP 工具暴增** ：  
接入 Apple 官方刚开放的 Xcode MCP 插件（PR #6338，通过 `xcrun mcpbridge` 连接），一口气挂上了 54 个编译、预览、UI交互、模拟器管理工具；再加上 Git、Exa 搜索、文档检索等，总工具数突破 60 个。
     * **后果** ：大模型标准的 Function Calling 要求把所有工具的 JSON Schema 全量塞进每一轮提示词。60 个工具平铺开，一句话没聊，**8,000+ Tokens** 已经蒸发了。
  2. **Agent Skills 泛滥** ：  
本地积累了 70+ 个场景技能（从飞书 20+ 个办公工具、iOS 设计规范，到虚幻引擎 Unreal MCP、专利交底书撰写）。DSH 等 Agent 框架默认会把所有 Skill 的名称和功能简介生成一个目录塞进 System Prompt。
     * **后果** ：又是 **3,500~4,000 Tokens** 凭空消失。
  3. **终端回显轰炸** ：  
好不容易开始干活，一次 `git diff`、一个编译测试日志，哗啦啦几百行输出灌进窗口，单次上下文瞬间被撑大上万 Tokens。

结果就是：**对话刚聊五六轮，上下文窗口就告急；每一轮即使只发一个字，也得为这上万字的固定“工具底座”反复付费。**

* * *

### 二、 MCP 解法：用 `mcp-meta` 替代全量平铺

大模型其实根本不需要在第 1 轮就知道“修改 String Catalog 翻译文件的第 4 个入参叫什么”。

我们改变了思路：**给模型一把钥匙，而不是把仓库里的所有零件挂在它胸口。**

我们在本地 Magpie / MCP-Hub 体系中落地了 **`mcp-meta`** 代理层：

  * 模型常驻可见的工具面只有两个：
    1. `mcp_tools(server)`：查询指定服务具备哪些能力。
    2. `mcp_call(server, tool, args)`：派发具体的工具调用。

### 三、 Skill 解法：拒绝一刀切，走向“核心常驻 + 长尾懒加载”

技能能不能也照搬元工具？我们尝试过把 70 多个 Skill 全部彻底隐藏，做成纯懒加载。

但很快踩了坑：**Agent 的主动嗅觉被阉割了。**  
当你要它改一段业务代码时，它根本想不起来要去调用“交付门禁（delivery-gates）”或者去翻“Obsidian 跨项目长期记忆库”。你必须像教小孩一样，每次都在 Prompt 里手敲“请使用某某技能”。

因此，我们设计了**分层加载策略** ：

#### 1\. Tier 1 核心常驻层（严格控制在 5~6 个）

  * **工程门禁与底座** ：`delivery-gates`（不准自签完成）、`obsidian-knowledge-base`（记忆库只读查询）、`retro`（复盘）。
  * **当前核心业务栈** ：`ios-design` / `ios-design-system`。
  * **开销** ：控制在 **~400 Tokens** ，确保绝对不会挤占窗口，同时守住工程红线与核心直觉。

#### 2\. Tier 2 长尾按需层（65+ 个）全部归入 `skill-meta`

  * **飞书全家桶（20+ 个）** ：`lark-approval`、`lark-base`、`lark-doc`、`lark-wiki`……
  * **垂直/偶发技能** ：虚幻引擎、专利写作、Office 文档精细排版、CI 提速体检等。
  * **机制** ：通过 `skill-meta search` 按语义检索长尾技能，或在用户提及“飞书打卡/导出PPT”时动态唤醒。

这一招把 Skills 的常驻目录开销直接抹去了 **85%** 。

* * *

### 四、 终端截流：把 RTK 融入 Agent 肌肉记忆

工具和技能收束后，上下文里最大的动态垃圾就是 **终端命令的冗长输出（占活跃窗口 59%）** 。

在 Codex 或 Claude Code 里，官方提供了底层 `PreToolUse` 钩子，可以通过 `rtk hook` 自动拦截并过滤命令。但在 DSH 或其他原生直接调用 `bash -c` 的 Agent 框架中，没有现成的底层钩子。

我们直接把规则刻进了全局工作纪律 [`~/.dsh/AGENTS.md`](https://blog.7caifei.com/2026/11/~/.dsh/AGENTS.md)：

> **RTK 智能截流提速（全机统一标准）** ：高回显命令优先使用本机全局 `rtk` 过滤代理（如 `rtk git status/diff`、`rtk pnpm/cargo test`、`rtk xcodebuild`、`rtk err <cmd>`），从源头削减巨量日志，保护上下文空间与执行速度。

实际跑下来，Agent 在需要排查 diff 或看测试报错时，会条件反射般执行：

    rtk git diff  
    rtk err xcodebuild test -workspace MyApp.xcworkspace  
      
  
---|---  
  
单机 2.5 万次命令实测截流了 **530 万 Tokens** ，彻底解决了长输出爆上下文的问题。

### 总结

大模型时代，很多人的直觉是“把所有能给的能力一次性全塞给它”。但在工程落地中，**无限堆砌工具的结果不是变得全能，而是瘫痪与昂贵** 。

**让绝大多数工具和技能退到幕后，以“元工具”按需索引，守住静态前缀保护 Prompt Cache** 。把真正宝贵、干净的上下文空间，留给你的代码、架构和思考。

## English Version

### Results and Hard Numbers First

No buzzwords. Here are the verified metrics from our Mac developer environment:

  * **System Prompt Base Overhead** : Slashed from **14,500 Tokens** to **~1,200 Tokens** (**91.7% reduction**).
  * **Tool Selection Collisions / Hallucinations** : Dropped from ~18% misfires when 50+ tools were flat-listed to **0 misfires**.
  * **Prompt Cache Hit Rate** : Boosted from near-zero stability (invalidated by any minor tool/skill tweak) to **> 92% consistent cache hits** across extended sessions, slashing TTFT by ~60% and cutting API billing dramatically.
  * **Terminal Truncation Gains via RTK** : Integrated RTK command filtering, saving over **5.3 Million Tokens** across 25,558 executed bash commands (averaging a 35.7% token reduction per call).

In short: **We abstracted 50+ MCP tools (including Apple’s 54 official Xcode tools) and 70+ local Agent Skills into two elegant “Meta-Tools”, allowing the AI to discover, invoke, and discard capabilities purely on demand.**

* * *

### 1\. The Bottleneck: How Tools and Skills Bloat the Context Window

As we integrated AI deeper into full-stack and native macOS development, our environment expanded rapidly:

  1. **Explosion of MCP Tools** :  
Enabling Apple’s official Xcode MCP bridge (`xcrun mcpbridge`, Anthropic PR #6338) added 54 tools overnight (build, test, canvas preview, string catalog edits, UI automation). Along with Git, Exa Search, and docs, we had over 60 active tools.
     * **Cost** : Standard Function Calling requires full JSON schema declarations for every tool in every single turn. Flat-listing 60 tools consumed **8,000+ Tokens** before a single word was typed.
  2. **Proliferation of Agent Skills** :  
Our local catalog grew to 70+ skills (20+ Lark/Feishu integration skills, iOS UI design guidelines, Unreal Engine MCP skills, patent drafting, office automation). Most harnesses dump the entire summary catalog into the System Prompt.
     * **Cost** : Another **3,500–4,000 Tokens** vanished into thin air.
  3. **Verbose Terminal Logs** :  
A single `git diff` or verbose compiler output would flood the active context with thousands of unnecessary tokens.

The consequence: **Context limits were hit within 5–6 turns, and every trivial question cost a fortune due to re-sending the massive tool payload.**

### 2\. The MCP Solution: Replacing Flat Lists with `mcp-meta`

An LLM does not need to know the fourth argument of a localization catalog tool on Turn 1.

Our core insight: **Give the agent a key to the tool shed instead of strapping 60 power tools to its back.**

We introduced **`mcp-meta`** within our local Magpie / MCP-Hub infrastructure:  
The agent sees only two universal tools:

  1. `mcp_tools(server)`: Inspect available tools on a specific server.
  2. `mcp_call(server, tool, args)`: Dispatch a structured execution.

### 3\. The Skills Solution: Tiered Architecture over Blind Lazy Loading

It immediately backfired: **The agent lost its intuitive autonomy.**

#### Tier 1: Core Pinned Skills (Strictly 5–6 items)

  * **Engineering Baseline** : `delivery-gates` (no self-signed completions), `obsidian-knowledge-base` (read-only permanent memory), `retro` (session reviews).
  * **Active Focus** : `ios-design` / `ios-design-system`.
  * **Footprint** : **~400 Tokens** , safeguarding engineering boundaries and intuitive habits without bloating context.

#### Tier 2: Long-Tail On-Demand Skills (65+ items) via `skill-meta`

  * **Collaboration Suites (20+ items)** : `lark-doc`, `lark-approval`, `lark-base`, `lark-sheet`…
  * **Niche Workflows** : Unreal Engine development, patent disclosure drafting, automated slide generation, CI speed audits.
  * **Mechanism** : Dynamically searched via `skill-meta search` or triggered contextually.

This sliced skill catalog overhead by **85%**.

### 4\. Terminal Log Truncation: RTK in Agent Muscle Memory

With tools and skills optimized, raw terminal stdout became the largest remaining token drain (**59% of active tokens**).

While tools like Codex and Claude Code feature native `PreToolUse` hooks for auto-wrapping commands with `rtk`, bare-metal bash execution engines lack pre-execution hooks.

We baked the protocol directly into our global rules ([`~/.dsh/AGENTS.md`](https://blog.7caifei.com/2026/11/~/.dsh/AGENTS.md)):

> **RTK Log Truncation (Machine Standard)** : High-verbosity commands must prioritize the local `rtk` proxy (e.g., `rtk git status/diff`, `rtk pnpm/cargo test`, `rtk xcodebuild`, `rtk err <cmd>`), pruning spam logs at the source to preserve context and speed.

Now, whenever inspecting diffs or build errors, the agent instinctively runs:

Over **5.3 million tokens** have been saved across 25,500+ commands on this machine.

### Conclusion

In the age of LLMs, the naive instinct is to feed the model everything upfront. In real-world engineering, **dumping all tools into context doesn’t make an agent omnipotent—it makes it confused, slow, and expensive.**

**Push tools and skills behind the curtain using meta-tool interfaces, and defend your static prompt prefix to maximize cache hits.** Save your clean, precious context window for actual code, architecture, and reasoning.

在[上一篇关于 FCM 的文章](https://zhul.in/2026/02/20/xiaomi-china-version-fcm-push-debug/)里我提到，我已经在为出国做准备了。现在人已经到了海外，日常坐车、买咖啡基本都是刷卡，Google 钱包就成了我手机上使用频率最高的 App 之一。但国行 HyperOS 的「双击电源键」只能打开小米钱包，每次掏出手机还得解锁、找图标、点开，节奏一下就被打乱了。

前几天我在 GitHub 上看到了 [DustinYe/PowerWallet](https://github.com/DustinYe/PowerWallet) 这个项目，标题就是「双击小米手机电源键，直接打开 Google 钱包」，免 root，可惜只适配了小米 13 Ultra 的某一个 ROM 版本。我 fork 了一份打算搬到小米 15 上，折腾了一圈以后发现，**这件事在 HyperOS 4 上其实只需要一条 adb 命令** ：
    
    
    adb shell settings put system double_click_power_key launch_QAW_wallet
    

剩下的篇幅，我按「原生 Android 的机制 → 小米做了什么 → 原项目做了什么 → 我的 fork 做了什么」的顺序讲清楚这条命令为什么有效，以及为什么最后还是要做成一个 App。

## 测试环境

  * 小米 15 国内版（dada），HyperOS `OS4.0.0.22.XOCCNXM`，Android 17
  * 已开启「谷歌基础服务」，Google 钱包已安装并绑卡，默认 NFC 付款应用为 Google Pay
  * 未解锁 Bootloader，无 root

## 原生 Android 的机制

Android 11 引入了一套叫 **Quick Access Wallet** （QAW，快速访问钱包）的系统接口：钱包应用实现一个 `QuickAccessWalletService`，系统就能在电源菜单、锁屏或者手势里直接调起它。Google 钱包的这个服务由 Play 服务提供，叫 `com.google.android.gms/.tapandpay.globalactions.WalletQuickAccessWalletService`。

值得注意的是，QAW 并不绑定某个特定的钱包，而是**先读取默认 NFC 付款应用，再去这个应用里找 QAW 服务** 。所以「打开哪个钱包」其实是由默认付款应用决定的。小米钱包并没有实现 QAW 服务，我实测把默认付款应用改成小米钱包以后，双击电源键只会弹出一句提示：

> 当前默认钱包不支持双击电源键打开，请修改设置

也就是说，`launch_QAW_wallet` 只能用来打开 Google 钱包这类实现了 QAW 的钱包，打不开小米钱包。

后来原生 Android 又在「双击电源键」这个手势上加入了「打开钱包」的选项，对应 Secure 表里的 `double_tap_power_button_gesture=1`。

## 小米做了什么

HyperOS 并不直接使用原生的那个设置，而是用自己的 `double_click_power_key`（位于 System 表）来决定双击电源键做什么，再同步给原生设置。日志里能看到这个同步过程：
    
    
    MiuiSingKeyShortcutObserver: DTPB-Wallet syncAosp function=launch_QAW_wallet enabled=1 gesture=1
    

DTPB 就是 Double Tap Power Button。国行的设置界面里只能选小米钱包（`mi_pay`）、乘车码、相机等选项，但系统开机时打印的功能列表里，其实还有一个 `launch_QAW_wallet`：
    
    
    ShortcutFunctionManager: init config,function=mi_pay, supportActions=[double_click_power_key]
    ShortcutFunctionManager: init config,function=launch_QAW_wallet, supportActions=[double_click_power_key]
    

它就是原生的「打开钱包」。国行之所以看不到这个选项，是因为它被定制配置关掉了：
    
    
    InputFeature: DTPB-Wallet support=false reason=disabledByCustFeature
    

系统还注册了 `MIUI_REGION_CHANGED` 广播，我猜这个开关是按地区下发的。但它只是被藏了起来，运行时并没有人拦它：我手动把值改成 `launch_QAW_wallet` 以后，**解锁和锁屏状态下双击都直接打开了 Google 钱包** 。

把原生 Android 和小米的逻辑放在一起，双击电源键之后发生的事情是这样的：
    
    
    flowchart TD
        Press(["双击电源键"]) --> Key{"double_click_power_key"}
        Key -->|"mi_pay"| Mi["小米钱包"]
        Key -->|"launch_QAW_wallet"| NFC{"默认 NFC 付款应用"}
        Key -->|"null / google_pay"| Nothing["什么都不做"]
        NFC -->|"Google Pay"| QAW["Play 服务的<br/><b style='color:#b45309'>QuickAccessWalletService</b>"]
        QAW --> GW["Google 钱包"]
        NFC -->|"小米钱包"| Tip["提示：当前默认钱包<br/>不支持双击电源键打开"]
    

小米做的另一件事，是在开机时检查这个值。如果它认为当前的值「不支持」，就会把它清掉：
    
    
    MiuiSingKeyShortcutObserver: set double_click_power_key to null, because function not support
    

## 原项目做了什么

原项目当时并不知道 `launch_QAW_wallet` 的存在，所以绕了一个大圈：

  1. 把 `double_click_power_key` 改成一个系统不认识的值 `google_pay`，让系统的双击动作失效；
  2. 通过 adb 用 `app_process` 启动一个以 shell 身份运行的常驻进程，用 `getevent` 监听电源键的按下与抬起，自己识别双击；
  3. 识别到双击后，用 `am start` 打开 Google 钱包的刷卡页，锁屏时再配合配套 App 处理解锁状态。

思路很巧妙，但有两个问题：这个常驻进程重启后就没了，每次重启都要连电脑重新激活；而在 HyperOS 4 上，`google_pay` 这种不认识的值同样会在开机时被系统清掉。我一开始就是先把这套方案原样搬了过来，后来在排查一个「备份里的原值莫名变成 `null`」的问题时，才顺藤摸瓜发现了开机清理和 `launch_QAW_wallet`。

## 我的 fork 做了什么

说穿了，核心就是开头那条命令。我的 fork 做的是在这条命令周围补齐三件事：

### 1\. 改用原生的 launch_QAW_wallet

不再需要常驻进程，也不用自己处理锁屏，全部交给系统。小米钱包模式就是把值写回 `mi_pay`。

### 2\. 切换模式时同步默认 NFC 付款应用

默认付款应用存在 `settings secure nfc_payment_default_component` 里。Google 一侧是 `com.google.android.gms/.tapandpay.hce.service.TpHceService`，小米钱包则是 `com.android.nfc/.cardemulation.ESEWalletDummyService`（走的是 eSE）。切换到 Google 钱包模式时把默认付款改成 Google Pay，切换到小米钱包模式时改成小米钱包；如果你选的是第三方付款应用，就不动它。

前面说过，QAW 打开的是默认付款应用的钱包，所以这一步不只是顺手：**两种模式各自对应一组设置，缺一不可** 。

模式 | `double_click_power_key` | 默认 NFC 付款应用  
---|---|---  
Google 钱包 | `launch_QAW_wallet` | Google Pay  
小米钱包 | `mi_pay` | 小米钱包  
  
尤其是切回小米钱包的时候，只改默认付款应用是不够的，双击会提示「当前默认钱包不支持双击电源键打开」，**必须把`double_click_power_key` 也改回 `mi_pay`**，而这一步同样需要 adb。

如果那时恰好不方便用 adb（比如已经把开发者选项关了），还有一条不需要 adb 的退路：在系统设置的「辅助功能 → 通用 → 快捷手势 → 双击电源键」里，把它改回「公交 / Mi Pay / 门卡」。不过插件并不知道你这么改过，如果它记录的仍是 Google 钱包模式，下次开机并具备 adb 条件时，它会把值改回 `launch_QAW_wallet`。所以想长期使用小米钱包，最好还是在方便的时候到插件里切换一次。

### 3\. 让 App 自己执行这条命令

这条命令必须由 shell 来执行，普通 App 是写不了的：
    
    
    You cannot keep your settings in the secure settings.
    

`double_click_power_key` 不是公开的设置项，SettingsProvider 只允许 system、shell、root 和预装的特权应用修改它，普通应用只要 targetSdk 高于 22 就会被拒绝，**即使已经通过`pm grant` 拿到了 `WRITE_SECURE_SETTINGS` 也不行**。

所以我参考冰箱（Ice Box）、Shizuku 的做法，让插件自己扮演 adb 客户端，连接本机的无线调试来拿到 shell 权限：

  * **首次设置** ：在开发者选项的「无线调试」里点「使用配对码配对设备」，然后在插件的通知里输入 6 位配对码。配对完成后，插件通过 shell 给自己 `pm grant` 一个 `WRITE_SECURE_SETTINGS`。
  * **切换模式** ：插件用这个权限打开无线调试（`adb_wifi_enabled` 位于 Global 表，这个是能写的），通过 mDNS 找到本机 adbd 的端口，连上自己，执行 `settings put`，再把无线调试关掉，整个过程大约 5 秒。
  * **开机写回** ：开机后调度一个要求连接 Wi-Fi 的 JobScheduler 任务。如果你选的是 Google 钱包模式，开机后的值是 `null` 或 `mi_pay`，就写回 `launch_QAW_wallet`；如果是其他功能（比如你在系统设置里改成了相机），就不动。开机时无法区分「系统填回的 `mi_pay`」和「用户选的 `mi_pay`」，所以想长期用小米钱包的话，请在插件里切换，`mi_pay` 本身就能扛过重启。

插件切换模式的过程大致如下：
    
    
    sequenceDiagram
        participant App as 插件
        participant Sys as 系统设置
        participant Adbd as 本机 adbd
        App->>Sys: 打开无线调试（adb_wifi_enabled=1）
        App->>Adbd: mDNS 发现 _adb-tls-connect._tcp
        App->>Adbd: 用配对过的密钥连接 127.0.0.1
        App->>Adbd: shell: settings put（双击设置 + 默认付款）
        Adbd->>Sys: 以 shell 身份写入
        App->>Sys: 关闭无线调试（adb_wifi_enabled=0）
    

开机写回的判断逻辑则是这样的：
    
    
    flowchart TD
        Boot(["开机"]) --> Check["HyperOS 检查 double_click_power_key<br/>可能清空、填回 mi_pay 或保留"]
        Check --> Mode{"插件记录的模式"}
        Mode -->|"小米钱包"| Skip["什么都不做<br/>mi_pay 本身能扛过重启"]
        Mode -->|"Google 钱包"| Job["调度一个需要 Wi-Fi 的任务"]
        Job --> Wifi{"连上 Wi-Fi 了吗"}
        Wifi -->|"还没有"| Wait["等待"] --> Wifi
        Wifi -->|"连上了"| Adb["打开无线调试并连接自己<br/>（需要开发者选项）"]
        Adb --> Value{"当前的值"}
        Value -->|"null / mi_pay"| Write["写回 <b style='color:#b45309'>launch_QAW_wallet</b>"]
        Value -->|"launch_QAW_wallet"| Ok["已经正确，不动"]
        Value -->|"其他功能"| Keep["尊重用户的选择，不动"]
    

**需要强调的是，这个方案并没有绕开 adb。** 插件只是替你临时打开无线调试，不管是切换模式还是开机写回，那一刻都需要 adb shell 权限，也就是必须开着「开发者选项」和「USB 调试 / 无线调试」。这和原项目「每次重启都要 adb 激活一次」本质上是一样的，只是把电脑省掉了。

## 关于 adb 客户端的实现

无线调试的配对和连接涉及 SPAKE2、TLS 之类的协议细节，说实话我自己也不是那么懂，这部分代码全部交给 AI 照着 AOSP 的 adb 源码写的，我只负责在真机上测试、看日志、反馈问题。感兴趣的朋友可以直接去仓库里看代码。

实际使用中值得一提的只有一点：HyperOS 会在 App 切到后台的瞬间把它冻结（日志里是 `freezeUid SUCCESS ... reason=tobg`），我第一次测试时就卡在了切去设置页找配对码的那一步。所以一定要给插件允许「自启动」，并把省电策略设为「无限制」。

## 一些注意事项

  * **全程依赖开发者选项** 。很多人日常会关闭开发者选项，比如 HSBC HK 这类银行 App 就不允许在开启开发者选项的手机上使用。如果你也是这样：关闭期间无法通过插件切换模式，需要小米钱包时只能去「辅助功能 → 通用 → 快捷手势 → 双击电源键」手动改回「公交 / Mi Pay / 门卡」；小米钱包模式重启后不受影响；但 Google 钱包模式在重启后可能被系统清掉，在你重新打开开发者选项、连上 Wi-Fi 让插件写回之前，双击都不会打开 Google 钱包。另外，关闭开发者选项后，已授予的 `WRITE_SECURE_SETTINGS` 和无线调试配对会不会被收回，我还没有验证。
  * **需要 Wi-Fi** 。无线调试只能在 Wi-Fi 下工作。
  * **配对可能过期** 。Android 默认会撤销 7 天内没有连接过的无线调试密钥，好在每次切换和开机写回都会连一次。万一过期了，在通知栏重新输入一次配对码就行。
  * **插件有网络权限了** 。它只连接 `127.0.0.1` 上的 adbd，但持有一把被 adbd 信任的密钥，无线调试开着的时候可以随时拿到 shell。介意的话，可以在开发者选项里「撤销 USB 调试授权」。
  * **不想装插件的话** ，开头那条命令手动执行一次就行，只是重启后可能需要再执行一次。

## 结论

国行 HyperOS 4 自己就藏着「双击电源键打开 Google 钱包」的能力：它就是原生 Android 的 Quick Access Wallet，HyperOS 里叫 `launch_QAW_wallet`，只是没在设置界面里露出来，开机时还可能被系统自己清掉。

所以整件事说穿了，就是**用 adb 权限改一下`double_click_power_key` 这个设置**，再把默认付款应用对应好。反过来想用小米钱包时，也得把它改回 `mi_pay`，因为 `launch_QAW_wallet` 打不开小米钱包。我的 fork 只是把「什么时候执行这条命令」自动化了：配对一次，以后切换模式和开机写回都不需要电脑，但前提是开发者选项一直开着，这对需要关闭开发者选项才能用银行 App 的朋友来说并不友好。

至于为什么 Quick Access Wallet 在国行被标记为 `disabledByCustFeature`，却在运行时完全可用——大概是因为没人会在国行手机上用 Google 钱包吧。

n8n Labs 把个人智能体 Nod 装进了你自己的电脑：它能跨应用、跨网站订酒店、取消订阅、下载发票，碰到付款、发送、发布、删除这类动作会先停下来核对你的原话。软件开源免费，模型费用另算，单次任务超过 5 美元默认要你点头。能不能放心把付款键交给它，看的不是它会不会搜酒店，而是它每次停住时，你看不看得懂它在做什么、花了多少。

Nod 像一位拿着你家门钥匙的私人助理：它能在应用和网站里替你跑腿，但钥匙不是全权授权，涉及发送、付款、发布和删除的动作，仍要经过你的明确同意；网页或邮件也不能冒充你下令。 

## 它不住在云端，住在你的笔记本里

Nod 是 n8n Labs 推出的个人智能体。它独立于 n8n 核心产品，装在你自己的电脑上，连的是你个人的账户——不是团队共用的那套流程。

它处理的是“一个人的待办”，不面向团队共享流程。装好 Nod、连上账户、说清要什么，它就去应用和网页里把这件事做完。现阶段它以研究预览版（尚未正式定版的测试版本）发布，代码采用 Apache 2.0 开源许可；作为独立应用，使用时不需要 n8n 账户。

Gmail、Calendar、Drive、Slack 这些有官方连接的应用它能进，真正拉开差距的是另一半：没有官方连接的网站，它照样在网页里点、填、翻页，把一整件事从头做到尾，而不只是按某个应用里现成的按钮。

官方列出的任务很具体：找到符合出行需求的酒店，并在用户确认后预订。它能把查找与后续行动连起来，但预订仍以用户点头为前提，不会看到合适结果就直接付款。

## 它怎样代用户完成订酒店？

Nod 接到订房任务后，在自己的浏览器里把预订走完，不是把页面交还给你。碰到发送、付款、发布或删除这类动作，它会先核对你的原话。

这种执行方式来自 Nod 的本地沙箱（电脑内隔离的运行环境）和独立浏览器。它既能在已连接的应用里工作，也能操作没有专用接口的网站，因此聊天工具原本列给你的待办事项，可以由它接手继续做。这里的关键不是回答得更长，而是从“找酒店”跨到实际预订。

你也可以通过 Telegram（一款即时通讯应用）或 WhatsApp（一款即时通讯应用）与它对话，不必守在电脑前；浏览器会在后台继续搜索和填写页面。

从交代需求到完成预订 提出订房要求→ 搜索合适酒店→ 核对关键动作→ 完成预订 

多个任务可以同时在后台运行，不必等酒店订完才开始下一件事；需要反复执行的任务还能按计划启动，例如定时查询价格。任务并行运行，解决的是等待问题；独立检查，解决的是权限问题。

这道检查本身是另一个模型，也会出错。所以它的判断标准很窄：只认你的话有没有覆盖这个动作。订酒店时，付款属于需要重点核对的动作；你的话没有明确覆盖，它就停下来问。这个机制不能替代用户看清金额与操作记录，但能在扣款前多设一道由系统执行的门槛。

![n8n Blog 官方配图 1](https://anymesgs.com/assets/img/n8n-local-agent-nod-media-1.png) 官方配图 1 · 来源：n8n Blog · 数据口径以原文为准 

## 它会记住你几个月前说过的话

普通聊天助手给建议、拟邮件、列待办，最后仍要用户逐项执行。Nod 会进入已连接的应用和网站，持续操作，直到任务完成。

Nod 会读取已连接应用，主动识别其中可接手的工作，并提出代为完成。它面对的是一项需要落地的任务，标志很直接：相关操作已经做完。

这种代办能力建立在持续关系上。Nod 会记住数月前的对话，不必让用户反复重述偏好和背景。在 LongMemEval（长期记忆基准，用于测试智能体能否记住过往信息）上，Nod 的官方公布成绩为 93.2%。

这是厂商提供的跑分结果，目前未见第三方复测，不能单凭它判断实际体验。

连接 Gmail（谷歌邮箱）后，Nod 还会检查用户过去如何措辞，让新草稿更接近用户自己的语气。普通助手可能临时模仿文风，Nod 则从历史表达中学习。这会影响它代写的邮件是否真能代表用户。

网站改版后，任务也不能停在半路。Nod 会记录一次任务是怎样完成的，下次沿用这些步骤，并在网站发生变化时修正操作方法。代办的最后一环，是继续动手做下去，而不是把事情交还给用户。

我们的判断：记忆是它持续代办的前提，前提之外还差一步验证——厂商跑分没有第三方复测，实际体验要等真实任务来检验。

## 登录信息留在本机，模型看不到密码和卡片

Nod 要替你登录、付款、发邮件，那密码和卡号会不会被模型看见？n8n Labs 的答案是不会：凭据存放、任务执行与模型调用被拆成三层，密码和卡片始终留在你机器上。

第一层是虚拟机。Nod 跑在你电脑上的私有虚拟机里，带自己的浏览器，登录网站、执行任务都在里面完成，不接管你正在用的浏览器窗口。数据、记忆和保存的登录信息都留在运行 Nod 的本机，不集中到 n8n 的云端。

第二层是加密。保存的登录信息和卡片在本机加密，提交时走模型读不到的私密表单。模型只知道「这一步要登录、要填资料」，看不到密码和卡片里的具体内容；真正动手填写的仍是本机上的 Nod。

第三层是权限。网页或电子邮件没法给 Nod 下命令，页面上的文字不会被当成你的新指令。Nod 发送、付款、发布或删除之前，另有一道独立检查确认这话是你说的——这道检查本身也是模型，也会出错，所以它拿不准时会回来问你。

## 用户能看清它做了什么、花了多少钱吗？

Nod 把操作与费用放在同一条记录里：用户不只看到任务完成，也能看到它登录过哪里、用过哪张卡，以及这项任务花了多少钱。

据 n8n Labs 官方介绍，Nod 会记录每次登录、卡片使用和应用内操作，同时保存每项任务的成本。记录的是“做了什么”和“花了多少”，因此用户可以按任务回看，不必只凭最终结果猜代理做过什么。

费用控制分成平时看账和付款前拦截两层。每项任务都会显示费用，任务结束后还会生成一张收据，用户可设置每月支出上限。计划任务同样会显示预计每月费用，这让重复执行的价格提前出现在安排阶段，而不是等费用累积后再追问。

场景 | Nod 提供的提示或控制 | 用户能判断什么  
---|---|---  
单次任务费用不超过 5 美元 | 任务页显示费用，完成后附收据 | 这笔任务实际消耗了多少成本  
单次任务超过 5 美元 | 付款前向用户确认，确认金额可以修改 | 是否接受这笔金额，以及是否调整后再执行  
长期或重复执行 | 显示预计每月费用，并允许设置每月支出上限 | 持续支出是否仍在预算内  
  
我们的判断：Nod 的费用控制不是靠一个总开关，而是靠记录和确认流程把每一笔支出摊开在用户眼前，前提是这些记录和确认本身准确。官方没有给出第三方复测数据，这是研究预览版的边界。

## 开场：三种条件，三种活动

先回顾一下前两期。第一期讲的是时代背景：科技越来越专业化，普通人越来越远离政治。科技和人的生活联系得越来越紧密，而政治本来就是讨论人怎样生活、怎样共同生活，所以科技和政治的关系越来越紧密；同时科技又越来越专业，普通人越来越无法理解。这是阿伦特的时代背景，也是我们这个时代的境遇。

第二期讲了“人的条件”。这本书的书名，王寅丽译作“人的境况”，正文里则都译成“条件”。我觉得都可以，环境、条件、境况都行。“条件”有前提的意思，人之为人的前提，但不要把它理解成逻辑学上的条件，也不要理解成本质主义意义上的前提，它更像相亲时问你“家庭条件怎么样”的那种条件，其实和“境况”差不多，两个词合着来理解就好。

阿伦特把积极生活分成三种：劳动、工作和行动。积极生活和沉思生活相对，沉思冥想、离群索居的生活先不谈；积极生活是普通人、常人都会去过的生活。为什么恰好是这三种？因为它们各自对应人的一种基本条件。当然，对应不是严丝合缝的，后面会讲到它们的异化和错位，这是现代性的问题。

第一种条件是人作为动物的条件：要吃喝拉撒，要温饱，没有衣服穿、没有房子住会冻死，没有东西吃会饿死；从人类整体来说，繁衍也属于这一层。对应这些动物性需求的，就是劳动。

第二种是工作。人不像鸟筑巢那样，只凭写在基因里的本能，在生命循环之内建造；人可以不建造，也可以在前人的基础上继续建造，造高塔、造钢筋水泥，比一般动物独立得多、丰富得多。这就是阿伦特说的世界性，这里继承了海德格尔：动物是贫乏于世界的，器物是没有世界的，一个杯子、一把椅子没有自己的世界，它们只在人的世界里组成整体。人活在自身之外，寓于用具和外物之中。工作不是为了解决动物性的需求，而是释放人性的特点，给这个世界增添原来没有的东西。

第三种条件是复数性，对应的是行动，更接近政治。王寅丽译作“复数性”，仲树译作“多元性”。从字面看，复数性是准确的；从意思看，多元性也到位。阿伦特要强调的不是人像蟑螂一样数量很多，几万只蟑螂也是复数，人的复数是说有很多个独一无二的人。行动要应对的就是这种复数性。从反面说，人与人有摩擦：我想在这儿开读书会，别人想在这儿蹦迪，有人要看电影，就这一块地方，归谁？这就需要商谈，商谈就是政治性的活动。从正面说，人多了，我想出类拔萃，想展示自己、实现自己，在人群中显示我的独一无二。这种独一无二不是躺着就能实现的，潜在的独一无二要靠行动在人群中实现出来。

三种积极生活又对应一个更大的条件，就是诞生性，它和有死性相对：沉思生活对应有死性，积极生活对应诞生性。这是对海德格尔的补充或者矫正。海德格尔强调人终有一死，这种有限性逼着你珍惜当下，认真承担自己的命运。阿伦特则从更积极的角度来讲人的基本条件。诞生性，我的理解就是总有新的东西降临。一个孩子诞生，不仅是世界上多了一个东西，而是世界中又多了一个世界，因为他能开展出来的可能性是新的、独一无二的。人为什么值得活？因为这个世界总是充满可能性。

## 作茧自缚：人造之物成了人的条件

阿伦特说道：

人的条件包括的不仅是生命被给予人的那些条件。人也是被条件规定的存在者，因为任何东西一经他们接触，就立刻变成了他们下一步存在的条件。积极生活置身于其中的世界，是由人的活动所产生的物组成的，但是这些完全由于人方得以存在的物，常常反过来限制了它们的人类创造者。除了人在地球上的生活被给定的那些条件外，人也常常部分地在它们之外，创造出他们自己的、人为的条件；尽管后者来源于人，因而是可变的，但也跟自然物同样具有了制约人的力量。……因为人类存在是被条件制约的存在，人类就不可能没有物而存在，而如果物不是作为人类存在的条件，它们就只是一堆不相干的物品的堆积，一个非—世界。

这里很有海德格尔的味道。物本身没有世界，物是在人的世界之中，才成为相关的、相互指引的；物由人来定义，反过来，人也由物来定义。人是“被条件规定的存在者”，人总是在制造和改变自己的条件，人的条件也是人造的。无论自然物还是人工物，只要进入人的生活世界，就成了人的条件。所以这里的condition译成“环境”“境况”，可能理解得更通一点，但“境况”又弱了一点，因为这里有一种强制性：你脱离不了你的条件，不能离开条件来说人是什么。

所以人是历史性的，而这个历史是人自己创造的：你创造出一个新东西，它又反过来成为你、你的后代和他人的条件、前提。今天也是这样。要是突然没有了自来水、没有了电，我们很快就得死一半吧。可这些条件是我们自己造的，几十年前还有很多人打井喝水、没有电，也照样生活；我们要是没有这些，就遭殃了。尤其是新加坡这样人口密集的地方，把电停一年看看会变成什么样。电是人自己造出来的，造出来以后又变成了人的限制，人依赖上它了。往回推到冰河时代，人好像不需要那么多条件也能活；今天可不行了，我们不断地通过制造来改变条件。我有个词叫“作茧自缚”：人编织一个茧，把自己包起来，躲在里头。这就是人的条件。

## 人的条件不是人的本性

要避免误解：人的条件不等于人的本性，与人的条件相应的所有人类活动和能力的总和，都不构成任何类似于人的本性的东西。无论是我们本书中讨论到的人类活动和能力，还是像思想和理性那样略去不论的活动或能力，甚至对活动和能力最详尽无遗的列举，都不构成所谓人存在的本质属性(意即没有它们，存在就不再是人的存在)。在人的条件中我们所能想象的最极端的改变，莫过于人从地球移居到另一个星球上。这一并非完全不可能的事情，意味着人将不得不生活在人造的条件之下，完全不同于地球给予的那些条件。的确，到那时，劳动、工作和行动，以及我们所知的思想都不再有任何意义了。然而，即使那些我们想象的离开地球的漫游者，也仍然是人；我们关于他们的“本性”所能做的唯一声明是：他们依然是受条件规定的存在者，即使现在他们的条件在很大程度上是人自己造的。

这是前一段的推论：人不断塑造自己的条件，也就意味着人没有固定的条件。我们今天的生活条件，到了未来可能就不再是那时的人的条件；最极端的例子就是移居火星，地球上现存的所有条件，都不再是他们的生存条件了。

一位参与者没看懂：为什么到了火星，劳动、工作、行动和思想就都没有意义了？

我的理解是，“我们所知的”不光修饰思想，也修饰劳动、工作和行动。火星居民也许还要劳动、还要行动，但已经不是以我们所知的方式了。阿伦特在这里可能也是想声明：她的三分法也是历史性的，不是一个绝对的分类，不管怎么列举，都不是人的本性。人的本性如果有什么不变的，那就是人总是有条件的存在者，但条件是会变的，对应于条件的积极生活的方式也会变。她不是说这些分类对火星居民绝对没有意义，而是说那时候怎样，我们不可知。她是在限定讨论的范围：不要把劳动、工作、行动当成对人的本性的揭示。

另一位参与者问：思想和理性也“不构成所谓人存在的本质属性”，这要怎么理解？

我说，思想和理性属于沉思生活，这本书略去不谈。劳动、工作和行动不是人的全部活动，只是积极生活的三种样式。但阿伦特也说，思想和理性同样不是人的本性。把人定义成劳动的动物、工作的动物，或者思想的动物、理性的动物，都是可疑的。人的处境是变化的，很难用一张清单列清楚“人就是做这些事情的存在”。

## 讨论：谁还在工作？

一位参与者说，自己没太明白劳动和工作在定义上的区别：劳动的需求来自生存本能，工作的需求来自对自己独特性的确证，但从这两个词上感受不到区别，第一感觉它们像是一体两面、同一个东西。

我说，这本书的一大主题，恰恰就是劳动和工作的混淆。我们这个时代的人容易混淆劳动和工作，这正是现代性的命运。但就对应的人的条件来说，人作为动物的条件和人作为创造者的条件，其实是容易区分的。马克思也说，人和动物的区别在于人能改造世界；改造世界，和在世界中生存繁衍、维系自己的生命，是不一样的。人和牛马是不一样的，现在的问题是人和牛马混淆了，所以劳动和工作也混淆了。

这位参与者又问：能不能暂时把劳动理解为生存性质的，把工作理解为创造性质的？

可以。工作是累积性的，给世界添加一个新东西；劳动是周而复始的，是永恒的循环，后面会讲，劳动是没有目的的。吃饱当然是目标，但这一顿吃饱了，下一顿还要吃，今天吃饱了，明天还要吃，你永远解决不了需要吃饱这件事。工作有目的：我要造一座桥，桥造完了，世界上就多了一座桥，明天它还在，你可以再考虑在桥上造个亭子。人把金字塔造完了，金字塔就立在那里，后人生活在一个有金字塔的世界里。物总在成为人的条件，人造出来的东西又成为人新的条件，这就是工作；劳动只是不断应付周而复始的需求。

另一位参与者问：一个人在家炒股，属于劳动、工作还是行动？

我说，在家炒股在很大程度上是一种异化的劳动，关键就在钱。造一座桥，桥造完就造完了；赚钱却赚不完，赚了今天的还要赚明天的，赚了八辈子用不完的钱还嫌不够，永远周而复始。炒股也好，金融也好，游戏也好，都有这个问题。

先前问火星的那位参与者追问：那能不能说，巴菲特这辈子一直只在劳动？

巴菲特是另一个问题，某种意义上，他已经变成一种政治生活了，或者说是一种炫耀性的劳动。但巴菲特的问题确实是我们时代的问题：赚钱无止境，赚到巴菲特那样的钱，八辈子都够了，还赚什么？钱是中介，钱的意义是去造东西。我要造一座桥，需要筹钱，筹到了，桥造出来，钱就花到位了。但如果赚钱是为了赚更多的钱，利滚利、钱生钱，就永无止境。阿伦特说，这种永无止境的事情，正是劳动所要应付的：今天吃饱了明天还要吃，永远喂不饱你。

这位参与者又说：人类造桥的需求也是永无止境的，这边造一座，明天那边造一座，后天到火星上还要造。

这也是问题。桥造完了还要造桥，地球上造满了，就要去火星。阿伦特一开始就在质疑飞向太空：为什么要逃离地球？好像地球已经被糟蹋完了，空间不够了。为什么空间不够？因为方向搞错了，是在野蛮地开拓。造完桥以后，你本可以在桥上造个亭子、在旁边造座楼、造条船，在前人的基础上增加多元性。阿伦特非常强调这一点：没有多元性，劳动和工作都会迷失。不是说工作就一定是好的，最核心的还是人的多元性；抓不住它，所有的目的都会变得永无止境，造了这座桥还要造那座桥。今天很多地方的基建就是这个问题。基建本来是为了让我们过更好的生活，可现在一个三四线小城市，造了四五个高铁站，造完一个再造一个。为什么？还是因为钱，因为资本的游戏，像四万亿那样的大放水；不是真的想在这里要一个火车站，而是要把钱花掉。这就是异化，工作也变成了劳动，劳动、工作和政治行动都异化了。这就是我们今天的处境。

又一位参与者说：社会没有给我们那么多工作的机会，大部分机会是劳动。比如桥其实是工人造的，不是设计师造的，工人每天只是垒砖，垒完这座桥再垒那座，他不是在工作，只是在劳动；而且明天就没钱了，拿了薪水还得去垒下一块砖。

是的，更多的机会给大家的是劳动。这就是阿伦特后面要讲的“劳动者社会”：社会是靠劳动的方式组织起来的。原本一个工匠，造一座桥、打一口锅，都是在工作；现在把工作拆成一个个环节，每个环节都周而复始、没有目的，你像驴子拉磨一样重复一个动作，再把所有人的动作串起来，取代原本的工作。

最先问劳动和工作区别的那位参与者接着问：如果工人是在劳动，设计师就一定在工作吗？对他来说，画完一张图纸还有下一张，这是不是也是劳动？那到底是谁在工作？

是啊，就是没人在工作了，这就是问题所在。现在可以说只有极少数艺术家还在工作。

先前问巴菲特的那位参与者觉得，这个定义是不是太狭隘了：难道只有艺术家和作者在工作，所有为了钱的都不算？

我说，我讲的是异化。异化不代表他们真的不在工作，你可以说工人在工作、设计师也在工作，只是这些工作异化了：其实应该当作劳动来理解，却又和工作混淆在一起。阿伦特这一段就是在说，劳动、工作和行动不是人固定不变的本性，它们会变化，我们要谈的是它们怎样变化、对我们来说是什么样子。这和海德格尔一样，描述我们的处境并不是贬低，不是说“这不对，你不要这样做”，而是先认清我们的命运、我们的处境：我们现在就是混淆了劳动和工作的界限，这意味着什么，才是要讨论的问题。阿伦特不是要证明现在没有人在工作，但可以说，现在很少有人像古希腊人那样工作，或者像古希腊人那样行动。就像到了火星，人可能还在工作，但可能不会再像我们今天这样工作。

## 讨论：为什么要分清界限？

一位参与者说，判断自己是在劳动还是工作，应该从很个人的意义上来看，没有绝对的标准。比如巴菲特，如果他觉得自己不是为了钱，而是为了留下一段故事，那可能就要另说。

我说，从个人角度当然可以这么看，但阿伦特讲的是一个普遍的问题，重点在后面要讲的劳动者社会：这个社会是以什么方式组织起来的。个别人可能很有创造性，目标和别人不一样，但从社会整体来说，巴菲特是有代表性的。无论巴菲特自己怎么想，大家都把他当成榜样，那么他示范的是什么？这是可以做概括性讨论的。

先前问巴菲特的那位参与者又提出：说到行动时谈到复数性，可在一个群体里，绝大多数人做的事是相似的，只有极少数人能做出超出一两个标准差之外的特例。绝大多数程序员可能写着相似的程序，更像劳动；只有极少数人能算是在工作。

我说，这种处境本身就是社会结构造成的，其实每个人完全可以不同。比如你的宿舍、你的班级，你会觉得大家都一样吗？你会看到每个人都有个性，因为你们有密切的交流和接触：你跟他谈恋爱了，我跟他闹矛盾了，寝室夜谈时我有这个观点、他有那个观点，他语文好、我历史好。通过充分的交流，你会体会到每个人都不一样。可一放到社会里，班里每个人都只是一个学号、一个分数，高考分数一拉，好像大家都差不多，这条分数线的一群人都送到工厂里打螺丝。从高考筛选到就业再到打螺丝，这个过程里没有交流，没有让每个人充分展示自己、充分接触他人的公共空间，大家当然就看起来都差不多。传统一点的人，街坊四邻都很熟，张家长李家短说得头头是道；我们都市人住在501、502、503、504，一格一格的，没有交道，也不认识，你是501，他是502，有什么区别？没有交流，就没有区别。

这位参与者问：这是时代的问题，还是人太多的问题？原本知道邻居，现在知道同学、同事，人太多了，没有精力去了解。

我说，人的圈子是层层叠叠的。不说古希腊，就说现代的民主制，美国的民主制也是分层的：先是街区，街区里就有政治活动；再往上是市、州、国家，每一级都有自己的讨论空间。到国家层面竞选总统的人很少，大部分人是选民，但在每一层里，每个人都有自己的位置。这种人人有位置的交流都是政治性的，胡同口聊天、张家长李家短，这些都是政治活动。现在这些政治活动都被扁平化、被压缩了。

有参与者接着说：工作其实很复杂，公司里有很多重复性的部分，更像劳动；也有创造性的部分，更像工作；我可能为了赚钱，同时又有可以积累的部分，本来就是掺杂的。

我同意，这本来就不是一个本质性的、非常确定的分界。但另一方面，混淆是不利的。阿伦特后面也会说，要过政治生活，就要有意识地分清界限：什么时候我的活动是为了劳动，什么时候是为了创造，什么时候是为了追求卓越、追求政治。没有这样的边界，政治就搞不好。她讲古希腊很重要的一点，就是公共领域和私人领域的边界非常清晰。

政治让每个人都独一无二，这需要公共的交流空间，但这个空间需要限制。一个限制就是要小一点，不能被拍扁。现在的社交媒体就是拍扁了，地球村，全世界的人挤在一个空间里，反而展示不了个人。传统上有边界，一个班、一个宿舍，是一个个小圈层。边界可以模糊，班级之间也有来往，但相对而言有一个边界：这一部分是班级内的集体生活，有友谊；另一部分是公事公办，是商业关系之类。有了这样的区分，公共生活才能健全地组织起来。

劳动的边界也是这个问题，因为劳动是永远解决不了的。现在国际上的很多政治困境，也是因为没有这个边界。比如有些环保主义者往名画上泼油漆，把手粘在墙上，质问“生命重要还是画重要”。这就是一种混淆。两者都重要，但不在一个层次上，混在一起谈，你好像只能说生命更重要：人都要死了，还要画干嘛？可一旦承认这一点，你就绕进去了，因为生命问题永远都有：非洲还有人饿死，这里的饥荒解决了，下一代还要解决，还有残疾人怎么办。那么我们什么时候才可以开始创造艺术？难道在全世界所有人的生命威胁被清除之前，都不要欣赏和创造艺术了吗？那些环保主义者就是这个逻辑。

阿伦特说，要认清一点：生命问题是永远解决不了的，这是劳动的宿命。解决了今天的生命危机，明天还有；你自己的解决了，别人的还没解决。那么人什么时候才能搞艺术、搞政治、搞哲学？需要一个界限，古希腊的私人领域和公共领域的界限就是这个界限。迈出私人领域，进入公共空间，就默认大家都已经吃饱了饭，不再讨论明天吃什么、饿死了怎么办；哪怕打肿脸充胖子，也要在衣食无忧的前提下进入公共生活。进入公共领域，私人问题就要被隔离开，在公共空间里谈的是生命需求之外的事情。这样，公共生活才可能健全地发展。这样的公共生活，和我们今天理解的政治也不一样。我们今天的政治商谈主要都是谈论有关生命需求的事情，所以说三种积极生活都在异化，政治生活也异化了。

## 人不能定义自己

人之本性的问题，奥古斯丁所谓的“我对我自己成了一个问题，似乎在个体心理学和一般哲学的意义上都是无法回答的。我们能认识、确定和定义我们周围万物的自然本性，但是我们无法对自己做同样的事——就像无法跳出自己的影子一样。另外，没有什么东西能让我们有理由假定，人像其他事物一样，有一种本性或本质。换言之，如果我们确有一种本性或本质，那么只有上帝才能知道或定义它，而首要的前提是他能像说出一个人是“什么”(what)一样说出这个人是“谁”(who)。此处的困难在于，人的认知模式只适用于认识有“自然”性质的事物，包括对我们自身的认识，也限于我们作为有机生命发展最高阶段的样本。但是当我们提出“我们是谁？”的问题时，人的认知模式就不起作用了。这就是为什么企图定义人的本性的各种尝试，都不可避免地终结于构造出某个神，哲学家的神的原因……但是定义人的本性的尝试很容易导致我们产生某种“超人”的观念，并把它等同于神，这一事实足以让人对“人之本性”的概念投去怀疑的目光。

这段读起来容易觉得没懂，其实它没说什么新东西，还是在说人没有本性。只是这一段是在和哲学家对话，所以显得难懂。

她强调的是，人不能自我定义，就像不能跳出自己的影子。人要定义人的时候，其实是在定义我自己、我们，是在自指。这和定义外物不一样。定义外物时，你可以站在客观的视角，把它放到一张图纸、一张图谱上来界定，这就是阿伦特说的对“自然”性质的事物的认知，也就是客观的、科学的视角。你也可以把人当作自然物来定义：人是一种什么样的猿类，基因图谱是什么样的，身高、习性如何，都可以客观地描述。但这些都是关于what的定义，不是关于who的定义，解决不了“我是谁”的问题。

阿伦特说，以往企图定义人的本性的尝试，都不可避免地走向构造一个神，比如柏拉图式的理念；而定义人的本性的尝试，又很容易导向某种“超人”的观念。前面讲过，人是历史性的，人通过塑造自己的条件来改变自己。这其实是把海德格尔的说法变成了人类的自我理解。按海德格尔的思路，你只要还在问“我是谁”，就证明你还没死，一切还不确定，你还没有成为一个确定的存在，所以这是自指的问题。人类也一样，人类在不断塑造自己的条件，甚至关于人的本质的那些哲学定义，本身也变成了人的条件。柏拉图提出他的学说之后，他的学说也成了人类的条件之一、成了人得以成立的历史背景。所以你永远没法站在一个客观的视角上，只能自己评论自己。

企图自我定义的人，往往走向两种模式。一种是超越性的：人不断在变化，那就设定一个永恒不变的东西来定义变化的人，这就是神，永恒不变的肯定不是人。基督教就是典型：人是神照着自己的样子造的，所以人有神性，而神性是永恒不变的。也就是在一个不断变化的存在中找永恒不变的东西，办法是虚构一个神。另一种是设定一个遥不可及的点，好像在这个点之下，一切变化又都变成了不变。前一个时代是往回找，从原始人来定义人：卢梭要先设定一个原始状态，高贵的原始人；霍布斯说原始状态是所有人对所有人的战争。这个原型根本不存在于现实中，是一个遥不可及的过去，但有了这个锚点，好像就抓住了人的本质。我们这个时代则是往未来找，用人未来的某种形象来定义现在的人，这就是超人，机械飞升、数字飞升，也是某种成为神的形象。

一位参与者问：那佛家“无我”这种说法属于哪一种？

我说，“无我”恰恰是非本质主义的。正统的佛学还是挺厉害的，它强调的就是人没有本质。佛教说不要执着，“无”也不是本质，既不要执于有，也不要执于无；不能说“四大皆空”，空就是人的本质，也不要这样说。它要破除的是执念：一定要找一个概念、一种本性或实体来解释不断变化的人类，这件事本身就是可疑的。所以佛教讲的“无”也是反本质主义的。

另一方面，人存在的那些条件——生命本身，诞生性和有死性，世界性，复数性以及地球——从来不能“解释”我们是什么或回答我们是谁的问题，原因很简单，这些条件从未绝对地限制我们。……现代自然科学之所以能取得巨大胜利，就在于它能从一个真正宇宙的观点来对待地球所限的自然(earth-bound nature)，也就是说，明确大胆地从地球之外取得一个阿基米德点。

这里还是在说，这些条件不是绝对的限制。讲到科学的视角，阿基米德点就是一个支点，一种宇宙的视角。阿伦特对现代科学并不是否定的态度，她承认现代科学开启了新的可能性、新的视角，人能从更高、更客观、更超越的视角来看待自己了。但这个视角的开辟本身也意味着非绝对性：并不是科学找到了一个更高的视角，科学就是那个绝对的视角；恰恰证明了没有绝对的视角，视角是在历史中不断变化、不断拓宽的。

这两段稍微有点啰嗦，其实都是在反本质主义。海德格尔有时也啰嗦，因为某种意义上是说给同行听的，那时的哲学还不像后现代以来，反本质主义已经不稀奇了（不过对我们今天的普通人来说，反本质主义也还值得一提）。她是在声明：虽然我好像在谈论哲学、谈论人的本质，但我谈论的不是人的本质。

## 讨论：古希腊真的那么美好吗？

中间休息之后，先前问巴菲特的那位参与者问：古希腊真的像描述的那么美好吗？

不美好。古希腊的美好建立在奴隶制之上，自由民大概只有一半，另一半是奴隶，还有外邦人，只有本邦的自由民才享有政治、享有公共生活，其实还是一种特权。不同城邦也不一样，最典型的城邦时代也是有限而短暂的。但古希腊示范出了一种可能性：在一个局部、在一段相对短暂的黄金时代，能组织起这样一种独特的城邦政治。这还是一个奇迹。奇迹不在于那时每个人都过得很美好，而在于它在古代社会示范出了这样一种独特的社会形态，而且这种社会形态一直影响着整个西方思想，乃至全人类的历史发展。

另一位参与者问：他们当时的行动谈论的是什么？奥林匹克精神应该也是那时出来的，现在反思起来，它可能也不是绝对好的东西。

奥林匹克精神就是追求卓越，用你的双手双脚胜过别人，这也是一种行动。古希腊的公共生活基本上都是行动。这个后面会讲到，先随便聊聊希腊人的几种基本公共设施。

（现场我漏讲了阿戈拉，把市政厅和阿戈拉的功能混一起说了，这里重新讲一下）

第一是市政厅。市政厅是议事中心，主要召开五百人会议之类，符合条件的公民经过抽签，决定加入五百人会议——议员不是选举出来的，是抽签出来的，每个人都有机会，而且每个人一生中只能当两次议员。

第二是阿戈拉Agora。这个词很难翻译，因为没有现代的对应物，经常译成“广场”或“市场”，它首先是一个公共广场，在议事厅附近，类似于中国大城市里的人民广场。但它同时也是一个嘈杂的市场，你可以在这里买卖，包括兜售你的思想（演讲）。然后它也是举办公民大会的地方，像陶片放逐、判处苏格拉底的投票，就是这类公共活动，有时更大规模的集会会到附近的山上举行；阿戈拉也包括法庭，法庭有专门的建筑，但很多时候公民陪审团就是直接在广场里辩论和审判的。

第三是剧院。剧院提供公共的谈资，大家一起欣赏和讨论悲剧、喜剧的内涵，包括什么是正义，什么是荣誉等等，这是公共生活的必要部分。希腊公民看剧是免费的（甚至还补误工费），作为公民，看剧既是权利也是义务。

第四是体育馆。希腊没有九年制义务教育，基础教育就是体育：可以不学数学、不学哲学，但每个公民都要送到体育馆接受身体训练，也包括一些文化教育。体育馆（gymnasion）这个词，词根就是希腊语的“裸体”，大家在那里裸体运动。一方面是希腊人对人的身体、对不假外物的力量特别看重；比赛时大家都脱光了衣服，不靠家里有钱、有势、有权，也不靠衣着光鲜，我跑得快就是我跑得快，这就是追求卓越。奥林匹克只是最大的体育盛会，大大小小的赛会和竞技非常多，很多地方女性也参加体育运动。

第四是浴场。从希腊浴场到罗马浴场再到土耳其浴，公共浴池文化源远流长，大家脱光了衣服在那里聊天，这是公共生活很重要的部分。

这就是希腊自由民的生活。他们吃饱了饭，不关心温饱问题，温饱由奴隶解决；吃饱饭没事做，就去市政厅、去市场、去剧院、去体育馆、去浴场。

## 积极生活一词的来历

进入第一章第2节，阿伦特说道：

积极生活一词承载且过度承载了传统的负担。这个词跟我们的政治思想传统一样悠久……产生于一种特定的历史聚合：苏格拉底的审判和哲学家与城邦之间的冲突。这个传统取消了与其直接政治目的无关的许多更为远古的经验，并最终以一种高度选择性的方式，在卡尔·马克思的著作中达到了终结。vita activa本身是中世纪哲学对亚里士多德的bios politikos(政治生活)的标准翻译，在奥古斯丁著作中已经出现……仍反映了这个词的原初意义：一种致力于公共政治事务的生活。

仲树把vita activa译成“实践生活”，也是有道理的。不过“实践生活”偏马克思，偏亚里士多德的话就是“政治生活”。积极生活这个词包含了政治和实践的意向，是西方思想史上一个非常重要的古老词汇：在亚里士多德那里讲的是政治生活、城邦生活，政治这个词基本上就是城邦；到了马克思那里，是实践活动，所以说这个传统终结于马克思。阿伦特后面会花较多篇幅讨论马克思，马克思很重要，但他也跑偏了，这个以后再说。这里讲的是这个词的原初含义：一种致力于公共政治事务的生活。

## 亚里士多德的鄙视链

亚里士多德区分了自由人可能选择的三种生活方式，自由，意即完全不受生存必需品和由于生存必需而产生的关系的束缚。自由的前提条件就排除了所有首要目的在于维生的生活方式——不仅包括劳动的生活(劳动是奴隶的生活方式)，而且包括自由手艺人的制作生活和商人的敛财生活。简言之，任何人自愿或非自愿地为了他全部或暂时的生存，丧失了他运动或活动的自由倾向，就都被排除在了自由生活之外。而其余三种生活方式的共同点是它们都关注“美”的事物，即关注既非必要又非纯粹有用之物：在享乐生活中，美是用来消费的；在致力于城邦事务的生活中，卓越产生了美言嘉行；在探索和沉思永恒之事的哲学家生活中，恒久的美既不会因为人们的营役而生成，也不会因为人们的消遣而改变。

亚里士多德说的自由人的三种生活方式，就是享乐、搞政治和搞哲学，这三种都关于美，前提都是自由。这也回答了前面的问题：希腊人在干什么？亚里士多德亲自回答了，自由人有三种，享乐的、搞政治的、搞哲学的。不自由的人在干什么？在劳动、经商和制作。

这里制作已经被归入非政治的一类，和劳动放在一起了，这是柏拉图之后的偏见。前面讲过，阿伦特更看重苏格拉底及以前的政治传统，柏拉图之后过分抬高沉思生活、贬低政治。不过亚里士多德对生活方式的概括还是有代表性的，还是希腊式的。希腊人对奴隶当然都是贬低的，苏格拉底和之前的人也一样；分歧在于诗人和手工艺人的地位，他们是在柏拉图那里被贬低的。其他希腊人本来很喜欢诗人，荷马史诗、吟游诗人在希腊的地位都不错。柏拉图之后非常强调自由的生活，就觉得那些艺人虽然不是全部生活都被必需品支配，但也部分卷入了必需品：造出来的东西要卖钱，要养家，就被看不起了。商人也是，在法律上可能也算自由民，但在更贵族、更精英的自由民看来，他们和奴隶没什么两样，成天为生活必需品奔波劳碌，格调比较低。

先前问巴菲特的那位参与者问：放在现代的话语里，是不是富二代在鄙视链的顶端，完全不用工作、本身就很有钱的人，鄙视那些要自己想办法赚钱的人？

我说，不是。现在的鄙视链很多是看有钱没钱，有钱就受尊重，这和希腊人很不一样。富二代也是有要求的，不是随便就可以鄙视别人；富二代如果没有选择一种自由的生活方式，也是要被鄙视的。希腊人没有想富不富的事，因为他们的奴隶制是体制性的，普通的自由民也有奴隶，有奴隶并不需要你很富，只要你是自由民就行。他们的鄙视链在于：解决了生活必需之后，你追求什么？亚里士多德的鄙视链里，追求享乐的最低，搞政治的高一点，哲学家最高。奴隶根本轮不到被鄙视，奴隶在他眼里不是人。

有个传说：亚里士多德为什么和亚历山大反目？因为亚历山大后来娶了外邦人，他统治的版图很大，很多政策放松了自由民和其他人的区别。在亚里士多德看来，那些人都是barbaros，也就是野蛮人，话都不会说的人，怎么能跟他们搞好关系？于是师生之间有了芥蒂。是不是因此产生芥蒂，这是野史；但这种鄙视是真的：你怎么能跟那些人称兄道弟，还娶了一个野蛮人？在他们看来，野蛮人不是人。在自由人的基础上，才谈得上追求什么。

另一位参与者说：放到今天的个人角度，关键在于维生怎么定义。如果一个人深受消费主义影响，觉得维生需要很高的成本，他可能一直处在不自由的状态；但今天也可以用很低的成本就达到维生，变成一个自由民。

是的，这就是现在说的精神贵族。今天维持温饱确实很容易，很多发达国家就是这样养闲人的，你什么都不干也能吃饱饭。那么接下来你要干什么？这就是问题。

## 连君王也不自由

这里还是在讲积极生活这个概念在亚里士多德那里的来源：

亚里士多德……看来劳动和工作都不够有尊严，不足以构成一种完整意义上的生活，一种自主的和真正属人的生活方式；因为劳动服务于必需的东西，工作生产有用的东西，它们都依赖人类的需要和缺乏。……但在他们看来暴君的生活方式不能说是自由的，也跟政治生活没什么关系，因为它“仅仅”是一种必然性。

这还是鄙视链。不说富二代，就是君主，也要看是什么样的君主，不一定是自由人。城邦制度下当然没有君主。如果你不是自由选择的，生下来就继承了王位，就要为万千子民操劳忙碌，干不了别的，那你算什么自由？你也只是一个奴隶。所以在希腊人看来，不光波斯的普通人不是自由人，波斯的王也不是，他们都是野蛮人，都受困于必然性，总要去解决那些必须解决的问题。统治就是必须的：治理那么庞大的国家，你必须统治，必须平衡、搞权术、搞制衡。受制于这些必须的事情，你就不是自由人了。

这也可以用来理解那个传说。亚历山大会说：我治理那么广大的地域，没办法，必须和他们联姻，才能有效统治。从亚里士多德的逻辑看，你说“必须”，那你就陷入必然性之下，就不自由了。

先前问富二代的那位参与者反问：难道他必须不能跟野蛮人搞好关系？

也不是不能，只是不要把他们当人。你和一群狼、一群狗有什么搞好关系、搞坏关系的？不是非要惹他们，而是你和他们根本不是人和人、自由人和自由人的关系。别把他们当回事，把他们当成自然，当成洪水，“这边闹野蛮人了”，就这样。

所以希腊人没有扩张的愿望。马其顿不是典型的希腊人，马其顿原本是农业地区，也属于近乎野蛮人的范畴。

马其顿人到亚历山大父亲那一代才被允许参加奥林匹克运动会，能参加奥运会，基本上就意味着被认定属于希腊人。

补充一下当时讲的不够严谨，事实上马其顿的先王公元前5世纪初马其顿国王亚历山大一世就参加了奥运会，但这不是因为马其顿人有资格，而是因为他论证自己具有希腊血统，自称祖先来自希腊的阿尔戈斯。之后也陆续有马其顿王室参与奥运会的记录，一直到亚历山大三世（亚历山大大帝）在位时，才有马其顿平民参与奥运会的获胜记录。因为奥运会只记录每个项目的冠军，所以不确定马其顿平面有资格参与奥运会的确切时间，我大概推定到亚历山大大帝的父亲那一代，是一个猜测。

更典型的希腊人没有扩张的需求。希腊城邦之间经常打仗，但很少听说哪个城邦兼并了另一个城邦（补充：有例外，如斯巴达和阿尔戈斯）。打仗为了什么？看希腊神话，为了抢女人，为了海伦，为了争夺荣誉、证明自己是英雄、为了复仇，打完了也不占领。版图一扩张，就有很多必须管理、必须治理的事情，就不自由了，所以他们不扩张。亚里士多德这里说的是典型的希腊形态，不是每个城邦都这样。总之希腊是人类历史上的一朵奇葩，是一种很罕见的文化形态。

## 讨论：希腊人的自由是什么？

先前说工人造桥的那位参与者问：从哲学的角度说，自由的定义是什么？自由也有很多限制，比如希腊公民也不能杀人放火、不能娶野蛮人。

我说，这些概念都是历史性的。阿伦特讲的不是哲学上的定义，而是以亚里士多德为代表的希腊人的典型定义：免于必需，免于操心那些必要的、有用的事情。我关心的都是无用的东西，我就自由了；成天忙忙碌碌操心有用的、必需的事情，就不自由。

这个定义影响了整个西方思想史。但后来的西方思想又加了一层，就是基督教的自由意志，它和我们今天日常理解的自由更接近。基督教的自由意志以上帝为模型：人是上帝造的，分有了一种神权，自由意志就是上帝想干什么就干什么，这是无限的自由。落到人身上，自由的人就是想干什么就干什么。所以在这个意义上，自由当然会有限制，有条条框框。这个问题本身，其实已经是从基督教的自由意志来理解了。

希腊人的自由概念根本不是在说有没有限制，而是有没有免于繁忙、免于烦心。免除了那些烦心事，你就自由了；至于在公共生活中还会受到这样那样的限制，和自由没有直接关系。自由不是无限制，而是无束缚，而这个束缚特指必需性和有用性的束缚。我常举一个例子：我要游泳，就找个水池；这时我想跑步，在水池里跑不了；我不能在水池里同时跑步、游泳又吃饭。这是自由受到了限制。但无论在水池里跑步还是游泳，都不是为了有用，不是为了明天吃什么、赚钱养家，我就是想运动、想玩耍，这样你就是自由的。

这位参与者说理解了：就是可以自由支配的时间，不是被动支配的。接着又问：如果达到了这种自由，没有目的了，就是去洗澡啥的，每天的生活不是很虚无吗？

恰恰相反，自由了才有目的。前面讲过，应付必需性才是没有目的的，因为必需性永远完成不了；自由的生活才开始有目的。比如我就想捏一个碗、打一口锅，这就是目的。打完一看，我做得多美啊。亚里士多德说的三种自由生活，最终追求的都是美。所谓“美”不要想得太高不可攀——“我今天美美哒”，这就是美；我今天捏了一个泥人，美美哒，这不就是目的吗？亚里士多德是鄙视这种制作的，但我认为，或者说阿伦特认为，这也是自由的。在苏格拉底之前，在一般的希腊人看来，工艺和诗也是自由的，是被柏拉图贬低下去的。

传统承认的那几种自由生活也都有目的。比如享乐，今天就去剧院看悲剧、喜剧，天天去看剧，这是有目的的；天天去搞政治、去言谈，今天讨论要不要处死苏格拉底、放逐苏格拉底，这些话题当然有意义。亚里士多德说追求美，我们说这就是打发时间，也是一种快乐、一种善。还有沉思、搞哲学，发现真理、理解真理，是最崇高的目的。哲学是无用的学问，数学也是没用的，今天很多数学家也会觉得自己是在纯粹求知，不是为了提高生产力，而是因为这个世界的奥秘很美。

所以自由民不是没有目的，而是没有功利目的。功利目的本身其实不是目的，而是要换算的：做完这件事能赚多少钱、生产多少粮食、调动多少能量，换算成生产力增值、社会财富增加，你才觉得它有目的。本质上，这件事已经没有目的了，它的目的被置换成了钱、财富、能量或食物，而那个目标永远填不满，是无止境的、循环的，只是好像是一个目的。

先前问富二代的那位参与者问：希腊人追求名声和荣誉，和追求钱不是差不多吗？

我说，今天中国人讲“追名逐利”，好像把名和利放到一块儿了，但至少在希腊人眼中，它们是完全分开的，在中国古人眼中也不一样。中国古代也贬低商人，但尊重名誉。不光大人物，普通人也是：什么叫晚节不保？什么叫贞节烈女？不都是名誉吗？所有人都咬着一口气在争名誉，皇帝也在乎史书怎么写、最后得个什么谥号。古希腊人也一样，追求钱、追求权力这些有用的东西，就落了下乘；追求的应该是名誉、虚名，越虚越好，这才是高的追求。

问自由定义的那位参与者总结说：无用就是美，越无用越美，反对的就是资本主义。

差不多是这个意思。现代的异化，可以说就是资本主义。但无用是前提，没有“越无用”这回事，无用是一个界限。无用是不能衡量的，没法说这个比那个更无用；无用是说你已经不关心它的用处了。它也可能有用：搞数学，成果可能被用上了，物理学家很开心，数学家说我没想让你们用啊。所以没有绝对的无用。这个“无”，就像前面讲的佛家，是不要执着，不要执于用；不执于用之后，才开始了高级的趣味、高级的追求。

至于不执于用之后追求什么，每个人可以有不同的方向，发挥人的多元性，这就是政治生活。而政治生活的起点，是把有用的关切排除掉。不是不要这些关切，而是把它们留在私人领域，留在奴隶的范畴，留在家政学里。今天的“经济学”这个词，在亚里士多德那里就是家政学，“家务治理”。经济问题需要研究吗？需要；要打理吗？要；要算账、要计量、要计算，这些都是需要的。但这些需要的事情一定不是政治问题，而是家政问题。“家政”这个译名也带了个“政”字，其实它不是政治，只是治理、管理，就是家庭内部、私人领域的治理问题，说白了就是管理奴隶。哪怕所有事都交给奴隶去做，你至少还得管理奴隶，这要耗费心神，所以管理奴隶也是不自由的，因为管理是为了让他们有用。但这些行为要被限制在家庭内部，出了家门，就不管那些问题了，到公共空间去管那些无用的问题。

什么是无用的问题？对希腊人来说，就是海伦归谁那种问题；看剧，讨论关公战秦琼，关公强还是秦琼强。这是普通的无用。还有研究数学、仰望星空看星辰变幻，或者做诗人、创作文学艺术。这些都是无用的活动。

## 讨论：今天的人怎样过无用的生活？

又一位参与者说：如果当代人想过这种无用的生活，首先温饱，然后没有太多追求，早上看看短剧，中午跟大家谈谈政治，晚上当当民科，探索一下真理。

我说，挺好。但问题在于，一是这些活动也异化了，变成用劳动和消费的逻辑来组织。希腊的剧院是按照公共生活的方式来理解和组织的，现代的短剧是按照劳动、生产、消费的那一套逻辑来生产和组织的。二是这些事情现在没有荣誉了，没有自我实现的意义感，因为整个社会都在贬斥它们。它们变成了消遣，而消遣是和劳动对立的。以前整个生活都是消遣，现在的消遣是有目的的，是为了让你有更饱满的精神去劳动，休息好了，才能健康工作五十年。

先前问富二代的那位参与者说：我怎么感觉现在是消遣到凌晨四点，第二天接着上班。

对。我一直认为这些活动的存在是积极的，它证明人类的积极生活不会轻易消亡，人是有这些需求的，只是这些需求和整个社会的趋向、组织方式是矛盾的。这些需求都被贬低成很糟糕、很肤浅的追求，也就没有更高的追求，而且会自我实现：越是贬低，它就真的越值得贬低，真的就没什么趣味。如果重视这些活动，人就能在这些需求之上发扬自己无用的爱好、自己的趣味、自己的创造力，这样的社会才是更积极的。这也是我们读历史的意义。真穿越到古代，你可能也受不了；但隔着距离看，至少能看到一种可能性，看到我们的现代生活不是理所当然的。古代人有不同的生活方式，至少在想象中更美好；回到那个时代当然还有那个时代的问题，但把它作为一种理想，在今天去复兴、去发扬，我们也许能过上比古代人更好、也比现代人更好的生活。

另一位参与者问：希腊神话是不是理解他们世界观的一个比较重要的入口？

算是吧，但希腊神话更底层一点。这里强调的希腊城邦生活是比较短暂的，基本上就是古典时期的黄金时代，也就上百年；希腊神话是更深的底蕴，但已经包含了希腊精神的一些要素，比如英雄主义。神话故事说来说去，就是抢女人、抢宝藏，都是无用的事情，不是为了苍生社稷。中国的神话不一样，神农尝百草、仓颉造字、伏羲做这做那（教人捕鱼）、大禹治水……明君圣王，全是在干有用的事情。希腊神话里，宙斯今天和这个人、明天和那个动物乱搞一通，是一种很奇葩的底层文化，但它已经有一种意向，就是不实用。

一位参与者说：感觉他们的神话里全是道德败坏，在别的神话里没见过这么多。

所以说很奇葩。当然，神话不能直接代表后来希腊古典城邦文化的形态，但它确实是一个底子：也只有那么奇葩的一个文化，才能发展出希腊那样的城邦生活。

讨论到这里，第三期阿伦特读书会结束。

相信很多人收到过很多陌生电话，我也是。陌生来电就算不是那种诈骗的类型，通常也会很烦。

第一次收到诈骗电话是研究生时。电话一接通就是一个福建口音，然后让我猜是谁。那是第一次收到这种电话，脑子里还没有“骗人”这个脑回路。我拼命回忆，并在脑子里搜寻哪个朋友是来自那边的。幸亏我比较宅，认识的人太少，要不然可能就真被骗了。后来还收到过一次，我立马就挂掉了。自此这个招数就不灵了。好吧，诈骗电话其实收到的不多。

但有段时间，广告、推销、贷款、携号转网电话可多了。尤其是有段时间，超多电话打过来，都是问我是不是xxx的家长。我们这里是xxx培训机构的blabla。我可不记得什么时候昭告过天下，我有xxx年出生的娃。好吧，昨天[刚说](https://www.seis-jun.xyz/blog/2026-11-10-watch-TV.html)了。

同样贷款也是，这个就和我的“身份”没有啥关系了。大概是这些年多起来的。总是告诉我，我有钱你要不要？我想，当然要啊，但你要我还的啊。这种电话，就跟社会大佬做放水生意一个样，只差把刀架你脖子让你帮他花钱了。只是不是架的刀，架的是电话。

这些电话还非得接几个才知道到底是个啥。最初接通我还听他们掰扯，最后说谢谢。但听说，如果你脾气好，会被他们标记“有希望”，以后还接着打，好不张狂。还好现在有些电话已经被标记了是骚扰，那就好得多了。

面对陌生来电，妻子的选择通常是从来不接，而我也总结出了应对陌生来电的策略。需根据自己的情况来选。

例如如果自己很忙，电话突然响起，瞟了一眼，号码不认识我理都不理，让他自个儿响。电话响又不是早上的闹钟响。

如果自己稍微有点空，我会让小爱同学帮我接听。并且看看小爱同学说啥，那边又说个啥。我发现如果是真人，还会多说两句。有时一接听，小爱同学还没有说什么，人家就挂了。我猜多半是骗子也很厉害，整的是AI通话啊。当然也有可能和小爱同学聊过太多，已经患有小爱同学惊恐症了。

如果我实在闲来无事，我会接通，然后和客服聊聊。显得和她很熟一样。人家也是拿钱办事的牛马，何必对人家那么凶呢，对吧，也许人家的老板还在身后监工呢。不过聊到最后就只能不好意思，让她这单生意落空了。不知道她应该是高兴还是骂娘呢？~~为啥不是骂爹？~~

对的，土澳有个大学~~没错是我的母校B~~ 的教授[训练了一个应对诈骗电话的大预言模型](https://www.forbes.com.au/covers/magazine/how-a-sydney-professor-built-an-ai-army-to-scam-the-scammers/)。专门用来“吊”诈骗人员。这个AI会扮演比较容易被骗的“客户”。总是给骗子以希望，但又同时不厌其烦地问东问西。把骗子骗得团团转。据说目前已“诈骗”了不少诈骗分子的时间。诈骗分子把时间都花在了AI上面，那用来诈骗咱们的就少了啊。时间就是金钱嘛。可怜了那个和AI聊了半天，信心满满最后希望落空的牛马啊。

这种事，你报出来干啥嘞？不怕人家骗子不知道吗？兴许是足够自信，不怕骗子能够识别啊。也对，这种事情爆出来，也许骗子压力更大啊。以前骗子还觉得可能遇到了真潜在客户，现在不得不提前就琢磨，如果我骗的是个AI，那是他被骗，还是我被骗？

有时不管三七二十一，把陌生来点一股脑儿摁掉也可能会有麻烦。例如，你的外卖或者快递。总不能为了避免被陌生来电骚扰，连热气腾腾的外卖都不要了吧。不过还好，一般外卖或者快递都会至少打两到三次。当然也有其他情况。

有一次一个陌生电话打来，我就没接。后来打了第二次，原来是娃忘记带东西在学校借老师电话打给我。为啥打给我呢？因为他已经打过他老妈的电话，但妻子不接陌生来电。因此又才打给我，可怜的娃啊，要是换做我，我可能会以为被爸妈抛弃了啊。

总之现在都不怎么打电话了，要打一般也是用微信，还可以先问问对方方不方便接。

希望天下再也没有电话诈骗的牛马了啊。

因为牛马不骗牛马啊。

# [](https://blog.lusyoe.com/article/qingping-image-skill-workbuddy#📝-前言 "📝 前言")📝 前言

写博客最打断思路的，往往不是写，是配图。

一段话刚写完，想插张截图，于是切出去：截图保存到本地 → 改个英文名 → 压缩一下体积 → 打开图床网页上传 → 复制 CDN 链接 → 回到编辑器拼成 `![](url)` → 再检查一遍有没有拼错。

一张图七八步，配三张图思路就断三次。换封面更麻烦，还得记着回后台把旧图删掉，不然 CDN 里堆一堆没人用的文件。

前阵子我把这套流程封成了一个 WorkBuddy 技能，现在它已经正式上线技能市场 —— **青萍 AI 图床** （`qingping-image-upload`）。

装好之后，上面那串操作变成一句话：**「把这张图传到图床，链接写进文章里」** 。

这篇就说说它能做什么、怎么装、以及几个用起来才知道的细节。顺带一提，这篇文章的封面和下面那张对比图，都是用它自己传上去的。

# [](https://blog.lusyoe.com/article/qingping-image-skill-workbuddy#😮‍💨-以前一张配图要绕多少步 "😮‍💨 以前一张配图要绕多少步")😮‍💨 以前一张配图要绕多少步

把老流程摊开看，其实每一步都不难：

  * 截图或导出，存到某个文件夹里
  * 文件名带中文或空格，得先改成英文 kebab-case，不然 CDN 上直接 404
  * PNG 动辄几 MB，转 WebP 压一下才敢往文章里塞
  * 登录图床，选文件，上传
  * 复制外链，回到 Markdown 补上 `![]()` 和 alt 文字
  * 要换图：传新的、改引用、回后台删旧的，顺序错一步文章就空图

麻烦的不是哪一步，是**加起来太碎** 。写到一半切出去操作一圈，回来常常忘了刚才要接哪句话。

![以前手动传图与现在用技能传图的流程对比](https://img-cdn.lusyoe.cn/images/lusyoe/2026/11/10/qingping-skill-compare.webp)

# [](https://blog.lusyoe.com/article/qingping-image-skill-workbuddy#📦-技能已上线，怎么装 "📦 技能已上线，怎么装")📦 技能已上线，怎么装

WorkBuddy 是腾讯出的全场景 AI 工作台，技能（Skill）相当于给它加一个专门的能力包：把一套固定流程和注意事项写清楚，需要时自动按这套流程执行，不用每次重新交代。

「青萍 AI 图床」现在是技能市场里的正式技能，两条路都能装：

**从技能市场装** ：点左侧菜单【专家·技能·连接器】→ 选【技能】进入【技能市场】→ 搜「青萍 AI 图床」→ 点右上角加号安装。装完在对话里就能调用。

**一句话装** ：直接在对话里说「帮我安装青萍 AI 图床技能」，WorkBuddy 会去市场里找到并装上。

第一次用要配一个 API Key：登录 [img.lusyoe.com](https://img.lusyoe.com/)，点右上角个人信息，生成并查看 API Key，粘贴到对话里就行。这个 Key 默认只在当前会话生效；要是嫌每次都粘麻烦，可以让它写进本地 `.env` 或 shell 配置，之后每次自动读取。

# [](https://blog.lusyoe.com/article/qingping-image-skill-workbuddy#💬-怎么用：把「传图」说成一句话 "💬 怎么用：把「传图」说成一句话")💬 怎么用：把「传图」说成一句话

装好之后不用记命令，也不用管脚本放在哪，说人话就行：

  * 「把这张封面传到图床」→ 返回 CDN 链接和 `image_id`
  * 「这张截图先转 WebP 压缩再传」→ 自动压完再上传
  * 「把文章封面换成新这张」→ 传新图、更新文章里的引用、最后删旧图
  * 「删掉 image_id 6934xxx」→ 按 ID 清理图床上的旧文件

关键不在于它丢给你一个链接，而在于**它会把链接写回文章** 。换图时按「先传新图 → 更新引用 → 再删旧图」的顺序走，中途不会出现线上空图；更新引用之前，还会把 CDN 上的文件下载回来跟本地比对一次，确认字节一致才收工。

对写 Markdown 的人来说，这一步才是真正的省事：图片已经躺在文章里了，不用再回编辑器手动贴一次。

# [](https://blog.lusyoe.com/article/qingping-image-skill-workbuddy#🔧-几个真省心的细节 "🔧 几个真省心的细节")🔧 几个真省心的细节

**默认不擅自动你的图。** 拿到什么文件就原样传什么。要不要转 WebP 压缩（质量 75）会先问一次，可以选「仅这次」或「以后都压缩」，选了后者就不再反复打断。

**文件名的坑它替你挡了。** 图床的物理路径跟本地文件名走，跟上传时填的 name 无关，中文名很容易 404。技能里写清了这条规则，上传前会检查，必要时先重命名再传。

**换图不会把文章搞出空图。** 同名文件重复上传会命中「已存在、复用旧 URL」，新图其实根本没传上去。所以换图一律用版本化文件名（如 `cover-v2.webp`），引用生效后才删旧图。

**边界写得明白。** 单文件上限 30MB，支持 WebP / PNG / JPEG，外链域名是 `img-cdn.lusyoe.cn`，上传成功同时给 CDN URL 和 `image_id`，两个都别丢。

# [](https://blog.lusyoe.com/article/qingping-image-skill-workbuddy#✍️-对写博客的人意味着什么 "✍️ 对写博客的人意味着什么")✍️ 对写博客的人意味着什么

最大的变化其实不是省了几分钟，是**思路不用中断** 。

以前配图是一次任务切换：从写作切到文件管理，切到浏览器，再切回编辑器。现在它只是写作过程里的一句话，图片出现在文章里，人还停在原来的思路上。

批量写系列文章、临时换封面、插图微调重传，这些以前最容易摆烂的环节，现在都只是一句话的事。工具没变多，中间要记的事变少了。

# [](https://blog.lusyoe.com/article/qingping-image-skill-workbuddy#⚠️-用之前记三点 "⚠️ 用之前记三点")⚠️ 用之前记三点

  1. API Key 只放本地环境，别写进文章、别提交到仓库。
  2. 删图只认 `image_id`，上传成功时留好它 —— 图床没有查询接口，事后补不回来。
  3. 外链是公开的，私密截图、带个人信息的图别往上传。

# [](https://blog.lusyoe.com/article/qingping-image-skill-workbuddy#写在最后 "写在最后")写在最后

工具做到最后，最好的状态就是让人感觉不到它。

以前传一张图要记七八个步骤，现在只需要说一句「传到图床」，剩下的交给技能。青萍 AI 图床技能已经在 WorkBuddy 技能市场上线，写博客的朋友可以装上试试 —— 至少，配图这件事不会再打断你了。
