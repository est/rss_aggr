你在仓库根目录启动 agent，想让它检查整个项目。换到 `services/api` 下面再启动，希望它沿用团队配置，同时照顾这个子目录的约定。

这时，同一条命令会碰到几个问题：在哪儿找配置，哪一份设置生效，相对路径从哪里算起。再把命令放进脚本，原来能弹出来问你的审批，现在还有人回答吗？

这些事在第一次模型请求之前就该说清。前两篇拆了[循环](https://www.echovic.com/blog/ai/coding-agent-series-01-layers)和 [Harness](https://www.echovic.com/blog/ai/coding-agent-series-02-harness)，这篇先不往里加能力，先把入口这段路走顺。

入口先解析命令行，分清用户要启动会话、跑一次任务，还是只看帮助。`--help` 和参数拼错这种情况，到这里就能结束，不用加载模型客户端。解析结果先留成普通数据，等工作范围和配置都检查过，再选择对应的运行入口。

## 先确定在哪里工作

我会先把三个位置分开：启动命令时的目录，这次任务实际工作的目录，以及用来发现项目配置和指令的项目根。

它们可以相同，也可以不同。比如在仓库根目录传入 `--cwd services/api`，工作目录就指向子目录。这个参数名是举例，你自己写入口时要明确规定：相对路径按启动目录解析，目录不存在就报错，别悄悄创建一个空目录继续跑。

项目根则需要另一条定位规则。可以向上找 Git 标记，也可以要求用户显式指定。无论选哪一种，都应该把结果保留在启动诊断里。工作目录选错，后面再聪明的文件搜索也可能是在错地方找。

项目指令还要有自己的发现范围。[Codex 的官方说明](https://developers.openai.com/codex/guides/agents-md/)是先读全局指令，再从项目根走到当前工作目录，沿途发现指令文件；每层最多选一份，`AGENTS.override.md` 优先于 `AGENTS.md`。没有找到项目根时，只检查当前目录的项目指令。

这说明当前目录会影响加载什么，但没有说当前目录就是可写边界。指令文件写着「只改这里」，也不能替代程序里的路径限制。

这篇只确定从哪儿找文件。指令怎样进入提示词，留到指令层那篇再讲。

## 配置叠上去之前，先决定哪些能进来

初版可以先用一个容易解释的顺序，从低到高：
    
    
    内置默认值 < 用户配置 < 已信任的项目配置 < 指定环境变量 < 显式命令行参数

这是下面实验的教学约定，不是全行业规则，也没有囊括组织管理策略。

例如，[Codex 配置文档](https://developers.openai.com/codex/config-basic/)把项目配置放在用户配置之上，项目内更靠近工作目录的配置优先；项目层只有在项目受信任时才加载。命令行覆盖普通配置，组织要求还会额外限制哪些值能用。

[Claude Code 的设置文档](https://code.claude.com/docs/en/settings)又明确提醒：环境变量没有统一占据一层，和设置项谁先谁后，要按具体字段看。列表也有自己的合并规则，不能拿一个对象覆盖函数解释全部行为。

我会先把可调偏好和硬限制分开。默认模型可以选一个生效值；禁止写入某个目录的约束，不能因为项目配置排在后面就被放宽。安全策略怎么组合，后面专门写，这里先别把它混进普通设置的覆盖逻辑。

命令行解析还有个小坑。假设用户文件写了批处理模式，你没传 `--mode`，解析器却默认填了 `interactive`。再把所有解析结果覆盖进去，文件里的值就丢了。

我的处理是：解析阶段保留「用户没填」这个状态，只合并显式传入的字段。真正的默认值集中放在最底层。

![机器人出发前核对配置卡片与工具背包](https://www.echovic.com/_astro/dcd599fd53c57beafb18675b54c39e33d41842e559e1cb641d28cc848c2b0334.tHHyqM87_2YXFI.webp)

值定下来之后，还要留下它的来源。只看到 `model = demo-project`，你仍不知道该改哪里；再看到 `source = project.json`，排查才有了落点。

## 批处理不能靠关掉界面凑出来

交互和非交互，说的是输入从哪里来、进度往哪里送、要不要等下一条输入。权限模式说的是一次动作能不能做、需不需要审批。这是两件需要分别配置的事。

有终端界面，不代表能随意写文件；没有界面，也不代表必须放开所有权限。批处理遇到需要确认的动作，如果没有可用的审批通道，就应该明确拒绝或退出，不能一直等一个不存在的人，也不能顺手当成同意。

输出也得提前定好。[Codex 的非交互文档](https://developers.openai.com/codex/noninteractive/)说明，普通 `codex exec` 把进度发到标准错误，最终回复写到标准输出；加 `--json` 后，标准输出改成逐行 JSON 事件流。

这样脚本才能知道自己接的是最终文本还是事件，避免把彩色启动横幅也当成结果。至于编辑器接入或常驻服务，入口需要选对适配器，不必在这里把协议再实现一遍。

## 第一次请求之前，能报的错先报

把参数、目录和配置解析完，我希望先得到一份可检查的启动计划，再把它交给交互或批处理入口。

![从解析参数、定位目录、合并配置到启动预检的教学流程](https://www.echovic.com/_astro/459d610699ae8f0f649a5d72d57400213ba89709b66da6f7bb067e8b1493f5bf.C6VULfNS_ZwyxYa.webp)

启动计划里可以有工作目录、项目根、选中的运行方式、模型名、指令文件路径，以及这些设置来自哪里。它不该是一份配置文件的原样转储。

API key、认证头、连接串不能跟着诊断输出。就连报 JSON 语法错，也只需要文件定位和行列号，没必要把附近那段原文一起打印出来。

配置文件损坏、参数组合冲突、批处理缺少任务输入，这些错误不需要花一次模型请求来判断。我的教学实现会停止启动，错误送到标准错误，退出码为 2，标准输出保持为空。真实项目可以选择别的约定，但要让调用方能分清成功和失败。

这也不意味着启动预检能预测所有问题。网络是否可达、服务端是否接受请求，仍可能在后面失败。能在本地确定的先确定，别把文件解析错误拖成一次难读的模型调用错误。

## 跑一遍配置到底听谁的

下面这个小程序只做配置合并和启动预检，不接模型，不执行工具。它在临时目录创建两份假配置，结束后清理，不读你的用户目录或真实凭证。

用户配置故意写成 `batch`，项目配置只改模型名。项目层要加 `--trust-project` 才会读取。模型名也限在几个 `demo-*` 值里，避免把任意输入带进诊断。

保存成 `launch_demo.py`，用 Python 3.9 或更新版本运行：
    
    
    import argparse
    import json
    import os
    from pathlib import Path
    import sys
    import tempfile
    
    parser = argparse.ArgumentParser()
    parser.add_argument('--model')  # 不设默认值，避免盖掉文件里的值
    parser.add_argument('--mode', choices=['interactive', 'batch'])
    parser.add_argument('--approval', choices=['ask', 'deny'])
    parser.add_argument('--trust-project', action='store_true')
    parser.add_argument('--prompt', default='')
    parser.add_argument('--broken-project', action='store_true')
    args = parser.parse_args()
    allowed = {
        'model': {'demo-default', 'demo-user', 'demo-project',
                  'demo-env', 'demo-cli'},
        'mode': {'interactive', 'batch'},
        'approval': {'ask', 'deny'},
    }
    values, sources = {}, {}
    
    def merge(data, origin):
        if not isinstance(data, dict):
            raise ValueError('配置顶层必须是对象')
        for key, value in data.items():
            if key not in allowed:
                raise ValueError('发现不支持的配置字段')
            if not isinstance(value, str) or value not in allowed[key]:
                raise ValueError(f'{key} 的值不在演示白名单中')
            values[key], sources[key] = value, origin
    
    try:
        with tempfile.TemporaryDirectory(prefix='agent-start-') as folder:
            root = Path(folder)
            (root / 'user.json').write_text(json.dumps({
                'model': 'demo-user', 'mode': 'batch', 'approval': 'deny'
            }), encoding='utf-8')
            (root / 'project.json').write_text(
                '{' if args.broken_project else
                json.dumps({'model': 'demo-project'}), encoding='utf-8')
            merge({'model': 'demo-default', 'mode': 'interactive',
                   'approval': 'ask'}, 'default')
            names = ['user.json']
            if args.trust_project:
                names.append('project.json')
            for name in names:
                merge(json.loads((root / name).read_text(encoding='utf-8')), name)
            model = os.environ.get('MINI_MODEL')
            if model is not None:
                merge({'model': model}, 'env:MINI_MODEL')
            merge({k: getattr(args, k) for k in allowed
                   if getattr(args, k) is not None}, 'CLI')
            if values['mode'] == 'batch':
                if not args.prompt.strip():
                    raise ValueError('batch 缺少非空 --prompt')
                if values['approval'] == 'ask':
                    raise ValueError('本例 batch 不支持等待审批，请显式用 deny')
            print(json.dumps({
                'effective': {k: {'value': v, 'source': sources[k]}
                              for k, v in values.items()},
                'project_loaded': args.trust_project,
                'request_sent': False,
            }, ensure_ascii=False, indent=2))
    except (OSError, ValueError) as error:
        if isinstance(error, json.JSONDecodeError):
            message = f'配置 JSON 无效：第 {error.lineno} 行，第 {error.colno} 列'
        elif isinstance(error, OSError):
            message = '演示文件读写失败'
        else:
            message = str(error)
        print(message, file=sys.stderr)
        sys.exit(2)

先运行前两条，比较 `effective.model` 的值和来源。第三条再加环境变量与命令行覆盖，环境变量前缀写法适用于 Bash/Zsh：
    
    
    python3 launch_demo.py --prompt "检查示例"
    python3 launch_demo.py --trust-project --prompt "检查示例"
    MINI_MODEL=demo-env python3 launch_demo.py --trust-project --model demo-cli --prompt "检查示例"

结果依次是 `demo-user` 来自 `user.json`，`demo-project` 来自 `project.json`，`demo-cli` 来自 `CLI`。第三条去掉 `--model demo-cli`，就会看到环境变量生效。这些命令假设你没有另外设置 `MINI_MODEL`；若设置过，先清除它再比较前两条。

注意第一条没有传 `--mode`，最后仍然是文件里的 `batch`。这正好能检查解析器有没有拿自己的默认值盖掉用户设置。

再试两次失败启动：
    
    
    python3 launch_demo.py --trust-project --broken-project --prompt "检查示例"
    python3 launch_demo.py --prompt "检查示例" --approval ask

前一条读到故意损坏的项目文件，后一条碰到本例不支持的批处理审批组合。它们都会退出，且不产生正常结果。这个例子选择拒绝 `batch + ask`，只为演示预检，不代表所有非交互产品都没有远程审批能力。

代码只合并平铺的字符串字段，没有实现真实项目根发现、指令加载、终端交互或权限执行器。输出里的 `request_sent: false` 也表示它停在预检阶段。可以把合并逻辑接回你自己的入口，再逐项补真实配置来源。

本地测试通过了 11 种情况，包括环境变量和命令行覆盖、项目未信任时跳过配置、坏文件、缺少输入，以及错误信息不回显测试用的敏感值。

## [](https://blog.giveanornot.com/led-earring-4/#%e6%b4%9e)洞 

下單之後大概 2 ~ 3 天就完工、一個禮拜之後就收到了，包裏我選寄順豐，沒意外是空運來的。

收到之後打開來看…哪尼！怎麼上面被打了奇怪的洞！！！（右上還有左下）

![](https://blog.giveanornot.com/led-earring-4/image.jpg)

跟客服溝通一番之後，他們的說法是：這是為了要在焊接的時候用的定位孔，如果不想要他們自己改設計的話，可以自己加上 [1.152 mm 的 NPTH 無銅孔](https://jlcpcb.com/help/article/how-to-add-tooling-holes-for-pcb-assembly-order)，也可以在下單的時候選擇「需要確認製作稿件」，不然就會由他們的工程師直接加上定位孔。

好啊…啊不就還好我只做了 10 個，不過也不影響功能就是了，問題不大。在圖中看起來好像很明顯，不過這整個耳環的寬度也才 2.5 cm 而已，實際上很小，而且在暗處的發亮的時候，根本看不到板子長什麼樣子。

還好焊上零件之後，該亮的都有亮，不該亮的也都沒亮（？），再裝上耳環的配件之後，就完工啦

……才怪 ┐(‘～`；)┌

我很快就發現有幾個耳環不會亮！！

本來還以為是我的電池座沒焊好，還是哪邊短路了。結果量了一圈，才發現是電池跟 PCB 上面的接觸不太穩。但不像是不夠緊，而是接觸的點不太對，這幾個就稍微上點錫上去增加一點接觸面積吧~

今天妻子感冒发烧了。上午照顾了一下，下午留她一个人在家吃了退烧药休息。我则顶替她的位置，勉为其难地享受了一场音乐剧《茶花女》。

我好像不是第一次听音乐剧，但这类剧不是我的菜，是妻子的。我就谈谈看剧的感受吧。

首先，这剧感觉讲了很多东西，突然觉得有点像我写的博客，通常是论点抛出来一堆，还没有论证清楚就我方唱罢你登场了。讲了爱情、面子、社会、荣耀、牺牲等等话题，对，还有一些私货，推广人家的浪漫法国啊。但是人家是音乐剧，不搞得这么丰富可能就不好看了啊。比如如果你就讲爱情，对，似乎就情情爱爱没什么好讲了，一定要讲情情爱爱不容易，怎么受到限制，又如何爱恨别离。

我的位置在21排，离得挺远，舞台上演员的脸都看不清楚，身边小姐姐都用上了眼镜。不知道哪位小姐姐身上香水喷的较多，整场音乐剧观影我周围都弥漫着香气。看到女主角服饰华丽，风姿绰约，让我觉得我那香气就是从主角身上飘出来的。颇有一种独特的四维沉浸感，仿佛就在主角身边啊，呼吁以后的音乐剧也可以加上对应香气，效果不错。

整个剧给人印象最深的是他们的演唱和舞台灯光。演员就不说了，因为我看不清。但看不清反而给他们蒙上了一层神秘面纱，你可以幻想女主有多么美，男主有多么帅，可以把最美最帅的脸给他们安上。他们唱的是法语原声，两边是翻译台词屏幕。没办法，听不懂，我总得歪着头，时不时看屏幕，有碍观影体验。声音是真好听，估计也是有听不懂的加成效果。看到他们唱的台词我就在想，要是这用中文唱出来得多尴尬啊。估计还是有翻译的锅，也许懂法语的人听起来就不会觉得尬。 就像我们听咱们的中国风曲目，听些古诗词的歌词也会觉得舒服，不尬。也不知咱们的音乐剧之类的文艺作品出口如何。但想要卖到别国，总需要好听啊。这音乐剧就是好听，声音婉转，歌词都和情节契合，让人沉浸在故事和情绪中。但是有个小问题，就是听完了以后，那些曲调就清空了。要我回想，我一个旋律都不记得。当然不能排除我音乐细菌太少的缘故，但有些歌听了就能哼唱啊。

好了，讲讲它的爱情吧。我已记不清有没有看过书，只讲讲就音乐剧展现出来的东西。男主阿尔芒，说总是有一双手在操控他的人生，他的爆发只在今朝。冲破束缚就谈个恋爱这点能耐？行吧追求恋爱也算勇敢。但整天来女主楼玛格丽特下盯人家看算哪门子的爱啊？是变态吧，是馋人家身子。话说，这样盯女主的男人多得很啊。

另外玛格丽特只见了男主一面，听男主表了白就给人家钥匙了，一副找到真爱的样子。结果第二天拿到钥匙的人排成了长龙啊。我明白女主是在试探和考验，但试的哪门子的探，就是玩弄大伙儿啊。男主直接气走了。女主开始哭诉自己不容易，名利场中逢场作戏，都想得到自己的身体，没有真爱。这也没描绘女主怎么惨到沦为交际花头牌的啊，要不也像杜十娘一样是被老鸨逼的吧。否则如何让人体会到你做头牌的不易呢？一方面说头牌是自己六年来辛辛苦苦干出来的，一方面又说纸醉金迷没有真爱。有点割裂，到底要哪个？

哭诉完，阿尔芒又回来了，算是考验通过了。然后两个人就相爱了。这才第二面啊同学，就亲上了。然后讨论私奔了。太奔放了。哦，法国啊。法国就算了吧。人家就卖这一套。

私奔到乡下。我的天，你们两个私奔就好好私奔好不好。阿尔芒的钱全靠父亲，玛格丽特的钱全靠以前的几个伯爵男爵，还持续不断的要？我的老天，这算哪门子的爱情啊？有没有一点责任啊？可能人家就是要浪漫一把吧。哦，法国啊。法国那就算了吧。

行吧。偶尔看一次还行。但人家的爱情观我学不来啊。

回头还是让妻子来欣赏吧。

> Installing 30 plugins felt great; cutting them to 20 a week later was the real experience. Architecture observations, market setup, and why the survivors stayed.

## Why Install Yet Another Agent Tool

Agent tools are not scarce in 2026; my terminal already hosts several coding assistants. What drew me to DeepSeek Harness (DSH below) was not the model but the positioning: it is not another chat app, it is an **agent runtime**. The model, the tools, the skills, even the UI can all be swapped out.

My first week was aggressive: after installing the official desktop app, I configured a third-party plugin market and loaded 30 plugins in one spree. Then came the most valuable part: trying each one, deleting, disabling. After a week, 3 are deleted, 7 are disabled, and 20 remain running. On the model side I skipped the official API and configured a third-party endpoint running Zhipu’s (Z.ai) GLM coding plan, so the model picker shows GLM-5.3. This post records what I observed about the architecture, how the plugin market is configured, and the curation from 30 down to 20.

## Architecture: A Layered Plugin Runtime

The short version: the DSH core is deliberately thin, and every capability lives in the plugin layer.

The install gives you a desktop app backed by a local web service (it listens on 127.0.0.1, exchanges a one-time token for a login state at startup, and keeps no credentials on disk), with the GUI served from that local service. The `dsh` CLI shares the same profile system as the desktop app, and the CLI help defines a profile as an “ordered stack of plugin-bundle patch layers”. In other words, every profile you build is a stack of plugins layered on top of each other; the core only does the scheduling.

The picture below is the layered panorama of this runtime.

![Figure 19: DeepSeek Harness layered architecture](https://jimmysong.io/blog/deepseek-harness-plugin-experience/dsh-architecture-en.svg) Figure 19: DeepSeek Harness layered architecture 

Day-to-day organization is workspaces plus sessions: each git repository is a workspace, each workspace holds multiple sessions, and each session has its own context, todo plan, and approval records. A plugin can contribute five kinds of things to this runtime:

  * Tools: functions the agent can call, such as the dozens of `ego_*` tools from the browser plugin
  * Skills: on-demand playbooks, such as this site’s blog-writing conventions
  * UI: sidebar buttons, tabs, and panels, such as the task board and the context dashboard
  * Subagents: dispatch work to another model or another agent
  * MCP connections: reach external resource servers

Precisely because capabilities live in plugins, deleting and disabling them is safe: the core never moves, and the stacked layers come and go. That is why I dared to install 30 at once and then subtract slowly.

## First Impressions: A Conversation That Feels Like an IDE

Onboarding is smooth and the Chinese UI works out of the box. A few details stood out:

  * Session titles are generated automatically; no naming chores
  * Tool calls render as collapsible cards; expand them for full inputs and outputs
  * The todo plan sits in its own strip above the input box, progress at a glance
  * Approval modes are configurable; I run Full access and tried an approval-gate plugin as a backstop, then stopped it once it proved unnecessary for daily use
  * A follow-up queue lets me fire questions while the agent is working; they get processed in order, and the last unanswered one never leaks into the saved session
  * The trajectory view records the whole working session as a timeline of model thinking, tool calls, and wait times, which makes post-mortems of how a task actually got done trivial

The trajectory screenshot below comes from a real task: fixing a caption-wrapping bug in the HAMI 2.11 release video. You can watch it extract frames to verify, spawn background render jobs, update its memory, and deliver the final cut, with the full reasoning about the width-estimate mismatch preserved in between.

### Third-Party API: the Zhipu GLM Coding Plan

DSH does not lock you to the official model; configure any OpenAI-compatible third-party API and you are in. I use Zhipu’s GLM coding plan: a subscription with a generous quota, ideal for high-frequency coding and writing, with no per-token anxiety. Credentials live in a local credentials file, the UI masks secrets automatically, and nothing leaks in normal use.

In practice GLM-5.3 is good enough at Chinese writing that I let it draft this very post: stable long-form structure, accurate terminology, and no real misfires in tool-call instruction following. A nice side effect of writing Chinese content with a Chinese-first model is that there is no translation detour in the thinking process.

## Configuring the Plugin Market in Three Minutes

DSH ships a set of optional official plugins; `plugin-market-bundle` adds custom plugin indexes, so you can add third-party market sources right in settings. I also installed `dshmarket`, which provides a full visual market: browse, search, open details, one-click install; the experience is close to a phone app store.

A one-click install just adds an npm package to the profile and asks for a restart. During the installation spree, `dsh-autorestart` was a blessing: it waits until every session is idle before restarting safely, never interrupting a running agent. It is very much a renovation-phase tool, though; once the plugin set stabilized I stopped it, because restarts stopped being a daily affair.

## From 30 to 20: A Week of Curation

Every install felt exciting in the moment, but only real workflows can judge a plugin. My bar was simple: anything I did not reach for again within a week had not earned its place; anything overlapping another plugin lost to the one that felt better; anything whose cost outweighed its benefit got switched off.

First the outcome: the 20 survivors, by family. Context and memory is the largest, which fits the nature of an agent tool: how you spend context and keep memory decides the agent’s ceiling.

![Figure 24: The 20 that stayed](https://jimmysong.io/blog/deepseek-harness-plugin-experience/plugin-families-en.svg) Figure 24: The 20 that stayed 

The profile still holds 27 packages: 20 enabled, 7 disabled; another 3 are deleted outright. To be clear, these 20 are not a “best of” list: a few of them are just on observation, and I do not necessarily use every one. Subtraction is not a one-time event either; it will continue, and the number will most likely keep going down. First the survivors, then the ten that did not make it.

### A Few Genuinely Useful Scenarios

Some highlights from actual use.

**Context dashboard** (dsh-context): every session gains a Context tab with a visualization of context usage: which messages consume how many tokens, and which ranges have already been folded away. When debugging “why did the context blow up again”, it is essential. Below is the dashboard for the same video task: 16 turns and 516 steps, tool calls taking nearly sixty percent of the token budget, a 96.63% cache hit rate, and a latency breakdown where waiting on the model is barely a fifth of the wall clock, tool execution dominates. Numbers that used to be gut feelings are now visible at a glance.

![Figure 25: The dsh-context dashboard: token composition, cache hits, and latency breakdown \(a live GLM-5.3 session\)](https://assets.jimmysong.io/images/blog/deepseek-harness-plugin-experience/dsh-context.webp) Figure 25: The dsh-context dashboard: token composition, cache hits, and latency breakdown (a live GLM-5.3 session) 

**Task board** (task-board): the cards are not sticky notes; each card maps to a real session run, and scheduled tasks are supported. I pinned the draft generation of a weekly community report on the board, and it fires on schedule automatically.

**Skill center** (skill-center): after installing twenty-odd skills, centralized management becomes a necessity. The skill center lists them all in one panel; toggle, create, delete, all in one place. Much nicer than digging through config files.

**The draw.io canvas** (@next-ai-drawio/dsh): I asked the agent to draw an architecture diagram from a requirement; the canvas opens live in the sidebar, and when I dislike something I just tell it in natural language and export the SVG afterwards. Drawing went from “open a diagramming app” to “two extra sentences”.

**The agent browser** (dsh-ego-browser): 34 `ego_*` tools cover navigation, snapshots, clicks, form filling, screenshots, and network watching, with a live observation panel on the right. I send it to research and verify page structures without ever touching a browser myself.

## The Ten That Did Not Make It

The rejection list is more informative than the winners, so here it is in full.

**Deleted, 3** : two browser plugins (dsh-native-browser, browser-skill) overlapped `dsh-ego-browser`; one browser is enough, so they went. `dsh-media-desk` (idea to script, cover, storyboard) looked cool at install time; I opened it twice in a week. Not part of my workflow, deleted.

**Disabled, 7** :

  * `billion-context`: context compression; saves tokens, costs speed; detailed below
  * `dsh-vision-router`: overlapped modlens; one vision chain is enough
  * `@restregular/dsh-memory`: of four memory plugins I kept three; this was the least used
  * `@xmanrui/dsh-im`: pipes WeChat, Feishu, and a dozen other IMs into DSH; impressive, but I do not want IM messages to become agent task sources for now
  * `dsh-approval-gate`: auto-approval gating; redundant once Full access became routine
  * `dsh-autorestart`: a renovation-phase helper with no job once the plugin set stabilized
  * `dsh-pocket`: reach the desktop DSH from a phone by scanning a QR code; great demo, but I still sit in front of the computer

All 7 remain installed but disabled: toggling a DSH plugin costs nothing beyond a restart, so any of them can come back the day I need it. That is why I keep subtracting without ceremony: disabling is not farewell, it is tidying up.

## The Efficiency Tax of “Million-Token Context”

The most instructive item on the rejection list is `billion-context`, which the community calls the “million-token context” plugin: it folds consumed conversation history into summary blocks and decompresses them on demand, so small context windows can run very long tasks. The token savings are real: the session that drafted this post ran on it, and a single compression reported saving about 59K tokens, with more accumulating over the session. Its ledger panel does the arithmetic bluntly: in the screenshot below, 378 requests accumulated roughly 116.7M tokens of compression savings, worth about 35 US dollars, with actual context use at 145K, 14% of the 1M window.

![Figure 26: The billion-context ledger: 116.7M tokens saved, roughly 35 USD in live estimates](https://assets.jimmysong.io/images/blog/deepseek-harness-plugin-experience/dsh-billion-context.webp) Figure 26: The billion-context ledger: 116.7M tokens saved, roughly 35 USD in live estimates 

The mechanism and its cost fit in one picture.

![Figure 27: The context-compression trade-off](https://jimmysong.io/blog/deepseek-harness-plugin-experience/context-tradeoff-en.svg) Figure 27: The context-compression trade-off 

But the cost is just as real: compression is not free. Every fold runs an extra model call to produce the summary; the heavier the task and the longer the history, the more often compression fires, and the slower the agent gets. My felt experience: heavy tasks drag noticeably. You save tokens and sacrifice speed. After weighing it up I disabled the plugin outright: for daily writing and coding, responsiveness is worth more than saved tokens; I will switch it back on for weeks-long research tasks. Once disabled, the duplicate Context tab disappeared with it.

A fun aside: after installing `dsh-context`, two tabs both named Context appeared at the top of every session, and I first assumed it was a UI bug. Reading the source confirmed the two plugins each register a same-named tab; the dsh-context settings can rename or hide the billion-context tab (environment variable `BILI_DSH_CONTEXT_TAB=0`), and the collision is solved.

## Conclusion

After a week, DSH feels like the “Kubernetes moment” for agents: the core only schedules, capabilities are all plugins, and even the UI is plugin-mutable. The third-party API decoupling is genuine; pairing it with Zhipu’s GLM coding plan makes Chinese tasks smooth and the cost predictable.

Beyond the architecture, the curve I most want to share is this one: the excitement of 30 installed, and the discipline of 20 kept, and I know that number is not the destination; what goes unused will keep being disabled and deleted. A thriving plugin ecosystem is both a dividend and noise; the real skill is subtraction: keep only the one that feels right among overlaps, disable what you never reach for, and switch off whatever costs more than it returns. My advice is simple: set up the market, start with five or six plugins, do not hoard memory plugins, and save context compression for the genuinely long tasks.

If you are also tinkering with agent runtimes, see my earlier [2026 AI infrastructure outlook](https://jimmysong.io/blog/ai-2026-infra-agentic-runtime); DSH is a concrete sample of that thesis landing.

## [](https://www.jeffjade.com/2026/11/15/261-ikea-effect/#什么是宜家效应？ "什么是宜家效应？")什么是宜家效应？

宜家效应是一种有趣的认知偏见，描述了人们如何对自己参与创造的产品产生非理性的依恋。这个名称源自瑞典家具零售商宜家，他们的产品通常需要顾客自行组装——但这种现象远不止于家具。

关键在于，仅有努力本身——无论结果质量如何——就会产生依恋。当我们投入时间和精力创造某物时，我们会产生一种心理所有权，使我们对该物体的估值超过其客观市场价值。即使最终产品客观上不如替代品。

> 我们不仅珍视我们拥有的东西；我们更珍视我们帮助创造的——即使结果实际上并不更好。

这种偏见通过几种心理机制运作。认知投入使我们感觉对结果负有责任。我们努力的“沉没成本”创造压力，通过珍视结果来证明我们的投入是合理的。身份连接——我们把产品视为自身的延伸——放大了我们的依恋。

### [](https://www.jeffjade.com/2026/11/15/261-ikea-effect/#宜家效应的三层理解 "宜家效应的三层理解")宜家效应的三层理解

  * **入门** ：注意你对自己组装的家具、写的代码或做的饭有多大依恋——即使客观上类似的替代品明显更好。
  * **实践** ：在商业中，考虑提供让客户参与创作的“组装”或“定制”选项，增加感知价值和依恋。
  * **进阶** ：认识到宜家效应何时在扭曲你的判断——你可能过度估值自己的作品并拒绝切换到更好的替代品。

## [](https://www.jeffjade.com/2026/11/15/261-ikea-effect/#起源 "起源")起源

**Michael Norton** 、**Daniel Mochon** 和 **Dan Ariely** 在 2011 年的研究《宜家效应：劳动导致热爱》中首次系统记录了宜家效应。他们的研究涉及一系列巧妙的实验，展示了部分创造如何增加估值。

在他们最著名的实验中，参与者被要求要么自己组装宜家风格的书架套件，要么让其他人组装相同的套件。后来，当被问及对这些书架出价时，自己组装书架的参与者估值显著更高——通常比未组装的高 60-70%——即使组装的客观质量更差。

至关重要的是，研究人员发现这种效果取决于两个条件：参与者必须感觉自己成功创造了产品（不仅仅是随机组合零件），他们必须知道最终产品是预期的结果。当任一条件被违反时，效果就消失了。

这项研究揭示了热爱不是来自努力本身——而是来自成功完成一项有意义的任务，在那里你可以将结果视为“你的创作”。

* * *

## [](https://www.jeffjade.com/2026/11/15/261-ikea-effect/#核心要点 "核心要点")核心要点

  1. **成功重要，不仅仅是努力**  
宜家效应需要感觉成功创造了有意义的东西。随机努力没有连贯的结果不会产生依恋。

  2. **质量不驱动效果**  
人们经常更珍视自己组装的产品，即使客观观察者可以看到质量更差。依恋来自创造，而非质量。

  3. **效果延伸至家具之外**  
这种偏见适用于烹饪、DIY 项目、定制产品、书面文档、商业策略——任何我们通过努力“创造”的地方。

  4. **可能导致估值过高**  
宜家效应可能导致我们过度估值自己的创作并拒绝切换到客观上更好的替代品，这是决策中的潜在盲点。

## [](https://www.jeffjade.com/2026/11/15/261-ikea-effect/#应用场景 "应用场景")应用场景

  * **产品设计** ：需要一些组装或定制的产品会产生更强的客户依恋。各种产品中的“自己构建”选项增加感知价值。
  * **教育** ：主动完成练习题或项目的学生比仅接收信息的学生对学习产生更深的依恋——和更好的保持率。
  * **员工敬业度** ：当员工能看到工作的有形成果时，他们会产生更强的所有权和承诺。具有可见成果的项目培养更大的敬业度。
  * **营销** ：让客户参与产品开发或定制的品牌建立更强的忠诚度。用户生成内容活动有效地利用了这种效果。

## [](https://www.jeffjade.com/2026/11/15/261-ikea-effect/#经典案例 "经典案例")经典案例

### [](https://www.jeffjade.com/2026/11/15/261-ikea-effect/#LEGO-的“一起构建”活动 "LEGO 的“一起构建”活动")LEGO 的“一起构建”活动

LEGO 长期以来理解宜家效应的力量。他们的“一起构建”活动明确邀请家庭一起组装 LEGO 套件，将活动定位为共享创作而非乏味的组装。

市场研究显示，与购买预制展示模型或让人组装套件相比，购买 LEGO 套件并与家人一起组装的客户报告更高的满意度，更有可能再次购买。

LEGO 方法的美妙之处在于强调创作过程本身。说明旨在创造成就时刻（“你做到了！”），而 built 产品的最终展示加强了身份连接。这解释了为什么人们将儿时的 LEGO 创作保留数十年——它们不仅仅是玩具，而是个人创作。

* * *

## [](https://www.jeffjade.com/2026/11/15/261-ikea-effect/#边界与失效场景 "边界与失效场景")边界与失效场景

宜家效应并非普遍适用：

  1. **失败的尝试** ：当创作努力明显失败时，效果反转——我们可能估值甚至低于我们没有尝试的时候。
  2. **过于复杂的任务** ：如果任务太难，努力与结果之间的差距太大，挫折感会超过依恋。
  3. **专业领域** ：知道“好”是什么样子的专家可能不太容易受到影响，因为他们可以准确判断质量。

关键危险是宜家效应可能导致我们非理性地偏好自己的创作，即使存在更好的替代品。这可能适用于我们自己的写作、商业策略、产品或任何我们投入过的产出。

* * *

## [](https://www.jeffjade.com/2026/11/15/261-ikea-effect/#常见误区 "常见误区")常见误区

**误区：宜家效应意味着努力总是增加价值**  
**事实** ：该效果需要成功完成有意义的任务。失败或沮丧的尝试不会产生依恋——它们产生挫折感。

**误区：宜家效应只适用于物理产品**  
**事实** ：该效果强烈适用于智力和创意工作——策略、写作、商业计划。任何我们创造出的产出都会产生一些依恋。

**误区：质量在宜家效应中不重要**  
**事实** ：虽然该效果可以压倒质量担忧，极差的质量仍然可以减少依恋。当结果至少可以接受时，效果最强。

## [](https://www.jeffjade.com/2026/11/15/261-ikea-effect/#相关概念 "相关概念")相关概念

  * **[沉没成本谬误](https://meta.niceshare.site/zh/effects/sunk-cost-fallacy)** ：因为先前投入的资源而继续一种行为，不管未来价值如何——与努力证明方面相关。
  * **[禀赋效应](https://meta.niceshare.site/zh/effects/endowment-effect)** ：倾向于把我们拥有的东西估值高于其市场价值——与心理所有权方面重叠。
  * **[确认偏见](https://meta.niceshare.site/zh/effects/confirmation-bias)** ：搜索证实现有信念的信息的倾向——可以加强我们对自身创作的正面看法。

# [#](https://forcheetah.github.io/2026/11/15/Article05/#正文) 正文

不知道从什么时候开始，考公热门了。985、211 考公，硕士、博士考公，海龟也考公。现在多地推出放宽考公条件的规定，年龄放宽到 19-40 岁，学历放宽到高中和中专，有些地方还放宽专业和工作经历的要求。这只能进一步增加考公的竞争。

考公越来越卷，是因为考公被认定通向人生坦途：工作稳定轻松，收入和福利好，受人尊重。但果真如此吗？

必须说，公务员受人尊重是应该的，特别受人尊重则无必要。各行各业都应该受人尊重。公务员受到额外尊重并非因为手中的权力。现在各级纪检很紧，有权没权都必须严格按规定行事，谁敢越权，好不容易考上的公可能就没了，不敢也不值得造这个次。公务员受到额外尊重，实际上还是因为工作稳定轻松、收入和福利好。说得俗一点，尊重来自人无我有。

但人们似乎忘记了：40 年前，曾经有过 “大下海”。这不是特指公务员的，当年也没有公务员的说法。大下海中有大量国企、学校里的 “干部编制”，当然还有大量政府机关工作人员，后者就相当于今天的公务员了。

大下海发生在 90 年代的大下岗之前，而且大下岗并不涉及政府机关工作人员，主要是国企人员。大下海是因为机关工作的收入太低，机会天花板太低，而 “外面” 的机会和收入要好得多，当然风险也要高得多。下海不光有捕到大金鱼的，也有淹死的。

升迁缓慢、官场叵测、天花板低的问题在今天同样存在。实际上，这是全世界公务员的共同问题。在西方，除了有特殊抱负的，很少有顶级人才考公的。特殊抱负主要指外交和安全团队，这些地方入职要求很高，收入倒也只是高于平均水平，真想发财还是不行的。

西方外交官的收入还是按照公务员标准，并无特出。但根据派驻地的风险和生活条件不同，有丰厚的外派津贴，纳税比照军人优待，住所由使领馆提供，吃饭好像也有额外津贴，好像长期出差一样。可以带上家属，孩子教育也由使领馆津贴，通常为当地的外国人学校。安全团队就是各路间谍啦，他们的收入和待遇只能猜，估计和外交官相当。

公务员的升迁通常缓慢，飞黄腾达是少数。很多人科员一干十几年，好不容易爬上科长位置了，还要接着爬处长。在当年一起 “入公” 的同伴中，能爬上厅局的是例外，最后爬上部级的肯定是凤毛麟角。

实际上，比照西方的话，厅局以上就是政务官了，不是公务员。在中国，这些都是公务员，但还是有 “队伍内跨行” 的质的区别的。大部分公务员可能一辈子的天花板也就是处级，如果不是爬到科级就再也爬不动的话。必须说，公务员才是上升通道拥堵的典范。

也就是说，公务员在某种意义上是最接近 “一眼望穿人生” 的职业。这是有些人的人生首选，但不是大多数才华出众、抱负高远的人们的人生首选。在考公竞争激烈的今天，能过五关斩六将考上的，还真是才华出众、抱负高远的群体。他们一入职，可能就面临 “一眼望穿人生” 的困惑。当年大下海的机关工作人员中，大多数正是因为 “一眼望穿人生” 而 “外面的世界很精彩” 而下海，这在今天同样成立。

但为什么考公又突然火爆了呢？

不是因为外面的世界不精彩了，而是因为外面世界的精彩与风险并存，而人们越来越关注风险，有意无意地忽视精彩了。

社会流动性和上升通道是一个热门的话题，“躺平”、孔乙己、上香的话题都由此而来。但不可否认的是，在过去四十年里，中国产生了世界历史上最大数量的成功人物。他们不仅在事业上成功，也得到丰厚的经济报偿。随着中国向质量经济的转型，中国在继续产生更大数量的成功人物。只是当变化成为常态，稳定的增长也被感受为呆滞了人们期待的是永远的加速增长，即使在奇迹频出的中国也太难了。这或许可看作积极意义上的温水煮青蛙，煮过了就感觉不到了。

不管在任何时候、任何地方，谁都抱怨生活艰难。生活中每天看到、碰到的不如意的事情再小，也在不断刺激我们，提醒我们生活的艰难。生活中积极向上的事情则因为事小或者对进步习以为常而被无视了。不过过了一段时间，还是能看到正面的变化。

都说一出国就爱国，这还真是距离产生美。因为距离远了，生活中如意的、不如意的小事都看不见了，看到的只是大趋势，而中国的大趋势是积极向上的，这是大部分人们都不质疑的。即使躺平族、孔乙己族也不否认中国大势向好，他们只是认为这些向好的大势在时间上还遥远，也与自己的生活太隔膜，“歼 - 20、神舟 15 号跟我有什么关系？”

弄潮儿首先要在波浪前站起来，才能冲浪，但这是另外一个话题了。实际上，跟在波浪后面貌似风险小，别忘了还有下一道波浪。对于中国公务员来说，下一道波浪可能正在到来。

高薪养廉在原则上没有错。公务员也是人，也有七情六欲，收入上过于拮据可能影响政务效率，也增加 “逼使” 为生活所迫的公务员 “动歪脑筋” 的可能。公务员的收入和福利是靠地方财政支撑的，中国的地方财政可能面临艰难的转型。

在贫困地区，地方财政要靠转移支付支撑；但在更多的地方，地方财政在很大程度上靠土地财政支付，个人所得税和房地产税还是被认为针对少数人的 “惩罚富人税”，撑不起地方财政的大梁，工商税收还是不足的。

土地卖不动了，靠房地产拉不动地方经济了，这已经是共识。不管各地如何努力，政策的威力是有限的。中国住房存量已经很大，二三四线的空置率已经很高，北上广深的扩容潜力都可能触顶。

北上广深一旦放开政策，一段时间里还是会有不计代价入市的，但不计代价实际上还是要有本钱才能不计的，生活成本继续飙升最终会压抑消费冲动。北上广深的房价在不小程度上不只是由于刚需，还由于升值预期。一旦升值预期受到打压，房市深冷可以预期。

随着老龄化的深化，老一代的逝去，北上广深还有大量 80-00 年代建造的低质量连排多层公寓会空置。年轻人不愿住，服务人口则随着服务对象的逝去而消散，拆迁、就地改造升级则有不可承受的成本难题，空置而卖不出去的存量会对北上广深的房价也早晨很大压力。再说，偏远地段的房价都高，卖不动，中心地段的房价更高，如何就热销了？

土地财政路线遇堵，今后地方财政问题怎么解决？相信各级政府都在想这个问题，解决方案肯定不会轻松愉快，首当其冲的就是公务员队伍，高待遇难以为继，裁员倒是可以预期。

裁员不仅增加留用人员的工作负担，也影响政府服务质量，但数字化和人工智能可能提供解决方案。

大数据解决了大量文秘工作，人工智能则有可能解决大量重复性、有确定规则可循的工作。这就 “顶替” 了一大部分公务员了。

ChatGPT 近来成为非常热门的话题，其中的学术层面、道义层面、哲学层面不在本文讨论范围之内，但有一点可以肯定：这依然是根据历史数据 “训练” 的，在数学上可以比照为经验模型，只是具有自适应能力，能根据新的输入和激励持续更新模型，与时俱进。

ChatGPT 并不具备创造性思维和批判性思维能力，基本上只能根据已有定论泛泛而谈。人们惊叹其强大能力更多是出于意外，而不是 ChatGPT 真的实现了 “强人工智能”。比如说，问问 ChatGPT 对歼 - 20 和 F-22 的比较，TA 就只能泛泛而谈网上随处可见的八股调了，一点真知灼见都没有。

其实几年前的 AlphaGo 已经具有类似的特征，但 Chat GPT 的特出之处在于自然语言处理能力，可以理解人类的自然语言，也可以便于人类理解的自然语言形式输出，甚至具有一定程度的生动性。在某种意义上，ChatGPT 可看作以自然语言输入输出的通用人工智能模型，而不是 AlphaGo 那样针对围棋而且需要特殊输入输出方式的专用人工智能模型。

不难想象，大部分政务服务窗口并不需要创造性思维，并不需要真知灼见，还是以按部就班的程序性工作为主。一般性问答和处理可以通过某种 Chat GPT 在网上或者办公处所的公共智能终端解决，加上人脸或某种生物特征识别以确保隐私也不是难事，再简单点可通过密码、短信确认码等双重甚至多重认证进入。

更加高级但依然例行的居民服务也有可能通过人工智能完成。

ChatGPT 还善于生成八股文、官腔文。这对公务员既是好事，更是坏事。好事是减轻了工作负担，坏事是可能直接把工作也给顶替了。反过来，官场上有从大量八股文、官腔文中提取有用信息的需求，ChatGPT 有可能成为有效的 “过滤器”，抓重点。官员们生成八股文是给别人看的，可不是给自己看的。用人工智能自动生成文件、从海量文件中抓重点可能又替代了一些公务员的人力。

总之，公务员队伍中不需要创造性思维、批判性思维的岗位会越来越少，但创造性思维、批判性思维加上责任感意味着公务员的工作不再轻松，而且待遇未必有多高。这对有志在公务员道路上建功立业的人来说不是问题，但对希望 “啃公、躺平” 一族来说，就未必是福音了。

学历不等于能力，过度学历是一种浪费，这已经成为共识。新的公务员招聘条例反映了这样的共识，也意味着已经进入体制内的公务员也不能靠学历作为盾牌，资历都未必能可靠。这和 “外面” 的职场一样：如果资历高了，待遇高了，但所做的工作与新科员工一样，担当的责任也一样，即使公务员没有 “35 岁门槛”，此生到此为止是一样的，真的到了裁员的时候首先被辞退也不意外。这显然不符合才华出众、抱负出众的人们而考公成功的人们的期望。

坦途不仅要坦，更是要真的通往理想彼岸的途。

人们对考公的突然热衷来自于对未来的不确定性的忧虑。

已经得到的就不再珍惜，得陇望蜀是人的本性。生活太稳定了，一眼望穿人生的时候，就会 “人心思变”，就会下海。生活太动荡了，一眼看不透明天，就会 “人心思稳”，就会 “上岸”。

40 年前，在长期呆滞后，社会流动性和上升通道刚刚开通，人们迫不及待地下海。40 年后，社会持续激变，人们开始无视变化带来的机会。但对变化带来的不定性产生越来越大的畏惧，挤上考公的独木桥。这是可以理解的。但看不到考公的局限性，也可能对人生规划带来困惑，而不是解决困惑。

炒股要追高杀低，关键是要看准变化。呆滞的股市是没有玩头的。世界是注定要变化的，赶在潮头前面才是人生赢家，追潮而看不到身后的又一波潮头则容易成为人生输家。

考公不是坏事，但和考研一样，要想清楚为什么考公。考研是为了在学业上深造，不是为了推迟就业；考公是为了服务公众，不是为了躺平。考公并不通向人生坦途。成功人生本来就没有坦途。

# 快报视频文案的具体表达[#](https://auvetu.com/posts/stn-writing-methods-note/#快报视频文案的具体表达)

[【STN屎蛋】BOSS直聘，在线审稿（2026.09.20）](https://www.bilibili.com/video/BV18eeq65Exg)

## 1\. 开头：抓住注意力[#](https://auvetu.com/posts/stn-writing-methods-note/#1-开头抓住注意力)

  * 开头是观众注意力最高的时刻，应当选择观众能够理解、产生共情的切入点。
  * 后续叙述必须接住开头吸引来的注意力，并在此基础上继续引申。

## 2\. 叙述：明确面向对象[#](https://auvetu.com/posts/stn-writing-methods-note/#2-叙述明确面向对象)

根据目标观众调整叙述方式：

  * **高深玩家** ：可以进行具体、详细的论述。
  * **大众玩家** ：抓住即使完全不了解背景的人也能理解的主要矛盾。 
    * 要有直观的画面感。
    * 尽量让不了解相关知识的观众也能听懂。
    * 可以适当加入包袱。

## 3\. 信息承接：重复、补充与情绪抬升[#](https://auvetu.com/posts/stn-writing-methods-note/#3-信息承接重复补充与情绪抬升)

  * 信息量很大的事情，不能只在开头简单提及，还需要通过重复等方式讲清来龙去脉。例如：怪猎太刀与其他武器之间的矛盾。
  * 在叙述过程中，适当补充信息、抬升情绪，让观众逐渐理解事情的全貌。

## 4\. 引申：注意观众的理解成本[#](https://auvetu.com/posts/stn-writing-methods-note/#4-引申注意观众的理解成本)

  * 引申时要考虑观众是否能够理解。
  * 例如：从怪猎资源倾斜的矛盾，引申到对卡普空的论述与批判。 
    * 熟悉背景的观众可能很容易理解。
    * 面向大众玩家时，这种引申可能增加理解成本。
  * 不恰当的引申容易造成信息过载，甚至让观众的观感中断。 **注意「知识的诅咒」：** 不要默认观众拥有与作者相同的背景知识，引申需要谨慎。

## 5\. 情绪与梗：降低理解门槛[#](https://auvetu.com/posts/stn-writing-methods-note/#5-情绪与梗降低理解门槛)

  * 最容易让大家产生共鸣的，是大家都能理解的情绪。
  * 不必讲过于复杂的逻辑推理，否则观众容易听困。
  * 可以直接呈现矛盾、寻找责任归属，究竟是谁的错，以此吸引注意力。 **核心观点：** 梗是情绪的浓缩，情绪的结构不是叙事的基础。

# 屎蛋杂谈写作三步法[#](https://auvetu.com/posts/stn-writing-methods-note/#屎蛋杂谈写作三步法)

[【STN屎蛋】BOSS直聘，看看网友的稿（2026.09.27）](https://www.bilibili.com/video/BV1oDa86aEgX)

## 核心思想[#](https://auvetu.com/posts/stn-writing-methods-note/#核心思想)

好稿子都有两个观点：

  * **起点观点** ：用来出发的观点，即作者最初的直觉、情绪或判断。
  * **终点观点** ：用来抵达的观点，即经过观察、验证和推理后，最终想表达的认识。 三步法的核心就是：

  1. **找到两个观点** ：明确自己想从哪里出发，又想抵达哪里。
  2. **修建一条路** ：搭建从起点观点通往终点观点的逻辑与情绪路径。
  3. **检验这条路** ：观察读者能否顺利理解、接受并获得预期体验。

## 一、下笔前：找到并验证「我想说什么」[#](https://auvetu.com/posts/stn-writing-methods-note/#一下笔前找到并验证我想说什么)

这一阶段的目标是明确文章的核心观点，区分自己的直觉与经过验证的认识。

### 1.1 自我观点察觉[#](https://auvetu.com/posts/stn-writing-methods-note/#11-自我观点察觉)

先观察自己对某件事的第一反应。

  * 问自己：对这件事，我的第一反应是什么？
  * 区分情绪与事实： 
    * 情绪：「这也太傻逼了。」
    * 事实：「这设定跟原著不符。」
  * 把第一反应不加修饰地写成一句话。 **原则：** 第一反应只是候选观点，不急着为它辩护，也不必马上修饰。

### 1.2 第三人称观察与校验[#](https://auvetu.com/posts/stn-writing-methods-note/#12-第三人称观察与校验)

将自己的观点放到第三人称视角下，与客观事实对照。

  * 哪里能够对得上？
  * 哪里存在矛盾？
  * 哪些判断缺乏事实支撑？ 当观点与事实发生冲突时，只有两种处理方式：

  1. **修正观点** ：原来的判断确实存在错误。
  2. **深入挖掘矛盾** ：矛盾本身可能就是文章真正值得讨论的地方，说明自己发现了更深一层的问题。 例如： 「金刚狼没有男人味」与「漫威金刚狼恰恰是自洽的祖师爷」发生冲突。 进一步挖掘后，观点可能变成： 不是金刚狼没有男人味，而是这款游戏把他的雄性魅力转换成了受害性。 **原则：** 不要急于消灭矛盾，有时矛盾本身就是观点深化的入口。

### 1.3 资料补充与勘误[#](https://auvetu.com/posts/stn-writing-methods-note/#13-资料补充与勘误)

建立一张两栏勘误表：

我知道什么| 我不知道什么  
---|---  
已经掌握、能够确认的事实| 尚未确认、需要进一步核实的内容  
  
对于不知道的内容：

  * 要么查证；
  * 要么在文章中如实说明「我不知道」。 涉及厂商关系、作品设定、数据等事实性说法，应当先核实，再进行论述。 尤其需要注意：核心观众可能会逐帧查证。 **原则：认知不一定要深，但必须诚实。不要把未经确认的猜测包装成事实。**

### 1.4 观点位置考察：明确起点与终点[#](https://auvetu.com/posts/stn-writing-methods-note/#14-观点位置考察明确起点与终点)

判断自己写下的那句话究竟是起点观点，还是终点观点。

**如果它是终点观点：**

进一步追问它是否足够深入：

  * 这只是一个情绪指控吗？
  * 能否再向下挖掘一层，找到背后的结构性原因？ **如果它是起点观点：** 它暂时经不起勘误也没有关系。 起点观点的职责是把读者拉进来，但作者必须修建一条完整的论证链，将它送到终点观点。 **本阶段交付物：**

  1. 一句话论点：明确写出起点观点与终点观点。
  2. 两栏勘误表：明确自己知道什么、不知道什么。

## 二、下笔中：先想效果，再搭骨架，最后填细节[#](https://auvetu.com/posts/stn-writing-methods-note/#二下笔中先想效果再搭骨架最后填细节)

### 2.1 文体察觉：先认清发动机，再选择文体[#](https://auvetu.com/posts/stn-writing-methods-note/#21-文体察觉先认清发动机再选择文体)

文章的文体由两个问题决定：

  1. 你是从情绪出发，还是从事实出发？
  2. 你是从结论出发，还是从过程出发？ 由此可以组合出四种文章类型：

出发基础| 叙述方向| 对应文体  
---|---|---  
情绪| 结论| 吐槽立论型  
事实| 结论| 论证型  
情绪| 过程| 体验还原型  
事实| 过程| 考据科普型  
  
**核心原则：发动机决定文体，不要让文体反过来束缚发动机。**

审阅其他作者的文章时，也应当先识别作者的发动机：

  * 保留其优势；
  * 替换其薄弱环节；
  * 不要把所有作者都改造成自己。

### 2.2 逻辑大纲：三层结构[#](https://auvetu.com/posts/stn-writing-methods-note/#22-逻辑大纲三层结构)

搭建文章骨架时，分为三个层次。

#### 第一层：列出想要的东西[#](https://auvetu.com/posts/stn-writing-methods-note/#第一层列出想要的东西)

暂时不考虑顺序和逻辑，先把自己希望文章实现的效果全部列出来。

主要包括：

  * **情绪引导** ：希望观众产生怎样的情绪？哪里暴躁、哪里安静、哪里顿悟？
  * **观点表达** ：有哪些观点是自己真正想表达的？
  * **趣味包袱** ：有哪些特别好笑的内容，不展示出来会觉得可惜？ 这一层只负责收集，不急着组织。

#### 第二层：钉住逻辑骨架[#](https://auvetu.com/posts/stn-writing-methods-note/#第二层钉住逻辑骨架)

将第一层列出的内容组织起来，搭建一副自洽的骨架。

需要同时满足：

  * **逻辑自洽** ：观点之间能够形成合理的推导关系。
  * **情绪自洽** ：情绪的铺垫、变化和释放符合文章的整体体验。 骨架不是一稿定型的，而是用来不断删改的。 修改时应当：
  * 动一处，看全身；
  * 如果整体结构因此崩塌，就重新排列；
  * 不要因为已经写过某段内容，就舍不得删除。 **几条硬规则：**

  1. 顿悟句只允许出现在结尾。
  2. 删除包袱之前，先检查它是否在其他位置承担了 callback（前后呼应）功能。
  3. 桥段不要超过全文的十分之一。

#### 第三层：填充细节[#](https://auvetu.com/posts/stn-writing-methods-note/#第三层填充细节)

将具体素材、包袱和过渡内容填入骨架。

包括：

  * 补充事实与案例；
  * 填充具体描写；
  * 安排笑点与包袱；
  * 补充段落之间的过渡。 **修改完成的标志：每一段只剩下一个需要回答的问题。** 本阶段最终交付物：一副能够持续删改、调整的文章骨架。

## 三、出产后：复盘并进入下一轮[#](https://auvetu.com/posts/stn-writing-methods-note/#三出产后复盘并进入下一轮)

文章发布后，不需要做过于复杂的工作，主要完成两件事。

### 3.1 享受读者反馈[#](https://auvetu.com/posts/stn-writing-methods-note/#31-享受读者反馈)

享受观众的夸奖与互动。

评论区本来就是情绪峰值应该出现的地方。

### 3.2 记录不足与问题[#](https://auvetu.com/posts/stn-writing-methods-note/#32-记录不足与问题)

记录文章中不好的地方：

  * 哪些观点没有表达清楚？
  * 哪些逻辑存在问题？
  * 哪些段落效果不理想？
  * 哪些地方与预期的读者体验不一致？ 将这些问题归档，留到下一篇文章的下笔前阶段处理。 **写作方法论是一个循环：** 出产后发现的问题，就是下一篇文章第一步的素材。

## 四、附：审稿时增加一步——反向工程[#](https://auvetu.com/posts/stn-writing-methods-note/#四附审稿时增加一步反向工程)

三步法原本是作者自查表。

在审阅其他人的文章之前，需要先增加一个步骤：**从成稿反推作者的认知路径。**

重点判断：

  1. **观点位置** ：作者的观点停留在哪一层？是起点观点，还是终点观点？
  2. **写作发动机** ：作者究竟是从情绪还是事实出发？从结论还是过程出发？
  3. **真正想写的内容** ：哪些段落才是作者真正想表达的？哪些只是为了衔接而后续添加的内容？ 完成反向理解之后，再使用三步法审视文章。 否则，原本用于帮助作者的框架，就可能变成强行套用所有人的模具。

## 核心总结[#](https://auvetu.com/posts/stn-writing-methods-note/#核心总结)

写作不是单纯地把脑中的想法依次写出来，而是一个从直觉到认知、从认知到表达、再从读者反馈回到自我修正的过程。

**先找到自己想说什么，再思考怎样把它说清楚，最后检验别人是否真正接收到了。**

## AI 还没横扫就业市场，先挤掉的是年轻新人

澳大利亚央行的一项监测显示，人工智能对就业的冲击尚未普遍显现，却已在软件开发和客服等 AI 暴露度较高的行业留下一个年龄断层：15至24岁劳动者的就业表现弱于年长者。

澳大利亚央行经济学家 Mike Major 建立了一套劳动力市场监测工具，把最容易最早显现影响的两类对象放在一起观察：刚进入职场的人，以及任务理论上更容易被人工智能AI 暴露度（岗位任务与AI技术的关联程度）较高的职业。软件开发、文书和客服都在名单内。基准时间是 2022 年末 ChatGPT 发布之时，研究以招聘职位、年龄组就业率和失业率的变化寻找信号。

结果是总体就业岗位仍然存在，但不同群体的下落速度不同。自 ChatGPT 发布以来，招聘职位在所有年龄组都减少，其中人工智能暴露度最高的第五组降幅最大。组内再拆分，15至24岁劳动者和刚毕业不久的年轻人就业率走弱、失业率上升；同一批高暴露职业中，年长劳动者的就业表现则更强，部分群体甚至有所增加。变化先集中在新人身上，而不是平均落在所有员工身上。

**2022 年末** ChatGPT 发布，成为研究比较的时间基准。 **15—24 岁** 高暴露职业中就业表现弱于年长劳动者。 **第五暴露组** 任务最易受AI影响，招聘职位降幅最大。 

美国数据出现了相近的年龄分化。斯坦福大学 2025 年 8 月基于数百万份美国工资记录的研究发现，自 2022 年末以来，22至25岁劳动者在人工智能暴露职业中的就业率相对下降 13%，年轻软件开发者降幅接近 20%；同一批职业中，经验更丰富者的就业人数保持稳定或有所增加。这里的百分比是相对变化，不等于所有同类岗位都减少了相应比例。

Anthropic 2026 年 3 月的研究也发现，22至25岁求职者在暴露职业中的求职成功率下降约 14%，但整体失业率没有系统性上升。该公司内部审查显示，技术岗位中的初级员工占比从 2025 年初的 27% 降至 9%；到 2026 年 8 月，其人工智能代理记录的工时已是员工的 6 倍。Anthropic 自己承认，作为一家高度依赖人工智能的软件公司，这是特殊情况，不能代表整体市场。

现有证据还不足以把入口收缩全部归因于人工智能。澳大利亚央行研究人员警告，这项分析没有建立直接因果关系，衡量的是理论暴露度，而非企业实际使用情况；疫情后的商业周期变化和远程工作调整也可能影响数据。

匹兹堡大学团队分析 2026 年 1 月发布的 1060 万份 LinkedIn 个人资料及美国失业数据后发现，问题在 2022 年初已经出现，早于 ChatGPT 数月，利率政策和疫情后招聘过度增长后的调整都可能产生作用。

这也是整组数据最需要停一下的地方：招聘职位减少、年轻人求职变难与人工智能普及同期出现，却不等于三者之间已经证明存在因果关系。目前更确定的事实是，经济体尚未出现全面岗位崩塌，冲击却可能先发生在入门级岗位。软件开发和客服究竟会不会成为长期缩窄的入口，还需要后续招聘与实际采用数据继续分辨。

为何要紧 

## 入口缩了，但还看不到失业潮

真正值得担心的，是年轻人进入高暴露职业的通道是否正在变窄。

澳大利亚央行（负责利率与金融稳定的央行）研究人员从2022年末 ChatGPT 上线时开始监测软件、文职和客服等高暴露职业。

此后，职位广告（企业公开招聘岗位的数量）在各人群中普遍减少，受 AI 暴露最高的一组降幅最陡。15至24岁劳动者和年轻大学毕业生就业率更弱、失业率更高；同一批高暴露职业中，年长劳动者的就业反而上升。

这不等于所有年轻人的工作都更难找。2025年8月，一项基于数百万份美国工资记录的研究发现，22至25岁人群在高暴露职业中的就业，相对2022年末下降13%；年轻软件开发者降幅接近20%，更有经验者的就业则持平或增加。变化集中在职业内部和资历入口，并非失业率全线上扬。

AI 目前更像先压缩了新人通道。23岁求职者在软件或客服岗上少一个位置，不表示同年龄段的餐饮、物流或照护岗位同步减少；资深员工留任或增加，也不能抵消企业不再培养新人的成本。

Anthropic 的内部数据呈现了更明显的入口收缩：技术岗位中初级员工占比从2025年初的27%降至9%。不过，Anthropic 是 AI 使用高度密集的特殊样本，外部企业不能直接套用这一降幅。

该公司2026年3月的研究发现，22至25岁求职者在高暴露职业中的求职成功率下降约14%，却没有发现总体失业率出现系统性上升。

丹麦一项覆盖2.5万名劳动者的研究也划出了边界：AI 采用率达到64%，研究没有测到工资或工时的可辨变化，劳动者平均只节省了2.8%的工作时间。AI 已进入办公场景，不代表企业按相同比例替代岗位。

原因甚至可能早于生成式 AI。2026年1月，一项分析1,060万份 LinkedIn 档案及美国失业数据的研究发现，高暴露职业的问题在2022年初已经出现，比 ChatGPT 上线早几个月；美联储利率政策转向，以及疫情后招聘过度后的调整，也可能解释更多变化。

所以，“就业走弱”不能直接改写成“AI 已造成失业潮”。目前能确认的是，一些年轻新人在高暴露职业中的入口在收缩，部分资深岗位尚未减少；AI 是候选原因之一，直接因果仍待确认。这套机制如何运转、你该怎么应对，下一节展开。

## 钱包接进来，账单第一次能被追问

Gemini 现在能连接 Google Wallet。用户在 Gemini 里接入钱包，就能让 AI 直接拿账户里的交易记录出图、答问。数据是持续更新的，不是用户贴一次就停。

Google 负责 Gemini 应用与 AI 开发的 Josh Woodward 在 X 上展示了这项新连接：接入 Google Wallet 后，可以让 AI 即时生成消费图表，把支出可视化。这项用途被列为“个人财务洞察”的首要场景，但它目前仍是产品功能描述，不是已经公布测试结果的独立测评。

差别在哪？接入钱包之后，交易记录先成为可询问的上下文，Gemini 再据此回答“钱花到了哪里”这类问题——分析建立在持续更新的财务数据上，而不是一次性的文字描述。

官方还把识别订阅涨价、按上年实际支出制定节日预算列为后续能力。

机制 

## 订阅悄悄涨价，它靠什么发现？

同一个流媒体服务，这个月扣款比上个月高了几块钱——单看一笔账，看不出这是涨价还是汇率波动。Gemini 接入 Google Wallet 后，能做的第一件事，就是把同一服务的多次扣款摆到一起比。

Google 负责 Gemini 应用与 AI 开发的 Josh Woodward 说得直白：它能发现隐蔽的订阅涨价（同一服务前后扣款金额不同）。

普通聊天模型缺少完整付款记录时，只能依据用户贴出的单笔金额推测；Google Wallet 提供了持续交易数据，比较才有依据。取不取消订阅，仍由用户定。

反直觉 

## 去年的支出，能定今年的钱包上限吗？

按官方说法，Gemini 接上 Google Wallet，能拿去年实际花掉的钱生成今年的节日预算，前提是钱包里的记录够全。

Google 负责 Gemini 的 Josh Woodward 在 X 上把这项能力列为个人理财洞察的第三种用途：依据用户去年实际花掉的钱，制定节日预算（为年末节庆支出预留的金额）。基准从「凭印象填一个整数」换成了「个人历史支出」。

判断Gemini 不是凭空教人省钱，而是把钱包里的旧记录翻译成今年可以照着花的上限。 

基准从哪来？Google Wallet（Google 管理支付与交易记录的服务）掌握实际付款数据，Gemini 直接拿它当底。

这套方法能否成立，取决于历史数据是否完整。钱包记录若遗漏现金支付、退款、临时大额开销或家庭共同支出，得到的基准就会有缺口。现有材料只说明 Gemini 可以按上一年的实际支出制定节日预算，没有给出数据覆盖率，也没有第三方实测其预算准确度。

这个数字适合当上限，还是只适合当参考线？

方向 

## Gemini能看到多少账单数据，边界由谁划定？

Gemini接进Google Wallet之后，能读到的就不只是用户主动贴进来的那几句话。权限和数据处理方式，官方还没同步公开。

Woodward在X上公布这项新功能时，只说连接Google Wallet后可用于个人理财洞察，没有列出Gemini具体可读取的交易字段（每笔记录包含的金额、商户等数据项）。消费图表、订阅价格变化、基于往年支出的预算，这些功能需要哪些数据，公开说明没有展开。交易字段决定它能算什么，授权范围（系统获准查看和操作的数据边界）决定它有权看什么。

现有材料没有说明授权是否按数据类别或时间范围设置，也没有交代用户能否逐项查看、撤回或限制访问。它同样没有确认交易数据会被保存多久、是否用于改进模型，以及生成理财建议时是否会与其他信息一并处理。

在官方补出字段与授权说明之前，接不接入，取决于用户自己对敏感数据的容忍度。

动手 

## 图表已经能生成，扣款仍要自己核对

Gemini 接入 Google Wallet 后，能整理消费、发现订阅涨价、按去年实际支出做节日预算。这些目前都只是产品描述，没有第三方实测。

生成图表只说明 Gemini 能把消费可视化；识别订阅价格变化，才说明它开始比较一段时间里的账单。当前材料没有说明它依据哪些字段识别涨价，也没有公布识别准确率、漏报率或错误归因比例。

预算功能要从个人账本反查。Gemini 能按用户去年实际支出制定节日预算，分类、金额和时间范围是否合理，得对着原始账单看。

Google 的产品页面确认了“连接 Google Wallet 获取个人财务洞察”这一定位，但现有材料没有交代 AI 如何访问交易数据、权限能否撤回、记录保存多久，也未说明敏感字段是否会离开用户设备。涉及财务数据时，这些不是附带问题，而是决定是否值得接入的前置条件。

现在可以做的一次账本核验 1

连接 Google Wallet，生成一张消费图表，并与原始账单逐项核对。

2

检查订阅涨价提示，逐一确认续费金额和账单周期。

3

生成节日预算，对照去年实际支出检查分类与金额。

4

查看 Google Wallet 授权范围、数据保存期限和撤回方式；页面未说明的项目，等待官方补充。

5

等待第三方实测，再评估图表完整性、涨价识别准确率和财务数据处理方式。

发布后的真实使用里，最该记录的不是图漂不漂亮，而是它有没有漏掉交易、认错涨价、混用周期。这些错一次，预算就跟着错一次。

正常。Muse 的码不是在注册表单里填的，是注册完进设置里兑现，所以才强调「注册完立刻去设置」。

从你加入成功（账号建好）那一刻起算，不是点开链接的时间。稳妥起见，注册完五分钟内就把码填了。

填码本身免费，不需要为填码付任何费用。凡是打着「邀请码」旗号让你先付钱、或索要账号密码和验证码的，都是假的，别理。

**SmartPerfetto 1.19.0 已发布。** 相比上一篇更新记录覆盖的 1.15.1，这段时间最大的变化是分析引擎统一到 Pi Agent Core；同时升级了 Perfetto、补了新的数据分析能力，也围绕 TraceDemo 的多轮测试修了不少实际问题。

先把这次值得关注的内容列出来：

  * **分析引擎统一** ：从多套 Agent runtime 转向默认使用 Pi Agent Core，Web、CLI、API 共用取证与交付能力；旧的模型声明与 claim-verification 流程已移除。
  * **分析过程更好用** ：分析中途可以补充上下文，源码选择按会话保存；长会话的证据回读、预算收尾、连接中断和错误提示都有修复。
  * **能读到的证据更多** ：Perfetto 升到 v59.1，增加进程生命周期、JobScheduler 等观察；Bitmap、Doze、CPU PMU、相机和渲染分析也有更新。
  * **多轮验证留下了具体结果** ：合成样本、真实 trace、定向复测和最终发布包分别验证。哪些完成了，哪些只测了部分，后面会展开。
  * **不想装完整产品，也可以用 Perfetto-Skills** ：把独立 Skill 装进自己的 Codex、Claude Code 或 OpenCode，在已有 Agent 环境里分析 trace。

## [](https://androidperformance.com/2026/11/15/SmartPerfetto-v1.19.0-Release-Notes/#新架构：统一模型循环，把分析能力留在产品里 "新架构：统一模型循环，把分析能力留在产品里")新架构：统一模型循环，把分析能力留在产品里

一次 trace 分析包含不少不同性质的工作。模型要理解问题、决定接下来查什么；Skill 和 SQL 要实际取数；进程身份、时间窗口和数据来源要保持一致；最终还要把结论、HTML 报告和会话结果交付出来。

之前同时维护多套模型 SDK/runtime，这些工作需要跨不同执行方式接起来。现在默认由 **Pi Agent Core 负责模型请求和工具循环** ，SmartPerfetto 继续拥有策略、工具、Skill、SQL、身份与权限、报告和会话。Web、CLI 和 API 使用同一套后端分析能力。

[![从多运行时到 Pi Agent Core 的架构变化](https://androidperformance.com/images/SmartPerfetto-v1.19.0-Release-Notes/architecture.png)](https://androidperformance.com/images/SmartPerfetto-v1.19.0-Release-Notes/architecture.png)

 _图中展示默认执行路径的变化。1.19.0 仍保留旧 Claude /OpenAI 引擎的隐藏回退；它们不再是日常配置界面的可选项。_

Provider 仍决定 API、endpoint、模型和凭据。切换引擎时，已有配置需要保留原来的请求目标；恢复旧会话，也不能因为后来换了 active provider，就把会话悄悄发到另一家服务。无法迁移的旧配置会明确报错。源码授权、进程身份和 trace 归属检查也继续由产品控制。

Pi 在这里不会自动获得任意文件和 shell 权限。SmartPerfetto 使用的是自己的分析工具集合，源码读取仍需要对应授权。具体模块关系见[当前 runtime 架构](https://github.com/Gracker/SmartPerfetto/blob/v1.19.0/docs/architecture/agent-runtime.md)。

### [](https://androidperformance.com/2026/11/15/SmartPerfetto-v1.19.0-Release-Notes/#这次还撤掉了一套曾经投入很多精力的流程 "这次还撤掉了一套曾经投入很多精力的流程")这次还撤掉了一套曾经投入很多精力的流程

如果看过上一篇文章，会记得当时花了很多篇幅讲“答案声明与核验”：模型需要把结论和证据关系按特定格式声明，产品再解析、修复和核验。

1.16.x 还在继续修这套流程，包括声明格式、预算耗尽后的恢复和不完整引用。但真实模型运行里，声明、修复和最终正文之间仍然有交付摩擦；1.17.0 的发布记录也明确保留了启动、滑动探索运行未完成报告的限制。到了 1.18.0，**运行时模型声明与 claim-verification 流程被移除** 。

当前方向是把可确定的工作放到取证阶段：Skill/SQL 给出数据，生产者尽量说明单位、范围和语义，模型据此组织调查和解释。后端依然要守住身份、授权、预算和交付合同，但不能把“生成了一篇报告”包装成“每句话都完成了因果证明”。

我觉得这段取舍值得单独留下来。更新记录如果只写新增了什么，读者就会误以为旧文中的核验能力一直累加到现在；实际上这里发生过一次明确的架构调整。

## [](https://androidperformance.com/2026/11/15/SmartPerfetto-v1.19.0-Release-Notes/#分析中途补信息，长调查也能继续看证据 "分析中途补信息，长调查也能继续看证据")分析中途补信息，长调查也能继续看证据

分析已经开始后，用户常常才想起一条关键信息，比如“只看第二次启动”“这个进程刚刚重启过”。现在可以在运行中补充上下文，界面会显示这条补充是排队、已送达，还是未能应用。它不保证回溯修改已经完成的分析步骤，但用户能知道信息有没有进入本次运行。

源码选择也改成按会话保存，新会话从最近一次选择开始。用户主动发起时，可以导入本机 Claude Code/Codex 的第三方网关配置；导入只读指定配置文件，并通过系统对话框确认。**这不等于 Claude Code 订阅登录就能直接配置 SmartPerfetto** ，仍需要有效的 API 凭据。

长调查里，证据管理也影响体验。模型可能先查一个总览，几十次工具调用后又要回看最早的几行。我们扩大了有上限的工件工作集，同时限制直接送进模型上下文的行数，保留按需分页和回读的入口。这样能减少过早驱逐证据造成的中断，同时控制上下文体积。缓存依然有容量与生命周期限制。

Pi 的预算收尾和连接恢复也做了多轮修复：轮数或上下文接近上限时给最终结论留出空间；对可重试的服务错误和空闲流中断按次数、时间、轮次及已知费用约束恢复；保留已经完成的工具结果。费用上限只对有已知定价的模型有效，不能把它理解为对所有第三方网关都生效的硬性账单保证。

## [](https://androidperformance.com/2026/11/15/SmartPerfetto-v1.19.0-Release-Notes/#新的分析能力，先说清能看到什么 "新的分析能力，先说清能看到什么")新的分析能力，先说清能看到什么

### [](https://androidperformance.com/2026/11/15/SmartPerfetto-v1.19.0-Release-Notes/#Perfetto-v59-1、进程生命周期与后台任务 "Perfetto v59.1、进程生命周期与后台任务")Perfetto v59.1、进程生命周期与后台任务

1.17.0 同步了 Perfetto v59.1，包括 UI/Wasm、固定版本 trace processor 和生成的 SQL 知识。上游的 FrameTimeline 图层分组、堆视图导航和 CPU 时间等变化也进入产品。

分析侧增加了进程启动上下文、启动延迟、退出原因和状态转换；JobScheduler 同时利用 framework track events 与已有 ATrace 视图。缺少等待时长、取消任务或归属信息时，会保留对应限制，不能把未知直接写成零。

### [](https://androidperformance.com/2026/11/15/SmartPerfetto-v1.19.0-Release-Notes/#Bitmap、Doze、CPU-PMU "Bitmap、Doze、CPU PMU")Bitmap、Doze、CPU PMU

Bitmap 分析补了进程内已记录对象的 live set 形态、大小分布和大对象。排查图片内存时，可以从“占用比较多”继续看具体分布。不过，记录到的 Bitmap 对象与整个进程内存是不同口径。

Doze 分析增加 light/deep idle 的状态标签和转换时间线。快速切换值得继续调查，但单凭“切换频繁”不能证明异常耗电。

CPU PMU 分析增加计数器增量、事件比值和可用的进程归属信息，前提是 trace 录到了所需计数器。没有采集的硬件事件不会在升级后凭空出现，归属不足时也不能硬算到某个应用头上。

### [](https://androidperformance.com/2026/11/15/SmartPerfetto-v1.19.0-Release-Notes/#相机、渲染和显示之间的区别 "相机、渲染和显示之间的区别")相机、渲染和显示之间的区别

相机分析开始更明确地测量观察到的帧节拍，并统一 SurfaceFlinger 绑定判断。Buffer/Transaction 分析区分帧生产、事务活动和呈现证据；WebView、React Native、浏览器合成等路径有各自的条件。

这一点对“看起来有渲染活动，所以画面肯定显示了”的推断很重要。生产端活动只能支持对应阶段的观察，要确认显示，还需要绑定和呈现证据。产品中的渲染解释也改为维护中的教学卡，和管线目录一起校验。

## [](https://androidperformance.com/2026/11/15/SmartPerfetto-v1.19.0-Release-Notes/#TraceDemo-跑了几轮，具体修到了什么 "TraceDemo 跑了几轮，具体修到了什么")TraceDemo 跑了几轮，具体修到了什么

### [](https://androidperformance.com/2026/11/15/SmartPerfetto-v1.19.0-Release-Notes/#几个实际例子 "几个实际例子")几个实际例子

**错误信息要让人知道错在哪里。** 一次身份拒绝的关键原因，曾被很长的参数合同挤出结果摘要。现在优先保留安全的原因和下一步动作。SQL 日志也可以给出受限制的缺表、缺列、缺函数标识和查询哈希，帮助诊断，同时避免输出整段原始 SQL。

**模型的 SQL 先验也会过时。** `sched.is_idle` 就是一个具体例子：正确做法是通过 thread join 使用 `thread.is_idle`。我们补了按内置 schema 核对过的核心列速查、slice/thread 关联和窗口函数指导。相机单例复跑里 SQL 失败从 3 次变成 1 次，但两次查询总数不同，一个样本不够证明普遍降低了多少百分比。

**大数时间戳需要明确单位。** thermal 案例曾出现错误秒量级。现在只从单位明确为 ns、可以精确处理的值派生秒预览，保留原始单元格和时钟起点。定向检查中的 `394361.352 s → 394406.092 s` 对应 `44.74 s`。当时记录中的另一处频率单位标签问题仍未解决，不能一起算作修好。

**证据不足时，计划要解释缺什么。** 阶段反馈会列出缺失调用、已成功调用和带真实 tool-call ID 的失败调用。模型可以补查，或引用失败说明无法取证；这不会自动把未解决的调查项变成成功。

语义复核也留下了边界：多个并行线程的 CPU 时间相加，不能直接证明端到端关键路径；SurfaceFlinger 走 HWC，也不能推出全局 GPU 工作都来自目标应用。我希望读者能看到这些问题的存在，而不是只看到一串绿色完成标记。

> 博客侧栏那页友情链接，我加了三年，也放了三年。名字、头像、一句话介绍，摆得整整齐齐，然后就没有然后了——谁上周写了新东西，谁半年没更新，我一个都不知道。最近把它改成了一条会自动往前走的时间线：50 个站点、489 篇文章，谁更新了就自己冒出来。这篇把这套东西是什么、怎么跑的、以及我这边踩过的坑都摊开写一遍。

## [](https://dusays.com/posts/898/#一、友链页最大的问题，是它不会动 "一、友链页最大的问题，是它不会动")一、友链页最大的问题，是它不会动

大多数博客的友链页是一份静态名单。写进主题模板里，或者塞进一个页面，加完就再也不碰。它解决的是「我认识谁」，但回答不了「他们最近在写什么」。

以前想看朋友更新，只有两条路：装个 RSS 阅读器逐个订阅，或者自己写爬虫挨个站点抓。前者要维护一份订阅列表，后者要处理各种页面结构、反爬、站点下线，写起来不难，维护起来没完。

我最后的判断标准很简单：**这件事应该由服务端定时跑，不该由浏览器每次打开页面时算。** 所以做了个独立的小服务，给它一份友链名单，它负责抓、负责去重、负责存，博客只管拿数据渲染。

## [](https://dusays.com/posts/898/#二、给一个地址，它自己把整页友链接收下来 "二、给一个地址，它自己把整页友链接收下来")二、给一个地址，它自己把整页友链接收下来

最省事的地方在录入。不用一条条填站点名、主页、RSS 地址，直接把 `/friends/` 这类友链页的地址粘进去，它会解析出里面的链接和名字，之后还定期回看有没有新朋友。

不想让它解析也行，手动加单个站点、导入 OPML 都支持。三条路覆盖的情况不一样：页内自动解析适合友链页规整的；OPML 适合本来就在 RSS 阅读器里攒了一份订阅的；手动补适合个别没被认出来的。

## [](https://dusays.com/posts/898/#三、没-RSS-也能抓，四层依次兜底 "三、没 RSS 也能抓，四层依次兜底")三、没 RSS 也能抓，四层依次兜底

真正麻烦的从来不是「有 Feed 的站点」，而是那些没开 RSS、换了生成器、或者把 Feed 藏得很深的。这套服务按顺序试四层：

  1. **Feed** ：先找标准 RSS / Atom；
  2. **框架指纹** ：认出是 Hexo、WordPress 还是别的，按框架惯例去找；
  3. **启发式** ：从首页链接里猜文章页的规律；
  4. **自定义规则** ：前三层都不行，允许针对这个站点单独写规则。

关键是最后有个明确反馈：实在抓不到，会告诉你卡在哪一层，而不是静悄悄留个空。这点比「全自动」重要得多——抓不到可以人工补，不知道为什么抓不到就只能干瞪眼。

## [](https://dusays.com/posts/898/#四、按自己的节奏跑，别去打扰已经下线的博客 "四、按自己的节奏跑，别去打扰已经下线的博客")四、按自己的节奏跑，别去打扰已经下线的博客

文章和友链各设各的 cron，互不绑死。友链页一周回看一次就够，文章流可以几小时拉一次。

还有个容易被忽略的细节：**失败站点自动降频** 。某个博客连续几次连不上，就把它往后排，不再按原频率反复敲。友链里总有几个站点慢慢就不维护了，服务器关了、域名到期了，如果抓取器还每天准时去撞一次，日志里全是超时，也谈不上对人家客气。

我这边现在是 50 个友链站点、45 个正常抓取，剩下的自动降频，不再按原节奏去撞。

## [](https://dusays.com/posts/898/#五、后台：抓取状态都摊在桌面上 "五、后台：抓取状态都摊在桌面上")五、后台：抓取状态都摊在桌面上

服务端在跑，也得有个地方能看它跑得怎么样。后台是个独立的控制台，登录后第一屏就是概览：50 个友链站点里 45 个正常、5 个异常，收录 489 篇文章、449 篇已生成摘要，近 7 天新增 115 篇，抓取成功率 81%。下面按天铺开近 14 天的收录趋势，旁边是抓取健康的环形图和「需要留意的站点」——连续失败次数最多的几个直接列出来，不用翻日志猜。

友链管理页是平时最常来的地方。每个站点一张卡，主页、RSS 地址、文章数、最近成功时间和连续失败次数都写在上面；抓不到的会标出具体原因，比如目标站点拒绝访问、页面由 JavaScript 渲染导致静态抓取拿不到文章、连接超时。前面说的「失败站点自动降频」，在这里就是「已暂停采集 · 暂停于 1 天前」这样一条明明白白的状态，可以点「恢复」重新纳入，也可以进「规则」针对这个站点单独写抓取规则——正好对应第三节的第四层兜底。

设置页放的是需要自己决定的几件事：API Key 一键生成或重置，旁边直接给出可复制的 `curl` 示例；AI 摘要的开关、模型服务商和模型名都在这里填，用自己的 Key，Key 只存在自己的账号里；采集频率则把「多久抓一次文章」和「多久回看一次友链页」分开设置，互不绑死。

## [](https://dusays.com/posts/898/#六、数据是你的，接口也是开放的 "六、数据是你的，接口也是开放的")六、数据是你的，接口也是开放的

这套东西不要求你把页面嵌进博客，也不要求改主题。一个 GET 请求拿到结构化数据，前端想怎么排都行。

      "https://ducircle.dusays.com/v1/all?start=0&end=9&rule=created"  
      
  
---|---  
  
返回的是干净的 JSON：
    
    
    1  
    2  
    3  
    4  
    5  
    6  
    7

    {  
      "data": [{  
        "title":   "给博客换了个静态生成器",  
        "author":  "木子学习笔记",  
        "link":    "https://example.com/posts/42/",

`total` 是总数，前端拿它算分页；`summary` 和 `score` 没生成的时候是 `null`，所以渲染逻辑要允许字段缺失，别假设每篇都有摘要。时间字段是 ISO 8601，格式化交给前端。

鉴权头是 `X-API-Key`，也支持 `Authorization: Bearer`。Key 在后台「设置 → API Key」里生成，可以随时重新生成，每个 Key 只对应自己的数据，租户之间互相看不到。

## [](https://dusays.com/posts/898/#七、四个只读接口，字段沿用老习惯 "七、四个只读接口，字段沿用老习惯")七、四个只读接口，字段沿用老习惯

开放接口一共 4 个，全是 GET，全部只读：

接口| 作用| 主要参数  
---|---|---  
`/v1/all`| 文章流| `start`、`end`、`rule`、`site_id`、`only_summarized`  
`/v1/friends`| 友链列表| —  
`/v1/post`| 某站点的文章| `site_id`（必填）、`num`  
`/v1/stats`| 统计概览| —  
  
排序 `rule` 支持 `created`（发布时间）、`updated`（更新时间）、`score`（推荐分）三种。想做一个「本周最值得读」的榜单，把 `rule` 换成 `score` 就行，不用另写接口。

出错统一返回 `{"detail": "..."}`，中文说明，不甩堆栈：401 是 Key 缺失或已重置、422 是参数不合法并附具体字段、429 是限流、500 可以到服务状态页看。接口清单由 `app.openapi()` 实时生成，`/openapi.json` 可以直接丢给代码生成器，不会出现「文档写的和实际跑的」对不上。

## [](https://dusays.com/posts/898/#九、几个真踩过的坑 "九、几个真踩过的坑")九、几个真踩过的坑

**CORS 预检** 。浏览器直接调跨域接口，服务端得把博客域名加进白名单，否则预检就被拦下，页面一直卡在「正在连接」。如果不想动服务端配置，就在自己博客里加一层反向代理，变成同源请求。我选的是前者，加完用真实浏览器请求验一遍，别只看 `curl`——`curl` 不发预检。

**主题样式会盖掉自定义样式** 。页面挂在主题的 Markdown 容器里，正文的 `p`、`div`、`a` 都带着主题规则。字号被顶掉、多行截断失效、层间距莫名多出 20px，全是特异性不够。解法是把正文区所有选择器加上容器前缀提权，别偷懒写 `> div` 这种宽泛清零规则——它会把子元素自己设的间距一起干掉。

**明文 Key 别放进公开仓库** 。前端直接调接口，Key 必然暴露在页面源码里。只读 Key 风险可控，但更稳妥的做法是走一层反代，由服务端注入请求头。这个我还没改，先记着。

**别假设摘要一定有** 。`summary` 和 `score` 为 `null` 是常态，前端必须能优雅隐藏。我第一版没做这层判断，列表里出现了一堆空块。

家里的树莓派跑着一堆小东西：备份脚本、服务巡检、下载器、几个定时任务。每个都想在出事的时候通知我一下，于是各个脚本里散落着不同的发消息代码——这个直接调钉钉 webhook，那个攒了个 Telegram bot，还有一个硬编码了 Bark 的 URL。token 就这么散落在各个脚本的源码里，想换个渠道就得挨个改。装个现成的推送网关当然可以，但我的要求有点苛刻：树莓派 3B+ 只有 1GB 内存，上面已经跑着一堆东西，网关得安安静静待在角落里，不跟别人抢。

所以我写了[蜂鸟 Hummingbird __](https://github.com/canyuda/hummingbird)：一个自托管的消息推送网关，整个项目就一个 3MB 的二进制文件（Web 管理台已经内嵌在里面），常驻内存 7.5MB。脚本、定时任务、监控系统只需要调一个 HTTP 接口，剩下的事——模板渲染、多渠道分发、代理、日志——全部交给它。

---|---|---  
常态空闲 RSS| < 8 MB| **7.5 MB**  
二进制体积（含内嵌前端）| < 10 MB| **3.0 MB**

单元测试| —| 12/12 通过  
端到端自动化| —| 49/49 通过  
  
支持的渠道：钉钉机器人、企微机器人、企微应用（可直达个人微信）、飞书机器人、Telegram、Bark、ntfy、通用 webhook。每个渠道还能单独配 HTTP/SOCKS5 代理——比如 Telegram 走本机的 mihomo 出站，国内渠道直连。

## [](https://canyuda.top/posts/2026111544399/#先看用起来什么样) 先看用起来什么样

管理台上把三样东西配好：渠道（各家 webhook/token）、模板（`{{var}}` 占位符加默认值）、任务（把"哪个模板发到哪些渠道"绑定起来）。任务创建时发一个 token，之后所有推送只认这个 token。首次启动在 stdout 打印 admin 初始密码（只打一次），登录后强制改密：

这是蜂鸟最核心的设计：**调用方永远不能指定渠道** 。一个巡检脚本拿到的 token 只能把"巡检"模板发到它绑定的那几个渠道，别的什么都干不了。token 泄露了，爆炸半径就是"多发几条巡检消息"。

## [](https://canyuda.top/posts/2026111544399/#设计文档改了八版每一版都在砍东西) 设计文档改了八版，每一版都在砍东西

这个项目动代码之前先写了设计文档，开发过程中改了八版。回头看，八版修订记录的主要是砍掉了什么：

  * **v0.2，砍掉 async runtime** 。第一版设计是标准操作：tokio + axum + reqwest。写完算了一下内存账，光 tokio 的 4 个 worker 线程栈加调度器就要吃掉好几 MB，而我这个网关的并发量是什么？管理台偶发的几个请求，加上偶尔来的一条推送。把整条异步栈换成 tiny_http + ureq + std 线程，空闲 RSS 目标直接从 15MB 砍到 8MB。
  * **v0.3，砍掉内置定时消息** 。本来想做个定时推送功能，后来想想这是重新发明 cron——树莓派上现成的 crontab 调一下 push API 就完了。少一个常驻线程、一张表、一整套错过补发逻辑，管理台还少一整块 UI。
  * **v0.3，砍掉多用户** 。这东西就跑在我自己家里，多用户体系纯属自嗨。不过 schema 里还是留了 `user_id` 列，真有多方需求那天不用痛苦迁移。
  * **v0.6，砍掉自安装** 。曾计划 `hummingbird install` 一条命令注册成 systemd 服务，后来收敛成：交付物就一个二进制，无参数前台运行，服务化给你 unit 模板文档自己配。工具不做超出本职的系统改动。
  * **v0.8，任务模型重构** 。最早 token 是独立的一张表，调用时要指定发哪些渠道。改成了现在的任务模型：任务绑定"模板→渠道组"，渠道信息在服务端收敛，token 权限跟着绑定走。这版是重构不是砍功能，但动力一样——让 token 的权限边界更小。

每一条裁剪后面都有一个共同的判断：**这是在解决谁的问题** 。SSO、集群、多租户，这些在别的系统里是正经需求，在我这个"给一台树莓派用的推送网关"里就是包袱。单实例不是缺陷，是特性。

    pub fn render(template: &str, vars: &serde_json::Value) -> String {  
        let mut out = String::with_capacity(template.len());  
        let mut rest = template;

            let after = &rest[start + 2..];

                Some(end) => {  
                    let key = after[..end].trim();

                }  
                None => {

                }

## [](https://canyuda.top/posts/2026111544399/#一次推送在蜂鸟内部的旅程) 一次推送在蜂鸟内部的旅程
    
    
    flowchart LR    A[调用方  
    脚本 / cron / 监控] -->|Bearer token| B["/api/push"]    B --> C[任务绑定解析  
    模板 → 渠道组]    C --> D[" 模板渲染"]    D --> E1[钉钉]    D --> E2[企微]    D --> E3[飞书]    D --> E4[Telegram  
    经 mihomo]    E1 & E2 & E3 & E4 --> F[(push_logs

每个渠道实现同一个 20 行的 trait，全部是出站 HTTP：钉钉 webhook 要 HMAC-SHA256 加签（约 40 行），企微应用要管 access_token 的获取缓存和过期刷新（唯一有状态的渠道，约 120 行），Bark 和 ntfy 一个 GET 就完事（约 20 行），通用 webhook POST JSON 兜底。出站统一 10 秒超时，渠道官方限速（钉钉/企微每分钟约 20 条）错误如实返回，不内置重试——重试是调用方 cron 下一轮的事。

渠道级代理的实现也简单：按 proxy URL 缓存 ureq Agent，常态就两个 Agent——直连一个、mihomo 一个，keep-alive 复用连接，不为每条推送重建。`via_proxy` 字段写进推送日志，Telegram 抽风时一眼能看出是不是代理的问题。

## [](https://canyuda.top/posts/2026111544399/#内存是抠出来的不是架构出来的) 内存是抠出来的，不是架构出来的

架构图再漂亮，7.5MB 也是一个个细节抠出来的。开发中印象比较深的几处：

**argon2 参数必须调** 。密码哈希用 argon2id 没争议，但 crate 默认参数 m=19MiB——每次登录瞬时申请 20MB 堆内存，对一个空闲 7.5MB 的进程来说太奢侈了。调到 m=8MiB/t=2/p=1，内网场景强度足够，登录峰值压到 +9MB 且转瞬即逝。

**SQLite 单连接加 Mutex** 。WAL 模式、`cache_size=-512`（512KB 页缓存）、`busy_timeout=5s`。这个量级上一个连接绰绰有余，连接池纯属浪费。推送日志攒批落库（1 秒或 20 条触发 flush），后台任务每天删一次超期日志（默认保留 90 天），避免高频写。

**消息体上限 64KB** ，超限拒绝；无常驻大 buffer。线程模型是主线程 accept、每连接短命线程、后台任务临时 spawn 完了就回收——没有任何常驻后台线程。

这些细节单独拿出来都不起眼，每一处省的不过是几百 KB 到几 MB，但空闲内存的预算就是这样一点点攒出来的。

## [](https://canyuda.top/posts/2026111544399/#测试怎么保证的) 测试怎么保证的

单元测试 12 个，覆盖模板渲染器的边界情况（未闭合括号、非字符串变量、相邻占位符）、各渠道的参数签名、URL 编码。真正的信心来自端到端测试 `tests/e2e.sh`：起服务、起一个本地 webhook 接收器，把认证、渠道、模板、任务、推送、日志、设置、安全边界（token 用错模板要 403、旧 token 重生成后要失效、暴力登录要锁账号）全部过一遍，最后连内存指标一起断言。发布时是 44 项，之后每修一个问题就补一条复现断言，现在 49 项。CI 里每次提交跑全套。

## [](https://canyuda.top/posts/2026111544399/#发布之后真实实例跑出来的问题) 发布之后：真实实例跑出来的问题

v0.1.0 发出去，部署到树莓派上实跑，头几天连着发了几个补丁版本。这些问题的共同点：写代码和跑 e2e 的时候全都发现不了，只有真实使用才暴露。

### [](https://canyuda.top/posts/2026111544399/#一个打码功能差点把渠道全废了) 一个打码功能差点把渠道全废了

这是最险的一个。安全设计里有一条：`GET /api/channels` 返回时对 secret 类字段打码，webhook 查询串脱敏成 `?***`，防止管理台泄露凭据。结果这个功能反噬了——打开渠道编辑弹窗，表单里填的是打码后的值；用户没改任何东西直接点保存，前端把 `***` 原样 PUT 回去，真实凭据被占位符覆盖，渠道当场失效。"我只是打开看了一眼"就把钉钉机器人弄坏了，而且没有任何报错。

修复放在服务端而不是前端：`channels_update` 检测到 secret 字段的值精确等于占位符时，保留库中原值；输入了新值才正常覆盖。前端改只能护住一个入口，API 层改才护得住所有调用方。e2e 为这个场景加了复现断言：打码回写后直查 SQLite 验证原值还在，且渠道测试消息仍能送达——断言总数从 46 项涨到 49 项。

教训记下来：**在接口的一边做防呆，就要检查另一边会不会被它绊倒** 。打码是给"看"的安全，回写是"改"的路径，两条路一交错就是数据丢失。

### [](https://canyuda.top/posts/2026111544399/#升级脚本的-set-e-陷阱) 升级脚本的 set -e 陷阱

v0.1.2 加了树莓派一键升级脚本（下面细说），CI 打包和升级脚本里都用了 `set -e` 想做到出错即停。真机上一跑发现问题：`set -e` 对管道只看最后一个命令的退出码，管道前面失败、后面"成功"的组合会静默继续。升级这种覆盖二进制的操作静默继续下去，坏一半的状态比直接报错难处理得多。修复是补上 `set -o pipefail`，顺手给 CI 产物加了 sha256 校验文件，升级脚本下载后先验哈希再替换。

### [](https://canyuda.top/posts/2026111544399/#刷新闪一下登录页) 刷新闪一下登录页

管理台登录后刷新页面，会先闪现登录页再跳回概览。原因朴素：前端只区分"已登录/未登录"两态，页面加载时要先调 `GET /api/auth/me` 确认会话，请求没回来之前被当成了"未登录"。修复是补上第三态"探测中"——me 没响应前既不渲染登录页也不渲染主界面，会话确认后再路由。一个小小的三态，线上观感完全不同。

### [](https://canyuda.top/posts/2026111544399/#管理台翻新和截图是怎么拍的) 管理台翻新，和截图是怎么拍的

v0.1.3 把管理台整体翻新了一轮：渠道/模板/任务的增删改全部弹窗化，浏览器原生 `confirm` 换成自定义确认弹窗，模板变量和任务绑定改成了可视化编辑器，概览页加了推送统计图表。这批文章里的截图就是翻新后的 v0.1.4 界面。

## [](https://canyuda.top/posts/2026111544399/#升级-备份-卸载) 升级、备份、卸载

## [#](https://exia.de5.net/p/cls-empty-slots#结论)结论

CLS 不是 0 的时候，第一反应都是去查图片有没有写宽高。我的图片早就补齐了 `width` / `height`，布局偏移还是有 **0.0176** 。

偏移来自三个空位：导航里的登录格、栏目条、标签条。它们的共同点是**HTML 到手时是空的，内容要等 JS 拉完接口才填** 。填进去的那一刻，下面所有东西重新排一遍。

位置| 桌面 1440| 移动 390  
---|---|---  
登录格 `#nav-user`| 整条导航左移 55px| 导航多折一行，+53px  
栏目条 + 标签条| 列表下推 40px| 列表下推 **182px**  
  
三处改成服务端直出后，移动端 4× CPU 降速下的 CLS 是 **0** 。

一句话记住：**首屏元素的高度和宽度，在 HTML 里就该是最终值。** 让 JS 去补，等于每次访问都先演一遍错版，再当着读者的面纠正。

## [#](https://exia.de5.net/p/cls-empty-slots#一-先分清哪些偏移是图片的)一、先分清哪些偏移是图片的

`layout-shift` 是 `PerformanceObserver` 里最不被重视的一个。它给的不是一个分数，而是每一次偏移的明细：变了多少、影响了哪几个元素。

js
    
    
    new PerformanceObserver((list) => {
      for (const e of list.getEntries()) {
        if (e.hadRecentInput) continue;          // 用户自己点出来的不算
        // e.sources 里每一项就是被推走的那个元素
        for (const s of e.sources) {
          console.log(e.value.toFixed(4), s.node?.className || s.node?.tagName, s.previousRect, s.currentRect);
        }
      }
    }).observe({ type: 'layout-shift', buffered: true });

改之前跑一遍，`sources` 里点名的不是 `img`，是 `#catbar`、`#tagbar`、`#nav-user` 这三个。分数小是因为被推的是列表容器，面积大、位移小；移动端那 182px 就没有这么客气了。

顺带排除了两个常见嫌疑：图片全都有宽高，`font-display` 也没问题（整站用系统字栈，`-apple-system` 那一套，没有 web font 交换）。

## [#](https://exia.de5.net/p/cls-empty-slots#二-51px-那一格)二、51px 那一格

`#nav-user` 在 HTML 里原来是个空 `<span>`。`app.js` 拿到 `/api/me` 之后才知道该填「登录」还是「后台」，中间隔着一次网络往返。

填进去的瞬间，nav 多出一个有宽度的子项，整条导航往左让位：

视口| nav 宽度| 位移  
---|---|---  
1440×900| 415px → 360px| 左移 55px  
390×844| 高 366px → 419px| 多折一行，+53px  
  
55px 是「登录」那个链接的 51px 加上 nav 的 `gap: 4px`。窄屏更难看：nav 本来就在折行，多这一项正好越过一行的边界，整条导航从两行变三行，首屏内容整体下移 53px。

修法是别等：

js
    
    
    /* 匿名访客先填上真实的「登录」链接，不是占位符 */
    `<span id="nav-user"><a href="/login">登录</a></span>`

css
    
    
    /* span 不参与 flex 布局，里面的 <a> 才是 nav 的那个 item */
    #nav-user { display: contents; }
    /* 万一真的空了，也别留一个空盒子在那占位 */
    #nav-user:empty { display: none; }

`display: contents` 那条不是装饰。少了它，`<span>` 自己变成一个 flex item，宽度塌成 0、`gap` 也套两层，填进去之后间距全错。

## [#](https://exia.de5.net/p/cls-empty-slots#三-为什么不用固定宽度的骨架块)三、为什么不用固定宽度的骨架块

`width: 51px` 那种占位块看起来更"正统"，但它不是。

51 是测量值，不是常量。字号缩放、换成英文、文案改成一个字，宽度都会变。骨架块能盖住第一次偏移，等真实内容进来再跳一次——等于把一次错的尺寸换成另一次错的尺寸。

服务端直接输出真实内容，宽度是浏览器算出来的，天然准。这不需要额外查询：这个链接本来就是静态的，`/login` 永远存在。

还有个副作用是好的：JS 挂了或者被拦了，导航仍然完整。骨架块在 JS 失效时就是一块空白。

## [#](https://exia.de5.net/p/cls-empty-slots#四-两个筛选条-40px-和-182px)四、两个筛选条：40px 和 182px

`#catbar`（栏目）和 `#tagbar`（标签云）是同一个病：两个空 div，等 `app.js` 拉完 `/api/categories` 才 `innerHTML`。

把这两块清空再量列表位置，差值是实际被推走的距离：

视口| 列表被下推  
---|---  
1440| 40px  
390| 182px  
  
移动端 182px 已经超过屏高的五分之一——这是读者打开页面后第一眼看到的东西在跳。

这两块的数据本来就在并行取（栏目计数、标签云和文章列表是三个独立的查询），在模板渲染阶段直接输出，零额外查询：

js
    
    
    // 三个 Promise 一起发，谁也不等谁
    const [list, counts, tags] = await Promise.all([listP, catCounts(env), tagsData(env.DB)]);
    body = renderCats(body, counts, tags);   // 服务端就把 HTML 写好

客户端那边只剩一件事：把当前栏目/标签标成选中态。不再建 DOM，也不会撑高容器。

## [#](https://exia.de5.net/p/cls-empty-slots#五-已登录的访客为什么不-ssr)五、已登录的访客为什么不 SSR

不能。HTML 是全站共享边缘缓存的，把用户名塞进去会串号——A 打开页面拿到 B 的登录态。

所以只有匿名态进 HTML，`app.js` 到了再替换**同一个 item 的内容** 。替换不新增 flex item，位移从「整条导航重排」降到几个像素，而且发生在页面已经可交互之后。

这里有个取舍要说清：登录态的宽度确实和匿名态不完全一样（「登录」51px，登录后是后台入口那一组）。但这条位移只在已登录访客身上发生一次，量级是几个像素，不会让读者觉得页面在动。

## [#](https://exia.de5.net/p/cls-empty-slots#六-改完的数字)六、改完的数字

移动端用 4G 模拟（1.6Mbps / 150ms RTT）+ 4× CPU 降速，桌面 1440×900：

指标| 桌面| 移动  
---|---|---  
LCP| 224 ms| 760 ms  
CLS| 0| 0  
INP| 32 ms| 16 ms  
TTFB| 51 ms| 152 ms  
  
CLS 从 0.0176 到 0 只改了渲染位置，没有动资源。LCP 和 INP 是同一批改动里的附带结果：首屏不再等接口，图片变成 `<picture>` 协商格式。

## [#](https://exia.de5.net/p/cls-empty-slots#七-边界)七、边界

  1. **骨架块不是不能用** ，它适合「真实内容要慢查询才拿得到」的场景。但骨架的尺寸必须等于最终尺寸，否则只是把偏移从一次变成两次。这个站的三个位置都是数据已经在手上，所以直接输出更好。
  2. **正文图片仍然是最常见的偏移源** 。这三处改完不代表 CLS 一定归零，`width` / `height` 少一个就前功尽弃。我这边的图是从上传时就量好尺寸拼进 URL 的，渲染时写成属性再把参数剥掉。
  3. **登录态替换仍然有位移** 。想彻底消掉就得给两种状态同一个宽度，代价是一个很宽的登录按钮或者一个很窄的后台入口，不值得。
  4. **`hadRecentInput` 要跳过**。用户点了按钮导致的下拉展开不算 CLS，不跳过的会把自己吓一跳。

## [#](https://exia.de5.net/p/cls-empty-slots#一条清单)一条清单

下次查 CLS，按这个顺序：

  1. 先抓 `layout-shift` 的 `sources`，看被推的到底是哪个元素。别猜。
  2. 该元素的 HTML 到手时是不是空的？空的就是病根。
  3. 数据是否已经在并行查询里？在，就挪到服务端输出。
  4. 只有拿到数据必须等一次往返、且快不起来的时候，才用骨架块，并且让骨架尺寸等于最终尺寸。
  5. 改完分别量窄屏和宽屏。同一个空位在宽屏是横向 55px，在窄屏是折行多出 53px——两个数不是一回事。

2026年秋季动画整体乏善可陈，不过一部女性向作品，「你好，我是受心上人所托来做恋爱药的魔女。」却得到了部分观众的关注与好评，令人意外。揭开神秘的面纱，其实它本身就是一部不错的作品，不需要加上“女性向”这类限定词来突出它的优秀。

## diomedéa的个性

「你好，我是受心上人所托来做恋爱药的魔女。」是一部典型的“现代diomedéa风味”作品，有稳定而温和的人物设计，有大致正常、有瑕疵但不多的画面，也有很多Q版形象，还有大量的心理活动描写。最终呈现给观众的，是一部相当有辨识度、虽然称不上顶级，但肯定在平均线之上的动画。

我个人非常喜欢diomedéa的行事风格。对于处理起来有难度的部分，不要硬撑，老老实实使用3D（或者幸运地获得实机画面）；合理安排特写与Q版形象的使用，既能节约作画资源，又不会明显影响观感；剧情大纲放心交给渡航，他能处理好大部分故事，还很擅长处理许多动画都做不好的心理活动描写。

![无语](https://xeonzilla.top/images/9fc054beed13dd5f.avif) 无语 

我在[「感谢对战。 ～大小姐才不玩格斗游戏～」](https://xeonzilla.top/tai-ari-deshita/)的观后感中提到过，diomedéa正在围绕几位核心人物形成一套有特色的制作班子，本作的核心制作人员中就有不少熟悉的身影。虽说稳定的制作团队不一定代表稳定的作品质量，但是动画公司“个性”的形成、粉丝群体的聚集，对diomedéa都不是坏事。

至少对我而言，目前的diomedéa已经渐渐有了和P.A.WORKS、CloverWorks等公司一样的地位。我期待的是这家公司（或其中的某个制作组）的下一部作品，而不是下一部作品究竟会是什么样子，因为预期已经稳定：我知道大概能看到怎样的画风、怎样的叙事风格。当然，呈现出超预期的作品会让我更加惊喜。

diomedéa目前处在一个比较尴尬的位置，既没有足够的产能和稳定的企划来源，无法做到每季度都有新作；也不是那种每年登场一次的真正的“小众精品厂”。我还是希望diomedéa能够稳住阵脚，将重心放在打磨作品上。只要产出精良的动画，自然会有很多动画观众记住这个制作公司。

## 有温度的视角

一直以来，我都很惧怕女性向作品中的心理活动，因为这些戏码中的大多数要么扭捏造作，要么放弃大脑。但是「你好，我是受心上人所托来做恋爱药的魔女。」中的内心戏码却让我感到非常享受，甚至可以说是本作的核心卖点之一。

女主的内心活动主要分为两个部分，一是对自己的自卑、不自信，二是对男主的各种欲望。这种“我喜欢他，但是我配不上他”的心理非常真实，也和女主各种回避却又渴望接近的举动相匹配。观众能从她的内心活动中感受到“她是一个活生生的人”，而不是“乙女游戏中的量产女主角”。

仅仅是窥视女主的内心，多少会让我这位男性观众感到一丝尴尬，但是本作还罕见地补充了男主的视角，让这些心理活动有了别样的风味。

![被撤下的桌布，消失的痕迹](https://xeonzilla.top/images/e7cce13ecd2505c4.avif) 被撤下的桌布，消失的痕迹 

男主的视角全部出现在女主之后，作为对女主内心活动的对应与回应。与女主一开始便暗恋男主不同，男主对女主的感情是在日常相处中逐渐萌生的。两种不同风格的关系递进，给观众带来了很多新鲜感。

两位角色其实都相当不善言辞，或者说比较内向。我们总能看到他们言行不一，又暗戳戳地在心里自我斗争。这类“阴湿”的心理活动是渡航的拿手好戏，两人表面上风平浪静，内心却波涛汹涌，再加上非对称的误解与回应，形成了一加一大于二的奇妙效果。

我曾经以为自己不会喜欢看女性向作品中男性角色的内心活动，但是最近的几部作品都在动摇这一看法，尤其是本作。没有心理活动，很多男性角色的爱情显得是那么苍白无力，尤其是以乙女游戏为背景的故事，只要女主登场，所有男性角色就会毫无理由地、死心塌地地爱上她。

然而本作不是。我们可以从男主的视角清晰地感受到他自身的变化：从简单地委托魔女，到渐渐参与她的生活、投入自己的感情，再到开始感到困惑与挣扎，呈现出一条清晰的、从陌生到坠入爱河的轨迹。

有温度的视角塑造了鲜活的角色，这是我觉得本作优秀的地方。本作很幸运，遇到了diomedéa和渡航，得以保留这一大特色。说不定渡航还为此增加了心理描写的篇幅。

## 新的时代

上个季度的「与奔驰于透明之夜的你，谈一场看不见的恋爱。」给我们带来了难忘的观影体验，其中一个重要原因就是它的原作仅有两卷，动画的故事因此相当完整。很巧的是，本作的原作同样只有两卷小说，而且已经完结。

![测试恋爱药](https://xeonzilla.top/images/19fd3da7762dcc36.avif) 测试恋爱药 

原作已经完结，在当下反而成为一种优势，因为新时代的观众往往更在意作品的细节与完整性。对于过于开放的故事，或是试图以节奏、速度掩盖逻辑漏洞和细节粗糙的作品，观众更容易提出批评。在这样的背景之下，已经完结且小巧精悍的作品自然成为动画化的不二之选。短小的篇幅更容易保留完整的故事信息，起承转合也自然流畅，不用担心动画要在哪里收尾、删除哪些次要信息。

这是一个既好又坏的时代。动画监督与脚本家的整体创作水准似乎有所下降，过剩的动画产能加上枯竭的原作资源，使得我们很难再见到跨时代的原创或改编动画作品；与此同时，动画续作的消息却比以往来得更快，甚至不少十几年前的老作品也迎来了复活。另一方面，商业价值不佳的中篇、短篇作品也获得了更多的动画化机会，让我们得以看到不少潜藏的优秀作品。

很难说这样的时代是好是坏，不过如果有更多类似「与奔驰于透明之夜的你，谈一场看不见的恋爱。」与「你好，我是受心上人所托来做恋爱药的魔女。」的作品，我不介意多看几部。

人都有习惯，有路径依赖，尤其是有了一定年纪的人，比如我这种中年人，走常走的路，吃常吃的饭，见常见的人，哪怕软件都只用常用的软件，待在自己的舒适区，可能是为了节省大脑的思考时间，可以直接利用长年积累的经验吧。

  * 我此刻在写文章时用的软件，也从用了好多年的Notepad++转到了VS Code，发现这款软件似乎更强大，还跨平台。

##  [__](https://aisurf.cc/clash-protocols-guide/#先搞懂：这些协议在对抗什么)[](https://aisurf.cc/clash-protocols-guide/#先搞懂：这些协议在对抗什么 "先搞懂：这些协议在对抗什么")先搞懂：这些协议在对抗什么

所有翻墙协议解决的都是同一件事：**让你的流量在网络审查设备眼里看起来「正常」** 。

审查系统（GFW）识别代理流量主要靠两招——一是「深度包检测」（DPI），拆开数据包看特征；二是「主动探测」，主动连你的代理服务器，看它的反应像不像代理。协议的进化史，就是一部和这两招的缠斗史：早期协议只管加密，后来加密不够了要伪装，伪装不够了要「借真实的网站当幌子」。

理解这条主线，下面每个协议的定位就都好懂了。

##  [__](https://aisurf.cc/clash-protocols-guide/#主力组：Trojan、VLESS、Reality)[](https://aisurf.cc/clash-protocols-guide/#主力组：Trojan、VLESS、Reality "主力组：Trojan、VLESS、Reality")主力组：Trojan、VLESS、Reality

这三个是 2026 年机场订阅的绝对主力，也是新手真正需要分清的三个。

###  [__](https://aisurf.cc/clash-protocols-guide/#Trojan：把自己扮成普通网站的老兵)[](https://aisurf.cc/clash-protocols-guide/#Trojan：把自己扮成普通网站的老兵 "Trojan：把自己扮成普通网站的老兵")Trojan：把自己扮成普通网站的老兵

Trojan 的思路一句话就能说明白：**既然审查设备放行 HTTPS，那我就让代理流量变成 HTTPS** 。

  * 基于 TLS 1.3 建连，配一张真域名证书，在外界看来就是访问一个普通网站
  * 服务端可以直接和 Nginx 这类 Web 服务器共存——探测的人真去访问，看到的是个正常网页
  * 配置不算复杂，Let’s Encrypt 免费证书就能跑起来

优点是稳：流量特征和正常 HTTPS 访问一致，日常用几乎不会被针对。缺点是它「像」一个网站，审查方如果持续观察流量行为模式，理论上仍有识别空间——这就引出了下面的 Reality。

###  [__](https://aisurf.cc/clash-protocols-guide/#VLESS：把加密外包给-TLS-的轻量选手)[](https://aisurf.cc/clash-protocols-guide/#VLESS：把加密外包给-TLS-的轻量选手 "VLESS：把加密外包给 TLS 的轻量选手")VLESS：把加密外包给 TLS 的轻量选手

VLESS 是 V2Ray 家族里 VMess 的减重版。它的设计有点反直觉：**协议本身不加密** 。

听起来离谱，其实是想明白了——既然大家最后都要套 TLS，那协议内部再加密一层就是重复劳动。VLESS 把加密完全交给 TLS/XTLS，自己只做最轻量的转发：

  * 去掉了加密和状态机制，握手开销更小，性能比 VMess 好
  * 必须配 TLS 用，裸奔等于明文
  * 支持 XTLS Vision 流控，专门优化代理场景下的 TLS 转发效率

和 VMess 的核心区别就一条：VMess 自己加密（中等伪装），VLESS 把这活儿全交给 TLS（强伪装、更高性能）。新机场新节点，基本都从 VMess 迁到 VLESS 了。

###  [__](https://aisurf.cc/clash-protocols-guide/#Reality：抗封锁天花板)[](https://aisurf.cc/clash-protocols-guide/#Reality：抗封锁天花板 "Reality：抗封锁天花板")Reality：抗封锁天花板

Reality 是 Xray 项目推出的协议，思路比 Trojan 更狠：**不是「伪装成一个网站」，而是「真的去连一个网站」** 。

  * 基于 TLS 1.3 + X25519，握手时「借用」一个公网上真实存在的大站（比如某科技巨头的官网，要求支持 TLS 1.3 和 HTTP/2）当门面，SNI 填的就是那个真站的域名
  * 主动探测打过来，流量会被转给那个真实网站，探测者看到的是真网页——不是「像」，是真
  * 不需要自己持有域名和证书，服务端配置反而比 Trojan 省事

代价是客户端门槛：Reality 需要 Xray 或 Mihomo 内核支持，老 Clash 客户端连不上。2026 年它已经是强审查环境里公认的最强协议，新机场宣传页上「支持 Reality」基本是标配卖点。

##  [__](https://aisurf.cc/clash-protocols-guide/#特殊场景组：Hysteria2、TUIC)[](https://aisurf.cc/clash-protocols-guide/#特殊场景组：Hysteria2、TUIC "特殊场景组：Hysteria2、TUIC")特殊场景组：Hysteria2、TUIC

这两个和上面所有协议走的不是一条路——它们基于 UDP 的 QUIC 协议栈，专攻**丢包和高延迟** 。

###  [__](https://aisurf.cc/clash-protocols-guide/#Hysteria2)[](https://aisurf.cc/clash-protocols-guide/#Hysteria2 "Hysteria2")Hysteria2

为烂网络而生：移动网络、跨境高峰期这种丢包严重的环境，TCP 系协议丢包就退避降速，越卡越慢。Hysteria2 反着来——用自研的 Brutal 拥塞控制，按你设定的带宽硬发，丢包不退让，烂网络下的速度表现一骑绝尘。打游戏（Steam、战网）、跨境视频通话这类对延迟敏感的场景是它的舒适区。

###  [__](https://aisurf.cc/clash-protocols-guide/#TUIC)[](https://aisurf.cc/clash-protocols-guide/#TUIC "TUIC")TUIC

同样是 QUIC 系，主打多路复用和 0-RTT 建连。和 Hysteria2 的差别在脾气：TUIC 用相对标准的拥塞控制，来得温和，长连接下波动小；Hysteria2 的 Brutal 更猛也更容易触发运营商 QoS。日常体验两者接近，选哪个主要看你家机场提供了哪个。

**共同的前提** ：你的网络环境得放行 UDP。部分公司网络、校园网会把 UDP 掐死，这种情况 QUIC 系协议直接没戏，老老实实用 Trojan/VLESS。另外这两个协议同样需要 Mihomo 内核客户端支持。

##  [__](https://aisurf.cc/clash-protocols-guide/#老将组：VMess、Shadowsocks)[](https://aisurf.cc/clash-protocols-guide/#老将组：VMess、Shadowsocks "老将组：VMess、Shadowsocks")老将组：VMess、Shadowsocks

###  [__](https://aisurf.cc/clash-protocols-guide/#VMess)[](https://aisurf.cc/clash-protocols-guide/#VMess "VMess")VMess

V2Ray 的元老协议，内置加密（AES-128-GCM / ChaCha20）、带时间戳防重放，巅峰期（2017-2021）是机场的绝对主力。现在地位被 VLESS 取代——伪装能力中等，无 TLS 时容易被主动探测识别。存量节点还很多，能用，但新部署没人再选它。

拿到 vmess:// 开头的链接，导入方法在 [Windows 翻墙教程](https://aisurf.cc/windows-internet-guide/) 里有完整截图演示。

###  [__](https://aisurf.cc/clash-protocols-guide/#Shadowsocks（SS）)[](https://aisurf.cc/clash-protocols-guide/#Shadowsocks（SS） "Shadowsocks（SS）")Shadowsocks（SS）

2012 年出生的轻量级加密代理，整个协议简单到惊人，也因此能在路由器、老旧设备上跑到飞起。问题还是老问题：太简单，特征被研究透了，严格审查环境下容易被识别。现在它的合理定位是**移动设备和路由器上的轻量方案** ，别拿它当主力翻墙通道。

##  [__](https://aisurf.cc/clash-protocols-guide/#退场组：SSR、HTTP-SOCKS5)[](https://aisurf.cc/clash-protocols-guide/#退场组：SSR、HTTP-SOCKS5 "退场组：SSR、HTTP/SOCKS5")退场组：SSR、HTTP/SOCKS5

**SSR（ShadowsocksR）** ：SS 的魔改版，加了协议混淆和流量模拟，早年抗封锁确实强过 SS。但它是私有分支、争议大、停更多年，新机场新客户端都在弃用。还看到教程推荐 SSR 的，直接关掉，内容至少五年没更新了。

**HTTP/HTTPS 代理** ：最古老的形态，只能转发 Web 流量，不支持 UDP，裸 HTTP 还是明文。企业内网、临时应急凑合用，翻墙就别想了。

**SOCKS5** ：通用转发协议，支持 UDP，但完全不加密不伪装。它的正业是本地转发、内网中转——比如给某个不认代理的软件单独走通道，很多软件的「网络设置」里那个 SOCKS5 填写框说的就是它。

**打游戏的** ：Hysteria2 或 TUIC，前提确认网络放行 UDP。游戏对丢包比对带宽敏感得多，QUIC 系的抗丢包优势体感明显。

**路由器/老设备的** ：Shadowsocks 还能再战。设备性能跑不动重型协议的场景，SS 的轻量反而是优点。

##  [__](https://aisurf.cc/clash-protocols-guide/#FAQ)[](https://aisurf.cc/clash-protocols-guide/#FAQ "FAQ")FAQ

**Clash Meta（Mihomo）和原版 Clash 有什么区别？**

原版 Clash 内核 2023 年就停止维护了，不支持 Reality、Hysteria2、TUIC 这些新协议。Mihomo（原 Clash Meta）是社区接棒的内核，主流协议全支持，现在的主流客户端——Clash Verge Rev、ClashMeta for Android——内置的都是它。还在用老内核客户端的，建议直接换。

**为什么我的 VLESS 节点连不上？**

按顺序查三样：servername（SNI）和 UUID 是否复制完整、端口有没有填错、TLS 有没有开。VLESS 本身不带加密，TLS 关了等于裸奔，服务端会直接拒绝握手。都对着还不行，就是机场服务端的问题，找客服。

**哪些协议抗封锁最强？**

Reality 第一，抓包都难和真实 HTTPS 区分；Trojan 和 VLESS+TLS 紧随其后，流量特征和普通网站访问一致。这三类也是 2026 年机场订阅的绝对主力。

**Shadowsocks 现在还能用吗？**

能用，但只适合轻度场景。SS 协议特征已被研究得很透，严格审查环境下容易被针对。移动设备、路由器挂 SS 做日常浏览问题不大，当主力翻墙通道就别指望它扛封锁了。

**机场默认给我的协议，需要自己换吗？**

基本不用。靠谱机场的默认配置就是 Trojan 或 VLESS（新机场多为 VLESS+Reality），直接用就是最优解。协议是机场服务端定的，你客户端这边只是「能连」和「连不上」的区别，换协议不解决速度慢的问题——速度看节点质量和线路，线路分直连、中转、专线三种，怎么选展开在 [机场线路怎么选](https://aisurf.cc/airport-lines-guide/)。

## [#](https://miu.sryze.cc/p/cls-empty-slots#结论)结论

CLS 不是 0 的时候，第一反应都是去查图片有没有写宽高。我的图片早就补齐了 `width` / `height`，布局偏移还是有 **0.0176** 。

偏移来自三个空位：导航里的登录格、栏目条、标签条。它们的共同点是**HTML 到手时是空的，内容要等 JS 拉完接口才填** 。填进去的那一刻，下面所有东西重新排一遍。

位置| 桌面 1440| 移动 390  
---|---|---  
登录格 `#nav-user`| 整条导航左移 55px| 导航多折一行，+53px  
栏目条 + 标签条| 列表下推 40px| 列表下推 **182px**  
  
三处改成服务端直出后，移动端 4× CPU 降速下的 CLS 是 **0** 。

一句话记住：**首屏元素的高度和宽度，在 HTML 里就该是最终值。** 让 JS 去补，等于每次访问都先演一遍错版，再当着读者的面纠正。

## [#](https://miu.sryze.cc/p/cls-empty-slots#一-先分清哪些偏移是图片的)一、先分清哪些偏移是图片的

`layout-shift` 是 `PerformanceObserver` 里最不被重视的一个。它给的不是一个分数，而是每一次偏移的明细：变了多少、影响了哪几个元素。

js
    
    
    new PerformanceObserver((list) => {
      for (const e of list.getEntries()) {
        if (e.hadRecentInput) continue;          // 用户自己点出来的不算
        // e.sources 里每一项就是被推走的那个元素
        for (const s of e.sources) {
          console.log(e.value.toFixed(4), s.node?.className || s.node?.tagName, s.previousRect, s.currentRect);
        }
      }
    }).observe({ type: 'layout-shift', buffered: true });

改之前跑一遍，`sources` 里点名的不是 `img`，是 `#catbar`、`#tagbar`、`#nav-user` 这三个。分数小是因为被推的是列表容器，面积大、位移小；移动端那 182px 就没有这么客气了。

顺带排除了两个常见嫌疑：图片全都有宽高，`font-display` 也没问题（整站用系统字栈，`-apple-system` 那一套，没有 web font 交换）。

## [#](https://miu.sryze.cc/p/cls-empty-slots#二-51px-那一格)二、51px 那一格

`#nav-user` 在 HTML 里原来是个空 `<span>`。`app.js` 拿到 `/api/me` 之后才知道该填「登录」还是「后台」，中间隔着一次网络往返。

填进去的瞬间，nav 多出一个有宽度的子项，整条导航往左让位：

视口| nav 宽度| 位移  
---|---|---  
1440×900| 415px → 360px| 左移 55px  
390×844| 高 366px → 419px| 多折一行，+53px  
  
55px 是「登录」那个链接的 51px 加上 nav 的 `gap: 4px`。窄屏更难看：nav 本来就在折行，多这一项正好越过一行的边界，整条导航从两行变三行，首屏内容整体下移 53px。

修法是别等：

js
    
    
    /* 匿名访客先填上真实的「登录」链接，不是占位符 */
    `<span id="nav-user"><a href="/login">登录</a></span>`

css
    
    
    /* span 不参与 flex 布局，里面的 <a> 才是 nav 的那个 item */
    #nav-user { display: contents; }
    /* 万一真的空了，也别留一个空盒子在那占位 */
    #nav-user:empty { display: none; }

`display: contents` 那条不是装饰。少了它，`<span>` 自己变成一个 flex item，宽度塌成 0、`gap` 也套两层，填进去之后间距全错。

## [#](https://miu.sryze.cc/p/cls-empty-slots#三-为什么不用固定宽度的骨架块)三、为什么不用固定宽度的骨架块

`width: 51px` 那种占位块看起来更"正统"，但它不是。

51 是测量值，不是常量。字号缩放、换成英文、文案改成一个字，宽度都会变。骨架块能盖住第一次偏移，等真实内容进来再跳一次——等于把一次错的尺寸换成另一次错的尺寸。

服务端直接输出真实内容，宽度是浏览器算出来的，天然准。这不需要额外查询：这个链接本来就是静态的，`/login` 永远存在。

还有个副作用是好的：JS 挂了或者被拦了，导航仍然完整。骨架块在 JS 失效时就是一块空白。

## [#](https://miu.sryze.cc/p/cls-empty-slots#四-两个筛选条-40px-和-182px)四、两个筛选条：40px 和 182px

`#catbar`（栏目）和 `#tagbar`（标签云）是同一个病：两个空 div，等 `app.js` 拉完 `/api/categories` 才 `innerHTML`。

把这两块清空再量列表位置，差值是实际被推走的距离：

视口| 列表被下推  
---|---  
1440| 40px  
390| 182px  
  
移动端 182px 已经超过屏高的五分之一——这是读者打开页面后第一眼看到的东西在跳。

这两块的数据本来就在并行取（栏目计数、标签云和文章列表是三个独立的查询），在模板渲染阶段直接输出，零额外查询：

js
    
    
    // 三个 Promise 一起发，谁也不等谁
    const [list, counts, tags] = await Promise.all([listP, catCounts(env), tagsData(env.DB)]);
    body = renderCats(body, counts, tags);   // 服务端就把 HTML 写好

客户端那边只剩一件事：把当前栏目/标签标成选中态。不再建 DOM，也不会撑高容器。

## [#](https://miu.sryze.cc/p/cls-empty-slots#五-已登录的访客为什么不-ssr)五、已登录的访客为什么不 SSR

不能。HTML 是全站共享边缘缓存的，把用户名塞进去会串号——A 打开页面拿到 B 的登录态。

所以只有匿名态进 HTML，`app.js` 到了再替换**同一个 item 的内容** 。替换不新增 flex item，位移从「整条导航重排」降到几个像素，而且发生在页面已经可交互之后。

这里有个取舍要说清：登录态的宽度确实和匿名态不完全一样（「登录」51px，登录后是后台入口那一组）。但这条位移只在已登录访客身上发生一次，量级是几个像素，不会让读者觉得页面在动。

## [#](https://miu.sryze.cc/p/cls-empty-slots#六-改完的数字)六、改完的数字

移动端用 4G 模拟（1.6Mbps / 150ms RTT）+ 4× CPU 降速，桌面 1440×900：

指标| 桌面| 移动  
---|---|---  
LCP| 224 ms| 760 ms  
CLS| 0| 0  
INP| 32 ms| 16 ms  
TTFB| 51 ms| 152 ms  
  
CLS 从 0.0176 到 0 只改了渲染位置，没有动资源。LCP 和 INP 是同一批改动里的附带结果：首屏不再等接口，图片变成 `<picture>` 协商格式。

## [#](https://miu.sryze.cc/p/cls-empty-slots#七-边界)七、边界

  1. **骨架块不是不能用** ，它适合「真实内容要慢查询才拿得到」的场景。但骨架的尺寸必须等于最终尺寸，否则只是把偏移从一次变成两次。这个站的三个位置都是数据已经在手上，所以直接输出更好。
  2. **正文图片仍然是最常见的偏移源** 。这三处改完不代表 CLS 一定归零，`width` / `height` 少一个就前功尽弃。我这边的图是从上传时就量好尺寸拼进 URL 的，渲染时写成属性再把参数剥掉。
  3. **登录态替换仍然有位移** 。想彻底消掉就得给两种状态同一个宽度，代价是一个很宽的登录按钮或者一个很窄的后台入口，不值得。
  4. **`hadRecentInput` 要跳过**。用户点了按钮导致的下拉展开不算 CLS，不跳过的会把自己吓一跳。

## [#](https://miu.sryze.cc/p/cls-empty-slots#一条清单)一条清单

下次查 CLS，按这个顺序：

  1. 先抓 `layout-shift` 的 `sources`，看被推的到底是哪个元素。别猜。
  2. 该元素的 HTML 到手时是不是空的？空的就是病根。
  3. 数据是否已经在并行查询里？在，就挪到服务端输出。
  4. 只有拿到数据必须等一次往返、且快不起来的时候，才用骨架块，并且让骨架尺寸等于最终尺寸。
  5. 改完分别量窄屏和宽屏。同一个空位在宽屏是横向 55px，在窄屏是折行多出 53px——两个数不是一回事。
