某一天的时候，忽然觉得自己左手的小指以及无名指有些麻。跟对象聊到这件事情得到的答案是：你该吃降血脂药了，要不你挂个心血管的检查去开个单子看看？

当然，这个指标也不是凭空猜测的，源自于5月份的体检结果：

[![](https://zhongxiaojie.cn/wp-content/uploads/2026/11/微信图片_20261116094032_495_64.jpg)](https://zhongxiaojie.cn/wp-content/uploads/2026/11/微信图片_20261116094032_495_64.jpg)

不过对于这个结果，我是多少有些怀疑的。因为体检完貌似很多人的这几个指标都有问题。当时对象还提议说，应该吃降血脂药了。然而，我的想法是，不想吃药，我想继续锻炼，毕竟那时候体重刚刚降下来，可能身体也在适应。想着再坚持继续运动一段时间，下半年去齐鲁医院再查一次。这刚好也就凑到了这个时机了。

打开小程序，搜心血管内科的挂号时间，周一没号，周二没号，周三依然没号，终于周五下午有号了。当时我还调侃，说不定等到周五的时候就已经好了。

期间自己也问了下所谓的阿福，答复说可能跟长时间玩手机有关系，这个答案自己还是有些认同的，毕竟秋假那几天手机真的是用的贼多。个人习惯又是习惯左手拿手机，为了防止手机掉下来，小指会从底部托住手机，大概就是这个动作导致的。

毕竟，因为动作问题，之前也出现过一次类似的情况。在跑步机上边跑步边看视频，差点把脖子看废了。也不知道是哪个大聪明设计的跑机器上用个支架还允许放手机或者平板看视频。那个位置跑起来真的是脖子稍微不解释的可能都折了，毕竟那个高度还是得低头才能看到。所以，如果用跑步机的话千万不要边跑边看视频哦。

终于，到了周五，虽然有缓解，但是却没完全消失。还是按时到了医院，诊室外面，人来人往，心血管科室人真的不少。

『你是怎么了？』医生问道。

『我左手无名指和小指有点麻。』我答道。

『额，那你挂我这个科室可能用处不大。如果只是这两个指头的话不会是心血管的问题，如果是心血管问题这种麻木或者疼痛都是放射性的。例如胸口的放射性麻木或者疼痛，整个手臂的麻木或者疼痛。除了这两个地方有点麻，还有别的症状吗？有没有胸痛等症状。你挂我这个科，我的确是帮不了你，可以挂个脊柱科啊什么的，我这里来的基本都是急性心血管问题的，你这个可以换个科室看看。』

『没有，就是这两个。以前体检的时候血脂有点高，在想是不是血脂问题导致的。』

『不会的，血脂问题不会导致麻木，如果你想查的话可以给你开个单子查一下。』医生边说边拿起了听诊器，在胸口的不同地方听了下。继续说道：『你也不用查太多，主要就查个血脂就行了。不过下午抽血可能有的指标不是很准，你明天抽血？』

『嗯，我看看明天吧。』

『不过你要是明天抽血，复查的时候我排版不一定能排上。你看看结果需要复诊的话，看我哪天在再过来。』

『不要紧，我看看情况吧，不行的话我可以挂其他的科室，脊柱科，运动医学科之类的。』至此，医生给开出单子来，主要检查就三项。等二天一早再来医院抽血。

周六早上，天空又开始淅淅沥沥的下雨，看来新的一轮降温又要来了。八点前到医院，此时牌号抽血的已经排到了76号，前面还有8个人。虽然诊室还没上班，但是提前开好单子或者住院的已经开始抽血了。

上午抽血，下午三点以后出结果，还在想着什么时候去取单子的时候，对象提醒说手机上就能查看化验单了。果然，打开小程序，化验单已经躺在那里了。

[![](https://zhongxiaojie.cn/wp-content/uploads/2026/11/微信图片_20261116094031_494_64.jpg)](https://zhongxiaojie.cn/wp-content/uploads/2026/11/微信图片_20261116094031_494_64.jpg)

看来，自己这半年的运动真的没白费，上次体检的时候是5.12现在11.14刚好半年多一点点点的时间。

[![](https://zhongxiaojie.cn/wp-content/uploads/2026/11/微信图片_20261116102704_507_62.jpg)](https://zhongxiaojie.cn/wp-content/uploads/2026/11/微信图片_20261116102704_507_62.jpg)

最近在雨天开车出去的时候，总是感觉雨刷已经无法刷干净玻璃了，在夏天的时候就买了新的雨刷，却一直没换上，主要的问题在于自己不知道怎么让雨刷进入维护模式，让雨刷立起来。

晚上搜索，搜到的文章都和视频的操作步骤都没啥卵用，包括抖音搜索到的视频：

小艺甚至还很贴心了给找了一些操作视频，但是那些视频里面的操作，我照着做了根本没啥用。

实际上，要解锁雨刷臂正确的操作应该是：

1.车辆熄火状态，不要踩刹车，一键启动，自检完成，再次点击熄火。

2.将雨刷拨杆调到最下面，处于雨刷关闭档位。

3.不要踩刹车，按住拨杆的同时按下点火开关，按下开关的同时松开雨刷拨杆。

4.此时雨刷臂就立起来啦，换之前在雨刷臂下面点个毛巾或者别的东西，防止雨刷臂不小心落下来。

5.更换完雨刷臂，依然不要踩刹车，再次按启动，此时雨刷臂就自动复位啦。

Today, November 16, 2026, Bear Blog introduced its [official API](https://docs.bearblog.dev/api/), making posts, pages and blog settings accessible through a documented interface.

I wrapped these endpoints into **🍯 Bear Blog Skill** and [open-sourced it on GitHub](https://github.com/somkanel/bearblog-skill). With the skill installed in Codex, Claude Code or another tool that supports Agent Skills, you can ask the agent to manage your blog in natural language:
    
    
    $bearblog Create a draft from this Markdown file and add the notes tag.
    $bearblog List all drafts and scheduled posts.
    

In Claude Code, invoke it with `/bearblog`.

This article itself was published from my workflow using 🍯 Bear Blog Skill through the official Bear Blog API.

The skill covers all seven documented endpoints. It can create, read, update and delete posts or pages, publish and schedule content, and update the homepage, navigation, CSS and other supported blog settings. It also exports post bodies and settings. Search and bulk editing combine documented API calls.

It uses only Bear Blog's official public API, with no private protocols, undocumented endpoints or unofficial platform capabilities. A standalone command-line client, built entirely with the Python standard library, is included for use without an agent.

**Only paid Bear Blog plans can generate API keys** , under **Settings → API** in the dashboard. To use the skill, you need Python 3.9+ and a local configuration containing your API key and original Bear subdomain. Use the Bear subdomain even if your blog has a custom domain.

最近上线了两个小站：**yee.cx** 和 **puff.ee** 。它们不是Demo，是为了解决实际工作痛点做的工具，**全部代码** 由Agent生成，我聚焦需求梳理、边界校验和细节打磨。

**先说 yee.cx。**

挑域名、收老域名、排查站点的时候，一直很烦来回切工具：查Whois一个站，看DNS解析另一个，查域名过往建站记录还要单独去归档站点翻快照。数据源分散，核对起来耗时间。 其中最关键的痛点是**建站历史** ：不少老域名注册时长看着不错，但历史上可能挂过垃圾内容或者违规站点。等买下来、投入建站之后才发现污点，成本很高。

yee.cx 把这些查询收拢到一处。输入域名，一次性获取 Whois、实时DNS、注册行情，核心就是建站历史查询，快速查看域名过往页面标题与快照线索，提前做风险筛查，不用在多个网站之间跳转核对。顺带放了精品域名清单和DNS托管入口。

[![](https://www.evan.xin/wp-content/uploads/2026/11/22.webp)](https://www.evan.xin/wp-content/uploads/2026/11/22.webp)

**再看 puff.ee，样机生成器。**

做设计演示、UI预览时，传统方案总有短板：本地Figma/PS模板笨重，每次替换素材步骤繁琐；多数在线样机工具需要上传图片到服务端，内部未公开原型不敢随便上传；免费工具大多自带水印，光影、阴影参数固定，成品同质化严重，想要双设备对比、视频样机选项很少。

puff.ee 的解决方式：全部渲染在浏览器本地，素材不会上传服务器，敏感原型可以放心使用。内置多款苹果设备样机，阴影、光源、圆角、边框都可以精细调节，支持导出高清PNG，视频素材导出WebM，还有独立的双机并排页面，适合对比演示。目前只做了桌面端，编辑器控件太多，移动端暂时不支持。

两个工具我自己日常都在用，持续迭代优化。

  * yee.cx：域名尽调、老域名历史风险排查
  * puff.ee：本地离线样机渲染，产出UI宣传图、演示视频

地址：

  * [puff.ee](https://puff.ee/)
  * [puff.ee/duo](https://puff.ee/duo) （新的功能 - iPhone Duo 模型）

今天不想讲道理，总之就是不讲道理。心情不好，大概男的每个月也时常有那么几天。

心情不好总是有原因的，心情不好多半是因为人或者事情。但如果我在这里讲是谁是什么事不就显得我小家子气。而且如果被说的人和被说的事情相关的人看到了就不好，会让我更不舒服，因为可能会找我麻烦。

当然心情不好，还有可能是自己没有想开。那如果我在这里说我自己的问题，不是显得自己有病吗？还分裂出第二个人格来和自己抬杠。但对于心情不好的那个，遇到抬杠，心情可能更不好了。

所以，我们就来说说今天的天气吧。今天是阴天，偶尔还下一些雨。

对，我怎么没有想到，就是这该死的天气会容易影响人的心情。

我之前想离开家乡的一个主要因素就是天气。老家那边多数都是阴雨天气。每年见不了多少次太阳。天每天都很低，往众生身上压过来，压得人喘不过气。

嘿，我干嘛要怪天气。那算了，谁都不要怪。不舒服就是不舒服。要接受自己心情不舒服。接受不了怎么办？

我不知道怎么办。但我能够坐下来敲字似乎已经说明已经接受了一大半。如果那天我没有办法好好坐下来敲字那可能就说明我有事情过不去、或者有情绪平复不了。

对了，这就想到我看到一些博主写的博客。读起来通篇都像是一位想通很多事情的老者。好吧，用老登来说可能确实不太好，但不得不佩服。按照我刚刚关于心情的想法，似乎说明他们心情通畅都还不错。或者至少都能够把自己负面的情绪压制住。然后写东西的时候显得是一位客观的站在自己身边的第三者。

当然我们不能说能好好坐下来写就一定是分裂出了第二人格在压抑情绪或者在主导自己的手写东西，能够坐下来好好写也有可能只是表明情绪已经消解了部分了吧。这么说岂不是说明一些博主真的很厉害，情绪一般就不过夜。

但，又觉得情绪不过夜的人是不是也显得太过于冷静，甚至冷血。好吧，那还真不一定。也有可能性格本身都是如此。不能因为处理情绪的快慢、方式、过程和别人不一样就说是有问题。总之就是不一样不能说人家有问题。而我们其实似乎很容易就回去认为不一样的人就是有问题，就可以歧视。

好了，我说不讲道理的。如果我已经开始讲道理，似乎说明我的感性脑的吵闹声已经小了。

不错啊，这又是写作带来的“副作用”吗？

为什么要说是副作用？因为我也不知道这算不算是可靠治疗啊。症状是没有了，可万一写作这种方法如我刚才所说只是帮助分裂出的我压抑有情绪的我呢。这就如同给轮胎打气，压抑多了轮胎的气足够多，突破临界以后就会爆掉的啊。

好了不多想了。写到这里，我的感受告诉我，问题没有解决，情绪确实走了，没有压抑。

行吧，没有道理，只有问题。

问题一点一点做吧。

七八年前，翻知乎还是一个习惯的时候，看到过一篇托马斯·托尔汉姆的文章：[我在星巴克的一个神奇发现](https://www.zhihu.com/question/274851168/answer/384375770)。作者在中国南北几座城市的星巴克观察了几千名顾客，发现北方城市顾客独坐比例更高；又故意把两把空椅子拉近、半挡住过道，统计路过者的反应——小麦区北方人把椅子挪开的比例约是南方的三倍，南方人更倾向于侧身挤过去，通过调整自己来适应环境。这篇文章往前追溯可以找到 2014 年发表于《Science》的 [Large-Scale Psychological Differences Within China Explained](https://www.science.org/doi/10.1126/science.1246850)，结论是：传统水稻种植需要共用灌溉水渠、协作换工，塑造了南方人更偏向相互依赖、整体性思维和避免冲突；小麦种植相对独立、靠天降雨即可，塑造了北方人更偏向个人主义和分析性思维。

本店藏书一直不少，而且陆续又有同好寄存，现在店里三处书架都摆不开了，吧台两个角落也堆起了书山。好在虽多却也齐整。这几年，凭着[定格咖啡馆](https://digg.cafe)在本地的历史和口碑，再加上「打卡」这一热潮的兴起，新客比例大幅提升。有个现象越来越让我感觉困扰：许多客人从书架上取下书来，拍几张照，就散乱丢在各处。实话实说，整理书架并非顾客的义务，但若是爱书人，我揣摩不出把书本留在饮品杯具旁的心境。除了书籍，更让人头痛的是桌椅，我没有整齐划一的强迫症，但换位思考之下，还是希望客人们进门就能看到座椅有序，让心情舒畅起来。然而现实情况是，许多客人热衷于构图，书籍也好、座椅也罢，只求此时此刻在相机取景框里好看，之后就抛之脑后了。以至于，几年前我们说咖啡师的工作其实是洗碗，现在已然不成立——主要工作是家政。碰上客人多的时候，几乎每个桌上都有书、每个座椅都离原来的位置差出三四米去。

* * *

是因为，我们在北方吗？我觉得开头提到的「大米理论」已经不足以解释。这篇 [The non places of social media](https://etymology.substack.com/p/the-non-places-of-social-media) 里提到，法国人类学家马克·奥热认为，地方或者说场所，是一个具有象征意义的空间。它塑造妳的身份认同，定义妳与他人的关系，并蕴含着历史感。比如妳的家和当地的咖啡馆。这些都有不同的规则，关于妳可以成为谁以及如何与他人互动。而非地方、非场所则只是为了效率而存在的交易空间：电梯、机场、酒店走廊，过客、匿名，不产生记忆也没有共同参照。场所会随时间变化生发出故事——比如十五六年前在定格咖啡相识的男女，今时今日作为伴侣再来光顾；非场所则是悬置的、没有故事。

是什么，让场所变成了非场所呢？我是说，毫无疑问，妳不会总是把场所（妳的家、朋友的家）搞得一团糟，然后转身就走；咖啡馆已经（至少在许多人心中）变成了非场所。上述文章中提到，是消除摩擦使然。在数字领域，消除摩擦意味着一键下单、无限信息流；在物理空间——我太熟悉了，几年前我就写提到过，人们越来越习惯进门不找吧台不和店家眼神交流，直奔座位，扫码点单。显然资本希望如此，消除摩擦，效率至上，别说话、付款即可。而顾客们，无形中被连锁品牌以及无孔不入的互联网宣传教育、规训，习惯了如此。最终，咖啡馆就变成了和检票口一样的地方，不交流，快速通过。然后呢？人们把虚拟的网络认作场所、家园。一张咖啡馆里拍到的边读书边喝咖啡的照片，在这里发生摩擦——有人点赞，有人评论，产生故事。

定格咖啡馆至今还是没有共享充电宝，但每个座位旁都有插座，我也为客人准备了不同接口的充电线。不管客人会不会和我眼神交流，我都还是会先打招呼，推荐优先选择直接在吧台沟通点单。这些物理世界的摩擦，在我们的人生中留下故事。当然，如果这个故事越讲越温暖，书架有序、桌椅整齐，岂不是更好吗。

## [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#什么是习得性无助？ "什么是习得性无助？")什么是习得性无助？

**习得性无助** （Learned Helplessness）是一种习得的被动状态：当个体反复经历结果与行为无关的负面事件后，会形成“我做什么都改变不了”的预期，并在之后的情境中放弃努力——哪怕控制权已经恢复。

> 不可控事件最深的伤害不是痛苦本身，而是让人相信：无论做什么，都不会有任何改变。

可以想象一个每晚都充不进电的手机充电器：一个月后你干脆不插了，即便有人已经换了新线。放弃的习惯比原来的问题活得更久。习得性无助横跨条件反射与认知：身体学会了被动，头脑编出了理由。它与[损失厌恶](https://meta.niceshare.site/zh/effects/loss-aversion)相连（失败尝试的痛苦感觉比潜在收益更大），也与[基本归因错误](https://meta.niceshare.site/zh/effects/fundamental-attribution-error)相关（把原因归给自己，而不是情境）。

### [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#习得性无助的三层理解 "习得性无助的三层理解")习得性无助的三层理解

  * **入门** ：当你脱口而出“没必要试了”，先检查一下——这个信念来自哪个具体经历？当前情境可能完全不同。
  * **实践** ：连续失败后，设计一个小成本实验来测试结果是否已经改变。一次成功就能撬动无助的框架。
  * **进阶** ：习得性无助受归因风格调节。内部归因（“是我不行”）让无助变得个人化，稳定归因（“永远不会变”）让它慢性化，全局归因（“我什么都做不好”）让它弥漫化。只要改变其中一个维度——比如从“稳定”转向“暂时”——就能开始逆转。

* * *

## [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#起源 "起源")起源

习得性无助于 **1967** 年在**宾夕法尼亚大学** 被 **Martin E. P. Seligman** 与 **Steven F. Maier** 发现。在一项经典的三组（联结控制）实验设计中，一组狗可以按压面板来终止电击，第二组狗接受与第一组完全相同强度和时长的电击但无法控制（面板无效），第三组不接受任何电击。随后，所有狗被放入一个穿梭箱，只需跳过低矮隔板即可逃脱电击。第一组和第三组很快学会了逃脱。但不可逃避电击组中约三分之二的狗根本不尝试——它们躺下来被动承受，尽管逃脱极其简单。

基础结果发表于 Overmier 与 Seligman（1967）的 _Journal of Comparative and Physiological Psychology_ 以及 Seligman 与 Maier（1967）的 _Journal of Experimental Psychology_ 。Seligman 在 1975 年的著作《无助感》（ _Helplessness: On Depression, Development, and Death_ ）中将这一模型扩展到人类抑郁。

**1978** 年，**Lyn Y. Abramson** 、Seligman 与 **John D. Teasdale** 在 _Journal of Abnormal Psychology_ 发表了重要的修正理论。他们指出原始模型无法解释为什么面对同样不可控事件时，有些人变得无助而有些人不会。答案是**归因风格** ：把坏事解释为内部的（“是我的错”）、稳定的（“永远不会变”）、全局的（“影响一切”）的人，最容易陷入习得性无助——也最容易走向抑郁。这一修正理论成为临床心理学最有影响力的模型之一。

* * *

## [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#核心要点 "核心要点")核心要点

习得性无助按可预测的顺序展开。理解每个阶段，就能看到干预的切入点。

### [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#1-不可控性是触发器 "1. 不可控性是触发器")1\. 不可控性是触发器

过程始于结果与行为真正无关的时候——按杠杆没用、努力学习成绩不变、向管理层抱怨石沉大海。制造无助感的不是失败本身，而是无法通过努力改变的失败。单次挫折很少触发这一效应；反复的、不可控的负面经历才会。

### [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#2-形成「行为与结果无关」的预期 "2. 形成「行为与结果无关」的预期")2\. 形成「行为与结果无关」的预期

经历了足够多的不可控事件后，个体建立起一个心理模型：“我的行为和结果是脱节的。”这个预期——而非痛苦本身——才是习得性无助的核心。它像一条隐形规则，过滤后续信息：成功被当作运气，失败被当作确认。

### [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#3-被动泛化到新情境 "3. 被动泛化到新情境")3\. 被动泛化到新情境

这种预期会溢出原始场景。在数学课上学到无助的学生，可能在科学课也放弃尝试。被不回应的上司打击的员工，可能对新的、支持性的团队也无动于衷。正是这种泛化让习得性无助如此有害——它会“旅行”。

### [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#4-归因风格决定深度与广度 "4. 归因风格决定深度与广度")4\. 归因风格决定深度与广度

1978年的修正理论表明，归因风格是一个调节旋钮。内部归因（“是我笨”）让无助变成个人的；稳定归因（“永远不会变”）让它变成长期的；全局归因（“我做什么都失败”）让它变成弥漫的。只要改变一个维度——比如从“稳定”转向“暂时”——就能开始扭转。

* * *

## [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#应用场景 "应用场景")应用场景

识别习得性无助是打破它的第一步。以下四个领域展示了它如何出现——以及如何应对。

**临床抑郁与心理治疗**  
认知行为疗法（CBT）直接瞄准无助性归因：教来访者识别、挑战和替换“内部—稳定—全局”的解释。治疗师会把“什么都没用”的叙事当作习得性无助的标志来处理。

**课堂学习**  
反复在某科目上失败的学生常得出“我不是学数学的料”——经典的内部、稳定、全局归因。教师可以通过提供早期、可达成的小胜利，并明确地把努力与结果联系起来，打断这个循环，让学生重新学到“行动是有用的”。

**慢性疾病与疼痛管理**  
慢性疼痛患者在之前的治疗失败后，有时会停止遵循治疗方案。临床医生通过设定小而可测量的目标——每天多走一段路、一个拉伸多保持几秒——来重建行动与改善之间的联系。

**职场脱离**  
经历反复裁员、重组或被无视的反馈后，员工可能不再提建议、不再争取晋升。管理者可以通过恢复真正的自主权来应对：让团队做出有实际后果的可见决定，并公开认可结果。

* * *

## [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#经典案例 "经典案例")经典案例

在 Seligman 与 Maier **1967** 年于宾夕法尼亚大学进行的三组实验中，24只狗被分成三组，每组8只。第一组（逃避组）可以按压面板终止电击。第二组（联结组）接受与第一组完全相同强度和时长的电击，但面板无效——它们无法控制任何事。第三组（无电击对照组）不接受任何电击。

24小时后，所有狗被放入穿梭箱。灯光信号预示即将到来的电击，跳过低矮隔板即可终止或避免电击。第一组和第三组的狗很快学会了跳跃。但第二组——联结、不可逃避电击组——约三分之二的狗未能逃脱。它们甚至没有尝试。它们坐下或躺下，被动承受电击，尽管只需简单一跳就能结束痛苦。

关键教训在联结设计本身：第一组和第二组接受了物理上完全相同的电击。唯一的区别是可控性。就是这一个变量——动物的行为是否有意义——决定了它之后是尝试还是放弃。这一结果已在多个物种中被复制，包括人类（用不可控噪音或无解问题替代电击的认知任务）。

值得注意的边界：并非联结组的每只狗都变得无助。个体差异（先前经验和气质）调节了效应大小，这一发现为后来归因风格在人类中的作用埋下了伏笔。

* * *

## [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#边界与失效场景 "边界与失效场景")边界与失效场景

习得性无助是一个有充分证据支持的模型，但误用它本身也可能造成伤害。

**边界一——并非所有被动都是习得性无助。** 有时不行动是理性的。如果一个系统确实不回应个人努力——操纵的游戏、结构性不回应的官僚体系——那么脱离可能是清醒的反应，而不是认知扭曲。把每一个放弃的实例都标记为“无助”，有可能是在指责那些准确识别环境的人。

**边界二——这一效应需要先前的不可控性，不是单次失败。** 一个考试不及格后感到沮丧的学生，并不是在表现习得性无助。这个概念适用于反复的、真正不可控的负面事件训练出了“努力无用”的预期。单次挫折后的沮丧是正常的；只有当这种模式泛化时，才成为习得性无助。

**常见误用——把概念庸俗化。** 说“我试了一次没用，所以我是无助的”是对这个术语的误用。习得性无助描述的是在持续不可控经历中建立的条件反应。把它当作日常挫败的随意标签，会稀释它的含义，也会让真正深受其害的人觉得被轻视。

* * *

## [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#常见误区 "常见误区")常见误区

因为“习得性无助”听起来直观，它很容易被过度简化。

**误区一：无助就是懒**  
习得性无助不是性格缺陷或缺乏意志力。它是对真实不可控性的条件反应。这个人通过真实经历学到了——努力不产生结果。称之为“懒”是把症状和原因搞混了，而且会阻碍真正有帮助的干预手段（恢复感知到的控制感）。

**误区二：它和抑郁是一回事**  
Seligman 本人将习得性无助提出为抑郁的模型，两者确实有大量重叠——尤其在被动、消极预期和消极偏见方面。但抑郁涉及额外的生物、社会和认知成分（睡眠障碍、快感缺失、反刍思维），超出了无助模型的范围。习得性无助是通向抑郁的一条路径，不是它的同义词。

**误区三：习得性无助无法恢复**  
恢复已被充分记录。在 Seligman 与 Maier 的原始实验中，研究者用手把无助的狗反复引导过隔板，直到它们开始自己跳跃。在人类中，认知行为疗法、小的可控胜利和归因再训练都已显示出效果。“无助是永久的”这个信念本身就是这一状态的症状——而且是可以治疗的。

* * *

## [](https://www.jeffjade.com/2026/11/16/262-learned-helplessness/#相关概念 "相关概念")相关概念

这些概念与控制感信念如何塑造行为和判断密切相关。

  * **[沉没成本谬误](https://meta.niceshare.site/zh/effects/sunk-cost-fallacy)** ：反面——因为过去的投入而坚持亏损路线；习得性无助则让你过早放弃。
  * **[聚光灯效应](https://meta.niceshare.site/zh/effects/spotlight-effect)** ：高估别人对你失败的关注度，强化了让无助加深的内部归因。
  * **[可得性启发](https://meta.niceshare.site/zh/effects/availability-heuristic)** ：过去的失败容易被想起，让被感知的失败模式膨胀，使无助感看起来比实际更合理。
  * **[正常化偏差](https://meta.niceshare.site/zh/effects/normalcy-bias)** ：相反的错误——假设坏事不会发生，而习得性无助则假设好事不会发生。
  * **[皮格马利翁效应](https://meta.niceshare.site/zh/effects/pygmalion-effect)** ：正面镜像——成功的期望创造成功，恰恰是习得性无助所摧毁的信念。
  * **[锚定效应](https://meta.niceshare.site/zh/effects/anchoring-effect)** ：早期的无助经历锚定了后来的自我效能评估，使信念更新变得困难。

前几天看到崔添翼在 X 上发的一条推文：

> 下一个超级 App 不必是面向所有人的一个超级 App。
> 
> 现在，每个人都有能力创造一个超级 App。
> 
> 下一个超级 App 也可以是只属于你一个人的超级 App。

只属于你一个人的超级 App。这个说法我特别认同。

后AI时代，只要你能自己做的东西，自己做都会是最合适。现存的所有app，特别是你需要重度使用的app，无论做成什么样，总是不太可能完全契合你自己的需求的，所以无论怎么去找app，成本上都不如自己直接做一个更合适。

还需要用别人app的场景，在我看来，目前还有两个，

一是对方有大量的资源你无法获取，比如微信，比如高德地图，比如支付宝，这些玩意好用吗？真的不好用。这几个哥们在已经如此臃肿的情况下，依然有很多我想要的功能它没有，比如一个好用的记账功能、行程记录功能，要是可以的话，我真的想给他们爆改一通。但耐不住人家掌握着个人开发者无法获取的资源，所以也只能捏着鼻子用了。

另一类就是现在确实有非常符合你自身需求的应用存在。比如对于我来说，obsidian就能满足我关于笔记的所有需求，所以我没必要自己再去做一个。

目前说开发自己的“超级app”，可能还为时尚早，毕竟商业上有太多的东西没有打通，比如上面提到的微信的数据、导航数据。

但是，如果说只是开发自己的“非超级”app，那现在就是最合适的时候了。特别是像什么记账、todo这种，每个人都觉得别人做的不好，是个人都想做一版出来给别人用的。究其根源，就在于每个人的习惯、审美都不一样，别人做出来的东西，自己用着就是不顺手。那不如自己做个好了，也别想着发出去给别人用，你觉得别人做的都是垃圾，其实别人看你的东西也是一样的。

我最近就把好多之前用文档或者纸笔维护的东西搓成了app，

比如我的网格化投资策略，搬到了app里，接近或者到了买入、卖出点，会给我标记出来，比之前记在文档里，自己去对方便多了。

接下来，分享一些开发app给自己用的心得吧。个人app由于访问量低，不会涉及很多奇奇怪怪的边界逻辑，开发起来其实会比商业app难度低很多的。

## [](https://lichuanyang.top/posts/62962/#App-壳-H5 "App 壳 + H5")App 壳 + H5

最好采用app壳内嵌H5的架构，app层只放必要的外壳，所有业务逻辑放到H5层。这样，app只需要安装一次，后边所有的功能更新都可以通过发布H5页面的形式做热更新。

## [](https://lichuanyang.top/posts/62962/#部署 "部署")部署

H5可以部署在cloudflare pages或者腾讯云EdgeOne上，免费额度都非常足。EdgeOne需要有已备案的域名，cloudflare在国内的网络环境中访问有一些延时，看各自取舍吧。

## [](https://lichuanyang.top/posts/62962/#后端 "后端")后端

如果需要后端服务，可以去oracle注册一个免费VPS，需要外币信用卡，风控比较严，申请下来有一定难度。当然了，到阿里云或者腾讯云买一个轻量服务器，一年99的那个，也足够用了。或者使用cloudflare D1、workers，或者neon的data api，都可以一定程度上承担后端功能。

如果完全不要后端服务的话，其实也是可行的。数据可以落到手机里的固定目录，这个目录用git、或者网盘管理，或者定期拉回电脑上管理，都是可以的。

## [](https://lichuanyang.top/posts/62962/#安全 "安全")安全

注意，如果需要后端的话，务必让AI帮你审一遍服务器的安全相关策略，不要留下明显的漏洞让人爆破。

## [](https://lichuanyang.top/posts/62962/#自动化 "自动化")自动化

app的安装和测试，连上数据线之后，都可以让agent自动进行。

## [](https://lichuanyang.top/posts/62962/#把流程固化成-skill "把流程固化成 skill")把流程固化成 skill

还有最重要的一点，上述所有的通用流程，一定要有意识的固化成流程文档或者skill吧。像上边提到的对vps的操作、cloudflare的各个产品的操作，agent都是完全可以做到全自动操作、不用开发者介入的。我们要做的就是让agent跑通一次流程之后，把这个流程固化成可复用的流程。

当各个部分的可复用流程都积累好了之后，我现在开发一个app基本也就一个小时以内就可以搞定。

先说结论：**大多数省税的动作，过了12月31日就来不及了。今年税法变化比较多，有几件事最好这个月就做。**

12月31日半夜，对税来说就是灰姑娘的午夜十二点。钟声一响，南瓜车变回南瓜，你想做的Roth转换、亏损抵税、捐款抵税，全都变成“明年再说”。而且年底大家都忙着过节，券商和会计师最后两周忙得连电话都接不过来，所以我建议11月就把这张清单过一遍。

## 一、今年新增的几条规矩

**1\. 50岁以上、收入高的人，401(k)补缴只能放进Roth。** 从2026年开始，如果你去年在这家公司的社安工资（FICA wages）超过15万，今年的补缴（catch-up contribution）就必须是Roth的，不能再税前存。公司计划里没有Roth选项的，干脆不能补缴。去工资单上看一眼，确认扣款类型是对的。

**2\. 州税和地方税抵扣（SALT）上限变成4万多。** 2026年是40,400。但收入（MAGI）超过50.5万以后，超出部分的30%要从上限里扣，最低扣到1万。

  * 例子：夫妻俩MAGI 55.5万，超了5万，上限减少30%×5万=1.5万，只能抵25,400。
  * 住在纽约、新泽西、加州这些高税州，地税加州税远超1万的朋友，可能又值得分项抵扣了，要和标准抵扣（夫妻32,200）比一比。
  * 已经出了账单的地税，12月31日前交，算在今年。

**3\. 65岁以上每人多一个6,000的扣除。** 2025年到2028年有效，不管分不分项都能拿。收入超过单身7.5万、夫妻15万以后，超出的部分每1块减6分。

  * 例子：单身老人家MAGI 8.5万，超了1万，减600，还能拿5,400。
  * 所以要做Roth转换的老人家要留意：多转一块，除了交税，这个扣除也在变小。

**4\. 捐款抵税规矩变了。** 从2026年起，分项抵扣的人捐款要先扣掉收入0.5%的“门槛”才能抵；不分项的人反而可以抵一点现金捐款（单身1,000、夫妻2,000）。不分项的这个扣除只算直接捐给公共慈善机构的现金，捐到捐赠者建议基金里的不算。捐得多的人可以考虑把几年的捐款放在同一年，比如通过捐赠者建议基金（donor-advised fund）。

## 二、每年都该做的年底动作

**5\. 用亏损抵税（tax-loss harvesting）。** 卖掉亏钱的投资，先抵赚钱的部分，还有剩的每年最多抵3,000工资收入，再剩的往后结转。在22%的税档，抵3,000就是少交660。注意洗售规则（wash sale）：卖之前或卖之后30天内又买了基本一样的东西，这个亏损就不能抵。什么叫“基本一样”？换一只跟踪不同指数的基金，一般没问题。

**6\. 收入低的年份，反过来“收割收益”。** 2026年，应税收入在单身49,450、夫妻98,900以下，长期资本利得税率是0%。刚退休、刚失业、在读书的人，可以卖掉一些涨了的股票再买回来，把成本提高，一分税不交。这个不受洗售规则限制，因为洗售只管亏损。

**7\. Roth转换。** 收入比平时低的年份，把传统IRA里的钱转一部分到Roth，把当前的税档“填满”。但转之前要看四条线：两年后的红蓝卡附加保费（IRMAA）、奥巴马医保补贴、上面说的老年人扣除、SALT上限。一不小心，省了税丢了补贴。

**8\. 存满401(k)。** 2026年上限24,500，50岁以上多8,000，60到63岁多11,250。401(k)只能从工资里扣，过了12月31日就没机会了。IRA和HSA可以等到明年4月15日。

**9\. 73岁以上，领完最低取款（RMD）。** 忘了领，罚的是没领金额的25%（及时补上可以减到10%）。70岁半以上的人，可以从IRA直接捐给慈善机构（QCD），2026年最多111,000，这笔钱不算收入，还算在RMD里。

**10\. 把FSA花完。** 医疗弹性支出账户是“用不完就没了”，有的公司允许结转一点（2026年最多680），有的给宽限期。去配副眼镜、买点常备药，都算。

**11\. 给孩子存529。** 很多州给州税抵扣，比如纽约州单身5,000、夫妻1万，大多要在12月31日前存进去才算今年。给孩子开了特朗普账户的，记得在官方应用里认领。

**12\. 自雇和有投资收入的，算一下预估税。** 第四季度的预估税2027年1月15日交。交够去年税额的100%（收入超过15万的是110%），就不会被罚。

#### 语法速通

虽然有了AI，但是基本的语法我们还是要知道的，不然看到AI生成的代码都是一脸懵逼。

内心OS：虽然目前大肥鱼、Kimi娘、狐狸娘都不太可能主动使用`random()`函数，大小姐倒是有些可能性。
    
    
    random(seed?, min, max, step?)

参数后面跟着问号表示可选，说明`min`和`max`是必填的。

**一些使用示意：**
    
    
    /* 基本使用 */
    random(0, 100)
    random(10px, 500px)
    random(0deg, 360deg)
    
    /* 步阶间隔 */
    random(0, 100, 10)
    random(0rad, 1turn, 30deg)
    
    /* 使用随机关键字 */
    random(auto, 0, 360)
    random(element-scoped, 0s, 5s)
    random(property-scoped, 0s, 5s)

    random(fixed 0.5, 1em, 40vw)  /* 这个Chrome暂不支持 */
    random(--unique-base property-scoped, 100dpi, 300dpi)
    
    /* 使用随机关键字和步阶间隔 */
    random(property-scoped, 0deg, 360deg, 45deg)
    random(--my-base, 1em, 3rem, 2px)

### 二、语法速通 · 真

基本使用没什么好说的，就是前后单位的性质要一样。

注意，相同的是前后单位的「性质」，并不一定非得是相同的单位。

例如下面的用法也是合法的，`20deg`和`1turn`都属于角度单位值：
    
    
    img {
      rotate: random(20deg, 1turn);
    }

`random()`函数比较难理解的就是前面的随机关键字。

这东西还是挺有用的。

具体如下：

  * 默认（省略 key，效果同`property-index-scoped`）。每个元素、每个属性各自独立随机，互不影响。
  * **element-scoped** 。让所有匹配同一规则的元素共享同一个随机计算结果，保持风格统一。
  * **property-scoped** 。在同一个属性声明中复用随机值。
  * **自定义标识符（如 –size）**。凡是传入相同自定义名称的 `random()` 调用，无论出现在哪个属性或元素上，都会共享同一个随机数。
  * `fixed <number>`。基于种子数值（0~1）生成固定随机数，每次刷新都是这个随机值。

#### 通过案例学习

让我想想用什么案例帮助大家学习……

有了，图片的圆角吧。

圆角有四个角，还有内外圆角区分，最适合演示了。

且看默认效果：
    
    
    img {
        border-radius:
            random(16px, 96px) random(16px, 96px)
            random(16px, 96px) random(16px, 96px);
    }

此时，每个图片的每个圆角大小都是随机的。

如下图所示：

![随机圆角效果](https://image.zhangxinxu.com/image/blog/202611/2026-11-16_171846.webp)

如果是`element-scoped`语法代码：
    
    
    img {
        border-radius:
            random(element-scoped, 16px, 96px) random(element-scoped, 16px, 96px)
            random(element-scoped, 16px, 96px) random(element-scoped, 16px, 96px);
    }

那么同一个图片的四个圆角大小是一样，但是不同的图片（虽然公用一个选择器）之间的圆角是随机的，就像下图这般：

![element-scoped作用区别](https://image.zhangxinxu.com/image/blog/202611/2026-11-16_201526.webp)

至于**property-scoped** 和自定义标识符，则需要对比效果才能见真章。

如果是**property-scoped** ，那么不同元素之间同一个属性的圆角随机大小是一样的。而使用自定义标识符，无论哪个元素、哪个属性，都使用一样的随机值。

且看下面的对比代码：
    
    
    img {
        border-radius: random(property-scoped, 16px, 96px) / random(property-scoped, 16px, 96px);
        /* 两层遮罩：整图减去居中的小方块，图片中间即被挖空 */
        mask: linear-gradient(#000 0 0) exclude, linear-gradient(#000 0 0) center no-repeat;
        mask-size: 100% 100%, random(property-scoped, 16px, 96px) random(property-scoped, 16px, 96px);
    }
    
    img {
        border-radius: random(--size, 16px, 96px) / random(--size, 16px, 96px);
        mask: linear-gradient(#000 0 0) exclude, linear-gradient(#000 0 0) center no-repeat;
        mask-size: 100% 100%, random(--size, 16px, 96px) random(--size, 16px, 96px);
    }

前者通过`mask`遮罩产生的镂空方格的大小和`border-radius`是没有关联的，因为随机值只与属性相关。

![圆角和遮罩尺寸无关联](https://image.zhangxinxu.com/image/blog/202611/2026-11-16_202539.webp)

但是后者镂空的方格大小则是和`border-radius`保持一致，圆角越大，挖空的方形越大，圆角越小，空格也就越小。

![圆角和镂空面积相关示意](https://image.zhangxinxu.com/image/blog/202611/2026-11-16_202735.webp)

至于`fixed`数值语法，这个就比较好理解了，给定一个0~1之间的种子计数值，返回一个每次刷新都不变的随机值：
    
    
    random(fixed 0.25, 16px, 96px)

这让我想起了我以前做过的一个需求，一堆素材列表需要随机排列，但是每一个用户的显示顺序又是固定的，就基于用户的userid生成了一个固定的随机排序算法。

感觉与这个类似。

### 三、要不来点更实际的应用

我，柯北，三十九，某研究院副研究员，项目聘用。

学生和外人都叫我"柯教授"，从不纠正。我的钙钛矿电池效率是19.3%，组会汇报时我也从不纠正PPT上写的"接近25%"。在科研圈，四舍五入是一种修养。

“项目聘用"的意思是：有工位、有门禁卡、有学生，但没有编制。聘期五年，还剩八个月，考核不过就收拾东西走人。门禁卡到期自动失效，比我的钙钛矿还准时。

我的课题叫《基于多维界面调控的纳米结构钙钛矿薄膜稳定性机理初探》。翻译成人话：钙钛矿效率很高，但放在空气里三天就坏，我研究它为什么坏。研究了五年，结论是因为空气。

这个结论不能写进结题报告。

那天晚上十一点，我在研究院后门的烧烤摊吃烤馒头片，最便宜的那种，六块钱三片。

手机上是第七封退稿邮件。审稿人三号写道：“作者对钙钛矿稳定性的理解停留在五年前，创新性不足。”

五年前，正好是我入职那年。这位审稿人可能认识我。

邮件下面弹出一条微信，是毛莉发来的：

“柯老师，薄膜又黄了。”

紧接着又一条：

“我妈说我再不毕业就回去考乡镇公务员，她已经帮我报了个面试班，三千八，不退。”

毛莉是我的博士生，二十八岁，延毕两年，全组唯一真正在做实验的人。她的手机里永远开着三个页面：实验数据、相亲对象资料、省考公告。我曾经劝她专心科研，她问我：“柯老师，那您能给我一个编制吗？”

我没回答，毕竟我自己也没有。

我盯着屏幕上那个"黄"字，想回点什么，想了很久，最后打了一个"好”，没发出去。 然后坐着睡着了。

隔壁桌坐着一个男人，三十六岁，叫秦九。

秦九是材料学博士，毕业七年没找到教职，简历投了一百四十多份，回复最多的是"感谢您的关注，您的背景与岗位暂不匹配"。他现在靠在咸鱼上接零活为生：代做PPT、代画机理图、代跑XRD数据，偶尔也代人排队挂号。

这单比较特别。

咸鱼帖子标题：【诚招】健康成年男性受试者，口服一粒，报酬两百元。

发帖人头像是一只哭泣的猫，ID叫"薛丽不想再写本子了"。帖子正文写着：“本品为钙钛矿量子点载体口服制剂，安全无副作用，已完成体外实验。伦理审批排队中，预计明年。”

秦九接单，因为他这个月房租还差两百。

现在胶囊就在他手心里，他已经攥了四十分钟，手汗把胶囊外壳泡得发软。

“安全无副作用”，那为什么头像是一只哭泣的猫？

“伦理审批排队中”，那就是没批。

“已完成体外实验”，那就是还没有人吃过。

他看了看隔壁桌那个坐着睡着的男人。

发际线后退，黑眼圈深得像旋涂失败的薄膜，嘴角挂着一点馒头渣，手机屏幕还亮着，上面写着"创新性不足"。

秦九看了很久，脑子里冒出一个念头：

这个人看起来，也不是很想活的样子。

他被自己这个念头吓了一跳。然后他又看了一眼那封退稿邮件，觉得这个念头好像也没什么错。

他左右看了看。烧烤摊老板在玩手机，另一桌的大学生在吵谁该付钱。

秦九把胶囊掰开，白色粉末倒进了柯北的啤酒杯。粉末在啤酒里冒了几个小泡，消失了。

他把两百块转账截图保存好，给咸鱼卖家发消息：

“已服用。”

想了想，又补了一句：

“不是我服的。”

想了想，删掉了第二句。

醒来时，烧烤摊老板正拿扫把戳我。

“柯教授，馒头片六块，啤酒五块。”

我迷迷糊糊端起杯子，一口喝干，觉得今天的啤酒有点甜。我想，可能是最近太苦了，味觉出现了偏差。

扫码，余额十块八。上个月的劳务费还在走报销流程，财务说发票抬头用了简称。 回家，睡觉。

第二天早上，我刷牙时发现了不对劲。

膝盖不响了。

我在楼梯上来回走了三趟，膝盖安静得像实验室凌晨三点的手套箱。我又低头看了看肚子，那圈跟随我十年的游泳圈不见了。我抬头看镜子，头顶那块我每天用发胶精心覆盖的区域，长出了一片浓密的黑发。

我凑近镜子仔细看。

那是十九岁的我。

和三十九岁一模一样的我。

我打小长得急。本科被当成辅导员，读博时去别的课题组借仪器，对方以为我是来查固定资产的。入职那天，院长穆钼拍着我的肩膀说：“小柯，你看起来比我还像老同志。”

穆院比我大二十一岁。

我的青春就是一段提前透支的中年。而现在，它连本带息地回来了，却依然长着一张中年的脸。

到研究院，门卫大爷说：“柯教授早，又熬夜改本子了？脸都肿了。”

隔壁组的研究员在走廊碰见我：“柯老师，你那个钙钛矿稳定性做得怎么样了？”

我说：“还在做。”

他笑着点点头：“不急，钙钛矿嘛，本来就不稳定。”

我知道他的意思是：你的聘期也是。

推开实验室门，毛莉正坐在手套箱前，一手戴着丁腈手套伸在箱子里，一手拿着手机跟她妈视频。

“妈，我在做实验……对，是正经工作……不，博士后不算编制……”

她看见我，匆匆挂断电话，指了指手套箱里那片薄膜：“柯老师，又黄了。”

我看了看那片薄膜。从黑色变成了黄色。行内人都知道，钙钛矿变黄，就是分解了。

毛莉看了看我，忽然说：“柯老师，您今天气色挺好。”

我心里一紧。

她又补了一句：“是不是想开了？准备转行了？”

我松了一口气。

无人在意。

与此同时，隔壁研究所五楼一间没有窗户的实验室里，薛丽盯着咸鱼聊天框里那三个字。

“已服用。”

她等了一整天，被试没有任何后续反馈。没有说头晕，没有说发烧，没有说变年轻。

薛丽，四十二岁，项目聘用研究员，海归。回国时她带着两篇顶刊，高校人事处的回复是：“您的年龄已超过青年人才申报上限。“她在这间没有窗户的实验室里，用自己的工资买原料，合成了一款号称能让细胞逆向生长的钙钛矿量子点。

伦理审批要排一年。她等不了一年，她的聘期也只剩一年。

她给被试发消息：“请问服用后有什么感觉？”

秦九盯着这条消息看了很久，回复：

“无异常。”

薛丽关掉手机，在实验记录本上写下最后一行字：

被试服药后无异常反应，判定药物无效。

她合上本子，把剩下的药瓶推到了抽屉最深处，跟她的离婚协议放在一起。

那天深夜，我一个人留在实验室。

手套箱里的氩气嘶嘶作响。十九岁的手不抖了，我第一次一口气旋涂出了一片完美的薄膜：均匀、致密、黑得发亮。

我盯着那片薄膜看了很久，心里涌起一种陌生的情绪。

我花了半天时间才认出来。那叫希望。

我拿起手机，想给毛莉发个消息，告诉她薄膜做出来了。

屏幕亮起，弹出一封新邮件。

发件人：人事处。

主题：关于项目聘用人员聘期考核的通知。

正文第一行：凡聘期内未取得代表性成果者，原则上不予续聘。

我又看了看手套箱里那片完美的薄膜。

身体可以年轻二十岁。

但聘期，一天也不会多给。

# [](https://blog.lusyoe.com/article/virtual-payment-session-key#前言 "前言")前言

青萍生图小程序的充值功能跑起来没多久，我就收到一类奇怪的反馈。

用户明明登录着，点充值却弹出支付失败，错误信息是 SIGNATURE_INVALID。

直译过来是签名无效，第一反应都会怀疑签名算法写错了。

可它时好时坏，刚进小程序的人付款一路顺畅，逛了一会儿再来充值的就挂。

折腾一圈才发现，锅不在算法，在登录态的时效上。

如果你也在做小程序虚拟支付，这个坑值得提前搞明白。

# [](https://blog.lusyoe.com/article/virtual-payment-session-key#报错的真面目 "报错的真面目")报错的真面目

我把失败订单和登录日志对了一遍，失败集中在登录后隔了一阵子才付款的用户身上。

虚拟支付拉起收银台要带两个签名，一个管商户，一个管用户。

paySig 用后台配置的 AppKey 计算，证明这笔请求确实出自你的服务端。

signature 用 session_key 计算，证明用户当下的登录身份。

SIGNATURE_INVALID 对应官方错误码 -15005，文档里的说法是用户态签名 signature 错误。

这个码只说明签名没通过，算法写错、字段拼错、key 旧了，报的都是它。

旁边还有个 -15007，含义更直接，就是 session_key 过期。

两个码症状很像，但 -15007 才是把原因说死的那个。

# [](https://blog.lusyoe.com/article/virtual-payment-session-key#弯路都走了一遍 "弯路都走了一遍")弯路都走了一遍

被报错文案带着，我先在签名算法上查了很久。

HMAC 的拼接顺序、字段增减、key 的编码方式，挨个对了一遍，都没问题。

也怀疑过 AppKey 拿错，沙箱和正式不同，没错。

真正的转折来自一次对照测试。

登录后立刻点支付，成功。

把小程序放半小时再点，十有八九会失败。

签名代码一行没动，变的只有时间，那就只剩登录态这一个变量了。

# [](https://blog.lusyoe.com/article/virtual-payment-session-key#算法没错，密钥旧了 "算法没错，密钥旧了")算法没错，密钥旧了

微信官方从不公布 session_key 的固定有效期，文档里能找到的唯一说法，是会根据用户使用小程序的行为动态续期。

小游戏虚拟支付的技术手册里倒是给过一个量级，失效时间是天级别。

但天级别不等于高枕无忧，任何一次新的 wx.login 都可能触发刷新，旧的 session_key 立即作废。

用户在手机和电脑同时登录，或者另一个模块悄悄调了一次登录，服务端那份 key 就旧了。

回头看那次对照测试，挂掉的多半不是 key 的寿命，而是它已经不被微信认可了。

旧 key 算出来的 signature，微信那边自然验不过。

报错只说签名无效，把人往算法上带，这是整个坑里最耽误时间的部分。

# [](https://blog.lusyoe.com/article/virtual-payment-session-key#支付前查登录态 "支付前查登录态")支付前查登录态

搞清楚原因后，方案反而简单，难的是放在哪查。

我先想过把 session_key 存下来一直用，可它随时会被新的登录刷掉，存的那份迟早变旧，走不通。

也考虑过进小程序时查一次，同样不够，浏览页面的几分钟里登录态照样可能变旧。

而 wx.login 有频率限制，官方禁止短时间内多次自动重试，高频重登不现实。

所以我最后把检查挪到了点支付那一刻。

点充值时，服务端先用 auth.checkSessionKey 校验手里的 key，客户端补一道 wx.checkSession。

有效就直接签名拉起收银台。

查到过期就静默重走一遍登录，拿到新的 session_key 重新签名，再拉起收银台。

整个重登用户无感知，最多觉得支付弹窗慢了半秒。

![支付前登录态检查的修复前后流程](https://img-cdn.lusyoe.cn/images/lusyoe/2026/11/16/pay-login-check@2x.webp)

官方手册也列了重登时机清单，进入时检查、报错后重登都在里面，我取的是点支付这一种，离签名最近。

# [](https://blog.lusyoe.com/article/virtual-payment-session-key#上线之后 "上线之后")上线之后

修复上线后，这类报错从日志里基本消失，用户也没再遇到点充值被失败弹窗拦住的情况。

顺手在监控里给 -15005 和 -15007 都打了标签，一出现就先往登录态查。

后来给青萍生图加新支付场景时，登录态检查已经封装成公共方法，新场景直接调。

当然它有边界，签名依赖登录态的接口才用得上，频次极低的场景报错后重试也说得通。

这个坑教会我的事就一件：报错文案说签名无效，不代表问题真的在签名。

## AI 需求升温，电子与电气机械出厂价同步上抬

10 月，电子与电气机械行业出厂价均环比上涨 0.1%。国家统计局将这一变化指向人工智能加快落地带来的需求回升。

在 11 月 16 日国新办新闻发布会上，国家统计局新闻发言人王冠华给出了两组数据：10 月份，电气机械和器材制造业、计算机通信和其他电子设备制造业的PPI（工业生产者出厂价格指数）环比均上涨 0.1%。这些行业覆盖发电及输配电设备、电机、线路器材，以及计算机、通信设备和电子元器件等生产环节，出厂价变化因此进入工业品价格统计。

AI 需求传导到了制造端。王冠华说，AI 快速发展正在推动产业升级，并带动电子、电气机械等行业需求回暖、价格上涨。新增需求已不只是停留在模型发布和项目融资层面。

环比各涨 0.1%，两行业合计对 10 月 PPI 同比涨幅形成约 1.18 个百分点的贡献。但这一贡献不能直接等同于 AI 需求单独造成的价格涨幅。官方将价格变化指向 AI 带动行业需求，同时提到低价无序竞争整治、产能治理等因素也在影响部分行业供求。

机制 

## 1.18 个百分点背后，AI 贡献了多少？

AI 需求已经进入工业价格统计，但两个行业合计的贡献，不能直接算成 AI 单独造成的涨幅。

国家统计局新闻发言人王冠华在国新办新闻发布会上说，人工智能（用算法让机器完成智能任务）正在从技术创新走向产业落地和场景重塑。这个变化先落到订单上：电子、电气机械等行业需求回升，企业出厂价格随之上涨。10 月，电气机械和器材制造业出厂价格同比涨 6.2%，计算机通信和其他电子设备制造业涨 5.9%。

1.18 个百分点里，AI 占多少？官方没拆，所以算不出来。这两个行业价格包含多种产品，也承受各自的供需、原材料和成本变化，统计局没有公布其中由 AI 需求单独贡献的百分点。6.2% 和 5.9% 不能直接视为 AI 带来的涨幅，它们能说明的是：AI 快速产业化和场景应用，与这两个行业的价格回升同时发生。

6.2% 电气机械同比涨幅 口径：电气机械和器材制造业出厂价格同比变化；10 月为 6.2%。来源：国家统计局新闻发布会。 5.9% 电子设备同比涨幅 口径：计算机通信和其他电子设备制造业出厂价格同比变化；10 月为 5.9%。来源：国家统计局新闻发布会。 约 1.18 个百分点 两行业合计影响 口径：两行业对 10 月 PPI 同比涨幅的合计影响，不是 AI 单独贡献。来源：国家统计局新闻发布会。 

传导路径倒是清楚：应用加快，抬高相关设备的采购需求，需求回升再推到出厂价格。只是现有官方数据没把 AI 订单与行业其他订单拆开，也没有只含 AI 需求的价格指数。约 1.18 个百分点是一份行业级贡献账，不是一份 AI 专属账。

下一步要看环比走势和订单变化放在一起怎么走。单月同比较高能确认价格在上行，却分不出 AI 需求、季节因素和其他行业供需各占多少。

反直觉 

## AI 在涨价，能源贡献却是它的约 3 倍

10 月 PPI（工业生产者出厂价格指数，反映工业产品出厂价变化）上涨，容易让人把视线直接锁定在 AI 带动的电子、电气机械涨价上，但真正撑住涨幅的是能源相关行业。

据中国经济网援引国家统计局发言人王冠华在国新办新闻发布会上的说法，油气开采、石油加工、化工、煤炭开采洗选、燃气生产供应五个能源相关行业，合计拉动 10 月 PPI 同比上涨约 3.63 个百分点。这个上拉影响较上月增加 0.8 个百分点，贡献并非停留在高位，而是当月继续加码。

判断AI 需求支撑了电子和电气机械价格，但能源五行业对当月 PPI 扩幅的贡献约为前者的 3 倍。 

AI 相关两类行业合计拉动 PPI 同比上涨约 1.18 个百分点。两个数字都是对 PPI 同比的拉动贡献，口径可比：能源组约是 AI 相关组的 3 倍。把 10 月 PPI 涨幅扩大主要归因于 AI，会低估能源价格的作用。

能源这轮上涨来自两组力量叠加。国际能源价格高位震荡，传导至国内油气开采、石油加工和化工行业；10 月进入迎峰度冬准备阶段，电煤和燃气需求季节性上升，煤炭主产区供应偏紧，又推高了煤炭与燃气行业价格。前一组反映外部价格输入，后一组来自国内季节性需求与供应约束。

电子和电气机械的价格上涨也有清晰的需求基础。AI 加快从技术研发走向产业落地和场景应用，拉动相关装备需求回暖。下一个需要观察的问题是，能源的高位输入会否继续向电子和电气机械等下游行业传导。

方向 

## AI 需求接得住下一轮涨价吗？

10 月工业生产者出厂价格（PPI）同比上涨 5.7%，涨幅较上月扩大 0.7 个百分点。下一阶段能否继续上行，要看国际大宗商品价格，也要看 AI 从技术研发走向产业落地后，能否持续转化为电子和电气机械行业的真实订单。

AI 需求已经进入价格数据。国家统计局新闻发言人王冠华在国新办新闻发布会上说得很直白：人工智能正在加快从技术创新走向产业落地和场景重塑，带动了电子、电气机械等行业需求回升和价格上涨。

行业信号可以核对：10 月，电气机械和器材制造业、计算机通信和其他电子设备制造业价格环比均上涨 0.1%，两个行业合计拉动 PPI 同比上涨约 1.18 个百分点。

但前面算过的那笔账，只能说明这两个行业在涨，说明不了涨的是不是 AI 订单。当前材料给出了需求回升和价格上涨的事实，没有披露 AI 订单的增速，也没有第三方复测数据。1.18 个百分点不能全部记在 AI 头上，更不能推断它会持续扩大。

能源相关行业提供了另一组观察变量。其价格受国际大宗商品走势、迎峰度冬需求和供应条件共同影响：国际能源价格高位震荡，叠加电煤、燃气需求进入季节性上升阶段，煤炭主产区供应偏紧。国际能源价格回落，或国内供应偏紧缓解，都会削弱这一轮价格推力；迎峰度冬需求继续增加，则可能让相关价格保持支撑。

判断 AI 需求是否接住价格，可以连续盯住三个信号：电子、电气机械价格的环比涨幅是否维持正向，行业订单是否随 AI 部署继续增长，以及 PPI 总涨幅在能源贡献变化后能否保持。若 AI 行业价格环比转负且订单没有增长，说明产业落地尚未形成持续支撑；若价格与订单同步走强，AI 对工业品价格的贡献才更可能延续。

王冠华对后市的说法是，国内产业体系配套完整、产业链供应链韧性增强，能源自主生产能力稳步提升，进口渠道日益多元，能够较好对冲外部波动；新兴产业需求释放也将继续支撑工业品价格。这话仍需后续数据验证：10 月的 5.7% 只是结果，能源波动减弱后，AI 需求能不能成为更稳定的价格支撑，要看后续数据。

动手 

## 下一期怎么验证，AI 需求真进了价格表

下一次统计局发布，先看两个数：电气机械和器材制造业、计算机通信和其他电子设备制造业的 PPI 环比。10 月这两个数都是上涨 0.1%，跟它比方向，比看总指数有用。

国家统计局给出的落点就是这两类行业。10 月，两者 PPI 环比（PPI较上月的环比变化）都上涨 0.1%。这已经给出观察起点：后续发布仍上涨，说明价格方向延续；转为下降或持平，则本次上涨没有立即延续。

订单是第二个观察点。发布会把人工智能产业落地、场景应用与行业需求回暖连在一起，但现有材料没有公布电子、电气机械企业的订单金额、交付周期或库存数据。读者可以等待企业公告、财报或官方行业数据，核对需求回升是否落实到订单变化，而不是只凭一个月的价格数据判断。

还要守住一条边界：价格上涨不等于所有企业利润都增加。原料、运费和采购成本若同步上涨，出厂价上升可能只是成本传导。国家统计局提出，新兴领域需求持续释放将继续支撑工业品价格，但国际大宗商品价格仍有不确定性；因此，观察电子和电气机械时，需要同时看订单与投入成本，不能把两项行业的涨幅直接等同于 AI 需求强度。

数据发布后，先对照行业分类确认“电子”和“电气机械”的口径，再比较相邻月份。材料只给出工业生产者出厂价格，没有零售价，也没有 AI 专项订单指标；这些数据出现之前，能够验证的是行业价格方向，不能精确算出 AI 究竟贡献了多少。

把下一次价格发布变成一次可复核的检查 1

记录电子与电气机械当月 PPI 环比方向，并与 10 月的上涨作对照。

2

查阅企业公告或财报，核对订单、交付与库存是否出现同方向变化。

3

对照原料与运费变化，判断出厂价格上涨来自需求还是成本传导。

## 先从我的托盘说起

我的 Windows 托盘右下角，曾经是一排截图类软件的「全家福」：截图用一个，录屏用一个，图片转文字再开一个，想把截图钉在屏幕上对照着看，还得再来一个。每个单看都不大，加起来几百 MB，关键是心累——截个图先想三秒该点哪个图标。

SnowAir 轻雪就是冲着这个痛点来的。开源（Apache-2.0）、免费，免费版只有一个 4.5MB 的 exe 文件，双击就跑。截图、标注、长截图、录屏、贴图、OCR、翻译，它一口气全包了。

丑话说在前面，省得你白跑一趟：

  * 只有 Windows 版，Win10 1809 以上 / Win11，64 位。Mac 和 Linux 的朋友可以关页面了；
  * 版本号还在 0.1.x，更新很快，个别功能（比如叫「晾衣架」的剪贴板）还挂着 Beta；
  * 离线 OCR、离线翻译的组件不在 exe 里，要去设置里按需下语言包。不下也能用在线识别，就是得联网。

它还有个专业版，基于 Qt6，多了 AI 大模型、屏幕镜像、超级动作、快捷翻译这些。界面和操作跟免费版一致，我的看法是：先用免费版，日常真用不上那些。

## 我觉得最值的三个功能

**贴图。** 把截图钉在桌面最上层，对着参考图干活。对参数、抄数据、比设计稿的时候不用 Alt+Tab 切来切去——这个功能用过的人都知道有多香，Snipaste 当年就是靠它封神的，轻雪这边也没落下。

**长截图。** 网页、聊天记录、长文档，一次拖到底截完，不用截三张再拼。写教程的人应该都懂拼图的痛苦。

**OCR 顺手。** 框一下图片，文字就出来了，还能接着翻译。不是那种要单独开软件、等它启动半天的正经 OCR，就是随手一框的事，频率对了。

配置是 Mac Studio M5 Ultra，36 核 CPU、80 核 GPU、256GB 统一内存、2TB SSD，苹果中国官网价 90,499 元。

机器买回来后，最容易踩的坑不是性能不够，而是一直找不到足够重要的工作交给它。今天测一个模型，明天跑一个渲染，后台截图不少，真正留下来的作品、交付和账单变化却没有。

把公开内容里只有开箱跑分的部分去掉，再看那些有连续调用、完整作品或可复现仓库的案例，这台电脑大致可以接管六类工作：**本地 Agent、AI 音视频创作、模型与工作流调优、私有资料处理、专业后期、macOS 开发测试。**

它能带来的收益则只有三种：**赚钱、省钱，以及隐私和自主权这类非现金价值。** 三种都成立，但不能混成一本账。公开案例能证明「有人确实这样做」，不能证明「买同款就能赚回 9 万」。

## [](https://h89.cn/archives/870.html#content-一这台电脑可以接管六类工作 "Permalink")一、这台电脑可以接管六类工作

![Mac Studio 六类用途与最终产物](https://blog-chenjim.oss-cn-shanghai.aliyuncs.com/2026/261116-mac-studio-six-deliverables.png-blog)

用途 | 最后留下什么 | 最可能产生的收益  
---|---|---  
本地 Agent 工作机 | 代码修改、研究报告、自动处理结果 | 减少已有 API 支出，提高内部交付能力  
AI 音视频创作 | 图片、音乐、视频、完整 MV 和工程文件 | 替代已有素材外包，销售内容交付  
模型与工作流调优 | 可运行配置、性能报告、输出对照和失败清单 | 减少调试时间，提供适配验收服务  
私有资料与家庭影像 | 本地问答、视频目录、人物索引和精选片段 | 保护隐私，减少人工整理和外部处理  
专业影视后期 | 转码文件、ProRes 母版、代理和特效结果 | 替代已有转码与后期支出，接固定任务  
macOS 开发测试 | 应用、构建产物、测试结果和环境清单 | 替代云 Mac、云 CI 或重复开发设备  
  
### [](https://h89.cn/archives/870.html#content-1-让本地-agent-长期值班不只是偶尔问几个问题 "Permalink")1\. 让本地 Agent 长期值班，不只是偶尔问几个问题

Chiphell 用户 lwzx 的使用记录很接近这套配置。他在 36+80、256GB 的 M5 Ultra 上常驻大模型跑长程编程 Agent，连续记录了 **11 天、52 个会话、10,025 次调用** ，同时保留 MiniMax H3 视频生成任务。更有参考价值的是，他持续调整缓存、并发和上下文上限来处理内存与稳定性问题，而不是只报一次峰值速度。

GitHub 项目 ultra-ultra 则展示了另一种分工：一台 256GB M5 Ultra 同时常驻两个模型，一个主 Agent 负责对话，8 个 worker 负责子任务，并验收 4、8、16 路任务分发。

这类用法的关键不是「本地也能聊天」，而是让 Agent 连续接管代码检索、修改、测试、资料整理和报告生成。原来就为这些任务支付 API 或云服务费用，迁移后才有省钱空间；要对外服务，则应交付配置和连续运行验收，不是卖一个聊天窗口。

### [](https://h89.cn/archives/870.html#content-2-把图片音乐和视频串成一条本地创作流水线 "Permalink")2\. 把图片、音乐和视频串成一条本地创作流水线

抖音博主「碳基生物退役指南」用一台 256GB Mac Studio 接管 AI 创作：Qwen 处理文本与代码，Qwen Image 出图，Yue2 生成音乐，MiniMax H3 生成视频，再让 Hermes Agent 调度这些能力制作完整 MV。除此之外，他还用 CPU 做 Remotion 4K 视频渲染，并把机器配置过程整理成开源工具。

这个案例的重点不是单张图生成得多快，而是**最终留下了一支完整作品和一套可以再次使用的流程** 。

如果原来就为素材生成、配音、视频初稿或渲染付费，迁回本地可能减少支出；如果对外接活，则应销售 MV、短片素材包或工程文件。只生成一堆没人使用的图片，既没有节省，也没有收入。

### [](https://h89.cn/archives/870.html#content-3-帮别人把模型和-comfyui-工作流跑稳 "Permalink")3\. 帮别人把模型和 ComfyUI 工作流跑稳

很多团队缺的不是又一个模型下载地址，而是某个模型、某个版本、某组并发在自己的任务上到底能不能稳定工作。

ComfyUI-AppleSilicon-Optimized 项目在 M5 Ultra 上持续测试 Wan、MiniMax H3、SeedVR2、YuE2 等图像、视频、超分和音乐工作流。其中一次回归把 **35 个工作流或模式案例执行两遍** ，并保留原始结果。GLM-5.3-Flash-M5-Ultra-oMLX 项目则围绕本地 OpenAI 兼容推理，提供模型补丁、服务脚本以及长上下文、视觉和 Agent 工具调用验收。

这些工作可以沉淀为明确交付：可复现命令或工作流、速度与内存峰值、输出对照、失败清单和适用边界。它比泛泛的「本地部署服务」更容易验收，也更能发挥大内存和多任务常驻的价值。

### [](https://h89.cn/archives/870.html#content-4-处理不方便上传云端的私有资料和家庭影像 "Permalink")4\. 处理不方便上传云端的私有资料和家庭影像

GitHub 项目 VideoScan 在做一件很具体的事：扫描家庭录像，提取媒体信息，识别人物，按年代整理并提取精选片段，最后形成可校验的私人影像档案。家庭素材不必交给云端人脸识别或外部整理服务。

同样的思路也适用于获得授权的合同、研究资料、内部文档和历史项目文件：在本地建立问答、检索、编目或批量整理流程，交付答案、索引、目录和失败记录。

这类收益首先是隐私和自主权，其次才是钱。只有原来确实付费外包整理，或者客户愿意为本地处理付费时，才出现现金改善。资料授权、人物信息和使用范围也必须先确认。

### [](https://h89.cn/archives/870.html#content-5-做转码调色和专业后期不只围着大模型转 "Permalink")5\. 做转码、调色和专业后期，不只围着大模型转

Apple 官方规格里，M5 Ultra 配有两个视频解码引擎、四个视频编码引擎和四个 ProRes 编解码引擎，支持 H.264、HEVC、ProRes / ProRes RAW 硬件加速。

PRONEWS 的职业调色师还实测了 8K RED RAW、ProRes 输出、DaVinci Resolve 的 AI 蒙版与 Relight、17 节点调色和 OpenEXR 多流播放。这是一次专业评测，不是长期自购使用证明，但至少说明它面对的不只是本地模型任务。

对普通工作室而言，更实际的交付通常不是「帮你体验 8K」，而是批量转码、ProRes 母版、1080p 代理、AI 蒙版或指定特效输出。原来就有外包，可以比较迁回后的实际费用；对外接单，则按素材规模、格式和验收结果报价。

### [](https://h89.cn/archives/870.html#content-6-当-macos-主力开发机把旧设备降为测试机 "Permalink")6\. 当 macOS 主力开发机，把旧设备降为测试机

VideoScan 的设备分工也值得参考：M5 Ultra 是日常开发机，原来的 M4 Studio 转为无头测试机，配合夜间轮值和持续测试。新机器负责写代码、构建和交互，旧机器继续承担后台任务，而不是立刻闲置。

这套方式适合 Xcode、Swift、跨平台应用和需要 macOS 环境的持续集成。它可以替代原来付费的云 Mac、云 CI 或重复设备，但验收物仍然是应用、构建产物、测试结果和环境清单，不是编译跑分。

## [](https://h89.cn/archives/870.html#content-二收益只有三种别把它们混成很值 "Permalink")二、收益只有三种，别把它们混成「很值」

![赚钱省钱与非现金价值三本账](https://blog-chenjim.oss-cn-shanghai.aliyuncs.com/2026/261116-mac-studio-three-ledgers.png-blog)

按原估算，这台机器每月折旧、资金和保守电费合计约 **1,966 元** ，不含人力。这个数字不是必须完成的收入任务，却是一面很好的照妖镜：所谓收益，到底能不能落到账目上？

### [](https://h89.cn/archives/870.html#content-1-赚钱只认已经回款的交付 "Permalink")1\. 赚钱：只认已经回款的交付

不要先卖「高配置」和「算力」，先卖别人愿意验收的东西。下面保留四个试销套餐，金额只是第一轮需求测试的锚点，不是市场均价或收入承诺。

试销交付物 | 固定范围 | 试报价  
---|---|---  
批量转码包 | 单批 ≤100GB，两种输出，含校验和失败清单 | 300 元/批  
MLX / ComfyUI 适配验收 | 约定模型或工作流、上下文与并发，含输出对照 | 1,500 元/份  
私有资料问答 PoC | ≤200 份授权 PDF，20 个约定问题，单机部署 | 3,000 元/次  
macOS 构建验收 | 1 个授权 Xcode 项目指定提交，不含签名和发布 | 800 元/次  
  
本地 Agent 调优、完整 MV 和私人影像归档也可以做成服务，但要先各拿一份样例验证需求。客户愿意付钱的是结果，不是机器参数。免费订单、口头夸奖和「以后有项目找你」都不能记收入。

### [](https://h89.cn/archives/870.html#content-2-省钱只认真实取消的账单和实际到账 "Permalink")2\. 省钱：只认真实取消的账单和实际到账

先导出最近三个月的 Mac 云主机、云 GPU、API、素材生成、渲染、转写、VPS 和持续集成账单。替代流程稳定运行后，真正取消旧服务，才算每月支出减少；只是关机但继续扣费，不算。

旧 Mac、CUDA 主机和显卡如果确实被替代，可以比较 Apple Trade In、平台回收和个人买家的到手价。旧设备出售属于一次性资产回收，不是这台电脑每月创造的收入，没到账以前按 0 算。

原来从未付费外包过的工作，迁回本地也不会凭空产生节省。比如旧设备功率计实测合计 1.2kW，迁移后每天少开 4 小时，按 0.617 元/度计算，每月约少 **88.85 元** ——这是真钱，但没必要夸大成几千元。

### [](https://h89.cn/archives/870.html#content-3-非现金价值隐私常驻能力和设备自主权 "Permalink")3\. 非现金价值：隐私、常驻能力和设备自主权

有些收益本来就不该硬折算成人民币：

  * 家庭影像、内部文档和客户代码不必上传第三方云；
  * 大模型、图像和视频工具可以常驻，不用每次等待冷启动；
  * 不被单一 API 的额度、排队和价格变化牵着走；
  * 主力机与旧测试机重新分工，减少桌面设备和环境切换。

这些价值可能很重要，但它们不会自动抵消每月约 2,000 元的持有成本。承认「我买它是为了更好用」，比编造一份收入表更诚实。

现金验证则很简单：如果实际取消 500 元账单，再收到一份 1,500 元验收报告款，当月现金改善才是 2,000 元。公司购买且用于经营时，还可以让会计确认设备税前扣除政策是否适用；那是条件性税务影响，不是个人购机补贴。

## [](https://h89.cn/archives/870.html#content-三这四件事看起来热闹却不是收益 "Permalink")三、这四件事看起来热闹，却不是收益

**第一，跑分和播放量不是回款。** 它们可以帮助展示能力，但不能直接填进收益表。

**第二，免费交付不是市场需求。** 连续询价无人付费，就应该下架或缩小范围，不靠免费订单制造繁荣。

**第三，理论可替代不等于实际省钱。** 没有旧账单、没有外包、没有旧设备被替代，相关节省就是 0。

**第四，能创建虚拟机不等于能收费出租。** Apple 标准许可允许最多两个额外 macOS 虚拟实例用于开发、测试、macOS Server 或个人非商业使用，同时明确排除 service bureau、time-sharing 等服务。VM 更适合隔离自有或授权项目的开发测试环境，不应写成收费出租的主路径。

出租、数字产品、课程和会员都可以后续尝试，但在收款、许可、数据和真实需求得到验证以前，不进入基础预算。

## [](https://h89.cn/archives/870.html#content-四别六种用途一起上用-90-天验证一条主线 "Permalink")四、别六种用途一起上，用 90 天验证一条主线

![30天60天90天验证一条主线](https://blog-chenjim.oss-cn-shanghai.aliyuncs.com/2026/261116-mac-studio-90-day-checkpoints.png-blog)

最稳妥的做法是选「一个主要用途 + 一个辅助用途」。主力开发就选 Agent 和构建，内容创作就选本地音视频和转码，私有资料处理就先围绕一类授权文档或影像做样例。不要先买齐硬盘、带宽和课程，再寻找问题。

  * **30 天** ：产出一个完整作品或验收报告，并至少停掉一笔真实账单，或完成一笔付费交付。
  * **60 天** ：确认至少一个流程每周重复使用，而不是不断换模型、换引擎和重新配置。
  * **90 天** ：核对实际回款、取消的支出、新增运维和投入时间，决定继续扩展、保持纯自用，还是停止追加投入。

如果仍在 Apple 官方退货期限内且商品符合条件，可以按政策申请退货；Apple 中国要求对符合退货条件的商品在交付之日起 **14 个自然日内** 申请。过了退货期，再比较继续持有与转售，不必为了证明当初买对而继续投钱。

这台 Mac Studio 的价值，不是把六种用途全打勾，而是让其中一两种变成稳定的工作流：**持续留下产物，真实减少账单，或者带来可以核验的回款。** 做不到现金收益，也不等于机器没用，只是别再拿效率和跑分冒充回本。

## 先约定上层究竟要拿到什么

这个系列里的 Provider，指负责适配模型服务 API 的那层代码。runtime 把内部消息、工具定义和模型选项交给它，它负责转换请求、消费响应，再交回内部结果。各项目的命名未必一样，这里按这个边界讨论。

先别急着写 HTTP。上层至少得和它约定好两种结构：
    
    
    ModelRequest
      model          本次模型标记
      history        有顺序的消息、工具调用、工具结果及必要非文本项
      tools          工具名、说明和参数约定
      stream         是否需要增量展示
    
    ModelReply
      status         ok / failed / cancelled
      text           收到的展示文本
      calls          完整调用候选：id、name、args
      finish_reason  归一后的终止原因
      usage          已知用量；未知字段不补零
      error          失败原因
      replay_items   下一轮协议要求保留的其他输出项

这是我们自己的契约，不是哪家 API 的字段表。实际实现可以用类型或数据类表达。后面的标准库实验就按其中这些字段返回结果。

把 `text` 和 `calls` 分开有个很实际的好处：界面可以先展示文字，执行管线只认完整候选。`failed` 也可以带回部分文字和已知用量，但不能靠「返回对象里还有点内容」推断本次成功了。

`replay_items` 也有必要。部分接口或模型要求下一轮带回非文本输出项。统一结构如果只剩一段文本和几个工具名，第一次请求可能看不出问题，续接时却已经丢了协议需要的东西。这些项应当按对应 API 保留和回放，不能把不同厂商的私有结构混着重传。

![一次模型请求经过能力校验、序列化、流式归一后交回 runtime，工具结果再进入下一轮](https://www.echovic.com/_astro/d89552fa47a0fad0a7c6f55c9cf32694d1066c5f2d4de96bfe2e03c16c629d0b.By3xaFtY_ZcGut.webp)

Provider 先检查要求能不能满足，再编译请求。比如选定的模型或端点不支持工具调用，教学实现就直接报错，不把工具列表悄悄删掉。真实项目也可能提供明确的降级路径，但要让上层知道降级了什么。

所以，换 `base_url` 只解决请求发到哪里。两端确实兼容同一份协议时，这样换很方便；一旦请求结构、工具表达或结束事件不同，就需要真正的适配。

[OpenAI Responses](https://platform.openai.com/docs/guides/function-calling)用 `function_call` 输出项表示函数调用；[Claude Messages](https://platform.claude.com/docs/en/build-with-claude/streaming)把它放在 `tool_use` 内容块里。它们可以映射为同一种内部候选，但原生字段、调用关联方式和生命周期都得分别处理。错误和用量也在这个边界里，不能只适配成功时的文本。

## 流式有三层，别从字节直接跳到工具

我们拿到的「一块数据」，可能是三种完全不同的东西。

最底下是网络字节块。一次读取可以停在 UTF-8 字符中间，也可以只有半条 SSE 记录。它和模型打算说多少内容没有对应关系。

往上一层是完整 SSE 事件。解析器要处理记录边界，再解析事件里的数据。这里讨论的 OpenAI Responses 和 Claude Messages 直连 HTTP 流式接口都使用 SSE，但事件结构并不相同。

再往上，才是文本增量、工具参数增量、终止通知等模型语义事件。我们自己写的适配逻辑，最好从成熟 SDK 已经解好的这一层接手。下面的实验也从这里开始，不手写一个只能碰巧跑通的 UTF-8/SSE 解析器。

回到两个 `read_file`。适配后可以得到这样的内部事件顺序：
    
    
    call_start  c1  read_file
    call_start  c2  read_file
    args        c1  {"path":"src/
    args        c2  {"path":"tests/test_convert.py"}
    call_end    c2
    args        c1  convert.py"}
    call_end    c1
    finish      tool_calls

这些事件名是教学约定，不是真实 API 协议。

如果只用一个字符串缓冲区，两个路径会接到一起。最小实现也得有一张表：键是内部调用 ID，值里放工具名、参数片段和块是否结束。`c2` 先拼完，只更新 `c2` 的状态，不影响还在等待的 `c1`。

原始分片未必每次都带完整 ID。OpenAI Responses 的参数增量可以按输出项序号和标识关联；Claude Messages 用内容块的 `index` 定位参数增量。适配器先追踪原生槽位，在调用身份稳定后映射为内部 ID。这里不能假定「每来一块，就新建一个调用」。

![蓝色机器人把传送带上的碎片拼成一把完整的工具](https://www.echovic.com/_astro/c3867e9d95a0e2dfa0fa380c846ace5d9060188e5df12e1a2a3cbc2f7c1704e3.DvS09vDD_Z2o8T5y.webp)

现在 `c2` 的 JSON 已经合法了，能执行了吗？这篇先选保守策略：等整次返回正常结束，再统一校验并交出候选。

它会牺牲一点提前执行的机会，换来一个好检查的边界。UI 的进度展示可以很早发生，工具执行不跟着半成品走。更激进的调度可以以后再加，前提是先讲清楚某个块完成和整次响应异常之间如何处理。

## JSON 完整，还差一次「能不能交付」的判断

有三种结束要分开：参数块结束，一次模型响应结束，整个编码任务结束。

第一种只说明一个块收齐了。第二种还要看结束原因，可能正常，也可能被截断或失败。第三种需要 runtime 根据任务进展继续判断。读完两份文件，显然还不能宣布单位换算已经修好了。

![按调用 ID 独立组装参数，确认正常结束并校验后交回候选，异常和取消保留原因与已知用量](https://www.echovic.com/_astro/5991a9549b2e199c879667488978d35d8b6255c063b8382e25ada21562844d03.DvDfZ6In_10szmL.webp)

我们的归一层用 `stop` 表示正常的无工具返回，用 `tool_calls` 表示正常交付工具调用，用 `length` 表示截断。这些名字只服务于内部契约。真实适配时，[Responses 的生命周期事件](https://platform.openai.com/docs/guides/streaming-responses)和 Claude 的 `stop_reason`、`message_stop` 要分别映射，不能照抄这几个字符串就算完成。

连接不再产生数据，也不自动等于正常结束。假设两个参数块都结束了，接着出现流尾错误，当前尝试仍然失败；如果 JSON 后面根本没收到预期终止，读到 EOF 也不能冒充成功。

用量要走一条独立的记录路径。流尾报错之前可能已经收到 `usage`。它说明本次尝试已有消耗，不能因为候选没提交就清零。Claude Messages 文档还明确说明，`message_delta` 中的用量是累计值，逐条相加会重复计算。

实验把用量归一成累计快照，同一字段覆盖更新，没收到的字段保持未知。取消时也带回最后已知快照。这个值未必是最终账单，本地停止读取不保证服务端立即停止生成和计费。

错误原因同样要留下。认证失败、不支持请求、限流、上游服务异常、传输中断，后续处理不同。正式实现可以给 `error` 增加类别、是否可重试和经过脱敏的说明；实验只使用合成错误字符串，避免把错误分类系统一起塞进来。

## 把交付边界写成一个能测的函数

下面这段是实验里决定是否交付候选的完整函数。`calls` 是前面那张调用表，每项有 `name`、`parts` 和 `ended`；`reason` 来自归一后的终止事件。

**这是教学模拟，不调用真实 API，不执行工具。** 本例只支持 `read_file(path)`，有一个调用无效就整批拒绝。路径权限和工具真正能不能执行，留给后面的管线。
    
    
    import json
    
    def finalize(calls, reason, usage, error=None):
        result = dict(status='failed', finish_reason=reason,
                      calls=[], usage=dict(usage), error=error)
        if error:
            return result
        if reason not in ('stop', 'tool_calls'):
            result['error'] = '缺少正常终止，或返回被截断'
            return result
        if (reason == 'stop' and calls) or (reason == 'tool_calls' and not calls):
            result['error'] = '终止原因与调用内容矛盾'
            return result
        ready = []
        for call_id, call in calls.items():
            try:
                if not call['ended'] or call['name'] != 'read_file':
                    raise ValueError
                args = json.loads(''.join(call['parts']))
                if (not isinstance(args, dict) or set(args) != {'path'}
                        or not isinstance(args['path'], str) or not args['path'].strip()):
                    raise ValueError
            except (ValueError, TypeError):
                result['error'] = '调用未完成，或参数不符合约定'
                return result
            ready.append(dict(id=call_id, name=call['name'], args=args))
        result.update(status='ok', calls=ready)
        return result

这里故意先检查整次终止，再解析参数。即便参数是合法 JSON，只要流尾失败，结果仍然是 `failed`，`calls` 仍为空。参数通过校验，也只得到候选，不在函数里读文件。

把组装和交付分开之后，这段可以直接测，不需要开一个 HTTP 服务。完整的[模拟程序](https://www.echovic.com/static/coding-agent-series/04/stream_demo.py)还包括能力检查、事件收集和下一轮历史关联；[测试文件](https://www.echovic.com/static/coding-agent-series/04/test_stream_demo.py)可以一起保存到同一目录。Python 3.9 或更新版本就够，不装第三方包。
    
    
    python3 stream_demo.py
    python3 -m unittest -v test_stream_demo.py

程序内置的是上面的交错分片，并分别演示正常、完整参数后的流尾错误、完整参数后的取消。正常时得到 `c1`、`c2` 两个候选；后两种都不交付候选，但带回已知用量与失败原因。正常路径再用两份假文件内容构造下一轮，整个过程没有访问真实源码文件。

我实际跑了 30 项测试。其中包括两个调用交错、不同字符串切分点、坏 JSON、缺块结束、缺响应结束、截断、结束后继续收到内容、模拟断线、用量快照倒退，以及工具结果 ID 对不上。所有测试通过。程序里的 token 数和 `cached` 值都是合成数据，不是成本报告，也不是缓存命中实测。

要自己改一个地方试试，可以删掉 `sample()` 中的 `finish` 事件，保留两份完整参数。再运行，观察 `calls` 是否仍为空。然后恢复它，只把 `c2` 的 `path` 改成数字，看校验会不会挡住。这两步能检查你的实现到底是在「拼出 JSON」时放行，还是在约定的交付点放行。

## 沿 Orca 的一条调用路径读下去

实验省去了真实传输层。想看它落到项目里是什么样，可以固定读 Orca [v0.5.20](https://github.com/echoVic/orca-agent/releases/tag/v0.5.20) 的 DeepSeek 适配路径，避免跟着会变化的默认分支跑。

入口是 [`deepseek_http.rs`](https://github.com/echoVic/orca-agent/blob/v0.5.20/crates/orca-provider/src/deepseek_http.rs) 的 `request_chat_streaming_with_budget`。它先通过 `conversation_to_api_messages` 编译历史，构造模型、消息、工具等请求字段，并在流式选项中请求返回用量。到这里才发 HTTP。

字节流交给 [`streaming.rs`](https://github.com/echoVic/orca-agent/blob/v0.5.20/crates/orca-provider/src/streaming.rs) 的 `parse_sse_response_with_partial`。往里读，`process_complete_lines` 处理跨网络块的行数据，`StreamAccumulator::push_line` 消费完整数据。工具参数经过 `accumulate_tool_call`，按 `delta.index` 找到缓冲槽，ID 到达后记录，参数则持续追加：
    
    
    if let Some(ref args) = func.arguments {
        buf[idx].arguments.push_str(args);
    }

这也解释了为什么进度事件不能直接当执行指令：收到一个参数片段时，连稳定 ID 都可能还没到。这里真正维护的是带身份和生命周期的缓冲状态。

同一个 `push_line` 里，有一小段顺序值得看：
    
    
    if let Some(chunk_usage) = chunk.usage {
        self.usage = Some(chunk_usage.into());
    }
    if let Some(error) = chunk.error.as_ref().filter(|error| reports_error(error)) {
        return Err(stream_error_message(error));
    }

先保存用量，再返回上游错误。外层的 `StreamParseError` 同时带原因和已知用量，取消、超时及提前 EOF 等路径也尽量把已知消耗带回去。它的 `finish` 检查则按自己的协议约定处理结束标记，并没有要求所有 API 都同时出现相同的标志。

回到 `request_chat_streaming_with_budget`，正常解析后还要处理结束原因、解析调用，最后才形成 Provider 的结果。在普通工具请求路径里，`length` 之类的结束不能混成正常交付。

这里有两处和教学实验不同，读源码时别硬套。

一处是坏参数。这个版本的测试 `streaming_invalid_tool_arguments_are_returned_for_tool_failure` 表明：传输正常但参数无效时，它可以保留原始参数，返回未解析成有效目标的调用，交给后续工具失败反馈，让模型纠正。我们的实验直接拒绝整批。两种选择的共同要求是无效参数不能进入实际执行，错误反馈放在哪层可以不同。

另一处是重试。这个 Provider 内部有受预算限制的流完整性重试，还检查是否已经发出进度，并合并不同尝试的用量。因此不能简单规定「所有重试只能在 runtime」。更实际的约束是上下层共享重试预算，别各自重试三次，最后请求次数相乘。

不过，请求重试和工具重试仍得分开。重新发一次模型请求，可能拿到新的调用 ID 或新的参数；它不能替你证明上一次写文件、发请求或执行命令有没有完成。`call_id` 用来关联调用和结果，也不自动提供全局幂等。执行去重需要 runtime 自己的操作、尝试和结果记录，后面写 runtime 时再展开。

## 前缀缓存，先拿两轮输入比一下

读实现和测试之后，agent 还要继续请求模型。此时固定指令通常没变，之前的历史也还在，新增的是刚才的调用和工具结果。

前缀缓存可以复用服务端已经算过的输入前缀。能复用到哪里，取决于模型实际看到的输入和该服务的缓存规则。我们先只看自己能控制的逻辑顺序。

设 `S` 是固定指令，`H` 是首轮已有历史，`ΔH` 是首轮之后追加的调用和工具结果。两轮跨了日期，日期片段从 `D1` 变成 `D2`；工具定义和模型保持不变。

![两轮逻辑输入对照：日期前置会提前遇到变化，日期放在历史后保留更多共同稳定部分](https://www.echovic.com/_astro/5d960b6e81f4a6ab523747f9c87c6f55557ea605369a510919e8b29ad52c83db.DzBo4o7t_2aqL7g.webp)

上半部分先放日期。第二轮还没读到 `S`，就已经遇到不同内容。后面的 `S`、`H` 即使没动，也不能据此算作从开头连续匹配的那段。

下半部分把当前日期作为单独的动态片段放到已有历史之后。第二轮保留 `S`、`H`，再追加 `ΔH` 和更新后的日期，前面那段稳定内容就更容易保留下来。

这图省略了厂商隐藏前缀，也没有画工具 schema 的内部渲染。它说明的是可控消息顺序如何影响变化点，不代表上半部分所有缓存都被清空，更没有把彩色方块当成真实 token 边界。

Orca v0.5.20 的日期处理可以沿代码核对。runtime 的 [`runtime_turn_opening.rs`](https://github.com/echoVic/orca-agent/blob/v0.5.20/crates/orca-runtime/src/runtime_turn_opening.rs)在轮次入口更新 `conversation.set_today(...)`，日期放进内部上下文；`system_prompt.rs` 有测试确认固定系统提示不含 `Today's date`。

再接着读 `deepseek_http.rs` 的 `conversation_to_api_messages`，它先序列化历史、工具调用和工具结果，历史处理完之后，才把 `render_internal_context(conversation)` 渲染出的动态片段追加到消息末尾。`context.rs` 中的同名函数负责渲染内部上下文。这样就能从「日期在哪里更新」一路追到「请求里最后放在哪里」，不用只信发布说明的一句话。

这条代码路径说明了它怎样减少动态内容对既有前缀的改写，不能据此推算缓存命中率。

[OpenAI 的缓存文档](https://platform.openai.com/docs/guides/prompt-caching)同样建议稳定内容在前、动态内容在后，但真实复用还受模型支持、可缓存边界、路由和有效期等条件影响。显式缓存断点也只适用于文档明确支持的模型与 API，不能套到所有兼容接口上。

实际整理请求时，我会先固定工具定义和固定指令的生成方式，保留既有历史，在末尾追加真正新增的内容。若接口支持 `allowed_tools` 这类能力，可以评估保留工具定义、单独限制当前可用子集。是否支持、如何渲染，仍要按具体接口核验。

这里做的是减少无意变化。比较两个 Python 字典的键顺序，或者计算两段字符串的共同前缀，都不能代替模型 token 和服务端命中数据。权限真的变了，就更新有效请求；不能为了缓存继续带旧权限。

缓存命中只是让服务端少重复算一段输入，不会替 agent 保存任务记忆。下一轮需要的历史和工具结果，仍要按接口要求提交或续接，不能因为上一轮命中过，就把必要上下文省掉。

## 最后把工具结果接回去，才算接完一次请求

`c1` 和 `c2` 通过后续执行管线，拿到两份文件内容之后，下一轮得能认出哪份结果回答了哪个调用。

在 OpenAI Responses 的函数工具路径里，模型输出的 `function_call` 带 `call_id`，客户端用同一个值回传 `function_call_output`。下面只摘出关联字段，示例 ID 是假值：
    
    
    {
      "type": "function_call",
      "call_id": "c1",
      "name": "read_file",
      "arguments": "{\"path\":\"src/convert.py\"}"
    }

对应的工具结果是：
    
    
    {
      "type": "function_call_output",
      "call_id": "c1",
      "output": "假实现内容"
    }

结果靠 ID 对应，不能靠「第二个结果应该属于第二个调用」。并行执行时完成顺序可能不同；读两次同名工具也不能靠工具名区分。实验中的 `next_history` 因此要求结果 ID 集合与候选调用精确对应。

接下来有两种会话组织方式，要按选定 API 分开实现。

客户端自己管历史时，把需要的旧输入和完整响应项保留下来，再加入本轮工具结果。对 Responses 来说，官方[会话状态文档](https://platform.openai.com/docs/guides/conversation-state)展示的是保留 `response.output` 等所需项，不能只摘 `output_text`。适用模型要求的非文本项、关联信息，也要继续带着。附件里的 `replay_items` 只是用一个不透明的合成项演示「不要在统一结构里丢掉它」，没有模拟真实 reasoning 协议。

如果使用 Responses 的 `previous_response_id`，就由服务端接上它已保存的响应，再按接口要求传入本轮新增项。此时不必把「客户端重传完整历史」那套机械地叠加一遍；上一轮哪些配置会继承，也要遵循该接口规则。

所以，说一次请求无状态，通常是在讲客户端需要提供足够的请求上下文。服务端有状态的续接 API 是另一种实现选择。两者都不等于 agent 没有任务状态，更不能据此推导服务端是否保存数据。

工具到底有没有执行、哪次尝试被取消、审批停在哪里，这些记录依然属于 runtime。Provider 帮它接模型，并不会因为拿到了一个响应 ID，就替它持有完整的任务执行记录。

搭到这里，可以先拿实验里的事件驱动自己的 Provider 边界：成功时交付两个候选，截断或流尾错误时不交付，失败仍保留已知用量，下一轮工具结果能按 ID 对回去。把这条路径跑稳，再接真实 SDK，出了问题就能分清是在协议适配里，还是已经到了执行管线。
