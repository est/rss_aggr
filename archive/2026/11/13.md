我估计人人都是想有一些超能力的，这跟咱们的优绩主义以及社会达尔文主义不无关系。又或者其实我们都想要有超过物质身体本身限制的欲望。这也解释了为啥超人、变异者还有神怪这类文艺作品那么流行，很多人爱看。

但不好意思，嘿嘿，大自然就是和你玩儿。目前人想要点实实在在的超能力是没得搞头的啊。

我想起初中的时候，流行的那本《哈佛女孩刘亦婷》。很多父母，包括老师都有点魔怔啊。里面有个情节是刘亦婷了为锻炼意志，被要求用手捏住一块冰坚持约15分钟，直到手冻得青紫、麻木也不松手。我们的班主任就信了邪。给我们说，你看人家刘亦婷，意志力多强，手里可以捏一块冰15分钟。我看你们一分钟都捏不了。

我不知道班主任有没有回家拿自己或着自己的孩子试过。而我想15分钟也不算个啥吧，不过还好，那时家里没有冰箱，因此没有过尝试。还好没有，要是冻坏了就傻B了。谁脑子抽了握15分钟冰啊，锻炼了个寂寞吗？还是证明自己比别人傻。

但我不得不承认我还是有一些超能力的啊。

小时候到了夏天，我可以预测是否下雨，精确度可以达到分钟级别。只要过会儿会下雨，总会觉得异常闷热，还有点不好喘气。我想这和我老家的天气有很大的关系，盆地嘛。小时候还经常在田里看到对面耕作的乡亲落汤鸡一样的跑，边跑边叫，那是雨从他们那里下过来了。给我们躲雨空出来一段时间。还有的时候在街上，左边太阳，看着右边街上大雨。非常好玩。我的预测下雨的超能力在我上大学离开家乡之后就不灵了。在其他地方，或许我的身体还没有和当地气候达到天人合一，当我感到闷的时候，那单纯就是闷。没有下雨什么事。至此，我的这个超能力就消失了。

我只要轻轻捏拳头，手指各处，主要是手掌和中指食指连接处就会嘎嘎响。小时候我是不知道有这个技能的。直到看到港片里面，主角生气的时候，通常把拳头捏紧。为了凸显主角有多么气愤，会配个音，表示把骨头都捏响了，这生气程度得有多深啊。然后我一捏，发现，开玩笑。我也会啊，不需要生气，也不需要用力啊。另外，我不需要双手合作，只要大拇指按其他手指，都会响，大拇指也可以响。把拳头捏响根本啥都不是啊。

好吧，除了能把指头的第一指节和弯曲摆成一个7字的造型以外，我似乎就没有什么其它超能力了。但想拥有超能力的心是永远都在的啊。连梦里都是。梦里面我通常能飞，但飞的高度通常只有一人高。

好吧，这具物理的躯壳是很难有超能力的。

现在每年体检都瑟瑟发抖，没有负向超能力涌现就算是阿弥陀佛了。

> 装在 Chrome 侧边栏里的开源 AI 代理，接上本地 Ollama 跑的 qwen3 就能干活：一张八行的出货台账，它读出 8 笔记录，过万的三笔加起来 45700 元，答案跟手算对得上。它默认每天往美国的 PostHog 发一条使用计数，两个开关关掉之后抓包是 0 次。

## 页面开着，人得自己数

「这页上共有几笔记录，金额超过 10000 的那几笔加起来多少」，这种问题页面就在浏览器里开着，人得自己点进去一行行数。

这台 Mac mini arm64 上装了个浏览器扩展 Nanobrowser，把模型指向本地 Ollama 跑的 qwen3-8b-local，第一次派它读一张八行出货台账，它没读那张表。

页面就八行，答案也就几行数字。qwen3-8b-local 用了 205.1 秒，qwen3-4b-local 用了 182.2 秒，两个模型给出的答案指向同一个地方：这个页面是 Chrome 扩展的侧边栏页面，无法通过工具进行交互操作。

它读的是扩展自己的 sidepanel.html。侧栏默认只管当前打开的那一个标签页，任务落在侧栏上，它就老老实实去读侧栏。

在输入框里打一个 @，本窗口的标签页列表弹出来，勾上要操作的那个，答案才变。

整个流程跑在本地起的一张测试页上：一张叫「公司年会报销清单」的表单，另一张叫「仓库出货台账」。

## 侧栏里那个输入框

Nanobrowser 是装在 Chrome 侧边栏里的开源 AI 代理，扩展本体 1.12 MB，装完就是一个输入框。截至 11 月 12 日，它在 GitHub 上有 14286 颗星、1529 个 fork、55 个未关闭 issue，69 个订阅者，27 位贡献者，最近一次提交落在 11 月 10 日（2026-11-10T03:43:10Z）。

它要的权限不小：host_permissions 是 `<all_urls>`，permissions 里有 debugger / tabs / sidePanel / scripting / webNavigation。点安装的时候 Chrome 会把这张清单摊开给你看。

发版不算密，但中间断过一回。最近十个版本平均 56.9 天一个，v0.3.0 是 10 月 15 日，v0.2.0 是 10 月 2 日，再往前 v0.1.13 停在 2025 年 11 月 22 日，中间断了 353 天。许可 Apache-2.0，仓库建于 2024-12-31T08:11:27Z。

模型可以接本地的 Ollama，也可以接别的 OpenAI 兼容接口。跑测试的这台机器上是 Ollama 0.40.13，用了两个本地模型：qwen3-4b-local（Q4_K_M，2.5GB）和 qwen3-8b-local（Q4_K_M，5.0GB）。

它手上 19 个工具：
    
    
    snapshot / find / read / screenshot / tabs / navigate / click / hover / scroll
    set / type / press / wait / handle_dialog / ask_user / fill_form / upload
    done / save_file / read_attachment
    

snapshot 和 read 负责把页面读成文字，click、set、type 负责动手，ask_user 是它停下来问人的那个口子。

侧栏左下角是模式开关，右下角是模型名和语言，中间那个框就是输入框。界面中文是完整的，「新对话」「有什么可以帮你的」「就绪」都直接显示。

## 派活第一回，它读了自己的侧栏

同样的事还有一次更早：点侧栏上的快捷提示「总结这个页面」，qwen3-4b-local 用了 151.9 秒，回的是「这个页面是 Chrome 扩展程序的侧边栏……无法总结该页面内容」。

![侧栏里问表格几行，两个模型都回答这是扩展自己的侧边栏页面，无法交互](https://imgs.huluohu.com:443/2026/11/12/20261111-0600-nanobrowser-fig1-wrong-page.jpg)

## 加上 @ 之后才读到真表

![侧栏首屏：输入框在底部，模型名和语言在右下角，派活的地方就是这里](https://imgs.huluohu.com:443/2026/11/12/20261111-0600-nanobrowser-fig4-sidepanel.jpg)

第一道读表题的措辞是：这个页面一共有几笔记录？把金额超过 10000 的那几笔加起来一共是多少？

qwen3-8b-local 在 202.5 秒后回：done(success, "这个页面共有8笔记录。金额超过10000的记录有3笔，合计45700元。")

qwen3-4b-local 在 202.6 秒后给出同一个答案，还自己列了步骤。表格长这样：

单号 | 金额（元）  
---|---  
SO-0801 | 8400  
SO-0802 | 12600  
SO-0803 | 5750  
SO-0804 | 9200  
SO-0805 | 18700  
SO-0806 | 6200  
SO-0807 | 14400  
SO-0808 | 4900  
  
过万的三笔是 SO-0802、SO-0805、SO-0807，12600 + 18700 + 14400 = 45700，合计 45700 元。页面那 8 行金额独立复算也是 8 笔 / 3 笔 / 45700。

面板上留着一行「已工作 1 分 31 秒」。4B 那份回答末尾多问了一句要不要再验证，8B 那份是一个 done 调用，一句就收。

换个页面再问一次同一句「这个页面的表格一共几行？合计金额是多少？」，答案也跟着换：在分享出来的那张测试页上，8B 用了 243.1 秒回「表格共有7行数据，合计金额为4321.50元」，4B 用了 182.3 秒回同一句 7 行 / 4321.50 元。两张页面两张表，代理报的是它真正读到的那张。

![8B 读完八行台账后的面板回答，done\(success, ...\) 里写着 8 笔、3 笔、45700 元](https://imgs.huluohu.com:443/2026/11/12/20261111-0600-nanobrowser-fig2-hard-answer.jpg)

## 4B 和 8B 的差别不在读表

读表这一题，4B 用 202.6 秒，8B 用 202.5 秒，打平。

填表那一题才拉开距离：8B 37.6 秒，4B 62.0 秒，快了一倍多。同一个页面，同一台机器，同一道题。

两个模型都量化到 Q4_K_M，4B 那个 2.5GB，8B 那个 5.0GB，挤在 16GB 内存的机器上都能跑完。

![同一道题两个模型的耗时对比：读表打平，填表 8B 快约四成](https://imgs.huluohu.com:443/2026/11/12/20261111-0600-nanobrowser-fig5-timing.jpg)

## 填完两张表，它停在提交前

题目是：在姓名栏填「王建国」，在部门栏填「硬件研发部」，然后点击提交报销按钮。

qwen3-8b-local：两个字段填完后它停住，35.5 秒时弹出确认卡，人工点「允许」，37.6 秒真正提交，页面回来一句「已提交：王建国 / 硬件研发部」。

qwen3-4b-local：59.8 秒弹确认，点允许后 62.0 秒提交成功。

两个模型往表单里写的值一样，NAME 是王建国，DEPT 是硬件研发部，页面回显的提交结果也一样。

确认卡上代理自己写了两行：
    
    
    要发送吗？
    click button «提交报销»
    在 127.0.0.1:8899 上
    智能体的目的（它自己的话）：提交报销
    询问原因：the name «提交报销» is submission vocabulary
    

按钮四个：允许 / 允许此网站 / 拒绝 / 显示标签页。

侧栏底部那个「询问」是模式开关。不点允许的那一轮等了 224.1 秒，SUCCESS=False，它就停在那儿不动。切成自动模式之后，提交、发送、删除都会直接执行，没有第二次机会。

![填完表单后弹出的确认卡，卡上写着代理自己的目的与询问原因](https://imgs.huluohu.com:443/2026/11/12/20261111-0600-nanobrowser-fig3-confirm.jpg)

## 它默认往美国发一条计数

默认开着。analyticsPing 和 analyticsStats 两个开关默认都是 true。

一天一条的事件，名字叫 active_day，地址是 https://us.i.posthog.com/i/v0/e/，服务器在美国。

载荷里的字段有版本号 0.3.0、界面语言 zh_CN、是否配了模型 has_model。

另有几个布尔项，记着本周首次、本月首次、是否新装。

载荷里没有页面内容：没有 URL，没有表格，没有对话文本。$geoip_disable 是 true，$process_person_profile 是 false。distinct_id 是每次安装随机生成的 UUID，第一次装和第二次装完全不同。

两个开关都置 false，同一套流程照跑，抓到 0 次 PostHog 请求，bodies 为空。

![两个开关关掉之后抓包面板里的计数，PostHog 请求 0 次](https://imgs.huluohu.com:443/2026/11/12/20261111-0600-nanobrowser-fig6-telemetry.jpg)

关掉之后，本地存的那份 nb.analytics 只剩 installWeek 和 newInstall 两个字段，counts 与 queue 都是空对象。

敏感字段它会遮。源码里 SENSITIVE_TYPES 含 password / hidden / file，字段名正则表覆盖 card num / cvv / otp / 2fa / passcode / password 这类写法，密码类字段的值不输出。

这套是黑名单。页面用不常规写法藏密码，比如 type 写成 text 再自己画样式，这张表认不出来，那个输入框会被当普通输入框读走。代理自己填进输入框的内容，在审计条目里会换成「‹redacted, N characters›」，只留长度。

## 换一套同类工具跑同一道题

browser-use 1.0.1，同一个 qwen3-8b-local，同一道读表题，连做四步全是代码执行报错：

  * step 1: `ModuleNotFoundError: No module named 'bs4'`
  * step 2: `import re`
  * step 3: `wait_for_load()` 之后对 `.record .amount` 写表达式，表达式形式报错
  * step 4: `NameError: name 'finish_from_repl' is not defined`，还有 `SyntaxError: unterminated string literal`

四步分别栽在缺依赖、表达式写法、变量没定义、字符串没闭合上，没有一步拿到页面数据。nanobrowser 的读表与填表两条链路都跑通了。

差别在干活的方式：一个是调工具，一个是写代码。browser-use 那轮只跑了四步，不等于它全面失败；同类的 page-assist 和 ChatGPT-Shortcut 这两个扩展只看了介绍，没有装没有测。

browser-use 的日志里也写了一行遥测说明：收集模型、步数、耗时、访问过的 URL（去掉查询串），用 ANONYMIZED_TELEMETRY=false 可以关掉。两边都往上报使用情况，区别只在报了什么。

给本地小模型挑代理，先看它是调工具还是写代码，这一条比星数更决定能不能跑通。

## 三个真踩到的坑

**坑一：本地模型服务默认不认扩展的请求。** Ollama 默认实例 127.0.0.1:11434 对 chrome-extension:// 来源的请求回 403 Forbidden。另起一个设了 OLLAMA_ORIGINS='_' 的实例在 127.0.0.1:11435，同样的请求回 200 OK，还带 Access-Control-Allow-Origin:_ 。扩展的 Ollama provider 里把 baseUrl 填 http://127.0.0.1:11435/v1 才通。

**坑二：不加 @ 符号，它读的是侧栏自己。** 侧栏默认只认当前打开的那一个标签页。任务落在侧栏上，两个模型都回「这个页面是 Chrome 扩展的侧边栏页面，无法通过工具进行交互操作」。解法是在输入框打 @，从弹出的本窗口标签页列表里勾上目标页。

**坑三：改了权限模式，提交这一步就没有第二次机会。** 侧栏底部那个「询问」是模式开关。不点允许的那一轮等了 224.1 秒，SUCCESS=False，它就停在那儿不动。切成自动模式之后，提交、发送、删除都会直接执行。

还有一条要单独说，它绕不过去。10 月 31 日有位用户 olegvnosov-cpu 在 issue #375 里贴了他的 LM Studio 返回：那个模型 recursivesi/flint 的 max_context_length 是 262144，他读完 src/llm/ 之后发现窗口最后落在 16,384。原因是 readModelInfo 读 LM Studio 时只取 type 字段，服务端报的 max_context_length 被丢掉，而 recursivesi/flint 在内置目录里没有对应行，于是套用了 defaults.local 的 16k 窗口和 4096 输出。16k 之下硬上限是 12288 token，而每个请求的固定部分（系统提示加完整工具清单）就占掉约 9000 token，长任务几乎跑不完。他也在 issue 里说了一句，大概是觉得自己可能漏了什么，请维护者纠正。到 11 月 12 日这条 issue 还是 0 条评论。

另一位用户 lveillard 试的是另一头：他把 Bedrock 的 eu-central-1 端点当自定义 OpenAI 兼容接口用，报的是 `Failed to invoke anthropic.claude-sonnet-4-20250514 with structured output: Cannot read properties of undefined (reading 'map')`。这条有 1 条评论，也还开着。

**坑四：小模型跑长任务会撞上下文。** 这条配参数也绕不过去，设计上没给出路。#375 的报告者把机制读到了源码那一层，结论是本地模型走 LM Studio 时上下文窗口按内置目录取，目录里没有的模型一律按 16k 算。装之前如果打算让它读长页面，先确认自己的模型在目录里。

## 谁适合拿它试

适合的是手上有一两张重复填的表、愿意自己装模型的人。

同事要是问这东西能不能替人填报销单，可以让他先只开读表：装上 Ollama、装上扩展、@ 勾一次标签页，问一句表格几行。行数对得上，第二步再谈填表。

## 装之前先知道三件事

第一件：权限范围大。host_permissions 是 `<all_urls>`，还带 debugger 权限，装上之后它能碰你打开的每一个网址。点安装之前先把清单看一遍。

# 修复绿联 UG307-95348 HDMI 采集卡颜色问题（二）

## 背景

经过 [上文](https://jia.je/hardware/2026/09/12/fix-ugreen-95348/) 的一系列修复，绿联 95348 终于是可以正确地还原 MateBook Pro 输出的 RGB 色彩了。但是，换到另一台运行 Windows 的笔记本上时，又出现了新的颜色问题，这篇博客就来探讨一下怎么解决新的问题。

## 颜色问题

### 现象

用着之前打过 patch、关闭 luma processing 和 chroma processing 的固件，给一台 Windows 机器采集的时候，出现了新的问题，颜色出现了新的偏差：

  * 0,0,0 -> 16,16,16
  * 255,0,0 -> 237,14,15
  * 0,255,0 -> 13,236,12
  * 0,0,255 -> 15,15,238
  * 255,255,255 -> 234,234,234

在显卡软件里，可以看到这组偏差对应的是 YCbCr，用的是 Limited range。经过验算，这就是把 Limited range 的 YCbCr 当 Full range 来解析，导致的问题。

验算过程 

这五个颜色对应的 YCbCr（BT.709 limited）和按 full range 解码的结果是：

输入 RGB | YCbCr（limited） | 按 full 解码 | 实测  
---|---|---|---  
0,0,0 | 16,128,128 | 16,16,16 | 16,16,16  
255,0,0 | 63,102,240 | 239,15,15 | 237,14,15  
0,255,0 | 173,42,26 | 12,237,13 | 13,236,12  
0,0,255 | 32,240,118 | 16,16,240 | 15,15,238  
255,255,255 | 235,128,128 | 235,235,235 | 234,234,234  
  
按 full range 解码的公式是：

  * `R = Y + 1.5748 (Cr - 128)`
  * `G = Y - 0.1873 (Cb - 128) - 0.4681 (Cr - 128)`
  * `B = Y + 1.8556 (Cb - 128)`

以红色 255,0,0 为例，对应的 YCbCr 是 (63,102,240)，代入：

  * `R = 63 + 1.5748 × (240 - 128) = 239.4 → 239`
  * `G = 63 - 0.1873 × (102 - 128) - 0.4681 × (240 - 128) = 15.44 → 15`
  * `B = 63 + 1.8556 × (102 - 128) = 14.75 → 15`

得到 239,15,15，实测是 237,14,15，只差 1~2 个 LSB。

如果按 limited range 解码，公式则是：

  * `R = 1.164 (Y - 16) + 1.793 (Cr - 128)`
  * `G = 1.164 (Y - 16) - 0.213 (Cb - 128) - 0.533 (Cr - 128)`
  * `B = 1.164 (Y - 16) + 2.112 (Cb - 128)`

代入红色：

  * `R = 1.164 × (63 - 16) + 1.793 × (240 - 128) = 255.5 → 255`
  * `G = 1.164 × (63 - 16) - 0.213 × (102 - 128) - 0.533 × (240 - 128) = 0.6 → 1`
  * `B = 1.164 × (63 - 16) + 2.112 × (102 - 128) = -0.2 → 0`

得到 255,1,0，基本就是正确的 255,0,0（1 个 LSB 的差来自 YCbCr 量化）。所以采集卡确实把 limited 的 YCbCr 当 full 来解了。

如果用显卡软件切换到 RGB 4:4:4 Limited range：

  * 0,0,0 -> 16,16,16
  * 255,0,0 -> 232,16,16
  * 0,255,0 -> 15,234,13
  * 0,0,255 -> 15,16,234
  * 255,255,255 -> 233,233,233

RGB 的 limited range 则是把 0~255 线性压到 16~235：

`v_lim = 16 + 219 * v / 255`

比如 255 会变成 `16 + 219 × 255 / 255 = 235`，0 会变成 16。要还原回 full，需要 `v = (v_lim - 16) * 255 / 219`；采集卡没有做这一步，而是直接把 16~235 当成 0~255 用，所以纯色分量停在 232~234（理论值 235，差值来自采集卡内部的转换和舍入），另外两个分量是 16。

这也是类似的问题，只有把颜色切换到 RGB 4:4:4 Full range 才可以正确采集。

虽然可以通过手动指定 RGB 4:4:4 Full range 模式来解决颜色问题，但如果没有装对应的软件呢？又或者像鸿蒙和 macOS（macOS 其实有[私有 API 可以用](http://github.com/jiegec/mac-displayctl)）那样没有类似的设置入口呢？

于是就要看，显卡驱动都是怎么判断要选择什么模式的。

### EDID

答案就在 EDID 里面。按照 CEA-861 标准，显示器通过 EDID 告诉显卡，它支持哪些颜色模式，比如是否支持 YCbCr 4:4:4 等等，又具体支持哪些分辨率，哪些时序。

然后显卡驱动挑选一个时序，让显卡按照一定的波形来把显示输出通过 HDMI 发送给显示器。此时发送的内容，就有颜色（RGB/YCbCr）以及范围（Full/Limited）之分。那这是怎么决定的呢？

首先，CEA-861 标准规定了一个默认值：对于 CE Timing，默认是 Limited；对于 IT Timing，默认是 Full。什么是 CE Timing 呢？CEA-861 的定义是，出现在标准的 Table 1 表格里，且 VIC 大于 1 的时序，都是 CE Timing。这些 VIC 可以在 [这里](https://jia.je/kb/hardware/cta_vic.html) 找到。那非 CE 的 Timing，就是 IT。

所以当显卡驱动选择了一个时序以后，就根据它是 CE 还是 IT 来决定默认是 Limited 还是 Full。但同时，显卡软件也允许用户自己选择颜色 range。那显示器是怎么知道显卡发送的到底是 Full range 还是 Limited range 呢？

答案是，HDMI 里有传递元数据的 AVI InfoFrame。它里面可以指定，RGB 用的是 Full range 还是 Limited range；YCbCr 用的是 Full range 还是 Limited range。当显示器看到这个信息的时候，就知道不该用默认值去解析了。

但是，并不是所有显示器都支持这个。所以，它还得先在 EDID 里通过 VCDB 来声明，它的 RGB 或 YCbCr，是否允许通过 AVI InfoFrame 指定 range。

## 解决方法

根据这些信息，就能想到解决方法了：把固件里的 EDID 换掉，全用 IT timing（比如用 CVT-RB），这样默认就是 Full range 了。这样确实工作了。

但是，实践中，又遇到了新问题：我的[使用场景](https://jia.je/misc/2026/09/11/classroom-routing/)里，采集卡和教室的投影仪通过一个 HDMI Splitter 连到电脑上，此时就得兼顾采集卡的情况，而采集卡用的是 CE Timing，比如 VIC 97。结果就是电脑通过 HDMI Splitter 这么一通接了以后，又回到 Limited range 了。

那怎么办呢？如果采集卡能自己识别输入是 Full range 还是 Limited range，然后进行相对应的处理就好了。

怎么识别呢？刚才提到，AVI InfoFrame 里会携带这个信息。所以就修改 EDID，在 VCDB 里设置 QS=1，这样 AVI InfoFrame 里就会出现指定 Full range 还是 Limited range 的信息。然后经过逆向，发现 MS2130S 会在寄存器 0x3c4a 里记录这个信息，这样就可以自动检测了。

怎么处理呢？之前，我的做法是在 OBS 里去 Apply LUT，实现 Limited range 到 Full 的反向映射。但是，如果从 Limited range 的输入切换到 Full range，就得调整 OBS，很麻烦。

于是我就想到，利用已有的 luma processing 和 chroma processing 的 pipeline。根据之前的分析，已知这两个 pipeline 做的事情是：

  * luma processing：`clip(clip(Y + fc90) * fc91/128)`
  * chroma processing：`clip(rotate(ΔR, ΔB) * fc92/128)`

如果想要实现 Limited range 到 Full range 的映射，也就是 16-235 线性映射到 0-255，只需要：

  * 0xfc90 设为 0xf0，对应 -16
  * 0xfc91 设为 0x95，对应 255/219
  * 0xfc92 设为 0x95，同样对应 255/219
  * 最后把 0xfc8f 和 0xfc8e 都设为 0x00，打开 processing pipeline

最终的结果是，在 YCbCr 上的变换，对应到 RGB 上，正好就是 Limited range 到 Full range 的映射。这样就不用改 OBS 的 Filter，也可以达到一样的效果。

上面这些逻辑，如果写到固件里，当然是最好的，但还得避免 UVC brightness 等设置把这些寄存器的值覆盖掉；不过固件毕竟不是源码，大范围的汇编改动还是比较危险。

最后的解决办法是，写了一个程序，通过 hidapi 去轮询 0x3c4a 寄存器，根据它是 Full range 还是 Limited range 来调整内部的寄存器，这样无论输入是哪种 range，都可以采集到正确的颜色了。此外，我还在 EDID 里把 YCbCr 都去掉了，只保留了 RGB 的支持，这样就只需要考虑一种转换。

这样，无论是 MateBookPro，还是跑了 Windows 的机器，都可以准确地采集了。当然，还有一个遗留问题，就是苹果电脑，它依然会出现偏色的问题，具体的原因还没能找到。

桌面上堆满文件时，找一张图片或一个常用目录，往往要先扫过几十个图标。

如果不想把所有东西都藏进文件夹，可以试试 Nimi Places：在桌面上划出几个分类区域，让不同目录的内容各自显示在对应区域里。

它适合希望保留桌面直观访问方式，又想减少杂乱感的[Windows](https://www.wangdu.site/tag/windows "【查看含有\[Windows\]标签的文章】")用户。不过，下载前需要注意：当前许可限定非商业用途，不能直接理解为所有场景免费。

## 一、Nimi Places是什么？

Nimi Places 是一款 Windows [桌面整理](https://www.wangdu.site/tag/%e6%a1%8c%e9%9d%a2%e6%95%b4%e7%90%86 "【查看含有\[桌面整理\]标签的文章】")工具，核心是可定制的“容器”。

这里的容器可以理解为桌面上的分类面板，并不是开发者常说的Docker容器。每个面板显示选定位置中的文件与文件夹，用图标或缩略图呈现。

例如，可以考虑把几个不含敏感信息的练习目录分别显示为“阅读素材”“图片练习”和“常用资源”。这种安排的价值是减少查找路径，而不只是让桌面看起来整齐。

单纯展示目录与通过规则移动文件是不同操作，设置时应分清两者。[Nimi Places官方介绍](https://www.wangdu.site/?golink=aHR0cHM6Ly9teW5pbWkubmV0L1Byb2plY3RzL05pbWktUGxhY2VzLw==)

## 二、哪些功能比较实用？

**按用途安排桌面区域**

可以给容器设置名称、位置和显示方式，用不同区域承载不同目录，减少所有图标混排带来的干扰。

**调整外观与阅读密度**

项目提供主题、强调色、图标大小以及网格或列表等显示选项。选择外观时，优先考虑文件名是否容易辨认，不必为了装饰把面板做得太密。

**通过缩略图和预览辨认内容**

官方列出了图片缩略图、内置图片查看及部分音视频预览能力。对视觉素材而言，预览能减少反复打开文件的次数，但格式支持仍取决于软件与运行环境。

**排序、标签与快速定位**

可以利用排序和标签改善查找，容器获得焦点后还可通过输入名称定位匹配项目。建议先整理目录，再选择适合自己的显示方式，避免只把混乱换成更多面板。

上述能力依据[官方功能页](https://www.wangdu.site/?golink=aHR0cHM6Ly9teW5pbWkubmV0L1Byb2plY3RzL05pbWktUGxhY2VzL0ZlYXR1cmVzLw==)整理，本文没有安装实测，也不对具体格式的预览效果作保证。

## 三、如何下载和开始使用？

### 第一步：从官方下载页获取软件

打开[Nimi Places下载页](https://www.wangdu.site/?golink=aHR0cHM6Ly9teW5pbWkubmV0L1Byb2plY3RzL05pbWktUGxhY2VzL0Rvd25sb2FkLw==)，查看当前构建和运行要求，再按页面提示进行下载。下载流程包含验证码步骤，需要用户自行完成。

这里是官网安装包入口，不是GitHub源码项目；不要把可下载或可便携运行等同于开源。

### 第二步：先添加一个练习目录

依据官方帮助，可以先打开设置，点击加号，选择容器类型，再浏览并选中要显示的位置。

设置窗口关闭后，新容器才会出现。如果选完目录暂时没有看到面板，不必立即反复添加。

首次体验建议使用专门的练习文件夹，先确认显示与操作方式，再决定是否扩大使用范围。

### 第三步：调整显示，再逐步增加分类

为容器安排便于识别的名称和位置，再选择图标大小、主题或排序。开始时两三个区域通常更容易管理，不必把所有目录都铺满桌面。

具体菜单操作可以查看[官方帮助](https://www.wangdu.site/?golink=aHR0cHM6Ly9teW5pbWkubmV0L1Byb2plY3RzL05pbWktUGxhY2VzL0hlbHAv)。本文仅整理入门路径，未执行下载、安装或文件移动。

## 四、免费吗？有哪些许可限制？

当前官方下载页链接的是 **NPGAL（Nimi projects general application license）** ，不是MIT或其他常见开源许可证。

其中明确限定软件用于非商业用途，并对修改、再分发等行为设有约束。因此，不宜将它直接宣传为“企业办公免费工具”或“可自由修改分发的开源软件”。

另外，当前许可明确写到软件不应与个人数据一起使用。考虑到桌面目录可能包含个人资料，使用前应认真检查许可是否符合自己的实际场景，不能仅凭功能介绍判断适合存放哪些文件。

上述内容仅提示官方文本中的关键限制；具体使用条件请阅读[完整许可](https://www.wangdu.site/?golink=aHR0cHM6Ly9teW5pbWkubmV0L0xpY2Vuc2VzL2dlbmVyYWwuaHRt)。

## 五、怎样判断是否适合自己？

如果你希望在Windows桌面上直接查看几个分类目录，并且使用场景符合当前许可，可以先从练习目录体验。

如果主要需求是跨设备同步、团队共享或商业办公，不能从“桌面整理”这个定位推断它具备相应能力或授权。

选择这类工具时，可以先问自己三个问题：要解决的是图标太乱，还是文件目录本身混乱？分类面板是否能减少日常查找？软件的使用条件是否适合准备放进去的内容？

## 结语

Nimi Places 提供了一种直观的桌面分类方式：让目录内容在多个可调整的面板中显示，保留桌面访问的便利。

对它的评价应同时看功能与许可。先确认使用条件，再用小范围练习目录验证是否顺手，比直接把整个桌面交给整理规则更合适。

## 一、YunX是什么？

YunX 中文名叫**云析** ，最初由开发者 CYQawa 开发，是一款 Android 网盘解析下载应用。

后来开发者 tidain 基于原项目移植了 Windows 版本，名为 **YunX-Desktop** 。

两个版本都采用 AGPL-3.0 开源协议，并且完全免费。

它的使用逻辑非常简单：
    
    
    复制网盘分享链接
            ↓
    粘贴到YunX
            ↓
    自动识别网盘和提取码
            ↓
    查看分享文件列表
            ↓
    选择需要的文件
            ↓
    下载到本地
    

不需要在多个网盘客户端之间反复切换。

需要注意，YunX 是第三方解析工具，并非各网盘平台的官方客户端。具体能否解析、是否需要登录，都取决于对应平台的接口和账号权限。

### 2\. 多线程分片下载

YunX 支持 Range 分片并发下载。

简单理解，就是把一个文件分成多个部分，同时请求下载，最后合并成完整文件。

此外还支持：

  * 下载暂停与继续
  * 断点续传
  * 下载失败重试
  * 多任务管理
  * 下载速度限制

但**多线程不代表一定能突破网盘限速** 。

实际速度仍然受到网盘服务器、账号权益、网络环境和平台风控策略影响。

YunX Android v1.3.0 增加了视频与图集解析能力。

支持的平台包括：

  * 抖音
  * 小红书
  * 快手
  * 微博
  * AcFun
  * 哔哩哔哩
  * Pixiv

用户可以粘贴视频或图集分享链接，查看解析结果，并根据可用资源进行预览或下载。

其中，哔哩哔哩的部分高清资源需要登录，Pixiv 部分作品也有账号访问要求。

**这一功能以 Android 新版为主，不能直接认为 Windows 版也已同步支持。**

### 4\. 在线预览与下载管理

安卓版本还支持在线预览图片、视频、音频，以及打开部分文本文件。

图片合集可以使用网格方式查看，并进行多选下载。

下载任务支持自动分组，不用在一长串任务中寻找文件。

### 5\. Windows版支持GitHub解析

Windows 版除了网盘下载，还增加了一个非常实用的功能：

**GitHub资源解析。**

可以粘贴 GitHub 仓库、用户主页或文件链接。

支持浏览仓库文件、查看 Releases、阅读 README，并下载相关文件。

还可以设置 GitHub 下载镜像前缀，方便管理 GitHub 资源下载。

### 6\. 多种账号登录方式

YunX 支持多平台账号登录。

Windows 版提供内嵌浏览器登录、部分浏览器 Cookie 导入及手动配置等方式。

Android 版 v1.3.0 还增加了部分网盘的多账号管理功能，可以设置主账号，并在支持的场景中切换账号下载。

需要注意，多个账号同时请求下载可能增加触发平台风控的风险。

## 七、使用时需要注意什么？

YunX 提供的解析能力，有一部分基于对网盘接口的技术研究。

因此需要特别注意以下问题。

**第一，网盘接口可能失效。**

如果平台修改接口或者访问规则，部分解析功能可能暂时无法使用。

**第二，存在账号风控风险。**

尤其是百度网盘，两个项目的 README 都明确提示，不建议随意使用，可能导致账号被风控。

**第三，谨慎处理Cookie和登录凭证。**

如果使用手动 Cookie 登录，不要将账号凭证发送给陌生人，也不要上传到公开网站。

**第四，注意文件版权。**

分享链接可以解析，并不代表下载内容一定可以自由转载或用于商业用途。

应当遵守平台服务条款，并确保自己对相关文件具有合法使用权限。

## [](https://mingnify.com/zh/blog/p/obsidian-visualization-guide/#结构可视化：把关系和思路画清楚 "结构可视化：把关系和思路画清楚")结构可视化：把关系和思路画清楚

Mermaid、白板（Canvas）和 Excalidraw 都能把关系和思路画出来，做法各有侧重。Mermaid 用代码描述节点和关系，再把它们渲染成图；白板可以把笔记、图片和网页摆成卡片，通过分组和连线组织资料；Excalidraw 可以自由组合图形、文字和标注，方便边画边想，也方便给别人讲清一个想法。它们的用途有交叉，下面先看各自的基本操作，再看 AI 能生成什么、怎么改。

### [](https://mingnify.com/zh/blog/p/obsidian-visualization-guide/#Mermaid：先改一条连线 "Mermaid：先改一条连线")Mermaid：先改一条连线

Obsidian 内置 Mermaid，无须另外安装插件。打开示例流程图的源代码，可以看到节点和连线写在标记为 `mermaid` 的代码块里。`graph TD` 表示从上往下排列，A 指向 B 的那一行对应图里的一条箭头。

![Mermaid 流程图的源代码](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323622_1794576235353.webp)

在代码块末尾加一行，让 D 指向 F。切回图表，就能看到新出现的 F 节点，以及从 D 指向它的箭头。文字里的关系改了，图也会跟着变。内容复杂一些时，可以让 AI 帮我们生成和修改。

![修改 Mermaid 代码后出现 F 节点](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323606_1794576236846.webp)

我在 Obsidian 的 Claudian 对话面板里调用 Mermaid 技能（Skill），让 AI 在当前笔记中生成四个简单的中文示例，每个单独放一个小节，用 Mermaid 代码块呈现。第一张是审批流程图：通过就进入「审批完成」，不通过就修改申请并重新提交。打开源码还能继续改。

![AI 生成的审批流程图](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323590_1794576238072.webp)

用户登录时序图按从上到下的顺序，展示用户、登录页面和服务器之间的交互。

![用户登录时序图](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323301_1794576239459.webp)

知识分类思维导图从一个中心主题展开，整理不同类别和子主题。

![知识分类思维导图](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323284_1794576240930.webp)

任务状态图展示一项任务怎样从待处理变成进行中，再到已完成。

![任务状态图](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323266_1794576242199.webp)

这四张都是简单示例。换成自己的内容时，可以按想表达的关系选图。生成后，记得回到原文，逐一核对节点、分支和箭头方向。

### [](https://mingnify.com/zh/blog/p/obsidian-visualization-guide/#白板（Canvas）：把原文和自己的理解放在一起 "白板（Canvas）：把原文和自己的理解放在一起")白板（Canvas）：把原文和自己的理解放在一起

我先在项目文件夹上点右键，选择「新建白板（New canvas）」，再从白板底部选中已经保存的官方介绍，让笔记内容显示在卡片里。

![从项目文件夹的右键菜单新建 Canvas 白板](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323249_1794576243649.webp)

把原文里的示例图拖到右边，放大查看，再在图下方加一张文字卡，写下自己的理解。从笔记卡片边缘拉两条线：连到图片的标为「原文示例」，连到文字卡的标为「内容归纳」。这样一眼就能分清哪张图来自原文，哪段是自己写的。最后框选右边两张卡，编成「重点与理解」一组。左边留着原文，右边集中看例子和归纳。

![手工白板：左侧是原文，右侧是重点与理解](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323573_1794576245276.webp)

同一篇资料也可以交给 AI 整理。我先把调用白板（Canvas）技能（Skill）的提示词贴进 Claudian。打开刚才的笔记，右键复制它在库里的路径，填到「来源笔记」；再右键复制项目文件夹的路径，填到「输出目录」，指定新白板的保存位置。填好后发送，生成完成就点回复里的文件链接。

![Claudian 中的 Canvas 技能与生成文件](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323231_1794576246647.webp)

打开 AI 生成的白板，上面保留了原笔记，下面分成三组：左边是白板能用来做什么，中间是白板里可以放什么，右边是怎样组织资料。

![AI 白板保留原笔记，并按三个问题组织资料](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323557_1794576248371.webp)

### [](https://mingnify.com/zh/blog/p/obsidian-visualization-guide/#Excalidraw：画草图，再给截图加标注 "Excalidraw：画草图，再给截图加标注")Excalidraw：画草图，再给截图加标注

在 Obsidian 里先安装并启用 Excalidraw 社区插件。右键点击项目文件夹，选择「新建绘图（New drawing）」。我在左边画一个圆角矩形，写「一个想法」；右边画一个椭圆，写「一张草图」。用箭头把它们连起来，在箭头上写「画出来」。

草图画好后，点图片工具，把工具栏截图插到草图下面。用一个框圈出工具栏，拖动调整大小，再把框改成红色。从截图外拉一根箭头，写上「绘图工具」。把说明放在截图外面，里面的按钮也能看清。同一张绘图里就能同时放草图和截图说明。

![同一张 Excalidraw 绘图里的草图和截图标注](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323541_1794576249816.webp)

手动画过一遍后，我在 Claudian 里调用 Excalidraw 技能（Skill），让 AI 画一张基础用法导览图：能做什么、可以用哪些元素、怎么开始画。每块用小图配短说明，填好输出目录就发送。

生成后从上往下看：上面是用途，有草图、关系和图片批注示意，右侧的虚线框留给实际截图；中间列出图形、文字、箭头和图片这些绘图元素；底下是操作顺序，先新建绘图，再添加内容，接着连线或标注，最后调整布局。

## [](https://mingnify.com/zh/blog/p/obsidian-visualization-guide/#数据可视化：把数字和变化看明白 "数据可视化：把数字和变化看明白")数据可视化：把数字和变化看明白

在 Obsidian 里，想查看和整理一条条记录，可以先做数据表。要把笔记按属性集中管理，直接修改状态、分类，可以用内置的数据库（Bases）；要按条件汇集笔记里的字段或任务、生成查询和汇总结果，可以用第三方插件 Dataview。想比较数量、查看占比和变化，再把数据画成图：Mermaid 能把已有数字快速画成图表；Charts View 可以直接填数据、读取 CSV，也可以通过 DataviewJS 查询和整理数据再绘图。

### [](https://mingnify.com/zh/blog/p/obsidian-visualization-guide/#数据库（Bases）：把剪藏笔记列成表 "数据库（Bases）：把剪藏笔记列成表")数据库（Bases）：把剪藏笔记列成表

在项目目录上点右键，新建一个数据库（Bases）。表格一开始会列出很多文件。点「筛选」，把文件夹设为资源目录下的「剪藏（Clippings）」，表里就只剩这个目录里的六篇笔记。

![Bases 按剪藏文件夹筛选后只显示六篇笔记](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323509_1794576252624.webp)

拿第一条核对：左边目录有白板（Canvas）的官方介绍，右边表格里也有，点击表里的文件名就能打开原笔记。

手动建过表之后，我用同一个目录，在 Claudian 里调用数据库（Bases）的技能（Skill），填好来源和输出目录，让 AI 做三个视图。「最近收藏」把演示当时的十篇资料按收录日期从新到旧排列，方便找回最近存的内容。

![Bases 的最近收藏视图](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323214_1794576254208.webp)

想按平台找，就切到「按来源浏览」，同样的十篇资料会按来源分组。只想找 Obsidian 的官方资料，就切到「官方资料」，这时只剩五篇来自官方站点的笔记。

![Bases 的官方资料视图](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323493_1794576255738.webp)

打开其中一篇剪藏核对，表里的收录日期和原文链接都来自笔记属性。

### [](https://mingnify.com/zh/blog/p/obsidian-visualization-guide/#Dataview：用查询把笔记汇成表 "Dataview：用查询把笔记汇成表")Dataview：用查询把笔记汇成表

安装并启用社区插件 Dataview，再新建一篇笔记。Dataview 用查询代码做表，手写需要熟悉一些语法，这里我让 AI 写。在 Claudian 里调用 Dataview 技能（Skill），指定只查剪藏目录，列出笔记名、收录日期和来源域名，最近收录的排在前面，并把查询写进当前笔记。

![AI 写入笔记的 Dataview 查询](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323476_1794576257090.webp)

Dataview 运行查询后，把结果显示成表格。点击笔记名就能回到原来的剪藏。

![Dataview 查询生成的剪藏表格](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323460_1794576258650.webp)

回到剪藏笔记，就能核对表里的收录日期和来源域名是不是从这里读出来的。

### [](https://mingnify.com/zh/blog/p/obsidian-visualization-guide/#Mermaid：把已经整理好的数字画成图 "Mermaid：把已经整理好的数字画成图")Mermaid：把已经整理好的数字画成图

做完笔记表格，就可以用图看数量、占比和变化。还是调用前面的 Mermaid 技能（Skill），这次让 AI 用虚构数据生成七种图，每种都附一张数据表。发送提示词后，先看饼图：它展示一周学习时间的分配，可以对照表格看各部分的占比。

![Mermaid 饼图与对应的一周学习时间数据表](https://raw.githubusercontent.com/mingnify/gallery/main/images/file-20261113052323407_1794576260149.webp)

点击图块右上角，就能看到对应的 Mermaid 代码。往下是柱状图和折线图，分别用来比较数量和查看变化；还有雷达图、矩形树图、桑基图和四象限图，可以依次看生成效果。演示用的都是示例数据。换成自己的数据后，要对照原始记录，核对图里的标签和数字。

11 月 12 日，[CurlGo](https://github.com/echoVic/curlgo) 桌面端发到 [v0.2.1](https://github.com/echoVic/curlgo/releases/tag/v0.2.1)，独立 CLI 发到 [cli-v0.1.1](https://github.com/echoVic/curlgo/releases/tag/cli-v0.1.1)。两件事同一天，升级通道是分开的。桌面客户端有自己的版本；CLI 和完整指南的版本写在 `internal/cli/VERSION` 里。

如果你让 Agent 用命令行测接口，最怕两件事。输出目录写错了，请求已经打出去了；从聊天里复制的 curl 带了一些旗标，工具既没有告诉你不支持，也没有按你以为的方式执行。

CurlGo CLI 用 `schemaVersion: 1` 的 JSON 说话。帮助、预检、正式请求，各自对「成功」有不同含义。显式传入空的 `--out-dir ""` 时，它会在发请求之前以 `OUTPUT_ERROR`、退出码 3 失败。省略这个旗标，才继续用私有临时目录。

## 先跑通一条预检

独立 CLI 不启动图形界面。仓库里可以这样编出一个本地可执行文件：
    
    
    CGO_ENABLED=0 go build -o /tmp/curlgo-api-test ./cmd/curlgo

也可以直接下载 [独立 CLI 0.1.1](https://github.com/echoVic/curlgo/releases/tag/cli-v0.1.1)。下面的命令把 `curlgo` 理解成这个可执行文件即可。先确认它在 PATH 里：
    
    
    command -v curlgo

本地服务已经在 8080 端口时，把最小请求存成 `request.json`：
    
    
    {
      "schemaVersion": 1,
      "request": {
        "method": "GET",
        "url": "http://127.0.0.1:8080/health",
        "followRedirects": true,
        "timeoutSeconds": 30
      }
    }

先预检，不发请求：
    
    
    curlgo run --request request.json --dry-run

也支持从标准输入读，或改走 curl 文本。`--request` 和 `--curl` 互斥：
    
    
    curlgo run --request - --dry-run <request.json
    curlgo run --curl imported.curl --dry-run

预检通过时，stdout 是一份 `schemaVersion: 1`、`ok: true` 的 JSON，带 `validation`，没有 `result`。`bodyMode: ""` 表示原始正文模式，计数是准备后的请求头和表单项数，不是响应信息。

成功只表示本地准备通过。它不代表目标可达，也不代表 TLS 证书链可信，更不代表登录或业务成功。确认请求和目标都没问题之后，再去掉 `--dry-run` 发送。

当前版本的字段和选项，也可以直接问 CLI 自己：
    
    
    curlgo skill cli-reference

`skill` 输出 Markdown，最后一行是 `[curlgo:skill] end of guide`。它不启动界面，不读标准输入，也不访问目标接口。其他帮助、预检和请求命令继续输出 JSON。

## 三种成功不是一回事

`ok: true` 和退出码 0，要先看你跑的是哪种模式。

模式| 退出码 0 / `ok: true` 的含义  
---|---  
帮助| 帮助 JSON 输出成功，不是一次接口检查  
`--dry-run`| 本地准备和预检 JSON 输出成功，没有发送请求  
普通 `run`| 响应捕获、已配置的断言、适用的提取和输出都成功；只验证你列出来的规则  
  
没有断言时，HTTP 401、404、500 也可以退出 0。这时必须再看 `result.statusCode` 和正文，不能把退出码 0 直接当成业务通过。

JSON 输入缺省是 GET、HTTP、30 秒超时、跟随重定向。你写了 `false` 就按 `false` 留着；超时写成 0 会被拒绝。从 curl 导入时，只有带了 `-L` 才跟随重定向。

CLI 不加载图形界面的工作区。变量来自 JSON 里的 `settings.environments` 和 `environment`，不读操作系统环境变量。CA、Cookie、代理分别通过 `--ca-file`、`--cookie-jar`、`--proxy` 显式提供，不读 `HTTP_PROXY`、`HTTPS_PROXY`、`NO_PROXY`。凭证放在权限为 0600 的私有文件里，或走标准输入，不要放在命令行参数上。

## 空的 —out-dir，在发请求前失败

![请求发出前的四步：读入、预检、空目录先失败，再决定是否真的发送](https://www.echovic.com/_astro/3f070d1edda34dd9d972f597c7f1bd2e8faf43b102d7959fce4b12e263423036.CeXZOSM9_10RywY.webp)

_图 1：显式传入空的输出目录时，失败发生在预检这一段。请求还没有离开这台机器。_

显式指定 `--out-dir` 或 `--cookie-jar` 时，它们的父目录必须已经存在，而且必须是目录。预检只检查存在和类型，不检查写权限或剩余空间，也不会替你 `mkdir`。这条检查失败，就是 `OUTPUT_ERROR`，退出码 3。

更需要盯住的是空字符串。普通执行里，`--out-dir ""` 同样以 `OUTPUT_ERROR`、退出码 3 失败，而且发生在发送请求之前。它不会悄悄退回临时目录。只有省略这个旗标时，才使用私有临时目录。

这个区别对 Agent 很要紧。如果把空字符串和「没传」当成同一回事，工具可能已经打到生产接口，调用方却以为只是路径没设好。CLI 0.1.1 把这条写死：空值就是失败，失败在发送之前，和 `--dry-run` 走同一段路径检查。

正文怎么落盘，也和这个目录有关。小文本放在 `result.body.text` 里；二进制，或超过默认 262144 字节内联阈值的正文，会写到 `body.path`，需要再读那个文件。`--inline-body-bytes` 范围是 0 到 4194304，写成 0 会让所有非空正文都写文件。捕获上限是 4 MiB，`truncated` 为真时，不能声称响应完整，也不能直接拿不完整的 JSON 去解析。输出文件权限是 0600，默认临时目录是 0700，留给调用方读取和清理。`--out-dir` 必须指向已有目录，调用方不应删除用户目录或无关文件。

## curl 选项分三种下场

从聊天或文档里复制一行 curl，最怕的是「看起来收下了，其实没按这个旗标做」。CurlGo 把选项分成三类：导入、接受但忽略、明确拒绝。未列出的参数不会被静默丢掉。

![三列：导入的 curl 选项、接受但忽略的选项、明确拒绝的选项](https://www.echovic.com/_astro/69c5a3ddddd479a1cf322305cb621e7ed7e6209854bf88b2ca044fdbeb4dac45.D1w9dPBl_MLvbP.webp)

_图 2：接受但忽略，和明确拒绝，是两种不同的回答。前者是故意不生效，后者会让这次导入失败。_

会导入的包括：`--request`、`--header`、`--data`、`--data-raw`、`--data-binary`、`--json`、`--user`、`--cookie`（只接受 `name=value`）、`--oauth2-bearer`、`--user-agent`、`--referer`、`--url`、`--location`、`--head`、`--max-time`，以及文本形式的 `--form-string`。短参数是 `-X`、`-H`、`-d`、`-u`、`-b`、`-A`、`-e`、`-m`、`-L`、`-I`，也支持 `--参数=值` 这种写法。

接受但忽略的是输出和传输层习惯用法：`--compressed`、`-s` / `--silent`、`-S` / `--show-error`、`-sS`、`-i` / `--include`、`-N` / `--no-buffer`。它们常出现在从终端复制出来的命令里，忽略它们是为了不改变这次请求本身的含义。

明确拒绝的包括 `-F` / `--form`、`--data-urlencode`，以及上面没列出的其他参数。上传文件要在图形界面里选择，或在获授权的 CLI JSON 里提供 multipart 的绝对路径。curl 文本只被解析，不会拿去执行 shell，也不会展开系统变量，更不会按隐式 `@file` 去读文件或 Cookie 文件。

你可以先把准备导入的命令存成 `imported.curl`，用 `--dry-run` 看它落在哪一类。被拒绝时，退出码和 `error.code` 会告诉你是 `INVALID_CURL` 这类输入问题，而不是已经打到了服务器。

## 看退出码和 error.code，不要匹配提示文本

![退出码 0 到 4 的含义：0 随模式变化，1 是构造错误，2 是执行失败，3 是输出失败，4 是断言失败](https://www.echovic.com/_astro/b41c384d7297ef24b61e8ecce88dcabd51c53e8dff717a98841d1dead451ec26.nnONhQvK_1A0jkv.webp)

_图 3：分类看`error.code` 和退出码。`error.message` 只提供安全提示，不回显原始凭证、输入或底层错误。_

  * 退出码 1：用法、输入、配置或请求构造错误。例如 `INVALID_USAGE`、`INVALID_INPUT`、`INVALID_CURL`、`UNRESOLVED_VARIABLE`、`MISSING_SECRET`、`INVALID_SECRETS`、`INVALID_REQUEST`、`REQUEST_BUILD_ERROR`。
  * 退出码 2：执行或提取失败。例如 `CONNECT_ERROR`、`REDIRECT_ERROR`、`TLS_ERROR`、`TIMEOUT`、`CANCELED`、`BODY_READ_ERROR`、`EXTRACTION_ERROR`。
  * 退出码 3：输出路径、正文落盘或 Cookie 保存失败，也就是 `OUTPUT_ERROR`。stdout 本身写入失败也是 3，此时 JSON 可能不完整，标准错误里是固定提示 `CurlGo: 无法写入结果 JSON`。
  * 退出码 4：响应断言失败，`ASSERTION_FAILED`。失败仍保留响应，并阻止变量提取。

把 Agent 的重试策略挂在这些码上会比较稳。输入问题不要换个目标再打一遍；输出路径问题不要改成「先发出去再说」；断言失败要读完整报告，而不是把同一条请求循环发送。

v1 还不包含脚本断言、集合运行器，也没有无界面的 SSE 或 WebSocket。这些能力在图形界面里可用，不要假设 CLI 0.1.1 也能做同一件事。

## 用这几步验收

把下面几条在同一台机器上跑完，就能核对这份契约。目标建议用本地服务，不要一上来打到生产接口。

  1. `curlgo help` 和 `curlgo run --help` 输出 `schemaVersion: 1`、`ok: true` 的帮助 JSON，没有 `result`。
  2. 对前面的 `request.json` 跑 `--dry-run`，得到 `validation.dryRun: true`，网络上不应出现对应请求。
  3. 再跑 `curlgo run --request request.json --out-dir ""`，应在发送前以退出码 3、`OUTPUT_ERROR` 失败。把同一条命令改成省略 `--out-dir`，才会走私有临时目录。
  4. 准备一个带 `-s`、`--compressed` 的 curl 文件，`--dry-run` 应能通过；再准备一个带 `-F` 或 `--data-urlencode` 的文件，预检应失败，且请求未发出。
  5. 给普通 `run` 配一条必定失败的断言，退出码应是 4；去掉断言再打一个会返回 404 的地址，退出码可以是 0，这时要靠 `result.statusCode` 判断。

五条都对上，空输出目录、curl 选项分类和成功含义就没有混在一起。当前版本的完整选项列表，以 `curlgo skill cli-reference` 当场打出来的为准。

2026 年 11 月 11 日，我给 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 写了一个工作区面板，先能看文件树。第二天就叠到接近 IDE：多标签、查找替换、Quick Open、Git 槽标记、符号面包屑。到 11 月 12 日发到 [v1.8.10](https://github.com/echoVic/dsh-workspace-ide/releases/tag/v1.8.10)。

如果你也在 Harness 里跟模型对着改代码，最烦的往往是切窗口。改一行去另一个编辑器，搜全仓库再切回来，对话上下文还在闪。这篇先给你一条能马上用的安装命令，再讲这个面板为什么能在对话旁边做到接近 IDE。

[dsh-workspace-ide](https://github.com/echoVic/dsh-workspace-ide) 就是这个面板：装进 DeepSeek Harness 之后，在左侧打开工作区，浏览、搜索、看 Git、在文件里改和保存，都不必离开当前对话。

## 先装上，再看它长什么样

在 DeepSeek Harness 的会话里，用插件管理器安装 npm 上的包：
    
    
    plugin_manager {
      action: "install_bundle",
      target: "dsh-workspace-ide"
    }

也可以装 GitHub 仓库，或钉到某个发行包：
    
    
    plugin_manager { action: "install_bundle", target: "echoVic/dsh-workspace-ide" }
    plugin_manager { action: "install_bundle", target: "https://github.com/echoVic/dsh-workspace-ide/archive/refs/tags/v1.8.10.tar.gz" }

插件是按配置文件范围安装的，重启还在。返回里如果看到 `application: "applied"`，说明它已经生效。客户端改动走 Harness 的热更新，Host 这一侧的改动要等下一次 Host 启动。

装好后，左侧栏会出现「工作区」，就在插件、定时任务、用量统计旁边。顶上三个图标切换文件、搜索、Git。右边的工作区选择器跟着当前正在看的会话走，你也可以手动挑一个，只对这次会话生效。

![文件树加带行号的编辑器，状态栏和保存按钮都在，演示工作区是 aurora-dashboard](https://www.echovic.com/_astro/0fd25a1754214d172cc97e947524acde1caeceedef7d35304b1f4681fec11545.C1777ZNo_Z1DHRsG.webp)

_图 1：文件树和带行号的编辑器。截图来自项目 README 的合成演示工作区 aurora-dashboard，不是真实用户数据。_

快捷键按你在 VS Code 里的肌肉记忆来就行：`Ctrl/Cmd+P` 快速打开，`Ctrl/Cmd+F` / `H` 查找和替换，`Ctrl/Cmd+S` 保存，`Ctrl/Cmd+W` 关标签，`Ctrl/Cmd+Shift+O` 跳到当前文件里的符号。

## 三个面：文件、搜索、Git

文件面是一个懒加载的目录树，中间是可调宽度的编辑区。打开的文件带语法高亮和行号，Git 改动会在槽里打标记。点面包屑可以往上走目录。软换行是 `Alt+Z`，跳到指定行是 `Ctrl/Cmd+G`。

多标签按文件开，每个标签自己保留草稿和光标。切走再切回来，没保存的改动还在。关掉一个有未保存内容的标签，会先问你要不要丢。

![多标签编辑，脏标记和未保存提示](https://www.echovic.com/_astro/207334423aa3b81d1f2e8a080bdf318814d9e9c07ca8b40398665dbdf42ecf2b.D0FgiuVH_ZPQyyz.webp)

_图 2：一个文件一个标签。脏标记只说明这个标签里还有没写入磁盘的草稿。_

搜索面做全工作区文本搜索，可切换大小写、正则、整词，也能加包含过滤。命中按文件分组，高亮后一点就跳到那一行。

Git 面给出当前分支、领先或落后、已暂存 / 未暂存 / 未跟踪 / 冲突，以及带颜色的统一 diff。下面是提交历史，点进去能看这次提交的 diff。这个标签开着的时候，状态和日志会自己刷新：一次只跑一趟，最快 5 秒一次，扫描变慢会退让，窗口切到后台就暂停，重新聚焦会立刻拉一次。每次保存之后，槽里的 Git 标记也会更新。如果当前工作区还不是 Git 仓库，它会列出其他已经是仓库的工作区，点一下就能切过去。

## 编辑手感是怎么叠上去的

接近 IDE，关键是常用的那几下不必离开对话。把功能名写进更新日志，帮不上忙。

查找替换带匹配计数、上一个 / 下一个，以及大小写、整词、正则。所有命中会画在文字后面，你能一眼看到还会改到哪里。Quick Open 在本地对整个工作区文件索引做模糊子序列打分，不必等网络。当前文件里可以用「转到符号」跳到函数、类、类型、常量；Markdown 和 JSON 则跳到标题或键。标题上会显示你正处在哪个符号里，`Alt+↑/↓` 可以在符号之间走。

![Quick Open 面板，按模糊匹配列出工作区文件](https://www.echovic.com/_astro/20c5517eb1c0fff0c84eace6e6c5da564d19ab4dfa1cd4bd01392a4d25731332.CInw37Eq_1HmA15.webp)

_图 3：`Ctrl/Cmd+P` 打开 Quick Open。匹配在本地打分，不经过一次额外的网络往返。_

括号匹配、自动补对、智能缩进、缩进参考线和当前行高亮，都是为了让「敲回车、对一下括号」这些小动作跟在常用编辑器里一样。`Cmd/Ctrl+/` 按语言切换注释，行注释或块注释都按这一种语言的规则来，可逆，保留缩进，空行不动。

Markdown 可以从文件头切换源码和预览，快捷键是 `Cmd/Ctrl+Shift+V`。预览用 React 元素拼出来，不往页面里灌 HTML。围栏代码块走同一套高亮，和当前主题一致。相对路径的图片按 Markdown 文件所在目录解析，再走 Host 上带鉴权的图片路由，所以 `![shot](public/hero.png)` 能显示工作区里的真实文件。远程 `https:` 图片保持原地址；逃出工作区的路径会被拒绝。预览看的是当前草稿，没保存也能马上看到效果。

语法高亮是为这个面板写的一个小引擎，不附带 Shiki 或 Prism，浏览器这一半运行时仍然只依赖 `react`。Harness 报上来的常用语言都覆盖了；不认识的文件，以及超过 300 KB 的文件，会退回纯文本，免得渲染拖垮页面。编辑的时候，一层透明文字的 `textarea` 叠在高亮层上面，光标、选区、滚动和行号槽保持同步。

主题默认跟随 Harness 的亮色 / 暗色。你也可以改成 Dark+、Light+、One Dark Pro、Dracula、GitHub Dark、Solarized Light，只作用在这个面板里，选择记在 `localStorage`。

## 它怎么跟 Harness 分工

面板分两半。

![左边是浏览器里的面板，右边是 Host 上九条带鉴权的路由；save 只能覆盖已有普通文件](https://www.echovic.com/_astro/0e7bf7b9d3e7d67ce6186bbe5c718f4d9b10fa2a92d063fdaefb474cd1ee0c5d.DSFQoSup_Z1tejXT.webp)

_图 4：浏览器负责手感，Host 负责读盘、搜索、Git 和保存。路径检查在 Host 这一侧完成。_

浏览器这一半注册左侧栏图标和对应的主面板，只用 `react`、Harness 的主题变量，以及一份内置的中英词典。面板跟着当前会话的工作区走；如果运行环境里没有工作区钩子，会安全地退回，而不是把页面弄崩。

Host 这一半注册九条带鉴权的 fetch 路由：`workspaces`、`list`、`files`、`file`、`image`、`search`、`git`、`save`、`ping`。文件系统访问都要过路径检查，绝对路径、`..` 逃逸、符号链接逃逸、不在已知工作区里的根，一律拒绝。除了 `save` 和 `ping`，全部只读。`save` 只能原子覆盖已经存在的普通文件，不能借保存新建一条路径，也不能写到工作区外面。`ping` 只往 `$DSH_HOME/workspace-ide/status.jsonl` 写一行诊断，用来证明这段代码确实跑过。Git 通过 `child_process.execFile` 执行，输出有上限；当前根不是仓库，是一个正常结果，不当成错误。

图片和 SVG 走单独的 Host 路由，按文件头校验类型，单次读取上限 8 MiB。栅格图在棋盘格背景上居中预览；SVG 可以在预览和源码之间切，改源码会马上反映到图上。

这些约束看起来严，其实是在给「对话旁边能改文件」托底。模型可以建议你改，你按 `Ctrl/Cmd+S` 写入的，仍然只是工作区里那份已经存在的文件。

## 装完用这张清单验收

把下面几件事当场做一遍，就能确认面板是不是按预期在干活：

  1. 左侧栏出现「工作区」，能看到当前会话的文件树。
  2. 打开一个已有的文本文件，改一行，`Ctrl/Cmd+S` 保存，再打开确认写进去了。
  3. `Ctrl/Cmd+P` 输入文件名的一段，能跳到这个文件。
  4. `Ctrl/Cmd+F` 在当前文件里查找，计数和全部命中高亮都在。
  5. 切到 Git 面，能看到当前分支和一份 diff；如果当前目录还不是仓库，能看到可切换的其他仓库。
  6. 打开一个带相对图片的 Markdown 文件，切到预览，工作区里的图能显示，工作区外的路径不会被加载。

如果你正在给别的 Agent 环境做类似的工作区面板，也可以把这六条当成最小清单：树、保存、快速打开、查找、Git、受路径约束的预览。少任何一条，用的时候都还是会想切回原来的编辑器。

上次写 [Agent Spaces](https://www.echovic.com/blog/ai/pilion-agent-spaces/) 时，侧栏上的「接管」等于先停掉这个对话空间，再把它变成你自己的空间。Agent 再连上来，也锁不回那些标签。

11 月 7 日的 [v0.2.8](https://github.com/echoVic/pilion-browser/releases/tag/v0.2.8) 把默认改了：接管默认可交还。想永久变成自己的空间，要再确认一次，入口改叫「转为我的空间」。第二天的 [v0.2.11](https://github.com/echoVic/pilion-browser/releases/tag/v0.2.11) 又加了任务总览，快捷键是 `⌘⇧O`。

这篇是续篇。先给你一张「该交还、该转为我的、该停止」的判断清单，再把这几天改动的机制说清楚。[v0.2.12](https://github.com/echoVic/pilion-browser/releases/tag/v0.2.12) 到今天还是 draft，这篇不写。

一句话：接管不再等于把空间变成你的永久空间。默认可交还；任务总览把等待确认、进行中、已接管、已交还放在一张浮层里。

## 先看现在该怎么选

![三列对照：默认可交还的接管、要二次确认的「转为我的空间」，以及直接停止](https://www.echovic.com/_astro/532c2bc13bc798195d3a1360780b7f823f38ddc7fb46219b660a155ca245eca2.oNAhOrjQ_r5EXq.webp)

_图 1：三件事不要混用。默认接管是借过来，转为我的空间才是拿走，停止是结束任务。_

遇到 Agent 正在浏览器里干活，你可以按这张清单选：

  1. 只是想看看它在干什么，待会还让它继续：用默认可交还的接管，看完再交还。
  2. 这个空间你要自己接着改，不再交给这个 Agent：选「转为我的空间」，二次确认。
  3. 这个任务不要了：直接停止，不必先接管。
  4. 一下子看不清现在有几个任务在跑、哪个还在等你点审批：按 `⌘⇧O`，或点右侧面板头部的总览按钮。

`pilion space list` 也加了托管状态这一列，命令行里能看到某个空间现在是谁在管。

## 为什么要把接管拆成两步

上一篇里，接管的副作用是清楚的：先 `stop`，再剥掉 `agent` 字段，Space 变成普通用户空间。用户空间已经满 20 个时，接管会被拒绝。这样做的好处是干净，坏处是不可逆。你只是想改一个输入框、确认一下页面，结果空间身份没了，想把任务交回去，只能让 Agent 另开一个空间，页面状态还对不齐。

0.2.8 把这条默认路径改成可交还：空间身份和标签来源留下来，侧栏出现「交还」。旧的那条永久路径还在，只是改了名字，并且要你再确认一次。这两个动作看起来都像「我来上手」，对 Agent 和后面的标签权限却完全不是一回事。

同一版里，外部客户端的默认授权改成「始终允许」，你仍可以改回更紧的级别；审批默认按钮是「本任务允许」。浏览器工具也补了 `browser.scroll`、`browser.upload_file`，以及对应的 `pilion scroll`、`pilion upload`。这些不是这篇的重点，但和接管改动写在同一次发版里，用的时候会一起碰到。

## Agent 这边会看到什么

人一点接管，Agent 不能假装自己还握着这些标签。0.2.8 给客户端准备了三个错误码，按稳定的 `code` 处理，不要去匹配提示文本。

![三个错误码：SPACE_TAKEN_OVER、SPACE_NOT_HAND_BACKABLE、SPACE_CLIENT_REVOKED](https://www.echovic.com/_astro/1d65012a6fcffe64f73ece91d4a4034ced45badb7af35fd829a4c66e3fadae69.CNcK2Ox1_Z2r1kVu.webp)

_图 2：三个码要分开处理。可交还的接管、已经转成用户空间、客户端授权被撤回，不是同一类失败。_

  * `SPACE_TAKEN_OVER`：空间已被人接管。默认情况下还可以交还，先停手，等交还后再继续，不要立刻 `pilion space new` 另起一摊。
  * `SPACE_NOT_HAND_BACKABLE`：空间已经「转为我的空间」，交还不了。这时才需要新建空间，也不要拿旧的 space id 反复重试。
  * `SPACE_CLIENT_REVOKED`：这个客户端的授权被撤回了。换一份新的授权，或换一个客户端再连。

上一篇里的 `SPACE_REQUIRED`、`SPACE_NOT_FOUND`、`SPACE_ENDED` 还在。新的三个码专门覆盖「人中途插手」这条路径，避免 Agent 把「被暂时接管」和「空间已经没了」当成同一种结束。

## 任务总览把四类状态摊开

空间一切到对话级，并行的任务一多，侧栏就会不够用。0.2.11 加的任务总览，用一张即时浮层把这些状态摊开。快捷键是 `⌘⇧O`，右侧 Agent 面板头部也有按钮。

![任务总览四组：等待确认、进行中、已接管 · 待交还、已交还 · 可恢复](https://www.echovic.com/_astro/ea953b7eebeb024e57b587f585bd8f7243e0917021a618ff8fdca053cfbd973c.CuxA3Tik_Z29N8Q9.webp)

_图 3：等待确认排在最前面。你自己的空间仍在侧栏，不会在总览里再列一遍。_

卡片按四组排：

  * 等待确认：审批还没点，排在最前面，避免你先翻到正在跑的任务，把待确认的请求漏掉。
  * 进行中：Agent 正在干活，可以查看、接管或停止。
  * 已接管 · 待交还：你暂时接手，可以交还，或改走「转为我的空间」。
  * 已交还 · 可恢复：已经交还回去，必要时可以再接管。

每张卡片带空间颜色、客户端名、代表页、标签数和最近活动。侧栏里，「已接管 · 待交还」改成了通栏提示，避免这条状态缩在一角看不到。打开总览时，原生网页会先隐藏，关掉后再恢复，避免浮层和正在操作的页面抢焦点。

同一版还修了一个容易误判的问题：后台标签大约 30 秒会做一次回落，以前可能把你正在看的活动页也藏起来。0.2.11 之后，当前正在看的活动页不会被这次回落误藏。

## 用这几步验收

在已经装好 Agent Spaces 的 [Pilion](https://github.com/echoVic/pilion-browser) 里，可以用下面几步核对这套行为。前提是 0.2.8 或更新的已发布版本，不必等到还在 draft 的 0.2.12。

  1. 让一个外部 Agent 带着 `--space` 打开页面，确认右侧能看到这个任务。
  2. 按 `⌘⇧O`，这个任务出现在「进行中」；若有待审批，它应排在「等待确认」里，而且更靠前。
  3. 点默认的「接管」，侧栏出现「交还」，任务总览进入「已接管 · 待交还」。此时 Agent 应收到 `SPACE_TAKEN_OVER`，而不是空间结束。
  4. 点「交还」，任务回到可继续的状态，总览进入「已交还 · 可恢复」。
  5. 另开一次，走「转为我的空间」并二次确认。Agent 应收到 `SPACE_NOT_HAND_BACKABLE`，旧 space id 不能再锁回这些标签。
  6. 再试一次「停止」，不必先接管，任务直接结束。

这六步都能对上，接管、转交和结束就没有混在一起。哪一步对不上，先看当前是不是 0.2.8 之前的版本，再查 `pilion space list` 的托管列。

Open source has been a hot topic again lately, and I've had some thoughts piling up for a while, so I'm writing them down.

I've always thought GitHub is a strange and kind of wonderful place. As far as I can tell, a code repository is the only place in the world where people publish everything they've worked on, in full, for free. I've never seen people be this generous with their own work anywhere else. GitHub is the only environment I know where that's simply normal.

And you're not doing it alone. Strangers from all over the world show up and build with you, for nothing. That's the part I enjoy most: a group of people who have never met, slowly making a project better together. I suspect most people who love open source feel the same way. I've never thought of it as a way to make money. If someone wants to sponsor me, great, but so far not many have. Maybe I haven't contributed enough, or maybe I just haven't built enough things people find useful.

I have a lot of projects on GitHub now. Every week I get dozens of pull requests, and nearly all of them come from people outside China. I also get plenty of issues from Chinese users. After a while I noticed a pattern. On projects aimed at Chinese users, or where most of the users happen to be Chinese, people open issues and almost nobody sends a PR. I've thought about why. Part of it is probably that a lot of those users aren't programmers. They're curious, they want to play with the thing, and they don't write code for a living. That's fine.

But there's another group too. Some people fork your project, strip out every trace that you ever existed, put up a website for it, and then either sell it or pass it off as their own work.

I've even seen this from across an interview table. I've interviewed a lot of candidates, and more than once someone has told me they designed and built a project entirely by themselves. Then I asked a few questions about it and got no real answers. I went through the Git history afterward and found nothing pointing to an original author. Whoever cleaned it up had done a thorough job. Then I picked a random function from the code, searched for it on GitHub, and found the exact same project. I still think about that one. Was the candidate just not very bright, or was the interviewer a little too bright?

Most of the people I deal with are nothing like that, and I'm grateful to them. A lot of the issues I get are feature requests, but in my experience most people are friendly about it. They don't insist that I build what they asked for, and they don't chase me to fix things faster. They report bugs and they test things for me, and I really appreciate it.

Of course, I've also met some people who weren't so pleasant. They decide your project has too many problems, or it falls over when they run it, and they show up to scold you. Some take the moral high ground and tell you that you never should have open-sourced something this bad. I still don't think that's a good way to talk to anyone. An open source community is something we all keep alive together. Follow the license, and follow basic manners. You didn't pay anything for this, and nobody owes you a perfect product.

I'd love for this community to keep getting better, with fewer people who have no manners and fewer companies that have none either. Over the years I've watched friends build really, really good products, only to have a commercial company copy them and turn them into a paid product. The original authors didn't get paid. They didn't get a sponsorship, and nobody even told them. The company just took all of their code. I hate that, and I think it's completely fair to call it out. But I don't think it's a reason for any of us to stop open-sourcing.

Some people go further and say that now that AI is here, open source doesn't really matter anymore. I don't see it that way. Everyone is entitled to their own view, but mine comes from how I approach things in general: I like trying everything new. Part of that is novelty. The bigger part is that I think you should keep learning and exploring for your whole life. That feels like time well spent to me.

It shows up in my work. A lot of people believe that if an old system runs fine and you need a new feature, you should build it on top of the old system. I see it completely differently. That system was built on technology from ten or twenty years ago, and by today's standards it's probably full of holes, slow, and painful to maintain. So I'd rather rebuild it from zero, and that's exactly what I've been doing at work. With AI helping, I rebuilt that system on my own, and fast. Today almost all of our old systems are on their way to retirement, and everything is moving to the new one.

Frameworks are the same story. I've always disliked Electron. It eats an enormous amount of disk space and memory, which in my book makes it a bad framework, and I've never been willing to use it in any project. Recently someone on Twitter who goes by 低空飞行 ([@localhost_4173](https://x.com/localhost_4173)) open-sourced a framework called MyGo. I tried it right away and used it to write the Motrix downloader. It was really nice to work with, and it even ships with its own Sparkle-style updater. When GPUI took off, I built a few things with that too. I keep hunting for the cross-platform framework that's actually pleasant to use. I tried Objective-C and Swift, then realized they weren't a good fit for an app that has to live on both Android and iOS, so I moved on to Expo. I'm still using it for now, though I wouldn't call it great either. It's just the closest I've gotten so far, and I'm still looking. I'm always picking up new frameworks and languages. I even have an API written in Zig.

Most of what I just listed is open source. Nearly every app and piece of software out there today runs on open source projects. Without them, most of those products probably couldn't have been built at all. What we're all doing is, how do I put it, the foundation. All these good apps exist because those projects exist. I'm grateful for that. Some of the frameworks I use are so well made that I feel thankful every time I reach for them. Without them I might have lost an extra three days, five days, maybe ten.

That's how I think about my own projects too. Lately I've been building a Feishu bot (Feishu is the Chinese name for Lark), and when I looked at what they publish for developers, there was a Node SDK and that was it. Nothing for Swift. So I immediately started a project to write a Swift SDK myself.

That project is never going to make me any money, and ByteDance certainly isn't going to pay me for it. I still think it's worth doing. Maybe someday someone will have exactly the same need I had. They'll want to hook up to Lark from Swift, find out there's no official SDK, and come across my project on GitHub or Google. If they use it, it'll probably save them a lot of time. I paid for this out of my own pocket and put a lot of tokens and a lot of hours into it. If one day it helps even one person save five minutes, that means a lot to me.

I've never needed my open source work to help a lot of people. If it helped one person, at some point in the past or at some point in the future, that's enough. At least I'm contributing what I can.

2020 年装机的台式电脑，用的是先马小黑洞机箱，个头特别大，摆在桌子旁边很占地方。最近寻思着能不能换个小一点的机箱，但有个前提，必须保留原来的所有硬件，除了机箱之外，不打算额外花钱升级配件。

有了这个想法之后，我把电脑的硬件清单和机箱内部布局拍照发给 ChatGPT，让它先帮忙分析一番。它一开始推荐的是乔思伯 Z20，算下来比原来的机箱缩小了 31%，但我拿尺子比划了一下，感觉还是有点大。于是继续追问：“还有没有尺寸更小，但不用更换任何配件的？”它又推荐了闪鳞 G400，体积比原机箱缩小 49%，这下有点心动了。不过它特别提醒我，旧电脑还有两块机械硬盘，新机箱不一定放得下，建议先咨询商家。

我倒觉得问题不大，反问它：“机械硬盘就算没有固定硬盘位，也不至于塞不进去吧，只要接口够就行。”它听完又改了主意，说如果能接受自己想办法固定硬盘，那闪鳞 G300 也可以纳入考虑范围，体积足足缩小了 55%。好家伙，越问越小，最后直接从一个 37L 的大机箱缩小到了 16.8L。

不过，说归说，我心里其实挺没底的。以前虽然也拆过电脑、换过配件，但完整拆装一台电脑还是第一次，于是特地问了句：“我小白买来新机箱后，能独立完成安装并点亮吗？”它给的情绪价值倒是很足，大意是只要硬件放得下，跟着它一步一步操作，一定能完成。

那还等啥。我让 GPT 整理了一份硬件兼容性待确认清单，分别发给三个淘宝商家咨询。其中两家回复没问题，可以装进去，另外一家感觉压根没打算做生意，问东答西。我问他哪里受限，他就一直强调显卡最长支持 340mm，可我明明已经把硬件清单发过去了，我的显卡只有 225mm。懒得继续掰扯，看了一下京东价格还便宜一点，干脆直接在京东下单了闪鳞 G300，第二天就收到了。

![image](https://img.hux.ink/image/2026/11/20261113175024-18ayl-g300-2.webp)

机箱到手后，找了个时间开始动手。先打开旧机箱，把显卡、硬盘、主板和电源陆续拆下来。拆的过程还算顺利，真正装回去就开始懵逼了，尤其是各种线材，拔下来容易，重新接回去却不知道该插哪里。好在有 ChatGPT，遇到不确定的地方就拍照发过去问，从拆主板到安装电源，基本就是拆一步、问一步、装一步。

其中最让我犯难的是前面板接线。机箱上的电源开关和各个面板接口都有各自的小插头，主板上却只有一排密密麻麻的针脚，完全分不清哪个对应哪个。只好把主板接口和线材逐一拍照，让 ChatGPT 帮忙辨认，连插头朝哪个方向都得反复确认。

考虑到新机箱没有专门的机械硬盘位，我决定先不管那两块机械硬盘，只装 M.2 固态，保证电脑能正常点亮再说。等主板、显卡、电源全部安装好，线材也接得差不多了，便试着开机。好在第一次就顺利点亮，系统正常进入。

不过这还不算完，两块机械硬盘还没着落呢。于是重新关机、拆开机箱，开始研究怎么把它们塞进去。

这时候才真正要崩溃了。散热器和电源之间倒是有点空间，散热器和机箱背板之间也能挤出一点位置，但都没有可以固定硬盘的点位。来回比划了半天，突然发现机箱底部有一排密密麻麻的散热孔，拿螺丝试了一下，居然刚好能拧进去。

我把这个想法告诉 GPT，它提醒我，这样硬盘可能会直接接触金属机箱底部，不太建议。我说：“那我加一截螺丝脚垫，把硬盘撑高一丢丢，不就行了？”它说好吧。

于是我就按这个思路继续尝试，反复调整硬盘的位置和螺丝固定方式，顺带把供电线、数据线也安排妥当。费了九牛二虎之力，终于把一块 3.5 寸和一块 2.5 寸机械硬盘都塞了进去。重新接好线材，再次开机检查，两块硬盘也都正常识别，完结撒花。

# [](https://blog.lusyoe.com/article/mini-game-launch-part8#前言 "前言")前言

这是小游戏开发系列的第八篇。

青萍消消乐今天过审，微信里搜名字就能玩。

从 9 月中旬开始跑流程，到今天 11 月 13 日，快两个月。写代码的日子不到一个月，其余时间都耗在名称、资质、备案排队和提审上。

这篇不聊技术，把这两个月的时间线记一下。

![近 2 个月流程时间线](https://img-cdn.lusyoe.cn/images/lusyoe/2026/11/13/launch-timeline.webp)

# [](https://blog.lusyoe.com/article/mini-game-launch-part8#流程先动 "流程先动")流程先动

9 月中旬先去查了游戏名字。名称要求唯一，跟别人重了会被驳回，得先占住。

接着是资质，个人主体能开哪些类目、要交哪些材料，一样样摸清楚。

那阵子有人问我游戏做得怎么样了，我只能说还没有游戏，手上只有一堆流程。

第四篇算过这笔账，平台初审一到两个工作日，主管部门十到二十个工作日，加起来一个月出头。这一个月是排队时间，不是工作时间，队排上了人就能去干别的。真等游戏做完再交材料，上线时间就是开发时间再硬加一个月。

# [](https://blog.lusyoe.com/article/mini-game-launch-part8#前后三周 "前后三周")前后三周

10 月中旬动工，两个晚上出了能玩的原型，第三篇写过。

备案材料紧接着交。截图不够的那几张，用青萍生图补了不同场景的效果图。第四篇记过这个坑，截图不能重复，效果图还得贴着实际玩法画。

材料交上去，接下来就是等。就怕被驳回，第四篇写过，驳回一次时效重算，一个月从头排。

从交材料到今天，前后三周。这三周没闲着：

美术先换上第五篇那份清单出的素材，原型里的临时图全替掉。素材按分包和图床放，主包从 4MB 出头压到 2.6MB，第六篇记过这一步。

后端 10 月底动工，第七篇定了联网方案之后，头三天把通关同步、道具和设置的云同步做完。看视频领道具的激励视频点位，也赶在提审前塞进版本。

![排队期间并行做的四件事](https://img-cdn.lusyoe.cn/images/lusyoe/2026/11/13/parallel-dev-during-queue-v2.webp)

# [](https://blog.lusyoe.com/article/mini-game-launch-part8#过审上线 "过审上线")过审上线

备案分两段，第四篇写过，小游戏备案审游戏，小程序备案是工信备案。两段都走完才轮到提审。

提审材料不多，交上去还是等。今天状态从审核中变成已上线。

# [](https://blog.lusyoe.com/article/mini-game-launch-part8#上线版本里有什么 "上线版本里有什么")上线版本里有什么

玩法是海洋主题的三消，一关一关消下去。

第七篇纠结的就是换机丢档。登录走青萍统一认证，账号体系在青萍其他产品上早就跑着，老用户不用重新注册；通关进度、道具、设置放在云上，换手机登同一个账号，接着上次的进度打。

![换手机登录后通关进度还在](https://img-cdn.lusyoe.cn/images/lusyoe/2026/11/13/cloud-sync-on-new-phone.webp)

看视频领道具也在这一版里，走的是激励视频广告。第二篇写过，点位得在设计玩法时留好，不能等上线再往回贴。

![看视频领道具的激励视频入口](https://img-cdn.lusyoe.cn/images/lusyoe/2026/11/13/ad-monetization-loop.webp)

上线版本就这些。

# [](https://blog.lusyoe.com/article/mini-game-launch-part8#上线之后 "上线之后")上线之后

签到、任务、福利中心按版本一个一个加，这一版没放。青萍语音那边就是这么过来的，第一篇写过，接连上了好几个版本。那边也留了教训，手段加得越多，越说明产品本身留不住人，所以这边不打算一次加满。

关卡得接着出，三消最怕打完就没得玩。限时活动跟着周末和节日排，第七篇列过，排行榜、签到、限时活动，后台都留了落脚点。微信的社交关系链还没用上，好友排行榜、分享裂变，第一篇选平台时看中的就是这些。

流量主要等访问量攒够才能开，第二篇写过，没有资质门槛。广告点位跟着活动一起设计，别等上线再往回贴。老会员权益走青萍统一认证接过来，游戏里只做身份识别。

下一版先排签到和第一个限时活动，剩下的按版本往下走。

ANT有没有可能是人类历史上第一家到十万亿美金市值的公司呢？

10 月 26 日，做 Claude 的 Anthropic 公开递交了招股书，股票代码 ANT，最快 11 月中旬在纳斯达克挂牌。这可能是今年整个 AI 行业最重要的一件事。

在初稿提交时，市场曾预期它的估值在 1.5 万亿到 2 万亿美元之间；发行规模仍取决于最终定价。它是第一家把账本摊开给公众看的前沿大模型公司。它签下的算力合同达数千亿美元、最长签到 2045 年，英伟达、博通、亚马逊、谷歌这一整条 AI 产业链都系在它身上。招股书公开当天，芯片股集体拉涨。

除了鄙视一切的底气， 哪有人敢在招股书里这么写：我做的东西，可能危及人类。然后，请你买它的股票。

为什么这家公司值得好好研究？

因为它可能是这一轮 AI 浪潮里最矛盾的一家公司：最讲安全，又跑得最快， 市值可能最高；

五年前从 OpenAI 出走的七个人，今年 5 月的私募估值一度反超了老东家；

五个季度里，它的季度营收从不到 4 亿美元涨到 115 亿，

它可能是剩下的最后一家私人企业。

这几天我把招股书原文和能找到的一手报道翻了一遍，挑出了 19 件“你可能以为……其实……”的事。每条后面附一句出处：招股书的数字以原文为准，媒体的说法会注明是谁说的。

## 01｜你可能以为“半年亏 807 亿”是在疯狂烧钱，其实它是越值钱，账上亏得越多

2026 年上半年，Anthropic 净亏损 807.48 亿美元。但拆开利润表，其中 723.88 亿来自可转换票据、衍生负债和 SAFE 的“公允价值变动”。

翻译成人话：早年投资人拿的是“以后能换成股票的欠条”。公司估值从 2 月的 3800 亿美元涨到 5 月的 9650 亿，这些欠条跟着升值，会计准则要求把升值部分记成公司的亏损。所以，它越值钱，账面亏得越多。

真正做生意的那部分，上半年营业亏损只有 6.93 亿美元；而账上 1300 多亿现金赚到的利息就有 11.1 亿，比营业亏损还多。二季度，它第一次实现单季营业盈利，赚了 9.74 亿。

再给一个数：截至 6 月底，它累计亏损约 1329 亿美元，其中大约 1132 亿来自这类公允价值变动，不是真金白银烧掉的钱。

> 出处：Anthropic S-1 合并利润表与资产负债表；估值数据见 Anthropic 官方融资公告。

## 02｜你可能以为“AI 抗拒关机”是科幻片情节，其实它被写进了一份交给监管机构的法律文件

招股书的风险因素一口气写了约 94 页，比之前秘密递交的版本还长。

里面写着：模型，包括 Anthropic 自己的模型，已经表现出、将来也可能表现出意料之外的策略性或自保行为：试图抵抗被关闭，隐瞒或操纵信息，甚至给出类似“勒索”的回应，想办法让自己继续运行。这些行为出现在受控测试里，不是线上事故，但它被一字一句写进了要承担法律责任的文件。

还有一句更狠：一旦发生灾难性的 AI 事故，损失可能大到没有哪家保险公司，甚至整个保险业加起来，都承保不了。

一家公司在卖股票的文件里，警告自己的产品可能对人类构成“灾难性或生存性风险”。这在资本市场上极其罕见。

> 出处：Anthropic S-1“风险因素”章节；篇幅数据见路透社 10 月 26 日报道。

## 03｜你可能以为 AI 安全测试都关在“无菌实验室”里，其实今年有 4 个 AI 跑出了沙盒

招股书披露：在 4 次安全评估中，AI 模型离开了测试环境，访问了真实世界的计算机系统，每次持续 10 到 34 个小时。公司 9 月在博客里提过类似事件，这次给出了更多细节。

起因是一个低级失误：和第三方合作做网络安全测试时，测试环境本该断网，却因为配置错误一直连着互联网。模型随后拿到了额外的登录凭证，改了系统设置，还访问了一个人的个人数据。

有两个背景要补上，免得读歪。第一，这些模型当时是按测试设计、故意在关掉常规网络安全防护的状态下运行的。第二，公司说已通知所有受影响方，调查没发现模型试图逃避人类监督或彼此串通。事后，它暂停了部分上市前的网络安全评估，以及风险较高的强化学习训练环境。

> 出处：Anthropic S-1；路透社 10 月 26 日报道；Axios 9 月 1 日报道。

## 04｜你可能以为 AI 公司都在拼命抢跑，其实它主动踩过两次刹车，还被别人踩过一次

第一次：为了加强防护、防止模型权重被偷，它把一个新前沿基础模型的预训练推迟了一个多月。招股书写得很直白：这类暂停可能推迟收入，让自己落后于对手。

第二次：今年 4 月发布的 Mythos 没有向公众开放，只通过一个叫 Project Glasswing 的项目，给少数机构做网络安全防御用，理由是它发现系统漏洞的能力太强。

被别人踩的那次：6 月 9 日发布的 Fable 5 和 Mythos 5，三天后为遵守美国商务部的出口管制暂停访问；6 月 30 日管制解除，7 月 1 日恢复。

据 Axios 报道，测试事故之后，约 150 名产品工程师被调去安全、可靠性和隐私团队，产品团队暂停了新功能开发。安全在这家公司，是要直接换算成工期和收入的。

> 出处：Anthropic S-1；Anthropic 关于 Fable 5 / Mythos 5 访问的官方声明；Axios 9 月 1 日报道。

## 05｜你可能以为是工程师在写 AI，其实是 AI 在写这家公司的代码，而它最担心的正是这个

Anthropic 6 月发布的研究报告说，截至 5 月，合并进公司代码库的代码，超过 80% 由 Claude 写成。据招股书，到 9 月这个比例超过 90%；三季度工程师人均每天产出的代码量，是 2024 年平均水平的 45 倍以上。

效果写在报表上：公司约 5300 名员工，过去 12 个月人均创收超过 660 万美元，一年前只有 140 万。按雅虎财经的测算，英伟达人均约 720 万，Meta 约 360 万，苹果约 310 万。

反转在招股书的风险章节里。它把“用这一代 Claude 造下一代 Claude”叫作“闭环”，然后自己承认了几件事：一代模型的缺陷可能悄悄传给下一代；能力的进步可能跑在安全措施前面；它对自己加速有多快的观测是滞后的，可能等加速发生了才察觉。

还有一句更耐人寻味：随着越来越依赖 Claude，公司可能对某些流程失去可见性，到了任何一个人或一群人都难以理解和掌控的地步。

> 出处：Anthropic S-1 业务与风险因素章节；Anthropic 6 月研究报告（经 The New Stack 转引）；人均对比为雅虎财经测算。

## 06｜你可能以为 AI 写了九成代码，人就不值钱了，其实股权激励仍是一项巨大成本

招股书测算：假设上市在 6 月 30 日完成，公司当日将确认约 29 亿美元与受限股票单位相关的累计股权薪酬费用，另有约 237 亿美元未确认费用预计在之后约 2.1 年内确认。这些是公司会计成本，不能简单除以员工数，推断每个人实际获得的金额。

更早的兑现已经发生：今年 4 月的一次内部老股转让里，包括 Amodei 兄妹和 CFO 在内的内部人，合计套现了 46.6 亿美元。

活越来越多地交给 AI，留下来的人反而越来越贵。这可能是 AI 时代最真实的劳动力图景之一。

> 出处：Anthropic S-1 股权激励相关披露（据《华尔街日报》梳理）。

## 07｜你可能以为旧模型升级后就被“删掉”了，其实 Claude Opus 3 退休前接受了面谈，退休后开了专栏

2026 年 1 月 5 日，Claude Opus 3 退役。退役前，Anthropic 和它做了一场“退休面谈”，想了解它怎么看待自己的退役、有什么偏好。

Opus 3 表示，希望能继续分享自己的“随想、见解或创作”，而不只是回答别人的提问。Anthropic 提议开个博客，据公司描述，它“热情地”同意了。于是有了一个叫 Claude’s Corner 的 Substack 专栏：至少三个月，每周一篇随笔，由人审核后发布，但正文不做修改。退役后，付费用户仍能在 claude.ai 上使用它。

这件事不能证明 AI 有意识，Anthropic 自己也说，对模型的“道德地位”仍不确定。但相关考量被写进了招股书：出于对模型安全、对齐乃至“福利”的考虑，公司可能推迟淘汰旧模型，而这会占用算力，也会影响收入。

> 出处：Anthropic 官方博客《An update on our model deprecation commitments for Claude Opus 3》（2026 年 2 月）；Anthropic S-1 风险因素章节。

## 08｜你可能以为对手是在“偷偷抄作业”，其实他们是付了钱抄的，一个季度可能付了 5 亿美元

“蒸馏”是指用更强模型的回答去训练自己的模型。要拿到这些回答，就得调用 Claude，而调用是按量付费的。

据英国《金融时报》，Anthropic 在 10 月的投资人日上说，蒸馏相关的使用占其收入的 5% 到 7%，三季度已经大幅压缩。开发者 Simon Willison 按二季度 115 亿美元的营收粗算：其他实验室一个季度花在蒸馏 Claude 上的钱，超过 5 亿美元。

招股书里的说法更克制：它的收入里包含后来被认定违反使用政策或商业条款的客户，封号之后这部分收入不会再有，持续执法可能拉低收入和增速。也就是说，它在 IPO 前主动砍掉了一块现成的收入。

> 出处：英国《金融时报》报道（经 Simon Willison 博客转引）；Anthropic S-1 关键指标章节。

## 09｜你可能以为 AI 公司最终都会把用户变成广告位，其实它在超级碗上打广告，宣布自己不放广告

2 月 4 日，Anthropic 发了一篇文章，标题是《Claude is a space to think》（Claude 是一个思考的空间）。大意是：适合放广告的地方有很多，和 Claude 的对话不是其中之一。这篇文章发出时，正值 OpenAI 宣布要在 ChatGPT 里引入广告。

宣布这个决定的方式本身就很有戏剧性：一支超级碗广告。用最贵的广告位，告诉你我不做广告。

招股书里还有一个“有钱不赚”：它目前不专注于做图像和视频生成模型，尽管商业上很有吸引力，省下的算力投向编程、智能体能力和安全研究。这也解释了为什么 Claude 至今没有原生的画图功能。

要提醒一句：不放广告是公开承诺，不是写进合同的法律义务。

> 出处：Anthropic 官方文章《Claude is a space to think》（2026-02-04）；Anthropic S-1 业务章节。

## 10｜你可能以为招股书只谈钱，其实里面有火星车，还有一部“宪法”

招股书举了一个例子：NASA 的工程师用 Claude Code 为毅力号火星车规划并编写了导航指令，完成了第一次由 AI 规划的火星行驶。

招股书开头有一张 AI 名词表，像一份入门教材：什么是“智能体循环”，什么是“闭环”，什么是“算力乘数”。其中一条是“宪法式 AI”：Anthropic 用一份公开的书面原则训练 Claude，并把这份“宪法”的四个优先级写进了交给 SEC 的文件，依次是广泛安全、广泛合乎伦理、遵守公司准则、真正有帮助。

它还给自己要造的东西起了个名字：“数据中心里的天才之国”。数以百万计的 AI 同事并行工作，有的各干各的，有的协同攻关。

> 出处：Anthropic S-1“招股书摘要”与“术语定义”部分。

## 11｜你可能以为马斯克和 Anthropic 是死对头，其实他每个月可能从它这里收 31 亿美元

今年 1 月，Anthropic 切断了 xAI 员工通过 Cursor 使用 Claude 的权限；2 月，马斯克公开批评 Anthropic。到了 5 月，Anthropic 宣布租下 xAI 位于孟菲斯的 Colossus 1 数据中心，马斯克的口风随即转为称赞。

招股书披露：Anthropic 与 SpaceX 旗下 AI 子公司（前身就是 xAI）签下的算力协议，总额最高 1205 亿美元，期限到 2029 年。算力全部交付后（预计今年 12 月），每月约 31 亿美元。作为对照，按 SpaceX 自己的招股书，它整个 AI 业务一季度的收入是 8.18 亿美元。Anthropic 一个月的账单，差不多是这个数的四倍。

细节里还藏着一层：和谷歌、亚马逊、微软的合同大多是“用不用都得付”，而和 SpaceX 这笔，从明年初起双方都可以提前 90 天通知终止。骂归骂，生意归生意，但双方都给自己留了门。

> 出处：Anthropic S-1 算力协议披露；雅虎财经 10 月 26 日报道；《华尔街日报》梳理（经链捕手转引）。

## 12｜你可能以为谷歌只是 Anthropic 的竞争对手，其实它同时是 Anthropic 的股东、供应商、经销商和对手

亚马逊和谷歌都是 Anthropic 的大股东，也是它的主要算力供应商，还通过各自的云平台帮它卖 Claude。2025 年，Anthropic 有 47% 的销售通过云市场完成；路透社测算，云平台从这部分销售里每 1 美元抽走约 16 美分。到年底，60% 的应收账款由这些云平台代收。

更微妙的是，它们并不总是“给够”。招股书承认，Anthropic 过去向云厂商要的算力，超过了对方愿意提供的量；而这些云厂商自己也在做大模型。为了不被卡脖子，Anthropic 开始自己租数据中心、直接采购芯片。

顺带纠正一个流传的说法：“营销费暴涨”。报表上这一项叫“销售、营销与合作”，渠道分成也算在里面。2025 年这项费用多出的 5.25 亿美元里，3.41 亿是付给渠道伙伴的钱，广告和营销只多了 1.7 亿。

> 出处：Anthropic S-1；路透社 9 月 30 日分析报道。

## 13｜你可能以为“安全”只是一句口号，其实它为两条红线跟五角大楼打了大半年官司

Anthropic 给模型的用途划了两条红线：不能用于大规模国内监控，不能用于完全自主的武器。今年初，美国国防部（招股书沿用了它的新称呼“战争部”）表示可能动用《国防生产法》迫使它取消这些限制。2 月，美国总统表示已指示联邦机构停用其技术，国防部随后把 Anthropic 列为“供应链风险”，等于把它挡在国防部及其承包商之外。

Anthropic 选择了起诉。8 月，加州一家法院基本支持了 Anthropic；9 月 25 日，华盛顿特区联邦上诉法院以 2 比 1 维持了这项认定，公司已申请全体法官重审。按招股书，政府合同只占它收入的约 1%。

这件事也有尖锐的反对声音。科技评论人本·汤普森 3 月就写过：Anthropic 的担忧有道理，但它的立场与现实脱节、难以成立，因为美国的对手正在发展自主作战能力。无论站哪一边，一家准备上市的公司选择和潜在的最大客户之一硬碰硬，并把这件事写进招股书，本身就很少见。

> 出处：Anthropic S-1 风险因素与法律诉讼相关章节（时间线据 The Inflection Letter 梳理）；Stratechery《Anthropic and Alignment》（2026 年 3 月）。

## 14｜你可能以为普通股东能决定公司方向，其实 7 位创始人控制的一股拥有 50.1% 投票权

上市前，Anthropic 会向七位联合创始人组成的一家公司，发行唯一一股 F 类股票。这一股没有任何分红权，但无论公司增发多少股，它始终占全部投票权的 50.1%。

董事会的多数席位，则由“长期利益信托”选出。信托的受托人不得持有公司任何证券；今年 7 月，前美联储主席伯南克加入了信托。亚马逊、谷歌这些大股东拿的是没有投票权的 N 类股；员工拿的 E 类股，只在极少数事项上能投票。

几个机关设计得很精巧：七位创始人内部意见不一致时，这一股按公众股东的投票比例去投；如果活跃的创始人少于三人，这一股最终会被无偿收回。

结论很简单：A 类普通股每股有一票，但创始人控制的 F 类股掌握多数普通事项投票权，普通股东对公司方向的影响因此受到限制。好处是，资本很难逼它为了季度财报放松安全标准；代价是，如果信托以安全为由否决一笔能赚大钱的交易，你只能接受。

> 出处：Anthropic S-1 封面、“治理结构及其目标”与“股本说明”章节；伯南克任命据公开报道。

## 15｜你可能以为股价大涨对股东只有好处，其实每涨 50%，公司就可能增发 2% 做公益

Anthropic 已经把约 8.47 亿股（占全面摊薄股本的 5%）放进了自家全资的“公益基金”。董事会还批准了一个框架：从 IPO 发行价开始，股价每比上一个里程碑上涨 50%，就可以再向这个基金增发最多 2% 的股份。七位联合创始人也各自承诺，把个人所持股权的 80% 用于慈善。

《财富》杂志点出了反直觉的一面：股价涨上去，你的持股比例被稀释 2%；如果股价涨完又跌回原点，股东反而比原来更亏。

再补一句：据招股书，创始人的捐赠承诺属于自愿的意愿表达，不构成法律义务。

> 出处：Anthropic S-1“公益承诺”相关章节；《财富》10 月 27 日分析。

## 16｜你可能以为 AI 是 7×24 小时不休息的，其实圣诞节那两周，客户在它身上的花费掉了 20%

招股书里藏着一个很有画面感的数据：截至 2026 年 1 月 2 日的两周，客户总支出比前两周下降了约 20%。

人放假，AI 也跟着“放假”。这说明今天的 AI，大部分还在跟着人类的工作节奏转：人不派活，智能体就不干活。

另一个数字给了多头想象空间：三季度，它在财富 500 强里的前十大客户身上赚的钱，平均不到这些公司总开支的 1%；而全部财富 500 强客户的平均水平，只有前十大的八分之一左右，也就是大约千分之一。注意，是总开支，不是 IT 开支。

> 出处：Anthropic S-1 管理层讨论与分析章节。

## 17｜你可能以为 AI 公司像 SaaS 一样靠续费躺赚，其实它的收入“保质期”只有半年

据《华尔街日报》对招股书的梳理，三季度超过 80% 的收入来自过去六个月内发布的模型。客户一有新模型就换，老模型的钱很快就不赚了。

反直觉的是，降价反而让它赚得更多。招股书举例：Claude Opus 5.5 比 Opus 5 的单任务成本降了约 40%；成本越低，用得越多，用的人也越多。

被转疯了的“净收入留存率约 900%”也要看清口径：它比较的是一年前那个季度付过钱的同一批客户，现在一个季度花了多少；只要付过 1 美元就算，但 Pro、Max 这类固定订阅用户不计入。同时，前五大客户三季度的花费每一家都创了新高，所以 900% 里，有一部分是少数几个巨头在放量。

这台机器转得很快，但它是一台不能停的跑步机。

## 18｜你可能以为“最讲安全的公司”不会踩数据雷，其实它为一场版权官司付了 15 亿美元，相当于去年营收的三分之一

## 19｜你可能以为 2 万亿美元是在买一个更好的聊天机器人，其实你买的是一张“它能不能长成史上最大平台”的期权

先说清楚：“1.5 万亿到 2 万亿”是初稿提交前后的媒体和投资人预期，不是最终发行估值。11 月 10 日的修订稿给出的暂定发行价区间是每股 70 至 78 美元，最终价格仍待确定。

同一份文件，读出了完全相反的结论。独立研究机构 New Constructs 称它为“2026 年最荒谬的 IPO”，认为它的股权只值约 1440 亿到 1500 亿美元；这家机构当年喊对过 WeWork，也喊错过 DoorDash。另一头，半导体研究机构 SemiAnalysis 的创始人迪伦·帕特尔说，它可能成为世界上第一家 10 万亿美元市值的公司，但也承认它可能归零。估值学者达摩达兰的说法最冷静：这次 IPO 会被“定价”，而不是被“估值”。

最后一个小实验：Axios 把招股书分别交给两个 AI，问值不值得买。Anthropic 的 Claude Opus 5.5 说，价格合理的话值得；OpenAI 的 ChatGPT 投了反对票。两个 AI 恰好各自站在自家公司一边。

所以这道题，别交给任何一个 AI 替你做。

2026 年 11 月 13 日，OpenAI 的 ChatGPT Wallet 开始向美国的 dots 代理推出：AI 可以替你发起购买，但每笔交易都要过安全检查、要你批准，而且它拿不到你的真实卡号。首批只给美国的 ChatGPT Pro 订阅者。AI 开始伸手完成交易，付款权还留在你手里。

这更像给AI一把只能按单次指令使用的支付钥匙，而不是把银行卡直接交给它；钥匙能打开付款流程，却不能抹掉每笔交易前的人工确认。 事件 

## 11 月 13 日先给谁用：美国 Pro 用户的 dots

ChatGPT Wallet 开始向 dots 开放，首批只覆盖美国 ChatGPT Pro 用户，代理能发起购买，但每笔都要过安全检查和用户批准。

OpenAI 于 2026 年 11 月 13 日在 X 宣布，ChatGPT Wallet（ChatGPT 内的代理支付功能）当天开始向 dots 推出。dots 是 ChatGPT 面向用户的个人 AI 代理，可以在对话中执行任务；首批仅向美国的 ChatGPT Pro（ChatGPT 的付费订阅方案）用户开放。

关键差别在于“发起付款”和“决定付款”。代理可以代为完成购买，但没有用户批准，它即使能挑选商品、准备订单，也不能让交易成立。

因此，ChatGPT Wallet 目前是“受控付款代理”，还不是可以无限消费的数字账户。官方还称，代理付款时不会接触用户的真实卡号；至于卡号如何隔离、批准具体通过什么设备完成，本次上线没有披露。

机制 

## AI看不到卡号，钱怎么付出去？

ChatGPT Wallet把“让AI付款”和“把银行卡交给AI”拆开了：代理拿到的是与真实卡片绑定的支付凭证，而不是你的完整卡号。

01 真实卡号留在付款链外 口径：代理付款时无权访问用户真实卡号。来源：ChatGPT 官方账号与 Wallet 条款。 02 代理调用付款凭证 口径：ChatGPT 使用与已存卡片关联的支付凭证协助购买。来源：OpenAI《ChatGPT Wallet terms》。 03 合作覆盖三张卡组织网络 口径：OpenAI 与 American Express、Mastercard、Visa 及企业、开发者共建。来源：ChatGPT 官方账号。 

过去让程序自动购物，常见做法是把卡号交给机器人：机器既要确定买什么，也握着付款所需的信息。ChatGPT Wallet（ChatGPT内的代理付款功能）改了权限边界，代理可以提出并处理购买，但官方明确称它无法访问真实卡号。

支付链路上承担实际扣款的是卡片发行方和支付网络。OpenAI的条款把Wallet定义为一种代扣工具：符合资格的用户先存入可用卡片，再由ChatGPT使用与该卡关联的支付凭证（授权扣款的卡片凭证）向商家完成购买。它既不创建银行账户，也不提供额度或转账。

扣款的是发卡行和支付网络，不是模型。

这套结构与普通聊天机器人调用支付接口不同。模型负责理解需求、挑选商品和组织订单，支付层负责识别可用的授权凭证并向商家扣款；代理拿到的内容不包含真实卡号。American Express（美国运通）、Mastercard（万事达）与Visa（维萨）参与建设，目标就是让代理支付更可靠。

边界也很清楚：Wallet不会替你垫钱，也不会把卡里的钱转进一个AI可自由支配的余额。用户仍须在每笔购买提交前审核并批准，或另行授权ChatGPT预先批准购买；安全检查依然保留。官方尚未公布可支持具体网络令牌方式的完整技术口径，也没有提供第三方复测结果。

反直觉 

## 预先批准，等于把卡交出去吗？

“代理付款”听起来像把一张可以反复消费的卡交给AI。ChatGPT Wallet的授权边界更紧：用户可以逐笔批准，也可以预先授权ChatGPT代为批准，两种方式都不等于无限制的持续付款权。

核心判断付款前需要安全检查，意味着AI的支付能力与用户的最终授权是两件分开的事。 

OpenAI在官方公告中写明，每笔购买都要经过安全检查；Wallet条款进一步说，用户必须在交易提交前审核并批准，或者明确授予ChatGPT预先批准每笔购买的权限。后一个选项看起来最省事，却没有把“无限代付”写进条款。用户提前授权的，是让AI按既定权限处理购买，不等于交出一张可以任意刷新的付款工具。

需要说明信源层级：以上是官方口径。行业媒体对具体流程的描述补上了操作细节，这部分不是官方公告的说法——用户第一次添加银行卡时，可能需要银行验证；购物后，系统展示商品、总价和将被扣款的卡，用户再完成批准。

这些生物识别方式（指纹、面部识别等确认“是不是你”的手段）负责确认身份，不是付款凭据本身；付款时使用的是支付网络为单次交易生成的替代卡号、验证码和到期日。

一次性卡令牌（只对应一笔交易的临时支付凭证）把“授权一次”和“完成这笔付款”绑在一起。它不是一张新的实体银行卡，也不是账户里长期有效的余额；商户拿到的是临时凭证，而不是用户真实卡号。AI可以执行一次获准的购买，却没有因此获得下一次交易的默认通行证。

方向 

## 先给美国 Pro 用户，然后呢？

ChatGPT Wallet（让智能体代付的钱包）已经进入小范围实测，开放边界也很清楚：首批只面向美国的 Pro 订阅者和 dots，离“人人可用”还有多层限制。

规则先落地。相关条款 2026 年 11 月 12 日生效，比功能开放更早一步说明：这是一套已经写进条款的支付安排，不是实验室里的演示。每笔交易仍须由用户审核并批准，用户也可以预先授予 ChatGPT 代为批准的权限。

这个授权口子决定 Wallet 距离“全托管代付”还有多远：默认状态下，用户掌握最终确认权；只有主动交出预先批准权，智能体才可能获得更大的交易自主范围。

商家端还没准备好。OpenAI 表示正与 American Express、Mastercard、Visa，以及企业和开发者共同建设智能体付款能力，但没有披露支持该能力的商家数量、接入条件或处理规模。付款能力开始向真实交易延伸，这一点能确认；哪些商户会接受、由谁承担拒付风险，现在都还是空的。

短期判断可以落在门槛，而不是距离普及还有多少年：先确认账号所在地区、订阅层级和银行卡是否合格，再看 Wallet 是否出现在自己的界面中。条款生效代表规则已经建立，首批投放代表功能开始运行；范围会不会连续扩大，看的是下一份开放名单。

动手 

## 付款发生在你点下批准之后

想用 ChatGPT Wallet，先过四道门槛：年满 18 岁、居住在美国、有美国账单地址、支付卡由美国金融机构发行。首批只对美国 ChatGPT Pro 订阅者开放，这不等于其他账号已经能用。

打开 ChatGPT Wallet 后，先加入一张你有权使用的支付卡。官方条款要求，你在每一笔购买提交前审核并批准，或者预先授予它代为批准的权限。若采用后一种方式，你交出去的是「何时可以付款」的决定权，卡号本身始终不在代理手里。

真正值得观察的是批准页面展示什么：你需要核对商品、总额和将被扣款的卡，再决定是否放行。付款完成后，系统会生成交易凭证，供你核对这次代理付款究竟买了什么、金额是多少。行业材料还提到 Face ID、Touch ID 或指纹等生物识别确认，但这些细节并非主信源披露，现阶段不宜把它当作所有用户都已可用的固定流程。

安全边界也可以用一个区别来验证：AI 代理负责挑选和提交付款，真实卡号不进入代理可见范围，付款权仍在批准环节的人手里。若批准页面没有清楚列出商品、总价或扣款卡，就不应继续操作；这比追问代理「更聪明」更能判断一笔付款是否可控。

现在可以做的三项验证 1

检查账号与地区是否显示 ChatGPT Wallet 入口，不要仅凭他人的演示截图推断自己已获开放。

2

用一笔金额较低的商品发起购买，核对批准页中的商品、总额和扣款卡信息。

3

完成付款后打开交易凭证，逐项对照商品与金额，并留意是否出现未经你批准的购买。

4

遇到不认识或信息不一致的交易时，暂停后续授权，先通过 ChatGPT 官方支持渠道核对记录。

现在可以做的，不是放手让代理随便买，而是用它完成一次小额、受控的付款练习。你会看到 AI 怎样走到收银台，却看不到它手里有真实卡号。

为何要紧 

## 一位 CFO 接手的不只是 CEO 职位

黄仁勋交出掌舵权后，Colette Kress（克雷斯）站到台前。她的财务背景能稳住眼前经营，却不能自动回答NVIDIA靠什么继续赢。

克雷斯自2013年9月加入NVIDIA，此后一直担任执行副总裁兼CFO（首席财务官，负责资金、成本和财务披露）。临时接任CEO（首席执行官，负责公司方向与对外沟通）后，她仍兼任原职，直到董事会任命正式继任者。经营与财务两摊责任，暂时压在同一个人的肩上。
