打开电视想看一个视频，却先看到会员入口、剧集推荐和一排不常用的内容。真正想打开的应用，反而要往菜单深处找。

如果你希望电视首页简单一点，可以了解一下 Aerial：把常用应用摆在眼前，背景留给风景，用遥控器就能进入自己想看的内容。

## 一、Aerial是什么？

Aerial 是参照 tvOS 风格设计的 Android [TV](https://www.wangdu.site/tag/tv "【查看含有\[TV\]标签的文章】") 桌面，面向电视、电视盒子和投影仪。它提供独立的主屏幕，用来启动应用、整理入口和展示壁纸、屏保。

项目在 [GitHub](https://www.wangdu.site/?golink=aHR0cHM6Ly9naXRodWIuY29tL3BlbmdjaHVqaW4vYWVyaWFsLXR2) 公[开源](https://www.wangdu.site/tag/%e5%bc%80%e6%ba%90 "【查看含有\[开源\]标签的文章】")码，软件代码采用 [MIT 许可](https://www.wangdu.site/?golink=aHR0cHM6Ly9naXRodWIuY29tL3BlbmdjaHVqaW4vYWVyaWFsLXR2L2Jsb2IvbWFpbi9MSUNFTlNF)，官网提供免费下载。它是独立项目，与 Apple 及电视品牌没有隶属关系。

它改变的是电视首页的使用体验。视频平台会员、有线电视和原有应用仍按各自规则使用，安装一个桌面不会获得这些服务的付费权益。

## 二、它能让电视用起来更方便吗？

### 常用应用集中放，少翻几层菜单

按照[官方功能介绍](https://www.wangdu.site/?golink=aHR0cHM6Ly9hZXJpYWwucXVzdC5tZS8=)，你可以调整应用顺序、放进文件夹，或者隐藏不常用的入口。比如把追剧、音乐和本地播放应用留在首页，把系统工具收进文件夹。

遥控器长按确认键可以打开整理菜单；也能扫电视上的二维码，用手机拖动排序、改名和换图标，减少遥控器输入文字的麻烦。

### 壁纸和屏保，让闲置的电视成为风景窗口

Aerial 提供航拍画面、每日图片及本地照片、视频等背景选择。屏保适合电视暂时无人操作时使用，壁纸则是桌面的背景，两者可以按自己的习惯设置。

航拍视频需要网络访问，流量和播放效果也取决于片源、网络与设备。影片和图片有各自的版权，软件开源不代表附带内容也可以任意再分发。

### 把常用信号源放到容易找到的位置

连接游戏机或电脑的人，可以关注 HDMI 入口和控制中心。项目支持把信号源加入主屏幕，但具体端口识别、亮度和音量控制，会受到电视固件影响。

例如，同样是“切换 HDMI”，某些设备能直接切到对应端口，另一些则需要打开电视自己的信号源面板。别把支持某个品牌理解为该品牌所有型号都表现相同。

## 三、哪些电视可以安装？

先看系统，再看具体型号。[仓库安装与适配说明](https://www.wangdu.site/?golink=aHR0cHM6Ly9naXRodWIuY29tL3BlbmdjaHVqaW4vYWVyaWFsLXR2IyVFNSVBRSU4OSVFOCVBMyU4NQ==)区分了几个版本：

设备情况 | 选择与注意事项  
---|---  
Android 5.0及以上 | 优先使用完整版 standard 安装包  
固件拒绝安装桌面类应用 | 项目另有 guard 包，按对应说明处理  
Android 4.0—4.4 | 使用 Aerial Lite，功能与完整版不同  
  
Lite 缺少桌面守护等功能。固件锁定主页键时，即使能够打开应用，也可能无法把它设成长期使用的默认桌面。

官网概览与仓库最新机型反馈并非始终同步，尤其是 TCL、雷鸟等不同固件的接管情况。安装前应查阅仓库当前的“支持的机型”和对应记录，核对型号、系统及已知限制。

LG webOS、三星 Tizen 等其他系统，不能直接安装 Android APK。不要只看电视品牌就决定下载安装包。

## 四、Aerial怎么安装？

最容易理解的方式是：先安装应用，再根据电视情况完成默认桌面或桌面守护设置。仅仅看到 APK 安装成功，并不代表主页键、开机和待机唤醒都已接管。

### 安装包下载：官方 GitHub 与[夸克网盘](https://www.wangdu.site/tag/%e5%a4%b8%e5%85%8b%e7%bd%91%e7%9b%98 "【查看含有\[夸克网盘\]标签的文章】")镜像

Aerial 1.99 提供三个安装包，先按电视系统选择：

文件 | 大小 | 适用情况  
---|---|---  
aerial-standard.apk | 约 3.1 MB | Android 5.0 及以上，优先使用  
aerial-guard.apk | 约 3.1 MB | 固件拒绝安装桌面类应用的设备  
aerial-lite.apk | 约 1.0 MB | Android 4.0—4.4，功能少于完整版  
  
  * 夸克网盘镜像：[Aerial 1.99 Android TV 桌面](https://www.wangdu.site/?golink=aHR0cHM6Ly9wYW4ucXVhcmsuY24vcy9jMWU3NDBhNzgyNzg=)
  * 官方发布页：[GitHub Releases v1.99](https://www.wangdu.site/?golink=aHR0cHM6Ly9naXRodWIuY29tL3BlbmdjaHVqaW4vYWVyaWFsLXR2L3JlbGVhc2VzL3RhZy92MS45OQ==)

网盘里的三个 APK 是官方 Release 的原样文件，未修改、未重新签名；文件夹内另附 `LICENSE`、字体许可证和 SHA-256 校验值。下载后可以先核对校验值，再安装。软件代码采用 MIT 许可；航拍影片版权归 Apple，由应用运行时从 Apple 服务器播放，安装包没有包含这些影片。如果网盘链接失效，以官方发布页为准。

### 用U盘安装：适合先了解界面

从[官网安装区](https://www.wangdu.site/?golink=aHR0cHM6Ly9hZXJpYWwucXVzdC5tZS8=)下载适合系统的 APK，放进 U 盘，再通过电视文件管理器安装。

装好后按主页键。如果系统允许选择默认桌面，可以选择 Aerial；如果仍然返回原桌面，就需要继续查看项目提供的设置方法。U 盘安装本身不能保证完成接管。

### 用电脑设置：先核对ADB和机型说明

[官方安装文档](https://www.wangdu.site/?golink=aHR0cHM6Ly9hZXJpYWwucXVzdC5tZS9hZ2VudC5tZA==)提供电脑安装、授权和验收步骤。ADB 可以理解为电脑与 Android 设备沟通的调试工具，电脑和电视通常需要位于同一网络。

部分设备通过网络调试连接，部分新系统需要先用配对码配对，还有些固件需要数据线授权，不能统一套用一个连接端口。涉及工厂菜单的机型，应先读完对应说明，避免误改其他参数。

官网也提供给电脑端 Agent 使用的安装说明。选择这种方式时，工具需要具备实际运行命令的能力；普通网页聊天只能指导操作。完成后应检查主页键、待机唤醒及当前前台应用，不能只凭一句“安装成功”判断结果。

本文根据官方资料整理，未在具体电视上安装测试，也没有执行连接、授权或安装操作。

## 五、安装前要知道的两个边界

**桌面无广告，不等于电视全程无广告。** [官方常见问题](https://www.wangdu.site/?golink=aHR0cHM6Ly9hZXJpYWwucXVzdC5tZS8=)明确说明，固件播放的开机广告无法由 Aerial 去除；视频应用里的广告也不属于桌面能控制的范围。

**不用root，也仍然需要设置权限。** 原生 Android TV 与品牌定制固件的实现不同，后者可能需要无障碍、通知使用权等机制维持桌面。原桌面会保留，项目也提供还原说明；正式改动前应了解自己设备需要哪些设置。

截至2026年11月16日本次核实时，[发布页](https://www.wangdu.site/?golink=aHR0cHM6Ly9naXRodWIuY29tL3BlbmdjaHVqaW4vYWVyaWFsLXR2L3JlbGVhc2Vz)显示 Aerial 1.99，更新内容包含多种设备的控制与适配修复。这也说明电视固件差异是实际使用中需要持续关注的问题，更新记录中的修复不能直接当作所有机型的验证结果。

## 结语

如果你主要通过固定的几个应用看电视，希望开机后更快找到它们，Aerial 值得了解。应用整理和风景背景，能让电视首页更贴近自己的使用习惯。

开始前先确认系统和型号，安装后再检查主页键与唤醒表现。一个清爽的桌面，也需要适合这台电视的设置方式。

距离 SKILLS 发布已经快有一年的时间了，记得刚发布那时候我和其他人一样都觉得这真是一个天才般的产品设计，让个人或公司可以将自己的某个业务打包成一个 SKILLS 供其他人调用。

甚至后面随着各大科技公司的裁员进行，离职的提炼自己的 SKILLS 也上过一段时间热搜，甚至还有调侃：离职的同事没有消失，只是住进了服务器里。

当时装了很多 SKILLS 有用没用的都是一股脑的安装，比如出名的 superpower，ponytail，grill-me 等等。

可是用了一段时间之后也没发现效果有多好，这其中我总结有以下几个原因：

### [](http://crossoverjie.top/2026/11/17/AI/skilldeck-upgrade01/#SKILLS-太多，对-AI-造成的干扰太大。 "SKILLS 太多，对 AI 造成的干扰太大。")SKILLS 太多，对 AI 造成的干扰太大。

我们都知道 SKILLS 的触发原理，每次和 LLM 的对话都会带上所有的 SKILL 的描述内容，让 LLM 根据对话的上下文选择使用哪个 skill，这个步骤对我们用户来说是黑盒，是否能选中你想要的那个 SKILLS 全靠 LLM 说了算。

而我们的 SKILLS 越多，SKILLS describe 里塞的内容也就越多，特别是一些功能类似的 SKILLS ，比如都是做 UI 设计的，都是做 Java 语法的，反而增大了大模型选中 SKILLS 的难度，有可能这次选择的是 A 进行触发，第二次选择了 B 触发，而两个 SKILLS 的具体操作步骤又不相同，从而导致实际做事的质量下降。

### [](http://crossoverjie.top/2026/11/17/AI/skilldeck-upgrade01/#大模型能力越来越强，逐渐替代了一些常见的-SKILLS "大模型能力越来越强，逐渐替代了一些常见的 SKILLS")大模型能力越来越强，逐渐替代了一些常见的 SKILLS

再 SKILLS 这个概念被 anthropic 提出的时候模型能力确实没那么强，或者说训练的语料也没有那么全。

当时也流行一种说法：我们将自己的擅长的领域打包成 SKILLS 之后本质上就是让大模型学习我们的技能从而将我们替代掉。

AI 发展到现在，确实已经吸收了很多优秀的 SKILLS 了，直接将这些 SKILLS 都训练到模型本身了。

也就是说对于一些常见的需求可能都不需要 SKILLS，比如一个标准的前端设计，iOS app 设计等。

如果我们还带上这些 SKILLS 可能也会造成和刚才提到的问题类似，对上下文造成污染。

直到有一天我 之前做的 [SkillDeck](https://github.com/crossoverJie/SkillDeck)(一个对本地 SKILLS 进行增删改查的小工具) 收到了一个 [PR](https://github.com/crossoverJie/SkillDeck/pull/61)：  
![[Pasted image 20261116230159.png]]

可以统计 codex 的对不同 SKILLS 的使用情况，收到这个启发之后我将其余的 Agent 也加上了这样的统计。

![](https://cdn.jsdelivr.net/gh/crossoverJie/images@main/images/images20261116175455528.png)

这样在 SkillDeck 的首页就可以看到哪些 SKILLS 经常被使用，同时哪些 SKILLS 安装之后一次都没有调用过，这样的 SKILLS 是否可以考虑直接删除了。

### [](http://crossoverjie.top/2026/11/17/AI/skilldeck-upgrade01/#其他更新 "其他更新")其他更新

昨天傍晚快下班的时候，微信突然弹出几条消息。发消息的人我没有备注，只挂着一个「网友」的分组标签。对方劈头盖脸就是一句：「居然让我坐到街边吃饭，这环境也太差了。」

没有称呼，没有前因后果，甚至连主语都没有。我盯着屏幕看了一会儿，完全摸不着头脑。往上翻了翻，对话框里干干净净，加上好友之后我们压根没说过话。通常来说，这种躺在列表里没有备注、没有聊天记录的人，大概率是某次线下场合见过一面，当时聊得还行，或者纯粹是抹不开面子顺手加上的。

还好我有在日历里记日常行程的习惯。顺着通过好友验证的那天往回找，总算拼凑出了当时的场景。那天我和朋友在外头聚会，这位是某个消费场所的服务人员。当时他挺健谈，说自己对长沙很熟，顺口给我们推荐了几家店；又说自己刚来杭州不久，想让我推荐几家本地高端、漂亮、好吃的馆子。出于礼貌和那点互通有无的客气，我认真报了几个自己常去的名字。

搞清楚来龙去脉，我才反应过来，他这是去了我推荐的一家烧鸟店。那家店在我心目中算是杭州非常 TOP 的水准，但走的是匠人精神的板前路子，不是那种装修得金碧辉煌的约会餐厅。

搞明白之后，我心里多少有点烦。首先我们根本不熟，连寒暄都省了直接甩脸子抱怨，这本身就很没礼貌；其次，要是真奔着吃东西去，菜还没端上来、一口没吃到嘴里就开始挑刺环境，实在让人很难接话。但转念一想，毕竟是自己随口推荐过的，我也没立刻发作，只是耐着性子确认：「你是说某某家吗？现在过去了是吧？」

他回得倒是快：「对，这个环境还好没带妹子来，不然我都尴尬丢人。」

看到这句，我的火气稍微上来了一点，但还是压着脾气回了一句：「你先尝尝看再说吧。」结果对方完全没有要停下来的意思，继续输出「这个环境真的差」。那一刻我突然觉得很荒谬，我既不是餐厅老板，也不是他的私人管家，实在没必要在这儿惯着他的坏情绪。于是我直接回他：「你如果想吃漂亮的环境，直接打开黑珍珠榜单，或者去吃人均 1000 元以上的米其林摘星店就好了。」

紧接着，他回了一句让我彻底失去耐心的话：「这种店也有环境一般的。」

看到这行字，我没再打一个标点符号，直接点进他的主页，勾选了「加入黑名单」。

按我以前的习惯，哪怕心里再不痛快，面上可能还会维持一下所谓的体面，随便敷衍个表情包糊弄过去，等过上一周半个月，再悄悄把人删掉。我以前写文章也聊过，我不怎么轻易拉黑别人，觉得在微信的社交礼仪里，单向删除算是基本操作，拉黑简直是某种规格极高的「荣誉」。但昨天我之所以毫不犹豫地拉黑，是因为我清楚，如果只是删除，万一他那句抱怨没发出去，或者过两天又想找我理论，还得重新申请加好友。对于这种连基本边界感都没有的准陌生人，我连在验证消息里再看到他头像的机会都不想给。

拉黑完把手机扣在桌上，我琢磨了一会儿这件事。为什么一个仅有一面之缘的人，会理所当然地把自己的消费落差转嫁到我头上？

说到底，有些人是不具备信息筛选和自我负责能力的。我给你提供信息，是基于当时的社交礼貌，而不是签了一份包你满意的售后服务协议。一家餐厅好不好吃、环境长什么样，大众点评上有图片，去之前哪怕花 30 秒搜一下，都能知道它是不是自己想要的风格。自己不做功课，到了现场觉得不符合预期，不去调整心态，反而像领导视察工作一样找推荐人问责，甚至用抬杠的方式来发泄情绪。这种巨婴心态，本质上就是把别人的善意当成了某种亏欠。

以前我面对这种越界的行为，总会有一点莫名的心理负担。总觉得是不是自己当时没把话说清楚，没提前补一句「那家店环境一般但味道很好」。但现在我想通了，成年人的世界里，每个人都该为自己的选择买单。当对方提出无理要求，或者带着恶劣的态度撞上来的时候，我们完全没有必要心存愧疚。

到了晚上快睡觉的时候，这事居然还有个后续。烧鸟店的老板给我发来微信，小心翼翼地问今天是不是有个客人是我推荐过去的。我说是，但就是打过一个照面的人，聊起来顺嘴提了一句。老板问：「他是不是说你了？」我说有点吧，但无所谓，本来就不熟。老板在那边挺不好意思，说那个人后来让老板代他向我道个歉。

接着老板才跟我还原了现场的情况：这家店因为每天接客量有限，一直都是预约制。这位客人自己预约了时间，结果给忘了，大老远跑过去已经迟到了很久，当时店里正是最忙、人最多的时候，位置自然没法挑，这才有了前面那一出。

你看，事情的全貌往往就是这样。一个因为自己守时观念差、破坏了规则而导致体验不佳的人，在向别人抱怨的时候，永远只会隐去自己的问题，把责任推给环境，再顺手把火撒在给他指路的人身上。我没有对老板评价这个人的任何行为，只是回了一句：「生意好是好事。」

至于那个躺在黑名单里的账号，大概就是我昨天顺手清理掉的一点生活噪音。在工作和日常里，我们会遇到太多这样缺乏边界、习惯性消耗别人的人。温和与礼貌应该留给懂得尊重的人，而面对毫无道理的消耗，果断、干脆地拒绝，不需要任何心理建设，就该像呼吸一样自然。

  * （optional）管理員過濾掉不合適的 link（灌水、無關內容、意義不明等等）。
  * 把 backlinks 更新到頁面還有 RSS Feed。
  * 有興趣的部落友透過訂閱 RSS Feed、或直接到頁面看來接收這些資訊。

雖然這個東西不大，不過如果有想一起把這個東西搞起來的（錢、力氣、時間），或是有興趣 follow 這件事情的後續發展，可以 [寄信給我](mailto:blog@giveanornot.com)，如果有人理我的話，我會把大家拉進 mailing list 一起討論這件事情~

在本届的 ESMO 会议上，LEAP-012 研究公布了总生存期（OS）第 3 次期中分析，也是最终分析的结果。尽管一些同类研究的 OS 数据还在随访，但中期肝癌的局部联合系统治疗的总体 OS 获益情况基本上已经可以下结论了。

## LEAP-012 的主要结果

这是一项随机、安慰剂对照的 III 期研究。适合 TACE 的中期肝癌患者（还包括部分不可切除的早期肝癌）按照 1:1 的比例随机接受 TACE+仑伐替尼+帕博利珠单抗（“可乐组合”） 或 TACE 联合安慰剂治疗。**值得注意的是，仑伐替尼和帕博利珠单抗最长用药时间是 2 年。**

![研究设计.png](https://i.typlog.com/whyes/8205069882_640978.png)

该研究采用的是无进展生存期（PFS）和 OS 的双重主要终点设计（dual-primary endpoints）。在此前的 PFS 的[期中分析中](http://whyes.org/2024/esmo-2024-leap-012-tace-len-pembro)，与 TACE 联合安慰剂相比，TACE 联合可乐组合显著改善了 PFS，本研究已经达到了主要研究终点，算是一项阳性结果的 III 期研究。

**在首次期中分析时，显示出了 OS 改善的趋势，HR=0.80（95%CI 0.57-1.11）** 。但不好的信号是，两组的 OS 曲线已经出现了合拢的趋势。

![OS期中分析.png](https://i.typlog.com/whyes/8205069873_382482.png)

在随后公布的[中国人群数据中](http://whyes.org/2025/leap-012-hcc-tace-len-pembro-china)，与全球人群相比，中国人群在 PFS 和 OS 上的获益均更多。此后，**TACE 联合可乐组合也在国内获批，用于不可切除非转移性肝细胞癌一线治疗的适应证。**

![OS中国人群.png](https://i.typlog.com/whyes/8205069863_217688.png)

在刚刚过去的 ESMO 年会上，LEAP-012 研究公布 OS 最终分析的结果。**在中位随访 44.2 月后，OS 未改善（40.4 vs 40.8 月，HR=0.98， 95%CI 0.76-1.26， P=0.4442）** 。值得一提的是，这项研究提示，对于适合介入治疗的中期肝癌，40 个月的生存期应该是目前的新基准了。

![OS最终.png](https://i.typlog.com/whyes/8205069853_389271.png)

从生存曲线上看，在随机后的最初 30 个月以内，两组的 OS 曲线出现了分离；但在 30 个月之后，生存曲线出现了合拢。因为治疗组中可乐组合最长使用 2 年，在治疗组停药，而对照组在肿瘤进展后会用上系统治疗，两组的 OS 曲线在后期合拢也是意料之中。

目前的研究结果充分提示：**对于适合 TACE 治疗的中期肝癌，早用（TACE 联合系统治疗）和晚用（TACE 治疗失败后再用系统治疗）系统治疗的 OS 区别不大** 。**LEAP-012 研究的结果额外提示，早用系统治疗的话，可以避免部分患者早期死亡，2 年生存率相差约 7%。**

在亚组分析中，乙肝相关肝癌和中等肿瘤负荷的患者似乎有一些 OS 获益信号（OS 的 HR 分别为 0.91 和 0.85）。

![OS亚组分析.png](https://i.typlog.com/whyes/8205069844_242439.png)

在 OS 的期中分析中，全球人群的 OS 生存曲线出现了合拢的趋势，而中国人群 OS 曲线还没有显示出合拢的趋势，不确定在这次的最终的 OS 数据中，中国人群的 OS 的获益会被稀释到什么样的程度。

## 临床上该如何使用？

### 什么样的中期患者适合 TACE 联合系统治疗？

**要不要选择联用系统治疗，还需要跟患者共同决策（shared decision making）** 。需要告知患者，尽管联用系统治疗提高了治疗有效率，显著推迟了肿瘤进展，但早用和晚用系统治疗之间的生存期没有差别，而早用还可能会带来更多的副作用并可能降低生活质量，让患者做出选择。但对于以下类型的患者，我建议尽早联用：

  * **单独使用 TACE，存在早期死亡风险的患者** 。在 LEAP-012 期中分析中，中等肿瘤负荷（>6 分）的患者接受 TACE 联合可乐组合治疗 OS 获益趋势更加明显。这些患者在治疗失败后容易出现肝功能受损，从而失去后线系统治疗的机会，因此建议尽早联用系统治疗。
  * **潜在可切除的患者** 。目前，潜在可切除没有统一的标准，一般认为，肿瘤分布范围不是太广泛的患者具有较高的治疗后手术切除的机会。

### 中期肝癌的临床治疗该如何优化？

考虑到目前中期肝癌的中位 OS 已经达到了 40 月左右，生存时间的延长对治疗的管理也提出了更高的要求。因为多数中期肝癌无法实现根治，局部和系统治疗可能会伴随着患者生命周期，因此需要做出一些取舍。**根据患者前期对治疗的反应，及时的降阶梯（de-escalation）（降低治疗强度的同时不太影响疗效）或升阶梯（escalation）（提高治疗强度以提高疗效）治疗是必然的选择，也是动态调整的过程。**

  * **疗效特别好的患者** ：可以提供 drug off holiday 选项，从而不让患者长期维持高强度系统治疗。在本研究中，接受 TACE 联合可乐组合治疗的患者中有高达 55.3% 的患者可以达到完全缓解（CR）（mRECIST 标准）。在临床上，患者的 CR 状态维持一段时间后（例如半年左右），可以尝试在密切随访时停药或者减药维持。
  * **疗效一般的患者** ：最佳治疗疗效被评估为疾病稳定（SD）、部分缓解（PR）或上述 CR 患者在停药间期肿瘤再次复活的患者，都需要药物治疗的长期维持。这给不良反应的管理提出了更高的要求。可能的调整的途径是，在局部治疗与系统治疗可以成为互相补充，如果患者对系统治疗耐受性较好，就少做局部治疗；反过来，如果系统治疗耐受性不佳或难以控制肿瘤，则增加 TACE 等局部治疗。
  * **上述患者中达到了转化治疗后手术切除标准的患者，可以选择根治性治疗** 。根治性治疗手段不仅包括手术，还包括消融、放疗，甚至肝移植。这些治疗一方面可以清除掉潜在耐药的残存细胞；也可以给患者在手术后提供 drug off 的机会，缩短了药物毒性的暴露时间。
  * **疾病进展后的调整** 。适时使用的一些局部治疗处理寡进展，必要时调整系统治疗方案。

## 学术上如何评价 PFS 获益，但 OS 不获益？

今年年初，EASL、AASLD 和 ILCA 联合发布了 [肝癌临床研究设计和终点选择的共识](https://www.nature.com/articles/s41571-026-01160-z) ，在这项共识中，对于适合TACE的肝癌：

  * OS 应该作为中期肝癌 III 期研究的主要研究终点（共识度 76%）；
  * 如果 OS 数据成熟时，显示出了有获益趋势，那则建议将 PFS 作为主要研究终点（共识度 76%）；
  * OS 临床获益的信号或趋势定义为：HR≤0.8（共识度 59%）；在 OS 符合等比例风险模型时，中位 OS 差值≥3 个月，在非比例风险情形下，36 个月时的限制性平均生存时间（RMST）绝对差值≥3 个月（共识度 70%）。

尽管这个评价方法是 Llovet 等人提出来的，但很可惜，在本次 ESMO 会议公布结果时并没有做这个事后分析。我尝试使用 Gemini 估算了一下，3 年内的 RMST 大约在 1.25 月，很遗憾，没能达到共识所提出的 OS 临床获益的信号。

## 总结

总之，现有研究均提示，对于适合 TACE 治疗的肝癌，早用和晚用系统治疗，患者生存期相当，需要根据患者的疾病特征和治疗取向等做出综合判断，确定要不要提早联合系统治疗，并在治疗过程中根据患者的耐受性和疗效做出动态调整，以期让患者最大获益。

## 引子

如果是今年找实习/工作的同学，可能会发现一个现象，那就是今年的计算机的工作是真的难找。很多公司不再招人，哪怕招人也没有前几年招得那么多，工资也没有那么高，与此同时，公司也在大量的裁员。

如果想要思考一下原因，那可以分为根本原因和直接原因来讲，直接原因就是「现在的工作不需要那么多人了」，学习过宏观经济学的小伙伴知道，劳动力本身就是一个市场，如果需求没那么多了，在供给一定的情况下，得到Offer的人的数量是下降的，与此同时，这些人的工资也是减少的。现实也是如此，不过现实是「需求减少」（公司不需要那么多人了）和「供给增加」（毕业生人数多了）两方面的因素。那么根本原因就是，AI替代了很大一部分的工作需求，导致对人类的需求下降了。画出供给-曲线图就长下面这样：

## 需求-供给曲线与特别的矛盾：简化的模型

需求曲线，是经济学的一个概念，它是一个「价格-需求量」的曲线，如果纵轴是需求量，横轴是价格，那么它就是一个第一象限，斜率为负的一条曲线（左上-右下）。这条曲线一般用来描述，「在不同的售价下，人们对于某个物品的需求量的变化」。网图如下：

![](https://pica.zhimg.com/v2-4dd643cd34e888b31ccabd279ba82252_1440w.jpg)

供给曲线则类似，它通常是一个第一象限，斜率为正的一条曲线（左下-右上），用来描述「在不同的售价下，厂家愿意生产的生产量的变化」。网图如下：

![](https://pic2.zhimg.com/v2-ecaecd9962fb126a49f869ded71fcb3b_1440w.jpg)

到这里就够了。

AI对于工作的替代，主要是在生产侧起作用的，也就是说，AI能够加速产品的生产，在一定程度上降低生产的价格，那么，在同样的售价之下，厂家愿意生产的产品量就更多了，这就导致了「供给曲线的右移」。但是，一个物品销量如何，不应该只考虑生产侧，而是也要考虑消费侧。我们来看看消费侧发生了什么，AI替代了工作，那么就会（已经）导致一部分人（很多人）失业，这就导致，在同样的价格下，人们愿意购买的东西更少了，或者说对于同样一个东西，人们会倾向于在更低的价格上购买，这就导致了「需求曲线的左移」。那么，在标准的市场供需模型中，这会导致售价（两条曲线的交点价格值）下降，但是销量（两条曲线的交点销售量值）是不确定的。

分两种情况讨论，短期和长期。短期来看，由于行业是有惯性的，大部分行业不会裁撤那么多的人，所以需求曲线的变化并没有特别明显的变化，而AI加速了生产过程，让商品的产出成本下降了，对供给曲线的影响是巨大的，所以可以看作「需求曲线不移动」以及「供给曲线」右移，销售的商品变多了，价格也比之前低了。这对于大家是个好事，我们可以用更少的钱买到更多的东西了。

长期来看，问题则会复杂一些，如果AI大规模替代人类劳动，部分劳动者失去工资收入，那么对于正常商品而言，居民需求曲线向左移动。那么交点的变化呢？分为两种情况：

  * AI创造的财富能够广泛分配，而不是集中在少部分人手里。
  * AI创造的财富最终集中在少部分人手里，而不是广泛分配。

第一种情况则和我们讨论的短期情况无差。而第二种情况，如果大部分人都没有财富了，那么对于正常商品而言，居民需求曲线将会极端向左移动，这样产品的销量变少（甚至比AI出现之前还要少！），价格下降。虽然价格下降了，但是人们也没那么多钱买所需的东西了。

也就是说，AI的发展不一定会给人类带来福祉，如果分配方式不均，那么人类的生活反而会比之前更差。这就是AI带来的可能矛盾本身。

## 黄昏已逝，黎明未到：技术的腐烂

> 这一段是我用英语写作的一篇文章的节选，翻译过来。

如果说AI的极限是代替了所有人的工作，那么从现在到那个理想时间点之间，还有非常长的路要走。截止到现在，AI替代的是一些比较简单的工作，诸如重复性代码写作，一些简单功能的实现，一些文书的写作。在之前，这些工作是有初等工作者（Junior Worker）去做的，他们在做的过程中不断积累经验以及对整个系统的理解，逐步成长为高等工作者（Senior Worker），但是，既然AI已经广泛地取代了这些初等工作，那么初等工作者，想要成为高等工作者就更难了。

也就是说，现在的高等工作者，依赖的是「过去美好时代的存量」（Stocks of the good old days），而初等工作者，则要面对越来越少的培养机会。在这里我们看到了一种工作经验上的K型分化（K-shaped economy of work experience），高等工作者由于从事那些暂时没法被AI替代的工作，他们的经验在不断加深，而初等工作者所能从事的事情，已经被AI替代了，所以只能越来越缺少经验。

究其原因，这依旧是「产品导向的经济系统」（Product-oriented economic system）所导致的，人们并不关注你做一件事情采取什么工具，花了多少时间，方法够不够优美，人们只关注你给出的产品能否解决他们的问题，让人们满意。一再压缩迭代周期、加快工时，不都是这个原因吗？在AI之前，游戏产业不也摒弃掉了上世纪的游戏的「尽可能优化」的传统吗？随着硬件的不断更新，游戏开发者们可以利用大量冗余资源，呈现游戏的效果。这导致游戏体积一再增大，但是开发时间变短了。这便是「产品导向的经济系统」带来的副作用，产品不再优美，它们变得快速、乏味、无聊，但是**有效** 。

这便是技术的腐烂。

## 一个装配的机器：未来的面貌

很多政治家、经济家、哲学家都犯了一个错误，他们认为他们的模型能够概括一切事物，能够预测一切将要发生的事。但是事实表明，没有人能真切地预测未来。正如德勒兹所想的那样——一切问题都是各种要素装配的产物。而这也是我喜欢德勒兹的哲学的原因。

我之前说过，「也就是说，AI的发展不一定会给人类带来福祉，如果分配方式不均，那么人类的生活反而会比之前更差。这就是AI带来的可能矛盾本身」，但是这一定会发生吗，我们的未来一定会导向反乌托邦吗？也不尽然。因为分配方式不均，如果导致广大人民的贫穷，那么人民就会起来反抗，研究出新的分配方式来。如果初等工作者始终没法变成高等工作者，这会导致广大的失业。经济问题到最后就变成了政治问题。

但是这一定不会发生吗，我们的未来一定不会导向反乌托邦吗？也不尽然。这完全取决于人们如何应对已经到来的危机。在一个群体中，逆来顺受者未必鲜见。不过，在我看来，如果大多数人都不幸福，都没办法维系自己生活所需，那么反抗是一定会到来的。

总而言之，我对未来是很乐观的，我们或许会在AI发展得十分先进的情况下，看到新的分配方式的诞生。不过，在这一天来临之前，我们还有很多苦要吃，很多路要走。

Bon voyage!

秦九这辈子做过很多亏心事。

博士期间他把一组失败数据"平滑处理"过，发了一篇三区；求职时他把"参与项目"写成了"主持项目"；在咸鱼上他接过代写本科毕业论文的单，题目是《论诚信在当代大学生中的重要性》。

但往陌生人啤酒里倒药，这是第一次。

两百块到账的那天晚上，他失眠了。他躺在城中村出租屋的床上，盯着天花板上那块像钙钛矿晶格一样裂开的墙皮，脑子里反复出现那个男人睡着时嘴角的馒头渣。

凌晨三点，他打开手机搜索：“钙钛矿量子点 口服 毒性”。

搜索结果第一条，是一篇综述，结论是：“铅基钙钛矿具有潜在生物毒性，体内应用研究尚处于空白阶段。”

第二条，是一则新闻：《男子网购"神药"致肝损伤，卖家称"已完成体外实验"》。

秦九关掉手机，坐起来，给自己倒了杯水，手抖得洒了一半。

他决定去看看那个人还活着没有。

第二天晚上九点，秦九准时出现在研究院后门的烧烤摊。

他也点了一份最便宜的烤馒头片，坐在角落，用菜单挡住半张脸，像一个蹩脚的私家侦探。

九点十五分，柯北来了。

秦九松了口气。活着。

然后他发现了不对劲。

柯北是跑着来的。

一个三十九岁的副研究员，背着一个看着就沉的双肩包，从研究院大门一路小跑过来，在塑料凳上坐下，气都不喘，掏出笔记本电脑就开始敲字。

秦九偷偷瞄了一眼屏幕。

《国家自然科学基金面上项目申请书》。

第二天，柯北又来了，这次屏幕上是《省自然科学基金申请书》。

第三天，是《横向课题技术方案书》。

第四天，柯北在烧烤摊上一口气吃了十串腰子，喝了两瓶啤酒，然后对着电话骂学生骂了十五分钟，中气十足，最后一句是：“这个数据你给我重做！做不出来别回来！”

挂了电话，他又打开了第四个本子。

秦九手里的馒头片掉在了地上。

他做了七年科研，见过无数中年副研究员。他们的共同特征是：腰不好，颈椎不好，脾气也不好，但骂学生只敢在微信上发语音，因为当面骂会喘。

眼前这个人，不像三十九岁。

但他的脸，确实是三十九岁。

秦九感到一阵寒意。他想起咸鱼帖子里那句话：可能使细胞逆向生长。

他掏出手机，打开咸鱼，给"薛丽不想再写本子了"发消息：

“那个药……如果有效的话，会是什么表现？”

对方秒回：“已判定无效，不用再反馈了，谢谢。”

后面跟着一个哭泣的猫表情。

秦九盯着屏幕，打了一行字：“可能有效。”

想了想，删掉了。

如果药有效，那就说明他给一个陌生人下了药，而且这个陌生人确实被改变了。如果药无效，那他就只是收了两百块，什么也没做。

在科研圈混了多年，秦九深刻理解一个道理：结论不重要，重要的是哪个结论对你更安全。

他回复：“好”

与此同时，柯北本人对自己的变化有一套完整的解释。

他把这归因于"终于想开了"。

人到中年，聘期剩八个月，这时候突然精力充沛、头脑清醒、熬夜不困，柯北觉得这是一种哲学层面的顿悟。他甚至在朋友圈发了一条：

“科研的意义，不在于结果，而在于过程。最近状态很好，感谢自己没有放弃。”

配图是手套箱里那片完美的薄膜。

这条朋友圈收到了三个赞。一个是他妈，一个是毛莉，一个是人事处的杨梓，点完赞后，杨梓顺手把他的名字从"建议不续聘"名单里移到了"待观察"名单。

理由是：精神面貌积极。

毛莉是第一个觉得不对劲的人。

周三组会，柯北主动做汇报。往常他汇报时会坐着，声音沙哑，说三句停一下喝水，PPT翻到第十页就开始说"后面的数据大家自己看"。

这次他站着讲了一个半小时，不喝水，不看稿，PPT翻到了第四十七页，最后还加了一句：“下周每个人交一份新的实验方案，我亲自看。”

全组鸦雀无声。

散会后，毛莉在走廊上拦住了组里的另一个硕士生：“你觉不觉得柯老师最近有点奇怪？”

“是有点。”

“我觉得，“毛莉压低声音，神情凝重，“他是不是知道自己不续聘了，在最后冲刺？”

“……有可能。”

“或者，“毛莉的声音更低了，“他是不是查出什么病了？”

硕士生愣住了。

“你看啊，“毛莉掰着手指，“突然变得特别有干劲，突然发朋友圈说’科研的意义在于过程'，突然开始亲自做实验——这不就是那种……知道自己时间不多了，想把没做完的事做完吗？”

那天晚上，毛莉在组里的群聊里发了一条消息：“大家最近对柯老师好一点。”

没有人问为什么。但第二天，柯北的桌上多了一盒枸杞、一束康乃馨和一张卡片，上面写着：“柯老师，加油，我们都在。”

柯北看着那张卡片，眼眶一热。

孩子们终于懂得了科研的意义。

周五晚上，毛莉照例跟她妈视频。

她妈每周三次准时打来，开场白永远一样：“吃饭了没？对象找了没？编考了没？”

毛莉一边应付，一边在实验室门口来回踱步。手机镜头扫过走廊，扫过研究院后门，扫过那家烧烤摊。

“等等！“她妈突然喊，“你往回转一下！”

毛莉转回去。

镜头里，烧烤摊角落坐着一个男人，用菜单挡着半张脸，眼睛死死盯着另一桌。

“这个男的是谁？“她妈问。

“不认识。”

“他天天在那儿吗？”

毛莉仔细想了想。好像确实是。这一周，每次她晚上望风，那个男人都坐在那个位置，点一份馒头片，坐到快收摊。

“好像是天天在。”

“多大年纪？”

“三十多吧。”

“干什么的？”

“不知道，看着像……“毛莉又看了一眼那个男人，他穿着一件洗得发白的格子衬衫，背着一个印着某985校徽的帆布包，“看着像搞科研的。”

她妈的眼睛亮了。

“搞科研的好啊！有文化！你去问问他单身吗？”

“妈！”

“你都二十八了！搞科研的配搞科研的，有共同语言！你去问问，问问又不要钱！”

毛莉挂了电话。

她站在研究院门口，远远看着那个男人。他还在用菜单挡着脸，盯着柯北那一桌，偶尔低头在手机上记什么东西。

毛莉忽然觉得，这个画面有点眼熟。

那是她每天在实验室里盯着手套箱的样子。

焦虑，执着，还有一点点绝望。

那天深夜，秦九在手机备忘录里写下了第一周的观察记录：

被试编号：001（未经同意）

第1天：存活。

第2天：存活。

第3天：存活。

第4天：存活，吃了十串腰子，骂学生十五分钟不喘。

第5天：存活。

第6天：存活，桌上出现康乃馨，原因不明。

第7天：存活。被人远远盯了很久。疑似暴露。

阶段性结论：药物可能有效，但无法确认。需要更近距离观察。

他盯着最后一行看了很久。

他知道，以他现在的身份，“更近距离观察"只有一个办法。

他打开研究院官网，点开"人才招聘"栏目。

第九条：柯北课题组诚聘博士后一名。要求：材料学相关专业博士，熟悉钙钛矿薄膜制备及手套箱操作，年龄三十五周岁以下。

秦九看了看自己的身份证。

三十六岁。

又看了看自己的简历。

犹豫了大概三秒钟，然后打开Word，把出生年份改了一年。

在科研圈混了多年，秦九深刻理解另一个道理：数据可以平滑处理，年龄也可以。

翻英伟达最新几季财报，你会发现“新加坡”这一行不见了。截至 2025 年 7 月的那个季度，这里的账单金额还有 102 亿美元，占总收入 22%；之后公司不再单列。现在，美国证券交易委员会（SEC）就这件事启动民事调查，问的是英伟达的披露有没有误导投资者——**查的不是芯片卖没卖出去，而是这笔钱该记在谁头上、有没有跟投资者说清楚** 。

打个比方：一家餐厅把外卖订单全记在“取餐窗口”名下，菜其实从后厨端到了城另一头。窗口的营业额再高，也不等于那一带有人吃饭。新加坡在这里就是那个取餐窗口——账单从它名下过，货基本不从它那里走。 事件 

## SEC 要问的是“说清楚没有”

美国证券交易委员会对英伟达启动民事调查，问的不是芯片卖没卖出去，而是财报有没有把投资者带偏。

消息由《华尔街日报》首发。调查性质是民事，不是刑事指控，也不涉及产品本身是否合规——这两条边界先划清楚，后面所有讨论才有落点。民事调查的靶心只有一个：英伟达的披露有没有误导投资者。换句话说，问题不在生意做没做成，而在账本讲没讲明白。

调查和一次报表口径调整撞在了同一段时间里。公司停止单独列示新加坡收入，就发生在截至 2025 年 7 月止的那个季度之后。那个季度新加坡账单的数字，下一节拆。

还有一条线并行推进。美国财政部长斯科特·贝森特给了 10 天，要英伟达董事会和外部律师解释公司是否为了抬高业绩而推动了“看似违规的销售”。这句话说得很直白，指向的是销售动作，而 SEC 盯的是披露文字——两条线问的是不同的事，却落在同一家公司、同一段财报期上。

对普通投资者来说，这件事的直接影响不在产品端。英伟达的芯片照卖，客户照下单；变的是你翻开财报时能看到的颗粒度。一家占收入两成以上的地区账单从表里消失，监管要追问的正是：这个变化有没有被充分说明，还是被悄悄带过。至于这笔钱到底该记在谁头上、停报之后投资者少了什么，得从那张 102 亿美元的账单说起。

## 22% 的收入从报表里消失了

英伟达最新一季总收入里，每 5 美元有超过 1 美元记在新加坡名下。这个数字后来不再单独出现。

据 WSJ 报道，截至 2025 年 7 月止的季度，英伟达在新加坡的账单金额是 102 亿美元，占当季总收入的 22%。这是财报里一个单列地区的收入口径（按客户开票地统计的收入分项），不是芯片的最终去向。公司自己的说法是，客户在新加坡开票，芯片几乎总是运往别处。

这个比例是什么量级？把它从分地区明细里拿掉，等于投资者少了一个能横向对比的坐标：你无法再从财报里看出这块收入的规模变化，只能从总数倒推。

最反直觉的地方在这里：新加坡本身不是这 102 亿美元芯片的消费地。开票地、发货地、最终使用地三者分离，是转口贸易的常规操作，本身不违规。但当一个开票地占到总收入 22%，它就不再只是会计科目，而是判断需求真实性的入口——钱从哪来、货往哪去，决定了这块收入该算在哪个市场头上。

停报的时点也值得留意。2025 年 7 月止季度是新加坡收入最后一次单列，之后这个分项从财报里消失。SEC 的民事调查问的正是披露是否误导投资者，两件事在时间上重叠。对普通投资者来说，直接影响是：过去能靠地区明细交叉验证的增长故事，现在只剩公司口径的总数。第三方复测目前没有公开数据，谁也无法独立确认这 22% 的构成变化。

你再次打开熟悉的代码仓库，让 AI 编程 Agent 修一个 bug：它却重新摸索测试命令、载入一堆很少使用的工具，还沿着上次的失败路径继续试错，Token 账单随之增长。微软与 UC Berkeley 等团队开源的 TokenEconomizer 试图让 Agent 记住同一仓库里已经学过的经验；官方在 277 个真实修复任务中测得，平均成本降低 **18.4%—30.9%** ，任务成功率则整体保持稳定。

这像给一位每天进同一间维修车间的人配一本活页笔记：记下哪台机器要先断电、哪把工具其实用不上、哪种修法上次根本无效。它不是替人修机器，而是在下一次开工前少走那些已经有答案的弯路。 

## Agent 每天把 Token 花在哪些重复上？

程序员每天回到同一个仓库，AI 编程 Agent（能读写代码、调用工具完成开发任务的模型代理）却常从零开始。微软研究团队在 SWE-Bench（用真实开源项目缺陷测试编程 Agent 的基准）上记录了 Claude Code 处理 60 个任务的工具调用与花费。

第一处浪费发生在仓库内部。同一仓库积累至少 5 个已完成任务后，30% 的工具调用重复了早期任务中的动作，例如再次摸索怎样运行测试。只有 7% 的调用与另一个仓库的历史动作相匹配，说明这些重复大多不是通用操作带来的，而是 Agent 没有记住眼前仓库已经学过的经验。

第二处浪费来自每轮都携带、却从不使用的工具说明。Claude Code 每轮收到 23 个工具描述（说明工具用途和调用方式的信息），其中 16 个从未被调用。开发者为一个仓库准备的工具越多，Agent 每次请求背负的说明就可能越重；未被调用的工具仍占用了上下文，让模型反复阅读用不上的选项。

第三处浪费藏在失败任务里。失败任务占全部任务的 17%，却贡献了 32% 的支出，比例接近任务占比的两倍。Agent 遇到同一个错误后反复换姿势尝试，消耗的 Token（模型处理文本时计量收费的基本单位）会不断累积；失败不只拖慢任务，还让账单更重。

## 一次旧会话，怎么帮下一次少走弯路？

TokenEconomizer 会读取已结束的会话日志，把多次尝试中确认的仓库经验带到后续任务。编程 Agent 不必每次都从零开始。

一次旧会话进入下一次会话 读取会话日志→ 识别仓库特有模式→ 更新起始经验与工具清单→ 介入重复失败 

仓库经验由微型经验（一行笔记，保存仓库特有知识）承载。插件先从不同会话中寻找反复出现的模式，单次任务的偶然发现不算数。至少多个会话确认，笔记才写入后续会话的起始上下文。

写进去的也可能被拿掉。后续会话若出现与笔记相矛盾的证据，插件就撤销这条经验，让它退出起始上下文。

工具裁剪（按仓库历史删去不常用的工具）负责减少 Agent 每次都要接收、却可能不用的工具说明。插件依据当前仓库的历史记录移除不太可能使用的工具，运行命令和编辑文件这两类核心工具则保留。如果后续任务确实需要，被移除的工具仍可恢复。

Agent 反复撞上同一个错误怎么办？插件会启用失败循环干预（识别重复失败并提醒改换方法）。裁判模型先判断 Agent 是真的卡住，还是虽然连续失败却仍在推进。确认已经卡住，Agent 才会收到一条简短提示，建议换一种方法。

## 不换模型，能省下多少？

不换编程 Agent，也不降低模型的推理强度，TokenEconomizer 在 277 个真实修复任务中把平均成本压低了 18.4%—30.9%。省下的是测试中实际消耗的 Token 费用。

这组结果来自微软研究院发布的评估。测试使用 SWE-Bench（真实软件缺陷修复基准），覆盖 6 个代码仓库、277 个修复任务，并测试 5 种不同的编程 Agent 与模型组合。6 个仓库与 5 种组合交叉形成 30 个仓库组合，TokenEconomizer 在全部 30 个组合中都是节省最多的方案。

微软研究院同时说明，统计包含插件自身调用模型的成本。这组数字来自项目方评估，尚未见第三方复测。

方案 | 277 个真实修复任务中的表现  
---|---  
TokenEconomizer | 30 个仓库组合全部节省最多，平均成本降低 18.4%—30.9%  
降低模型推理强度 | 可节省相当或更多费用，但任务表现明显下降  
默认方案 | 不增加仓库经验学习，也不改变模型推理强度  
  
降低推理强度确实能省钱，甚至省得更多，代价是任务表现明显下降；TokenEconomizer 的省钱不靠削弱模型，靠的是把同一仓库里已经验证过的经验用到后续任务上——前提是这些经验确实在后续任务里成立。

成本下降没有换来任务表现退步。5 种 Agent—模型组合中，有 4 种的 Pass@1（一次尝试即解决任务的比例）上升。“表现”按任务成功率衡量，不能直接等同于所有代码质量或长期维护效果。

## 省的钱，要到第几个任务才出现？

TokenEconomizer 不会从第一个任务就立刻省钱。它先支付学习成本，但到第 6 个任务时，全部测试仓库的累计成本都已低于默认方案。

每个仓库开始测试时，TokenEconomizer 都没有历史会话可供学习。第一项任务需要自行探索仓库、记录经验，并判断哪些信息值得留给后续任务复用。这个阶段可能比默认方案多花成本，因为插件正在建立仓库知识，记录还不足以支撑成本控制。

任务连续推进后，先前会话里确认过的仓库规律、工具使用情况和失败路径会用于下一次任务，单个早期任务的成本可能仍然偏高，同一仓库的任务累计起来，差异会随可用经验增加而改变。

到第 6 个任务时，全部测试仓库的累计成本都低于默认方案，学习投入已经被后续任务的节省覆盖。判断它是否值得接入，不能只看第一次任务，同一仓库连续使用后的累计账单更值得关注：第 6 个任务是本次测试中跨过默认成本的节点，但不代表每个仓库都会在更早时回本。

## 换个场景也能省，关键是历史会话能不能接上

两项测试都降了：连续网页开发降 16.0%—21.2%，安全审计降 6.4%—19.6%。差距指向同一个前提——任务能不能在同一个仓库里积累历史会话。

网页开发任务更接近日常使用。测试采用 Web-Bench（用于评测网页开发任务的基准），任务连续进行，成本降低 **16.0%—21.2%** 。方法不依赖某一种代码仓库或某一种 Agent：只要后续会话仍在同一仓库，插件就能复用已经形成的仓库经验，少走重复的探索。

安全审计的降幅是 **6.4%—19.6%** 。差别出在任务安排上——**每个任务都换一个新仓库** 。没有同一仓库内积累的历史会话，TokenEconomizer 就没有可跨任务复用的对象，降幅自然低于连续网页开发。

回到开场那个画面：反复处理同一代码仓库、每次都像从零开始的编程 Agent。它省下的不是换一个更便宜或更弱的模型，而是同一仓库里已经付过成本的探索。对于不把 Agent 会话日志留在本地的团队，这种以历史换节省的方案，代码与日志的隐私边界该怎么划？

### 字段值规范

  * `name` — 站点名称  
非空纯文本；HTML 用 `lang` 属性（BCP 47），JSON 用 `{ "value": "...", "lang": "..." }`。
  * `link` — 站点链接  
完整 URL，协议限 `http` 或 `https`，必须含域名。
  * `desc` — 简介  
纯文本，可带 `data-length="short"` 或 `data-length="long"`，省略表示不区分；语言标注同 `name`。JSON 中 `desc` 可为 `{short, long}` 对象或单一 `{value, lang}`。
  * `cat` — 标准化分类

**合法值** ：
    
    
    personal,tech,design,writing,art,life,academic,news,community,archive,indieweb,open-source,security,privacy,devops,frontend,backend,fullstack,mobile,ai,data,science,math,philosophy,history,language,education,finance,health,food,travel,photography,film,music,books,gaming,sports,craft,garden,pets,parenting,fashion,politics,environment,space,hardware,linux,windows,apple,android,web,accessibility,decentralization,selfhosted,minimalism,productivity,career,misc

  * `sub` — 自定义子类  
任意语言文本，通过 `lang` 标注语言；消费方忽略未知值。
  * `logo` — Logo 链接  
单一完整 URL 表示不区分；或 `data-light` / `data-dark` 各一个完整 URL。
  * `feed` — Feed 源链接  
完整 URL + `type` 属性，`type` 合法值：`application/rss+xml`、`application/atom+xml`、`application/feed+json`、`application/json`。可多个。
  * `sitemap` / `shot` / `news` / `contact`  
各为完整 URL，须含协议和域名。
  * `themecolor` — 主题色  
单一十六进制值表示不区分；或 `data-light` / `data-dark` 各一个十六进制值（`#` 加 3 或 6 位）。
  * `loc` — 展示/巡查位置  
合法值仅五个：`header`、`footer`、`nav`、`sidebar`、`content`。可多个。
  * `frd*` — 自定义扩展  
HTML：`data-frd*` 属性，如 `data-frdrank`；JSON：`frd*` 键，如 `"frdrank"`。后缀为小写字母或数字；值类型不限；消费方忽略不认识的扩展。

## Foreword

上一篇写了SU7 Ultra Mod是怎么做的，里面提到后面又做了一套自主控制器，用来替代我自己一圈圈试车。

实际做下来，这个东西比改Mod麻烦得多。AC不是CARLA，也不是专门给自动驾驶研究做的仿真器。它能把车开得很真实，但是没有一套完整的接口，让外部程序随便读取所有状态、修改所有物理量，再把整个世界精确存档。能读到的不一定能改，能改的不一定能稳定复现，画面上看起来一样的两次起跑，轮胎接触和悬挂约束也可能已经走到了不同的分支。

所以这篇主要记录几个问题：AC里到底有哪些黑盒，程序能自主控制到什么程度，怎么在CSP上接一个自己的AI车手，以及为了反复试参数，后面又补了哪些工程工具。

## AC里的黑盒

### 物理引擎

AC车辆的`data`文件并不黑。质量、悬挂、轮胎、动力、传动、气动和制动大部分都能看到，Mod作者改的也是这些参数。

真正黑的是这些参数进入AC以后怎么求解。

轮胎不是把`DX_REF`或者`DY_REF`乘一下就直接得到抓地，里面还有载荷、滑移、侧偏、外倾、温度、压力、磨损和路面接触。悬挂也不是只算一个弹簧长度，还要和车身、轮胎、路面碰撞、约束迭代一起解。

外部程序可以看到最后的轮速、载荷、`Fx/Fy/Mz`、滑移率和侧偏角，但是看不到AC求解器内部每一步怎么收敛，也没有接口把全部内部变量拿出来。CSP增加了很多能力，但AC和CSP的核心物理实现仍然不是一份可以随便改的开源代码。

这种情况下，AC更接近灰盒：输入参数和一部分状态是已知的，内部公式和历史状态不完整，只能用固定输入反复测它的输出。

### 原生AI

AC自己的AI也属于黑盒。

赛道里的`fast_lane.ai`、`pit_lane.ai`和`side_l.csv/side_r.csv`只是它的一部分输入。AI最终怎么选速度、什么时候刹车、怎么处理对手、黄旗、轮胎和失控恢复，并没有完整开放。CSP的New AI Behaviour又会在外面增加起步、追赶、橡皮筋和其它修正。

原生AI适合正常比赛，也能拿来快速判断一辆车会不会跑，但是不适合做精确的单变量试验。把AI Strength固定成100，AI两次运行并不一定是完全相同的驾驶输入，这样控制变量就控不住了。

这次做的控制器是直接接管玩家车的方向、油门、刹车和换挡，这样AI的驾驶策略才是可见的，可控的

### 赛道和路面

一开始我直接把`side_l.csv`和`side_r.csv`当成赛道边界，后面发现也不行。

这两个文件是AI线配套数据，不一定把所有铺装路肩都包括进去，也不等于比赛白线。KN5里的物理网格、`surfaces.ini`、材质名称和CSP扩展又会共同决定轮胎到底压到了什么表面。

最后真正可信的是每个物理帧四个轮胎的接地点和CSP返回的：

  * `contactPoint`
  * `surfaceSectionIndex`
  * `surfaceValidTrack`
  * `surfaceGrip`

这里还有一个很重要的边界：`surfaceGrip`是接触求解结果，只能读取，不能修复。

审计器现在同时能保留两种口径。一种按常见赛事规则，只在四轮同时出白线时判罚；另一种是这个项目最后使用的严格口径，要求车辆中心不离开赛道走廊，并检查四轮表面抓地。

### 会话状态

最麻烦的黑盒其实不是某个参数，而是“这辆车现在到底处于什么状态”。

位置、速度、朝向和挡位很好存，但一辆已经跑了几圈的车还包括：

  * 四轮多个温区的温度、压力和磨损
  * 油量、电量、发动机或电机状态
  * 悬挂和轮胎接触约束的历史
  * TC、ESC、TVC内部的积分、滤波和限幅状态
  * 外部控制器上一次方向、方向变化率、速度缩放和制动历史

CSP的`ac.saveCarStateAsync()`和`ac.loadCarState()`已经能保存很多车辆状态，不过实际测试仍然发现了一些没有跟着恢复的东西。例如这辆SU7底层仍借用了AC的燃油发动机传动结构，极端候选把转速拖到零以后，发动机stall latch会污染后面的测试；只恢复车的位置和轮速并不能解决。

轮胎四个温区也需要额外保存，SU7自己的SOC和电控状态要另外存，Python控制器的历史还要再配一份JSON。恢复以后还要留一段求解迭代，让轮胎接触和悬挂约束重新收敛。`loadCarState`很有用，但也不能把它理解成虚拟机快照，实际还是得多做一些DIY的工作。

## 控制

CSP Custom AI给了一个很直接的入口。外部程序创建指定名称的Windows共享内存，CSP检测到以后就把对应车辆的驾驶输入交给它。

这次实际使用的控制量只有：

  * 油门
  * 刹车
  * 离合
  * 方向
  * 升挡、降挡
  * 自动离合开关

读回来的基础状态包括车速、转速、挡位、位置、朝向和赛道归一化进度。更多的轮胎、车身和SU7电控数据由一个CSP Lua App采集，再通过另一块共享内存送给Python。
    
    
    AC/CSP物理
        ↓ 车辆、四轮、路面、电控状态
    CSP Lua遥测桥
        ↓ SU7.AI.Telemetry.v1
    Python AI车手
        ↓ 方向、油门、刹车、换挡
    CSP Custom AI
        ↓
    玩家车
    

这条链路的好处是控制器真的像人一样踩踏板和打方向，车辆物理还是AC在算。要对比轮胎或者电控时，不会因为AI直接给车身加了一个力，最后把物理问题遮掉。

相应地，外部AI也不能直接决定下面这些东西：

  * 某个物理帧必须产生多少轮胎横向力
  * 轮胎必须压在哪个三角面、获得多少抓地
  * ABS、原生TC和碰撞求解器内部每一步怎么算
  * 一次恢复以后，所有隐藏状态必须和上一次逐位相同

CSP物理脚本确实还能覆盖发动机扭矩、制动力，或者给车轮增加电扭矩，但那是车辆Mod的执行器，不是AI车手的权限。驾驶员层和车辆层如果混在一起，最后很难说圈速是线路快了，还是脚本偷偷把车推过去了。

## AI车手

这里叫AI车手，其实并不是让大模型看着屏幕玩，也不是先训练几百万步强化学习。

目前主体还是一个确定性的闭环控制器，外面再套自动调参。AssettoCorsaGym这类项目已经证明AC可以接RL和MPC，但是这次更关心可重复、可审计和能快速定位问题，所以先用传统控制会更合适。

### 线路

控制器第一件事是知道自己在哪。它会读取AC v7格式的AI线，把车辆位置投影到闭合线路上，得到最近点、当前进度、横向误差和航向误差，再向前找一个预瞄点。最早只用了Pure Pursuit，能跑完整圈，但是高速弯反应慢，发卡弯又容易追着误差来回修。后面把真人Replay、AC理想线和已经跑通的线路拆开处理：

  * 驾驶线决定车要走哪里
  * 参考方向决定正常情况下应该打多少方向
  * 误差反馈只负责把偏差慢慢收回来

现在的方向请求大概由几部分组成：
    
    
    参考方向前馈
    + 几何预瞄
    + 横向误差反馈
    + 航向误差反馈
    + 横摆反馈
    + 车身侧偏修正
    - 前轴/组合滑移卸载
    

最后再经过低通、方向速度限制和方向加速度限制，避免控制器一帧左打一帧右打。真人开车看起来是一个连续动作，AI如果只盯最近点，很容易把方向盘打成方波。

### 速度

有了线路还不够，真正决定能不能跑完的是速度规划。离线先根据曲率、动力、制动和摩擦椭圆生成一个基础速度曲线，再叠加真人遥测和已经验证过的局部修正。运行时不会等到当前点超速才刹车，而是提前向前看一段距离，计算后面目标速度需要多少减速度。纵向控制再把速度误差变成油门和刹车，同时处理几个限制：

  * 油门和刹车不能同时踩
  * 制动进入和释放都要连续
  * 前轮组合滑移过大时不能继续一边重刹一边加方向
  * 后轮滑移和车身侧偏过大时要收油
  * TC、ESC、TVC仍由车辆层负责，AI只根据最终车辆反应调整驾驶请求

这里很容易出现一个误区：理论速度曲线比真人快，不代表放进AC就一定能跑出来。准稳态模型没有轮胎松弛、瞬态载荷转移、路肩跳动和控制延迟，最后还是要让AC裁决。

### 状态机

一个能跑的控制器和一个能无人值守测试的控制器，中间还差一层状态机。

它至少要处理等待会话、接管车辆、起步、第一条残圈、暖胎圈、正式圈、计时线穿越、到点停车、失控中止和安全退出。

每一帧还要检查车速、路径误差、车身侧偏、遥测心跳和控制包是否更新。路径误差超过安全值时先全刹，其实每次直接判定失败了，重载到下一次测试了。

实际现在暖胎只做一次，然后把入口热状态保存下来，后面的候选不再重复付这几圈的成本，直接做状态加载即可

## 重复测试

### 配对热状态

现在一个检查点不是一个文件，而是三部分：

  1. CSP保存的车辆物理状态
  2. SU7车辆脚本的SOC和电控历史
  3. Python驾驶控制器的历史

三者使用同一个`state_key`。车、赛道、CSP版本或者暖胎方法变了，就换一个key；恢复时key对不上直接失败。

这解决了大部分重复预热问题。AC下次启动时也可以从磁盘加载已经保存的暖车状态，不需要重新跑三圈。进程还活着时更简单，直接在同一个会话里重复加载就行了。不过恢复以后还是要先跑一个原参数基线。如果基线的时间、末速和路径误差已经超出重复性范围，说明这个热状态或者当前物理会话不健康，后面的候选全部不能信，AC有时候莫名其妙会出现一些问题，导致圈速无法重复，很多问题都是边测，边发现，边改的。

### 常驻进程

测试系统后面又增加了常驻worker。

AC保持一个PID不退出，Python也保持一个进程不退出。新任务只是把JSON放到`inbox`，worker原子移动到`running`，完成后再放进`done`或`failed`。参数搜索、遥测解析和审计都在同一个Python进程里重复调用，其实就有了一个测试任务队列，生产消费都变得有序了，分析程序只要针对最终结果进行AI分析即可。测试SOP固化了，只用管理好测试流程就行了。
    
    
    persistent-worker
    ├── inbox
    ├── running
    ├── done
    ├── failed
    └── logs
    

正常候选只做两件事：恢复配对热状态，加载新的参数进行测试。

### 自动调参

控制器的参数太多，手工一次改一个同样很慢，所以搜索器使用JSON描述参数范围和它要修改的位置。
    
    
    {
      "parameters": {
        "c4_speed_scale": {
          "min": 0.82,
          "max": 0.94,
          "initial": 0.88
        }
      },
      "mutations": [
        {
          "type": "window",
          "key": "reference_speed_scale_index_window",
          "start": 650,
          "end": 1400,
          "parameter": "c4_speed_scale"
        }
      ]
    }
    

一批测试大概是下面这个流程：

  1. 从弯前检查点恢复原参数，重复跑基线
  2. 批量跑一组种子参数
  3. 不完整、失控、出界或违反抓地要求的候选直接淘汰
  4. 用安全样本拟合一个小的二次响应面
  5. 在预测有收益的区域继续采样，同时保留少量探索
  6. 对领先候选做重复测试，按稳健结果排序
  7. 只有局部收益超过门槛，才花时间跑完整圈和连续正式圈

这里没有让机器直接乱改几百个参数。每一批只开放少量有物理意义的量，例如一个弯的速度倍率、制动释放、预瞄距离、方向滤波、TC目标滑移或者TVC横摆变化率。

自动反馈学习主要用在两层。一层是上面的响应面搜索，解决“下一组参数测什么”；另一层是ILC，根据上一圈沿距离的速度和踏板误差生成下一圈的局部修正。机器可以自己继续试，但安全门限和晋级条件不能让它自己改。

## CSP

CSP在这里大概承担了三种工作。

第一种是车辆物理脚本。它运行在物理线程，可以读取车身和四轮状态，计算SU7的TC、ESC、TVC、SOC和目标横摆，也可以在明确校准以后调用电扭矩、制动力和其它执行器。

第二种是Lua App。它不负责画一个花哨界面，主要负责把每帧车辆状态、四轮接触和SU7电控状态写入MMF，并接受保存、恢复、配置切换和会话控制命令。

第三种是Custom AI。Python通过它接管玩家车的驾驶输入，不需要虚拟手柄，也不需要从屏幕OCR车速。

这三层特意分开：

  * 车辆物理脚本回答“这辆SU7怎么响应”
  * AI车手回答“驾驶员现在怎么操作”
  * 测试桥回答“怎么把实验重复起来并留下证据”

CSP也不是无限权限。不同版本的API会变化，有些函数只在preview里出现，有些字段单位和方向需要进游戏实测。这个项目固定CSP版本，每个用到的接口先做验证，单位、符号等等都不是很明确。

## 工程模板

这次真正有复用价值的，可能不是珠海某一个弯的参数，而是下面这些模板。

### 传感器和执行器适配

控制算法不直接到处调用CSP API。Lua先把不同版本、坐标、符号和单位整理成固定状态，Python再只面对统一字段。输出也只通过一个`Controls`结构写方向、油门、刹车和换挡。

以后换车或者换CSP版本，先改适配层，不用把整个控制器重写。

### 共享内存协议

每块MMF都有固定名称、固定布局、序号、心跳和确认序号。Python打开CSP已经创建的映射，而不是自己意外创建一块同名但断开的内存。

命令必须有`sequence/ack/status`，否则保存状态比较慢的时候，外部程序很容易把同一条命令执行两遍。

### 配对检查点

车辆状态和控制器状态必须一起保存。只保存车辆会丢方向滤波、积分器和线路进度，只保存控制器又会丢轮胎和悬挂状态。

检查点还要绑定车、赛道、CSP版本和配置key。这个模板不只适合跑圈，任何需要在同一初态做A/B测试的AC项目都能用。

### 数据驱动的试验配置

完整基础配置、局部参数范围、修改窗口、停止位置、审计规则、重复次数和晋级门槛都放在JSON里。搜索器只负责解释配置，不为每个弯再写一套Python循环。

每个运行目录再保存实际展开后的`run_config.json`。以后看到一条快圈，可以知道当时到底用了什么，而不是只剩下一个文件名叫`final_final2`。

### 常驻任务队列

一个AC进程、一个控制进程、多个连续任务。任务状态用目录和原子重命名表示，即使脚本中途退出，也能知道哪个任务还在跑、哪个失败了。

这比每个候选新开一次Python和AC快很多，也更容易阻止隐式重启。

### 自适应分段搜索

先把完整赛道分成可以解释的区段，在弯前保存检查点，只评估当前弯和必要的下游传播区。局部赢家再回完整圈验证。

这样机器可以一口气跑几十组参数，而不是每次都先跑三圈预热，再用整圈时间判断一个发卡弯有没有快20毫秒，相当浪费时间。

### 遥测、审计和证据

每个物理帧保存原始CSV，结束后再生成摘要和审计JSON。至少保留：

  * 车辆位置、速度、方向、油门和刹车
  * 目标速度、参考方向和每项控制修正
  * 四轮载荷、滑移、温度、压力、接地点和表面抓地
  * TC、ESC、TVC实际档位、请求量和执行量
  * 赛道边界、车辆中心和四轮出界统计
  * 使用的配置、程序版本、回放和校验值

最终成绩不能只留一张圈速截图。截图证明它显示过这个数字，不能证明车走在哪里、有没有压到错误表面，也不能证明下一次还能跑出来。

## 限制

现在这套系统已经能让AC保持一个进程，重复恢复热状态，自动执行参数组合，再根据结果继续搜索。但是它还不是一个通用的自动驾驶平台。

控制器对珠海和SU7做了很多专门处理，赛道索引窗口、真人参考线和局部限幅都很重。

另外，自主控制器跑得快，只能证明控制器和当前Mod的组合跑得快。它不能反过来证明Mod就一定和真车一样，车辆物理还是要用实车数据、固定输入和保留工况单独验证。

后面如果继续做，可以把当前确定性控制器当成安全基线，再接MPC、贝叶斯优化或者强化学习。新的策略先在已有走廊和稳定性约束里跑，超过基线以后再进入完整圈。这样学习算法负责找收益，工程模板负责保证它没有作弊。

## Summary

AC里实现一个AI车手，难点并不是把油门设成1、方向对着AI线。真正麻烦的是黑盒物理、隐藏状态、赛道接触、控制延迟和测试复现。

最后的系统也不是一个单独的驾驶脚本，而是一整条链路：CSP采集状态，Custom AI接管输入，控制器闭环驾驶，热状态缩短重复试验，常驻进程批量执行，自适应搜索选择下一组参数，审计器负责判定结果能不能算数。

做到这里，机器确实可以自己反复跑和自己缩小参数范围了，但它学得再快，最终还是要接受AC真实物理、原始遥测和回放的共同检查。

实际上即使有了这么一套东西，跑起测试来还是太慢了，跑一周距离人类记录都还差1s多，还是不满意，这东西还得优化，还是得想办法把测试、规划、搜索转变成确定性的算法或者控制循环来跑，有一个明确理论结果以后再转到AC上进行测试，不然效率太低了。

C 盘又红了，删来删去不知道删谁——[WizTree](https://www.huluohu.com/posts/tag/wiztree/ "WizTree") 读硬盘自己的总账本，几秒钟把整盘文件按大小摊开给你看，哪个文件夹在偷空间一目了然。

![WizTree 磁盘空间分析](https://www.huluohu.com/wp-content/uploads/2026/11/cover-ep02-v2.jpg)

> 适合谁：C 盘常年飘红、装了一堆游戏和素材、想一次性看清硬盘去向的 Windows 用户  
> 一句话结论：免费版功能全开，扫描按秒算，留它、删 WinDirStat  
> 下载：官网免费下，网盘已备好便携版，见文末

## 先说清楚

WizTree 是英国 Antibody Software 做的磁盘空间分析工具，最新版 4.33 发布于 2026 年 9 月 16 日，Windows 和 macOS 都有（macOS 叫 WizTreeMac 1.00）。个人使用免费，功能上不设卡：树状视图、彩色树状图、文件视图、重复文件查找、CSV 导出全在免费版里。商用要买 Supporter Code，25 美元起。

它和 WinDirStat 干的是同一件事，差别在路子。WinDirStat 是老老实实一个文件夹一个文件夹走过去数，WizTree 直接读 NTFS 硬盘自带的总账本（MFT，主文件表），一次把整盘的文件清单拿过来。所以它快是真快，不是界面动画快。

先把丑话说前头：第一，高速扫描要管理员权限，启动时会弹 UAC，那是读总账本的必要条件，不是它在搞小动作；第二，MFT 这招只在 NTFS 盘上灵，FAT32 的 U 盘、exFAT 的移动硬盘、网络盘会退回普通扫描，速度就没那么神了；第三，这篇的扫描耗时引自官网与几家实测评测的数字，界面图用的是官网原图。

还有一个数我不打算跟着喊：官网说比 WinDirStat 快 46 倍，那是拿 WinDirStat 1.1.2 那个近二十年没动的老版本比的。WinDirStat 2.5 开始也学会了读 MFT，所以 46 倍这个数，放今天不作数。我只认它自己的实测数字：官网截图一共 878GB、184 万个文件的盘，扫完 5.64 秒。

## 图文步骤 / 实测过程

**1\. 下载便携版，解压即用。** 官网下载页有安装版（4.9MB）和便携版 ZIP（7.4MB）两种，网盘里放的是便携版：解压出 WizTree64.exe，双击就跑，不写注册表。这份 ZIP 来自官网 diskanalyzer.com，SHA256 和官网公布的哈希一致。

![WizTree 树状视图与彩色树状图，官网图](https://www.huluohu.com/wp-content/uploads/2026/11/wiztree_treeviewwithmap4.jpg)

**2\. 选盘，点 Scan，等几秒。** 第一次启动会问你要不要管理员权限——点「是」，否则走慢速模式。选 C 盘点 Scan，进度条还没看清楚就扫完了。上面是按大小排好的文件夹树：Users 占了多少、Program Files 占了多少、Windows 下面 WinSxS 胖成什么样，一层层点进去就是。

**3\. 看树状图，找大块头。** 窗口下半截是彩色树状图：一个文件就是一个方块，越大越占地方。虚拟机镜像、游戏的 .pak 大文件、好几年前的备份，在图里都是刺眼的大色块，鼠标一点就知道路径。找空间先看这里，比在文件夹里翻快得多。

**4\. 切到文件视图，专盯单个大文件。** 文件视图把全盘文件按大小排队，前面几十个往往就占了小半个盘。想找重复的再切重复文件视图：按文件名+大小+日期比对，同样的安装包下三遍、照片导两份，全给你列出来，Dup Size 一列就是能腾挪出来的数。

![WizTree 文件视图按大小排序，官网图](https://www.huluohu.com/wp-content/uploads/2026/11/wiztree_fileview3.jpg)

**5\. 动手之前先看清，别删错。** 在结果里右键能直接删除、移到回收站、在资源管理器里打开位置。我的做法是：先删确定的（重复安装包、旧版本备份、下载文件夹里早忘掉的大文件），系统目录只看不动——WinSxS 看着胖，那是 Windows 的组件仓库，动它容易把系统搞出病。

## 适合谁 / 不适合谁

适合：C 盘 256GB 的轻薄本用户；装了 Steam、剪辑素材、虚拟机的；接手别人旧电脑想先看清硬盘的人。

不适合：只想一键自动清理、连看都不想看的人——WizTree 只负责让你看清，不替你决定删什么；Mac 用户请下 WizTreeMac，功能大体相同但不是同一安装包。

## 常见问题

**免费版和付费版差什么？**

功能上没差，免费版全开。付费主要是去掉捐赠按钮、去掉导出文件里的捐赠字样，以及商用许可和支持。

**为什么启动要管理员权限？**

读 NTFS 的 MFT 总账本必须管理员权限。不给也行，软件会退回普通扫描，慢一些但能用。

**它会不会偷偷删东西？**

不会。它只读不写，删文件必须你自己在结果里右键操作。怕误删就先用它看，再去资源管理器里动手。

**和 WinDirStat、TreeSize 比，留谁？**

我留 WizTree。WinDirStat 免费但慢，TreeSize 免费版功能阉割，WizTree 免费版功能全、扫描按秒算。唯一的坎是界面长得像二十年前的老软件——能接受这个，就没短板。

**Mac 能用吗？**

能，4.33 同期出了 WizTreeMac 1.00，macOS 12 以上可用，CSV 文件能和 Windows 版互通。

## 最后再划一遍重点

1\. C 盘红了别急着删：先用 WizTree 几秒钟扫一遍，树状图里最大的那几块就是答案。  
2\. 免费版功能全开，个人用一分钱不用花；认准官网 diskanalyzer.com，别去第三方下载站下改版包。  
3\. 只看不动系统目录，WinSxS 再胖也别手贱。

近日，笔者刷到一篇论文[《Your LR Schedule May Not Be Principled: Effective Learning Rate Scheduling in Weight-Normalized Training》](https://arxiv.org/abs/2610.40362)，里边分享了一种估计最优学习率的新思路：先将模型的训练动态简化成一个一维微分方程，然后在这个微分方程约束之下，基于变分思想去最大化某个目标，从而得到最佳调度。

这个过程最吸引人的地方，不是得到了一个具体公式，而是提供了一个把“训练直觉”翻译成“调度形状”的一般框架。接下来，笔者将分享自己阅读过后的理解，并做一些延伸讨论。

## 更新规则

原论文考虑的是Weight Norm（下面简称“WN”）类优化器，所以我们也从WN出发，其更新规则为

**Mac电脑突然自动重启后输入密码没反应，也不提示报错，多次重启后也没效果！**

解决方案：

关机进入恢复模式操作，通过"实用工具 > 终端"输入 `resetpassword` 命令来重置密码。

  * Intel芯片Mac：重启时立即按住 `Command (⌘) + R`。

  * Apple芯片Mac：关机后，长按电源键直到出现"正在载入启动选项"。

继续点击 “选项” → “继续”。

如果提示选择用户，选你的账户并输入当前密码（即使你平时输不进，这里通常能过）。

**打开终端**

顶部菜单栏 → “实用工具” → “终端”。

**运行重置密码命令**

在终端中输入以下命令（注意空格和大小写）：**resetpassword** ，按回车。

**图形界面重置密码**

会弹出一个窗口，标题是 “重设密码助理程序”。

左侧选择你的内置硬盘（如 Macintosh HD）。

右侧选择你的管理员账户名。

点击 “下一步”。

输入新密码（建议简单点，比如 123456，先确保能进系统再说）。

点击 “下一步” → “退出”。

**重启电脑**

关闭终端 → 左上角苹果菜单 → “重新启动”。

用刚设置的新密码登录。

最近几年，由于各种原因，中国内地投资客热衷美国股票市场，比如可以暂时规避CRS的资本利得税问题。但是有一个事情很多人没有注意到，美国联邦遗产税。

作为中国内地个人投资者，在没有美国国籍、绿卡或长期在美定居的情况下，这属于美国税法上的非居民外国人，虽然投资美股免交资本利得税，且股息税可按中美税收协定减免至10%，但一旦持有人不幸身故，其名下的美国资产将面临极其严苛的美国联邦遗产税。

美国遗产税的判定核心是“资产所在地”，而非开户券商所在地（哪怕使用的是[香港券商](https://tumutanzi.com/archives/17628)、[新加坡券商](https://tumutanzi.com/archives/17393)，只要底层资产属于美国境内资产，一律纳入征税范围），像美国公司股票、美国注册的ETF/基金这些都是属于美国资产，不过，存在普通美国银行的存款不属于美国资产。

包括中国内地居民在内的非居民外国人，遗产免税额仅为6万美元（按现行汇率，不到40万人民币），该额度数十年未随通胀调整。对比之下，美国公民及税务居民享有的极高遗产免税额（2025年为1399万美元）。

上述遗产税累进税率高达40%，也就是说，资产持有人去世当天，美股账户内美国境内资产的公允价值（不论盈亏，均按总市值计算）减去6万美元后，超出部分适用18%至40%的超额累进税率。超出部分达到100万美元以上时，边际税率即达到最高档40%。

遗产税这种问题在资产持有人在世时根本不是问题，但一旦遇到极端事件，这个问题就可能会变得很棘手。

# [](https://blog.lusyoe.com/article/zhihu-muted-7-days-own-blog#前言 "前言")前言

2026 年 11 月 17 日下午 5 点 32 分，知乎的站内信里躺着一条通知。知乎账号被禁言 7 天，理由写着，多次发布含有“垃圾信息与违规营销”的内容。

我盯着这几行字，一开始有点想笑。一年多在知乎吭哧吭哧发了 278 篇文章，落得这么个评价。

但冷静下来想，这个判定不算冤。278 篇里确实有不少是 AI 生成，我自己清楚。

# [](https://blog.lusyoe.com/article/zhihu-muted-7-days-own-blog#一纸通知 "一纸通知")一纸通知

![知乎账号被禁言 7 天的系统通知，理由为多次发布含有垃圾信息与违规营销的内容](https://img-cdn.lusyoe.cn/images/lusyoe/2026/11/18/zhihu-muted-7-days-notice.png)

通知不长。账号禁言 7 天，如继续发布同类内容将面临更严重的处罚，并要求自查已发布的所有内容，主动删除违规信息。

7 天说长不长，对一个靠写作维持节奏的人却不好受。更让我在意的是那句自查。

怎么查，查哪几篇，删到什么程度，通知里只让我去读《知乎社区规范》。删不删，我到现在也没想明白。

# [](https://blog.lusyoe.com/article/zhihu-muted-7-days-own-blog#大概踩了什么线 "大概踩了什么线")大概踩了什么线

想了一晚上，问题大概出在两个地方。

一是内容本身，同步过去的文章里不少是 AI 生成，标题冲着流量去，读起来就像营销稿。二是文章末尾挂着自己产品的链接。

放在自己的博客里，那是我的文章我的站，天经地义。搬到知乎，就成了违规营销。

独立开发推广就是这么难，得承认。可站在平台的角度，这个判定我也能理解。AI 内容泛滥成灾，平台不收紧口子，信息流就没法看了。

规则大概只能越来越严，判定大概只能越来越粗，平台宁可错杀。难受的是这条线画在哪儿，创作者只能猜。

今天留产品地址算营销，明天留个人微信算导流，后天出现一个品牌名，算不算广告。没人提前告诉你，只有处罚通知告诉你。

这次禁言给我最直观的一课是，在平台上写字，是在别人的地基上盖房子，图纸随时会改。

# [](https://blog.lusyoe.com/article/zhihu-muted-7-days-own-blog#平台给的不是你的 "平台给的不是你的")平台给的不是你的

278 篇文章，一年多攒下的东西，内容是我的。分发不是。

账号一禁，我能做的只剩看着。这 7 天里我发不出一个字，旧文章也不会因为我的更新被更多人看见。

平台给流量，流量随时能收回。平台给账号，账号随时能封禁。

你以为攒下的是自己的读者，其实是平台的用户。平台要对信息流负责，这没错，只是它的利益和我的利益从来不是一回事。

# [](https://blog.lusyoe.com/article/zhihu-muted-7-days-own-blog#卸载了知乎 "卸载了知乎")卸载了知乎

收到通知我一点都不生气，因为就在前几天，我已经把知乎 App 卸载了。

理由很朴素，每次打开知乎，开屏广告就弹出来，还带自动跳转。手指没碰屏幕，页面自己就跳进购物 App，返回键按半天回不来。

我只想安静看篇文章，不是想逛商场。

忍了几天，卸载了，世界清净了。所以通知到的时候，我甚至觉得它来得正好，替我做了一个早就该做的决定。

一个平台内容再好，如果靠折腾用户的注意力挣钱，创作者和读者都会被一起消耗。

# [](https://blog.lusyoe.com/article/zhihu-muted-7-days-own-blog#还好有个博客 "还好有个博客")还好有个博客

这次收到通知，我的第一反应除了想笑，还有庆幸。这些文章，博客上都有一份。

博客挂在 blog.lusyoe.com，域名自己买的，服务器自己租的，文章是一个个 Markdown 文件，躺在自己的仓库里。没有审核，没有禁言，文章留不留，我说了算。

它唯一的缺点是人少，少到几乎可以忽略不计。但这个缺点，这两年正在被另一件事抵消。

越来越多人不再刷信息流，有问题直接问 AI。现在的 AI 回答问题前，大多先去网上检索一圈。

平台的内容大多围在登录墙和 App 里，不登录看不到全文，爬虫也常被拦在门外。自己的博客是敞开的，我的 robots.txt 对爬虫基本全开，只挡了几个个人页面。

一篇没人看的文章，可能在某个深夜被 AI 抓走，过几周被引用给一个正在提问的陌生人。有多少人顺着 AI 的引用找过来，我说不清，这账算不明白。

但道理是通的，平台越收越紧，AI 越抓越广，站在这个口子上的人，手里得有一块自己的地。

现在我照常更新博客，公众号同步一份。知乎那边，解禁之后也不会再更新了。

博客是主营地，公众号是次营地。有人看的平台用来分发，没人看的地方用来扎根。

房子盖在自己的地上，风再大也吹不塌。

# [](https://blog.lusyoe.com/article/checkin-invite-rank-reward#前言 "前言")前言

前面几篇文章聊发福利，不管是会员体验卡还是折扣福利卡，走的都是同一个路数：平台在后台把人筛出来，卡直接发进账户。

收到的人自然是惊喜。

没收到的用户，压根不知道发生过什么。

暖是暖，但这套做法一直有个短板：激励是滞后的，想争取点什么的人，看不到一个明确的目标。

所以这次换个做法，青萍语音小程序把福利做成了两个公开的排行榜，邀请榜和签到榜。

奖励是什么、怎么拿、什么时候发，全部摆在明面上。

# [](https://blog.lusyoe.com/article/checkin-invite-rank-reward#把福利摆到明处 "把福利摆到明处")把福利摆到明处

之前的玩法，是平台先认人再发卡：连续签到满 7 天的，累计登录满 10 次的，系统识别到，卡就到账。

对本来就在天天签到、经常登录的人，这是实打实的回馈。

可对一个新用户，或者一个想主动争取点什么的用户来说，路径是看不见的。

做到什么程度能换到什么，事先没人说得清。

激励这件事，光靠事后惊喜撑不起来，得让人看得见目标。

排行榜就是干这个的：规则公开，进度实时可见，差多少一瞄就知道。

# [](https://blog.lusyoe.com/article/checkin-invite-rank-reward#邀请这条线 "邀请这条线")邀请这条线

邀请榜的规则一句话讲完：邀请满 10 个人，送一张正式会员福利卡。

计数口径也简单，好友通过你的邀请海报或邀请卡片进入小程序，注册成功就算一个人，不要求他再完成别的动作。

满 10 人，卡就到手，不限时段，攒够为止。

把觉得好用的东西推给朋友，朋友得了方便，自己离福利卡也近一步，这件事本身就不亏。

# [](https://blog.lusyoe.com/article/checkin-invite-rank-reward#签到这条线 "签到这条线")签到这条线

签到榜分月度和年度两层。

每个月签到次数排前 3 名的用户，每人一张正式会员福利卡。

年度这边，全年签到总次数排前 10 名的用户，月榜的奖励照常累计，年终还有一份神秘礼品。

为什么分两层？

月榜是短周期，坚持的人每个月都有一次兑现的机会；年榜是长周期，留给一整年都在的人。

坚持一个月不难，难的是坚持一整年。

至于神秘礼品是什么，先卖个关子，年底揭晓。

# [](https://blog.lusyoe.com/article/checkin-invite-rank-reward#奖品是正式会员 "奖品是正式会员")奖品是正式会员

两张榜的奖品是同一个：正式会员福利卡，Pro 版一个月的正式会员。

不是体验卡，是完整的 Pro 权益：更多音色槽、无广告、更多模型权限，还有更多高级功能。

体验卡和正式卡的差别，用过的人都有数：试用期间不含音色槽和积分赠送，正式卡全都有。

这张卡拿到手，就是一个月的完整 Pro 待遇。

![邀请和签到排行榜的奖励结构](https://img-cdn.lusyoe.cn/images/lusyoe/2026/11/18/rank-reward-structure.webp)

# [](https://blog.lusyoe.com/article/checkin-invite-rank-reward#一直都在 "一直都在")一直都在

这个活动长期有效，不设截止日期。

月榜每个月开奖一次，年榜按自然年统计，年底随神秘礼品一起结算。

不用赶在某个日期之前突击，把它当日常就行：顺手邀请个朋友，顺手签个到，剩下的交给时间。

从今天开始攒，下个月月底，榜单上见。
