这次配置的目标是用标准 RDP 客户端访问 PikaOS 虚拟机中正在运行的 COSMIC 桌面。  
FreeRDP 可以在 1920×1080 下显示桌面，KRDC 在这个尺寸下黑屏。将虚拟显示切到 1920×1200 后，KRDC 能出画。  
最终使用 1920×1200 和 AVC420，macOS 的 Windows App 与 Windows 自带的 `mstsc` 均通过实测，Windows 还需要允许保存该连接的凭据。

## [](https://blog.ponder.work/2026/11/22/cosmic-rdp-setup/#环境 "环境")环境

项目| 实测环境  
---|---  
服务端| PikaOS 4，x86_64，Linux `7.3.5-pikaos`  
虚拟化与显示| KVM/QEMU，虚拟输出 `Virtual-1`，对照测试使用 1920×1080 和 1920×1200  
桌面与登录管理器| COSMIC Wayland，`cosmic-comp`、`cosmic-greeter` 和 `xdg-desktop-portal-cosmic` 均为 `1.11.0-101pika1`，登录由 greetd 管理  
RDP 服务| Lamco RDP Server 原生 Debian 包 `1.4.5-1`，OpenH264 `2.6.0`  
客户端| KDE neon User Edition，KRDC `26.08.2`，FreeRDP 库与 `xfreerdp` 均为 `3.32.1`  
网络与认证| 局域网内直连 TCP 3389，服务绑定 `0.0.0.0`，使用 TLS 和 PAM，关闭 NLA

## [](https://blog.ponder.work/2026/11/22/cosmic-rdp-setup/#从仅观看恢复到可控制 "从仅观看恢复到可控制")从仅观看恢复到可控制

Lamco 最初检测到 COSMIC 提供 `RemoteDesktop` portal，于是走了 libei 路径。该路径在这台虚拟机上没有返回屏幕流，随后退回 ScreenCast-only，客户端只能观看。此前的屏幕共享弹窗也来自这条 portal 路径。

处理方式是把系统的 `cosmic-portals.conf` 复制到 `~/.config/xdg-desktop-portal/`，在已有的 `[preferred]` 段中增加这一行，再重启用户的 `xdg-desktop-portal.service` 和 Lamco 服务。这个覆盖只作用于该账户的 COSMIC 会话，也会影响同一会话中依赖 `RemoteDesktop` portal 的其他应用。

## [](https://blog.ponder.work/2026/11/22/cosmic-rdp-setup/#PAM-登录故障 "PAM 登录故障")PAM 登录故障

安装的 Lamco 版本拒绝 `auth_method = "pam"` 与 `security_mode = "auto"` 的组合。实测可用的服务端配置为：

配置能加载后，系统验证接受了同一个账户密码，RDP 连接却仍被 PAM 拒绝。关键线索是 `/proc/<PID>/uid_map`。Lamco 用户服务的文件系统沙箱把进程放进了只映射当前用户的命名空间。用 `systemd-run --user` 做对照测试时，系统密码验证辅助程序在普通用户服务中成功，单独加入 `ReadWritePaths` 后失败。此前测试已经放宽数项 systemd 沙箱限制，最后清除 `ReadWritePaths` 后，进程恢复到常规用户命名空间，FreeRDP 通过 PAM 成功登录。

这台测试虚拟机保留了放宽后的服务覆盖文件。结果说明文件系统隔离是当时仍在阻碍验证的一项设置，尚未逐项回加其他限制来确定最小变更。监听所有 IPv4 接口和放宽服务隔离都是这次实验环境的配置取舍，不宜直接当作长期对外部署的模板。

## [](https://blog.ponder.work/2026/11/22/cosmic-rdp-setup/#为什么-1080p-会触发-KRDC-黑屏 "为什么 1080p 会触发 KRDC 黑屏")为什么 1080p 会触发 KRDC 黑屏

故障的典型表现是客户端能登录，虚拟机端也能看到远程鼠标移动，但客户端窗口没有桌面画面。服务端日志表明桌面帧已经被捕获和编码。用同版本 KRDC 复现时，客户端在处理首批 `RDPGFX_CMDID_ENDFRAME` 消息时报告错误 16。在 KRDC 中切换到 RemoteFX 或关闭图形加速，均未恢复 1080p 画面。另一次用 `xfreerdp` 强制图形通道、服务端固定 AVC420 的对照测试，也复现了黑屏。

H.264 以 16×16 像素的宏块组织编码画面。1920 是 16 的倍数，1080 向上补齐到 `68 × 16 = 1088`。额外的 8 行属于编码填充，实际桌面高度仍是 1080。[ITU-T H.264 标准](https://www.itu.int/rec/dologin_pub.asp?id=T-REC-H.264-202408-I!!PDF-E&lang=e&type=items)

本例中，Lamco 同时创建了 1920×1088 的 RDP 图形表面，并将实际桌面尺寸设为 1920×1080。日志和源码指向同一处兼容问题。尺寸不一致使客户端走入图像缩放路径，而 KRDC 使用的 `PIXEL_FORMAT_RGBX32` 缺少这个版本的 FreeRDP 缩放映射。1920×1200 的宽高都是 16 的倍数，绕过了这次尺寸差异，两次显示结果也与这个解释一致。[Lamco 显示管线](https://github.com/lamco-admin/lamco-rdp-server/blob/v1.4.5/src/server/display_handler.rs) · [KRDC 渲染代码](https://github.com/KDE/krdc/blob/v26.08.2/rdp/rdpsession.cpp) · [FreeRDP 缩放实现](https://github.com/FreeRDP/FreeRDP/blob/3.32.1/libfreerdp/codec/color.c)

虚拟机显示模式| 客户端| 实测结果  
---|---|---  
1920×1080| KRDC 26.08.2| 能登录，远程鼠标移动可见，客户端黑屏  
1920×1200| KRDC 26.08.2| 能显示桌面  
1920×1080| `xfreerdp` 3.32.1| 能登录并显示桌面  
  
如果虚拟机使用 1080p，`xfreerdp` 可用以下命令连接。把示例地址和账户替换成实际值，密码按提示输入。

| 
    
    
    xfreerdp /v:192.0.2.10:3389 /u:vmuser /sec:tls /size:1920x1080 /from-stdin:force  
      
  
---|---  
  
## [](https://blog.ponder.work/2026/11/22/cosmic-rdp-setup/#Windows-和-macOS-客户端复测 "Windows 和 macOS 客户端复测")Windows 和 macOS 客户端复测

Windows 自带的 `mstsc` 起初提示“由于协议错误，会话连接将断开”。服务端日志表明，预填用户名以后，客户端已经发送了用户名，但密码字段仍然为空。操作者允许 Windows 保存该连接的凭据后，`mstsc` 正常连接。服务器记录了 PAM 认证成功，随后持续发送 1920×1080 画面。这与当前 TLS 模式下 Lamco 需要客户端在连接时提交密码的行为一致。[Lamco 凭据验证源码](https://github.com/lamco-admin/lamco-rdp-server/blob/v1.4.5/src/security/auth.rs)

macOS 的 Windows App 最初能显示第一帧，后续画面卡住。关闭客户端动态调整分辨率及 AVC444 省略辅助色彩数据的优化后，Mac 一次重连出现了黑屏。固定为 AVC420 后，1080p 又能显示首帧，但后续画面仍卡住。保留 AVC420，将虚拟机显示改为 1920×1200 并重启 Lamco 后，操作者确认 Mac 画面能持续刷新。这个结果确认了可用组合，尚不能确定 Windows App 内部在哪一步丢失了更新。

服务端最终采用 1920×1200、AVC420，并禁止客户端动态改变会话分辨率。操作者随后再次用保存过凭据的 Windows `mstsc` 连接，确认这套配置在 Windows 上也正常。
