妻子在[博客](https://www.seis-jun.xyz/blog/2026-11-04-global-hiking.html)里提到了斐济之旅，但没带上我。

放心，物理上带的不是别人，正是我，只是笔上给忘了。因此，我有必要也来补充说说。

是的，我们是从一个鸟不怎么拉屎的地方，去到了一个鸟很爱拉屎的地方，穿的拖鞋。我都忘记为啥平时都是穿拖鞋了，反正坐飞机也是穿的拖鞋。大概是太热了吧，我怕热。坐地铁往机场赶的时候拉肚子了。然后坐了一站路赶紧下车到地铁里的厕所放飞自我，还好妻子带了纸。

我们坐的好像是澳洲廉航啥的，并不是吃的少，而是如果你要订吃的，得加钱。但，不管怎么样，“空姨”和服务都比我从洛杉矶坐到加州的航班要好，尽管那次有吃的。那次给大家服务的是“空爷”，发的食物是几根萝卜条，还可以蘸酱。“空爷”说话还会喷射口水，和我高中的化学老师有得一比。

没多久就到岛上，应该是主岛Nadi。我们的目的地不在主岛，妻子订的是旁边一个小岛上的度假村。至今那个度假村还在给我发邮件，欢迎我再次光临。

下午到的，我们在主岛上住了一晚。那个季节还有热带气旋，飓风什么的。能不能去度假村还未可知。和我们一个时间去度假的还有我们的朋友，他们订的是另一个岛，差点回不来。第二天天气还不错，气旋旋到了我们朋友去的方向，我们才有机会坐上船。从宾馆到码头的路上遇到了当地采椰子的人。看到我们就热情地分享了一个椰子给我们，还帮我们开了盖。

我们俩没有怎么坐过船，听说还有45分钟的航程，我们提前已经备了晕船药。临上船，我们吃了一颗。一上船发现，我的天，这浪几乎会把我们甩出去。多往窗外看一眼都得晕。于是，我们各自又多吃了一颗。

稀里糊涂地就来到了妻子订的度假村，的确没有晕船，可能是因为嗑high了。

度假村有较为热情的迎接，给我们带了花环。接待员见到我们，就来了句“KoNi Jiwa”。我们都很high，没有和他计较。他告诉我们晚上有欢迎你们的篝火晚会。我们俩迫不及待地领了钥匙，到了我们的房间。那时还早，没到晚饭时间。

我们俩一倒头，就睡了。睡到了第二天上午。至今也不知道篝火晚会的火多么热。

第二天，我们已经一身热带装扮，“出岛”了。大约是有点兴奋，居然忘记涂防晒霜了。好吧，其实我们不是太知道怎么玩啊。总之就是泳池泡澡，沙滩晒太阳。是的，还有捉螃蟹。是我在捉，捉得不亦乐乎，妻子看我笑话。我们俩都不怎么会游，所以海里是不敢进去游的，水只敢末到膝盖。对了，还有个好玩的，就是在沙滩上捡生锈的硬币。不知道度假了口袋还要装那么多硬币干啥，我也不知道自己捡到有啥用。对，其余时间还是看了海，也就那样，因为平时会看很多海。就像妻子说的，有点厌海了，只不过颜色稍稍比平时看的海颜色淡些。

泳池就在房间外面，基本可以游到最后。整个度假度得浑身疼，对，皮也疼。回到家一周后，我就好些了，因为换了一层皮，原先的那层在一次洗澡时全揭了。

妻子问我读了她的博客有什么感受，我说，有些事情是经历了才会觉得不过如此，或者果真如此。

就像有些人说，一定要去拉萨才能有灵魂的洗礼一样。~~那是缺氧，脑雾吧。也是high了。~~

人民网日文版报道了山东大学国际问题研究院研究员高梓菁[文章](https://mp.weixin.qq.com/s/mTnqKS0ZV25ItbCXHxsB0Q)。翻译如下：

“日本右翼势力正试图将历史修正主义渗透到大众文化与日常生活之中。除修订历史教科书、发表否认侵略历史的政治言论、参拜靖国神社之外，日本右翼还通过动画、漫画、杂志、游戏、小说、互联网等各类信息传播渠道，试图改变社会对于战争历史的认知。

历史修正主义的传播往往带有隐蔽性。它未必直接否认侵略历史，有时会选择性截取部分史实，或是借助娱乐化表达、诉诸情绪的故事叙事，逐步淡化战争罪责。 就像纳粹旗帜这类具备明确历史含义的符号：当它被人当作猎奇玩物、调侃素材，或是用来彰显个性的元素随意消费时，和它深度绑定的种族主义、侵略战争、反人类罪行这些历史记忆，会在一次次模仿与传播中脱离原本的历史语境。久而久之，这个符号所关联的历史罪行本身承载的道德重量，就有被消解的风险。

这类认知偏差，还有可能影响年轻一代的国家认同与对外认知。一旦历史问题愈发受到民族主义情绪和网络舆论裹挟，正视侵略历史这件事，就会被贴上“否定日本国家形象”的标签；其他国家针对历史问题的批评，也容易被曲解成对日本的“无端指责”，甚至是“敌意攻击”。

倘若日本年轻一代渐渐把军国主义看作遥远的过往，将战争责任当成可以回避的政治争议，日本社会对于扩军、战争动员的警惕感也会随之减弱。

传承历史记忆，不能只依靠死记史实，更要培养人们剖析历史叙事、读懂历史背景、反思战争罪责的能力。日本年轻人如何看待战争，不仅关系到日本自身的国家走向，也关乎日本与亚洲邻国之间的相互理解，更会影响地区和平以及战后国际秩序的未来走向。 “

我的读后感：

哎，日本这个国家从历史上讲尚武，好征战。

古坟时代建立大和国的时候，就是把无数个小部落武力统一，那个时代就开始渡海去朝鲜，虏人，这些朝鲜人有炼铁或水稻种植技术，叫“渡来人”………

宫崎骏前两年的电影《你想活出怎样的人生》，讲40年代东京被轰炸，视角是日本是受害者，这种文化名人的带头作用是非常恶劣的………

对中国的战争是日本发起的，甚至波及东南亚，多少无辜的百姓，日本主流视角至今仍然是“日本和日本人是受害者，我们承受了轰炸和原子弹”，那日本你轰炸无数中国城市的时候呢，你怎么不觉得中国人是受害者，家破人亡了。如此双标，真是无比可笑又可耻，可耻。

日本“耻文化”根本不是中国人理解的耻辱感，那种对善恶对错的羞耻感。日本人这套“耻”的开关在“有没有被人看见、有没有丢面子，我做的坏事被你们看见了，我难堪了，我死不认账，我还要倒打一耙”……

日语作为我的专业，和日本文字文学文化历史打交道20多年了，我真心觉得从文学文艺方面，他们真的很有才华，有很多值得一看的民族特色的东西。但是这种尚武好争斗，武力里面充满野心的暴虐，真的够了，完全抹杀任何好感。你做错了，至少你像德国好好认错忏悔……

日本这种一衣带水的邻居，未来怎么处怎么看，它的历史态度抹杀一切好感，简直够了。中国得自己加油强大，日本的骨子里是畏威不畏德………

英国男子卡尔·布什比11月2日回到家乡英格兰东约克郡赫尔市，为一场历时28年、行程约5万公里的徒步环球之旅画上句号。

1998年11月1日，年仅29岁的布什比从南美洲最南端智利蓬塔阿雷纳斯出发，目的地是家乡赫尔。他为自己定下一条规则：不得搭乘任何交通工具，只能依靠双脚。这一走，就是28年。 

他这条路，有巨大的遗憾，错过了很多普通人的幸福，并不是“得到所有”，不是没有遗憾才叫完美的人生。

短暂的善意、一程的陪伴、咬牙坚持的时刻、守住一个很久的承诺，这些细碎的片段，拼起来就是意义。有人给你递一瓶水，陪你走一段，哪怕最后分开，这份相遇本身，也留下重量。

这个非常震撼的故事，卡尔用28年徒步五万公里，一路失去，一路相逢，带着遗憾走完长路。 终极的意义不在终点，它藏在每一步的经历里。相逢有别离，选择有得失，路终究要自己慢慢走。认真感受，好好经历，便是人这辈子生命的意义吧。

知乎里讲了很多关于卡尔的细节，太震撼了。小时候我也想要走很远的路 去很远的地方。大一点，看了《阿甘正传》更是对他一直跑一直跑的故事有点痴迷。

就讲讲我去过最远的地方吧。应该是南太平洋的岛。我穿着拖鞋，坐上飞机，从澳洲出发一直往东，追着太阳跑，飞在南太平洋上，我看见太平洋很宽也很平静，金光闪闪，也一瞬间想过掉下去死定定，澳洲航空的飞机还破破旧旧，也没啥吃的，空姐都是阿姨辈，我还想了我们国家什么时候可以阿姨做空姐，多好。很久很久，慢慢的出现一个接一个海中的岛，颜色从外围开始，碧绿的深绿的浅绿的一圈一圈。我看得见海浪，像白色的线。

机场非常简单，下地后发现椰子树很多，各国的旅行者，大家很礼貌，但是却隔着距离。我总是被认为是日本人，也许是中国人不多，看见我们这样的默认日本人，这是为啥，我也没想通？海岛比较落后，公交车很挤，热，下车需要拉窗户旁边的一根铃铛线……土著人很可爱，物价居然不便宜，我吃到了超级贵的一碗米饭，忍了，也得吃饭啊，米饭难得啊。毛姆《月亮与六便士》里面男主离开了伦敦到了南太平洋的塔希提岛（大溪地），原型是画家高更了，也算追剧了。

感受是赤道附近紫外线太厉害，随便什么样的防晒也是脱皮。在海边捡海带挖螃蟹，好像也差不多，哪里的海都这样。不会水，各种水的项目，在哪里的海都是只能看着，只能泡在游泳池里面。再远的地方，也需要吃饭睡觉，还在地球上，没离开。

感觉是算是去看了一次吧，太平洋中心是这样的。还遇见了刚刚台风吹过不久，风神很厉害。看多了海，后来厌海好多年。晕船很厉害，根本受不了海里面的颠簸，扛不住。

分享一个我去追剧的故事，再看着这个走了28年的故事，别人太震撼了。也算帮我们普通人实现了人生梦想吧，能活着走完这么长的路，太好了。

如果问我，想不想再去一次那么远的地方，我应该不想再去了。大概觉得都是海，飞不出地球。

一方面太劳累，飞好久，还有坐船，太颠簸。二来外国人多，大家总是隔着隔着，我也不懂为啥。土著蛮好的，洋人也有好的，就算能交流也没法深度交流，深度一点就要谈信仰了，懂圣经了，哎，不太行，不懂的。（今年在三亚，我们遇见蛮多俄罗斯家庭，我们很热情给他们讲英文，他们真的一点反应都没有。简单的英文怎么也会吧，就是拒绝交流。俄国人这个样子，罢了），就在自己国家好舒服，没有跨文化交际障碍。第三 大概就是天底下到哪里，到了天边，都需要吃饭休息，心安处，都是好地方。不用使劲要跑远了。气候条件有些地方很不行 医疗卫生条件也不行，甚至人生安全也是问题。所以走28年的，真的是放弃了普通人生，那生命去体验。很厉害的，道路又长又艰苦还险象环生，太厉害了。

先说结论：skill 的消耗不在于你「用」了多少，而在于你「装」了多少。装进去的那一刻，账单就开始计时了。

这话不是我拍脑袋说的。前几天跑完一个长任务，顺手翻了下 agent 的 token 统计面板，几个数字摆在一起，看得我有点沉默。

## [](https://lichuanyang.top/posts/48213/#一次实测：只加载了-1-个-skill，账单长这样 "一次实测：只加载了 1 个 skill，账单长这样")一次实测：只加载了 1 个 skill，账单长这样

先看任务整体的账。这个任务跑下来，总用量 184.4M token，1.84 亿。其中工具结果 87.1M（47.3%）、助手消息 84.9M（46.0%），这两块是大头，符合直觉：长任务嘛，工具来回调、模型来回写，钱主要花在这儿。

![Token 统计：总用量 184.4M，技能注入累计约 4.2M 占 2.3%](https://lichuanyang.top/img/skill-token-total.png)

然后看 skill 相关的那一行：**技能注入（累计）约 4.2M，占 2.3%** 。

4.2M 是什么概念？放在 1.84 亿里是 2.3%，确实是「说少不少，说多也不多」。但先别下结论，看看这 4.2M 是由什么叠出来的。

![当前上下文：467.6k / 1.0M 已用 46.8%，技能注入约 7.5k 占 2%](https://lichuanyang.top/img/skill-token-context.png)

任务结束时，当前上下文 467.6k / 1.0M，用了 46.8%。里面技能注入约 7.5k，占 2%。注意，这 7.5k 是单轮快照，每一轮都在。累计的 4.2M，就是这种东西乘以五六百轮叠出来的。

那这单轮 7.5k 里装的是什么？展开看：

![技能注入明细：4 项共约 7.9k，三次 skill-catalog 目录更新加一次 impeccable 技能加载](https://lichuanyang.top/img/skill-token-inject.png)

4 项注入里，3 项是 skill-catalog 的目录更新（1.3k、1.7k、2.0k），只有 1 项是真正加载技能正文：`Skill: impeccable`，2.9k。

把前提摆清楚：**这个环境里安装了不到 20 个 skill，整个任务全程只加载了 1 个。** 就 1 个。剩下的消耗全花在「目录」上：agent 要把「我有哪些 skill 可用」这份清单带在上下文里，装得越多，清单越长，固定开销越大。说白了，你用一个 skill，付一份钱；你装二十个 skill 只用一个，付的是二十个的目录钱，再乘以轮数。

## [](https://lichuanyang.top/posts/48213/#外推一下：无限制安装会怎样 "外推一下：无限制安装会怎样")外推一下：无限制安装会怎样

把账算明白只需要小学乘法。

目录里每个 skill 占一行名字加描述，粗算 50–100 token。20 个 skill 的目录约 1–2k token，和我实测里一次目录更新的体积（1.3k–2.0k）对得上。那如果像很多人一样，随手就装几个skill，装到一两百个呢？目录本身一轮就是 10k–20k token，雷打不动；一个任务跑几十轮，几十万到上百万 token 纯交给目录。

token 账单还是小事。真正贵的是另一笔：候选清单越长，模型挑错 skill、或者干脆漏掉正确 skill 的概率越高。就像在一箱别人的工具里翻自己的扳手，工具越多，翻错的那次越致命。skill 本来是来省 token、省口水的，装多了反而变成每轮必缴的税。

所以别纠结「skill 有没有用」了，真正的问题是「安装」这个动作本身太粗糙。npx 一条命令全量推给所有 agent，爽是真爽，账也是真账。我想要一种极其简单的方式，对 skill 做精细化管理：平时收在库里，哪个 agent、哪个项目需要，再投哪几个过去。

## [](https://lichuanyang.top/posts/48213/#flint：把-skill-当资产管，而不是当插件装 "flint：把 skill 当资产管，而不是当插件装")flint：把 skill 当资产管，而不是当插件装

这个需求我自己解决了一下，就是 [flint](https://github.com/lcy362/flint)（`local-skills-hub`）。之前写过一篇《[Flint：让 skill 成为个人资产](https://lichuanyang.top/posts/29684/)》讲它的设计哲学：local-first、数据主权、skill 只是磁盘上的普通文件。这篇不重复那些，只讲它怎么解决「按需开启」这件事。

核心思路一句话：**归集一次，投放按需。**

归集。所有 skill 的本体只存一份，放在你自己的仓库目录里，就是磁盘上一个普通文件夹，git 想怎么管怎么管。散落在各个 agent 目录里的、从第三方 npx 装来的、从别的目录导入的，flint 都能收进来：同名自动去重，来源分歧在 Health 页列出来一键修。收完之后，agent 目录里不再是各自为政的副本，而是指向仓库的软链。

投放。这是解决 token 问题的关键一步。flint 里有个「预设（Preset）」：一个 skill 包，成员可以是显式指定的几个 skill，也可以是「带某标签的全部」。然后到 agent 详情页，选一个预设，点「Apply preset」，**只有这个预设里的 skill 会被部署进该 agent 的 skill 目录** 。没链接预设的 agent，一个 skill 都看不到，目录注入自然是零。

换句话说，agent 上下文里那份 catalog 清单的长度，从此由你决定：写博客的 agent 只挂写作相关的三五个 skill，目录就只收三五行的税；跑前端任务的 agent 挂 impeccable 那一批，互不干扰。想换组合？改预设成员或标签，再点一次 Apply，完事。

智能体管理。flint 的 Agents 页按「实际 skill 目录」出卡片：多个 agent 共用一个目录就合并成一张卡、共用一套策略，不会给你演出「改了 A 发现 B 没生效」的戏码。每张卡上能做的事：启用或停用、覆盖目录、从库里逐个加 skill、套预设一键部署、单个 skill 选软链还是拷贝。目录里物理上有什么，agent 就看到什么，没有后台偷偷同步的玄学。

这套组合拳打下来，「装了 200 个 skill」和「这个 agent 能用 5 个 skill」就彻底解耦了。库可以无限大，税只按投放的交。

## [](https://lichuanyang.top/posts/48213/#顺便提一嘴：flint-还能干什么 "顺便提一嘴：flint 还能干什么")顺便提一嘴：flint 还能干什么

按需投放是主线，但归集和投放这两层搭好之后，剩下的功能基本是顺出来的：

  * Projects：给项目登记路径加标签，标签就是部署策略。匹配的 skill 进项目的 `.agents/skills`（可以跟 git 提交），再软链共享给各 agent 的项目级目录。换机器，项目自带技能包。
  * Health：六维体检（同步状态、重复、断链、配置、仓库、项目），问题列出来，一键修之前先让你确认。
  * npx 安装托管：把 `npx xxx skills install` 这类命令贴进去，flint 在受管目录里跑（自带 git 快照可回滚），装完直接进正常注册流程；更新就是源卡片上一个按钮。
  * 标签与元数据：标签优先写进 `SKILL.md` 的 frontmatter，就是 Claude Code 等 40+ 工具原生能读的那份；没回写的先在本地暂存，一键迁移。

安装就一行：`npx flint-skills-hub`，然后开 <http://localhost:8787。没有云、没有账号、没有遥测，skill> 是你磁盘上的文件，flint 卸了它们也在。界面中英可切换，日志可下载，都是顺带的手尾。

## [](https://lichuanyang.top/posts/48213/#回到开头那组数字 "回到开头那组数字")回到开头那组数字

1.84 亿 token 的任务，skill 注入累计 4.2M，占 2.3%。单看比例确实不能算多。但别忘了前提：这是个只装了不到 20 个 skill、全程只用了 1 个的环境。

skill 这东西，价值在「复用」，成本在「常驻」。管理方式粗暴一点，成本就常驻给你看。

所以下次手痒想 `npx` 全量装一套技能包之前，先问自己一句：这二十个 skill，我这个 agent 真用得上几个？

想清楚再装。或者干脆别装：归集进库，按需投放，让目录永远只留真正干活的那几个。

OpenAI 的 Tibo 连续更新 28 天的活动，按美西日期从 10 月 5 日持续到 11 月 1 日，北京时间 11 月 2 日结束。期间既有模型和功能更新，也有性能优化及额度重置。

图注：中文译文卡，非原帖截图。第 28 天的公告以“Banked 2/2”为题，为连续 28 天更新收尾。

来源：[Tibo／X 原帖](https://x.com/thsottiaux/status/2117035794678546764)。

这篇结合发布信息，回顾上下文、任务执行、缓存、模型及使用额度几个方面的主要变化。文中涉及的性能和用量数据采用官方公告口径，并非逐项实测结果。

## [](https://xilidou.com/2026/11/04/openai-28-days-updates-review/#一、扩大上下文并减少任务中断 "一、扩大上下文并减少任务中断")一、扩大上下文并减少任务中断

Sol 在 Codex 和 Work 中的默认上下文，从 272k 提升到了 500k，还可以手动调整到最高 1M，订阅使用没有长上下文附加费。

图注：中文译文卡，非原帖截图。第 7 天公告将 Sol 在 Codex 和 Work 中的默认上下文提高至 500k，并说明订阅使用不收取长上下文附加费。

来源：[Tibo／X 原帖](https://x.com/thsottiaux/status/2109430343346581527)。

更大的上下文窗口，可以容纳更多项目文件、表结构、测试代码和此前的讨论。对于涉及多个模块的任务，模型有机会同时参考更完整的材料，用户也可以减少拆分和重复提供背景信息的次数。当然，窗口扩大之后，仍然需要选择与任务相关的材料。

速度方面，官方宣布 Astra 和 Sol 在订阅中的默认生成速度提升约 50%。这里指的是模型生成速度，不能直接换算成整个开发任务的耗时，因为读取文件、执行工具和运行测试也需要时间。后续的算力和系统调整，则用于减少 model at capacity 错误，并在遇到这类错误时自动继续任务。

Instant steering 改善了任务执行中的交互，体验上更接近 Claude Code。用户中途补充要求或纠正方向后，Codex 能更快调整后续操作，减少继续执行原方案造成的浪费。桌面线程支持编辑之前的消息，方便修正已有指令。

Auto-review 处理的是操作权限。Codex 执行某些命令或申请权限时，需要先经过审批；Auto-review 会让另一个 AI 检查这些请求，符合条件的操作可以直接放行。活动第二天宣布，使用 ChatGPT 账户登录的用户可以免费使用这部分功能，不消耗订阅额度。它审核的是操作是否应当获准执行，代码质量仍然需要通过审查和测试确认。

这些更新减少了任务执行过程中的中断，也减少了用户等待和手动确认的次数。

## [](https://xilidou.com/2026/11/04/openai-28-days-updates-review/#二、减少重复计算，提高额度利用率 "二、减少重复计算，提高额度利用率")二、减少重复计算，提高额度利用率

缓存是这轮更新中持续调整的一部分。

同一个任务的多次请求，往往包含大量相同的背景信息。对于保持不变、能够匹配的输入前缀，缓存可以复用此前的处理结果，减少重复计算。

这轮更新先后涉及跨 subagent 复用上下文、延长缓存保留时间，以及通过路由调整提高缓存命中率。多个子任务使用相同背景材料时，可以减少重复处理这些材料的开销。

随后，API 增加了 12 小时缓存选项，已登录的 Codex 和 Work 用户恢复旧会话时，缓存命中也得到改进。另一项调整是，在对话中途改变推理强度，不再使缓存失效。用户可以根据任务需要调整模型的推理投入，同时保留已有缓存。

上下文窗口决定一次请求能够携带多少材料，缓存影响相同材料需要重复计算多少次。这些更新可以提高额度利用率，但缓存不等同于长期记忆，也不会让模型无限保留历史内容。

讨论 AI 编程时，模型能力通常最受关注。实际执行任务，还需要 harness 组织上下文、调用工具、处理权限，并在发生错误后恢复执行。长任务能否顺利完成，与这些环节的实现同样有关。

## [](https://xilidou.com/2026/11/04/openai-28-days-updates-review/#三、模型更新与-dot-使用入口 "三、模型更新与 dot 使用入口")三、模型更新与 dot 使用入口

这 28 天里，GPT-6 进入了 Chat，GPT-6.1 Terra 也重新发布。前者属于 Chat 的更新，并不代表当天 Codex 的底层模型也发生了相同变化。

Terra 的官方介绍重点提到写作、语气、对细微要求的理解，以及 computer use。同时，官方表示，相比 6.1 Sol，Terra 在 API 和订阅中可以提供两倍用量。这些是发布时给出的能力描述和用量口径，具体任务中的表现仍需要实际验证。

dot 的使用入口也有所增加。用户可以在 ChatGPT 手机 app 中创建并通过文字联系 dot；之后又增加了通过 iMessage、RCS 发送文字、图片和语音的方式。后者当时面向美国 Pro 用户提供预览。

## [](https://xilidou.com/2026/11/04/openai-28-days-updates-review/#四、订阅额度调整与-14-次重置公告 "四、订阅额度调整与 14 次重置公告")四、订阅额度调整与 14 次重置公告

第 25 天，OpenAI 宣布调整 Pro 和 Business Premium 的使用额度。

按照官方帮助页，Pro 100 和 Pro 500 的 Work、Codex 额度翻倍；Pro 200 原先较低的额度翻倍，原先较高的额度保持不变，此前预告的下调取消。Plus 不包含在这次调整中。Tibo 的公告还提到 Business Premium 额度翻倍，并暂时继续提供 dot 的扩展额度，dot 用量仍单独计算。

图注：第 25 天额度调整公告的中文译文卡，非原帖截图。不同套餐的调整方式，以正文说明及官方帮助页为准。

来源：[Tibo／X 原帖](https://x.com/thsottiaux/status/2115850175868727621)；[Pro 套餐额度说明](https://help.openai.com/en/articles/9793128-about-chatgpt-pro-tiers)。

此外，28 天中共有 14 次重置公告，分为 11 次即时重置和 3 次可保存的重置机会。即时重置分别出现在第 2、6、8、10、13、15、17、18、20、21、23 天；可保存的 banked resets 出现在第 3、27、28 天。其中，第 2 天和第 18 天同时包含功能更新与重置，因此不能把“更新日”和“重置日”简单划成互不重叠的两组。

图注：11 次即时重置与 3 次可保存的重置机会。此图按活动公告原创整理，不代表每个账户的实际到账次数；第 25 天的额度调整不计入重置。

来源：依据 [Tibo／X 活动公告](https://x.com/thsottiaux)原创整理。

banked reset 是可以先保存、之后使用的一次性额度重置机会，与当天直接重置额度不同，也不属于永久增加额度。有效期和适用条件，需要以具体发放说明为准。上述次数统计的是活动公告，并不代表每个账户都获得了完全相同的权益。

## [](https://xilidou.com/2026/11/04/openai-28-days-updates-review/#五、同期增加的-API-credits "五、同期增加的 API credits")五、同期增加的 API credits

10 月 28 日，OpenAI 还公布了 Pro 订阅附带 API credits 的安排：Pro 100、Pro 200 和 Pro 500 每月分别提供 100、200 和 500 美元的 API credits。

这项权益需要激活，首次激活时按当前订阅周期的剩余时间折算。额度在对应周期结束时失效，不会无限累积。它用于 API 调用，应与 Work、Codex 的订阅使用额度，以及一次性的重置机会分别理解。

这项公告与活动第 24 天处于同一天，但 Tibo 当天编号帖的主题是通过 iMessage、RCS 联系 dot。因此，API credits 属于活动期间的同期更新，不应写成第 24 天编号帖的内容，也不计入上述 14 次重置。

回顾这 28 天，更新涉及模型、任务执行和使用资源三个方面。更大的上下文增加了单次任务可携带的材料；缓存、审批和恢复机制减少了重复计算及执行中断；订阅额度、重置机会与 API credits 则分别增加了不同场景下的可用资源。将这些变化区分清楚，才能判断具体套餐和工作方式能够从中获得哪些改善。
