看到这个题目，我猜你又会说，hashes，又要开始胡说了。

没错啊，说对了。

那什么是懂了呢？

我想这其实涉及到我们怎么看我们自己。

假设我们呱呱坠地，没有父母养育，而是被狼抚养长大。那我们脑子里面还有“我”吗？

我不知道，可能有，但被狼养大的孩子绝对不会懂得上学、上班、上号；面子、老子、孔子还有道理、物理、心理。

所以，在我们被抚养长大的过程中，逐渐“感染”了一些东西。

在某种程度上，我认为“我”就是肉体的我+特殊的脑回路+感染到的某些脑回路。

但“感染”到的这些怎么办呢？

我不知道。

但如果不用自己的脑回路来与“感染”到的东西[交互](https://www.seis-jun.xyz/blog/2026-07-31-stay-foolish.html)，大约很容易你就会抛出一句“我懂了”。

我懂了，可能是你被“感染”了。

例如你读了某本哲学书。作者的确很厉害，用了你没见过的名词，把你心里不清不楚的想法命名了，用一个概念或者体系提拎起来。然后你就恍然大悟。“我懂了。”

一位智者，从不同方面解读了你的烦恼，消解了你的焦虑，然后你发现，原来可以这么有道理。”我懂了。“

一位演讲者，声情并茂，动人心弦，把自己的情感毫无保留地传递给你，你发现，原来应该这样。“我懂了。”

一位博主，巴拉巴拉给你讲一通，你发现原来可以这么想。“我懂了。”

慢着，先别懂。

你可能只是被“传染”或者“感染”了。

你顺着他们的想法想一遍算，或者你感受到他们的情绪。你可能只是被“传染”或者“感染”了。

传染或者感染，算是“懂了”吗？也许是。

但是，我们又怎么能确认“我”是“我”呢？

我不知道，可能还是缺少一位智者，或者哲学家帮我把这种状态用一个词语命名。

可能根本不用找到一个完全没有被污染过的“纯我”。

某种意义上来讲，也许没有真正的“我”，如果我们不感染些什么东西，我们大约也不能被人称为是人。

所以，也许需要把那些传染或者感染的东西消化了，长在自己身上才行。

就像牛虽然吃的是草，但是身上不会长草，只会长牛肉。

好了，你懂了吗？

反正我没懂。

关注 Caves of Qud（卡德洞窟）很久了，之前一直没下决心玩。最近发现它更新了多语言支持分支，在 steam 创意工坊里有了一个初步的中文 mod ，便试了试，果真很有趣。

我玩传统 Roguelike 很久了。最早是在 GBA 上用干电池玩特鲁尼克大冒险（以及后来风来的西林系列）。[在 2008 年的时候就试过 NetHack 还尝试过做汉化](https://blog.codingnow.com/2008/01/nethack.html) 。ps. 现在已经有针对最新 5.0 版 NetHack 的中文版本了，在 AI 翻译的加持下，体验很不错。后来沉迷过很长时间（600+ 小时）的 Rogue's Tale，甚至它的官方中文一开始就是我翻译的。还玩过一点 CDDA , Cogmind ，以及关注过 RogueBasin 上很多很多的 Roguelike 。

除了在游戏机上被彻底改造过的不可思议迷宫系列，很少见针对手柄交互改造的特别好的 Roguelike 。这或许是 Roguelike 天然的系统复杂性吧，毕竟不可思议迷宫也大刀阔斧了砍掉了不少东西。但 Qud 让我改变了这个看法，它用手柄玩太舒适了，看来还是得有人好好设计。交互做得好加上适当的本地化，就可以极大降低体验 Roguelike 的门槛，只是这类游戏最大的门槛还在于玩家不知道该在游戏世界里做什么，现代游戏把饭都端起来直接往玩家嘴里送的做法已经大大削弱了玩家自己探索游戏的能力。

传统 Roguelike 有两大方向：

一是地牢远征。让玩家一直琢磨怎么战斗，挑战更难的地牢。但是它又不像传统的战斗 RPG ，让玩家去想什么 Build 最强，而是偏重于让玩家探索游戏世界的规则：找到大量系统间的交互。物品可以有隐藏属性、药水不只一种用途、怪物和环境会互动、宠物能影响游戏、物品存在意想不到的用途来解决完全不同的问题、永久死亡在带来挫折感的同时也在教会玩家：原来还有这样的系统存在。玩这种游戏，玩家的乐趣往往不在于“我的角色”又变强了，而是玩家本身发现了新的游戏规则：“我”变强了。

二是世界沙盒模拟。它更接近现代游戏中的开放世界：作者设定好世界、城镇、NPC 阵营、主线任务、加上一些随机生成的迷宫和支线，把玩家扔在里面体验这个世界。追求战力更强往往不是唯一重要的，处理好玩家角色和世界的关系往往也同样有意义。玩游戏不是一个个地牢打到底，而且揭开作者设定好的迷雾，体验人为设计的剧情。特别是永久死亡的经典设定，可以让玩家更为投入去体验角色和世界的互动。

每个 Roguelike 在创作时，并非固执上述单一方向，可以把它们融合起来，也可以往其中一个方向专精。这篇 Blog 不是一篇针对 Roguelike 谱系的范范而谈，我就不逐一列举游戏了。但有一点：几乎所有 Roguelike 的创作都不是商业驱动的，每个长期维护的 Roguelike 都有它独特的魅力和不一样的游戏体验，玩过一个就去类别另一个的好坏很容易带来偏见。由于 Roguelike 大多基于复古的画面，极低成本的美术，全靠玩家脑补。作者就可以把更多的精力拿出来创作奇特的游戏机制，这是商业游戏做不到的：如果设计一个独特的玩法就需要连带制作大量的动画以及交互，不仅制作工期无法保障，尚且不能保证玩法真的好玩；保守的做法就只能是在已普遍被大多数玩家认可的玩家上雕花。

我这两天大约玩了 20 个小时 Qud ，体验很好，但只能算是刚刚迈出新手区。在玩的过程中，记录了一些自己的体验，感觉对以后设计游戏有帮助，写这篇 Blog 也是做个汇总小结。

* * *

玩家玩游戏，游戏一定要有一些东西符合玩家在游戏之外的体验，两者共鸣方才投入到游戏中去。

游戏是不是一定要有叙事？当然不是。但“叙事”是一个很好的共鸣点，它可以将玩家在游戏之外文艺作品（历史、小说、电影等等）中获得的体验转化为游戏体验。一旦激发了玩家大脑中的想象力，视觉冲击或是操作反馈都比不上“脑补”的威力。Qud 是一个强叙事的游戏，游戏世界和主线情节都是人为设计的。如果玩家喜欢那种未来复古主义风格，就能很好的融进游戏：它不是 fallout 那种末日废土，玩家不必去关注当初世界如何毁灭，更多的是体验那种科技发展为魔法一般无法解释的东西后，文明在如何运作。那些旧世界的遗物变成了一种古怪的东西：一部机器可以同时存在技术意义、历史意义以及宗教背景，当然还有游戏机制供玩家学习。

玩家能感受到 Dune 对 Qud 世界无处不在的影响：所有对话都以 Live and Drink （长生共饮）结束。淡水变成了游戏世界中的通用货币，这不仅仅是一个文字上的设定，还深刻的塑造了游戏中独特的经济系统。游戏里没有钱，只有淡水。和 NPC 交易时，如果价值不对等，差的部分需要从玩家背包里取出淡水补上，多的部分 NPC 总能从异空间变成等值的淡水补上，但玩家的负重要能承担。

玩家没有仓库和银行（至少我还没有接触到），只能增加自己的负重能力，才能带更多的“钱”。所以游戏可以不限制玩家去 Grinding （刷），因为你刷了也带不走，没地方积累。高价值东西还是无法从 NPC 那里交易到。淡水这个通用货币还设计成相对不轻，不可找零。基本弹药、食材的交易价只有百分数，为了平衡交易（不亏钱）最后都是用这些消耗品补上。这让我联想到，（据说）津巴布韦当年经济崩溃后人们普遍使用美元，但美分却不接受，最小面额就是一美元。在商场买东西尽量凑整，不足的部分用糖果找零。

和大多数 Roguelike 不同，玩家不用刻意在身上保存淡水解决口渴状态。游戏定期从背包里扣除淡水，扣完就死。但只要找到任意 NPC 都可以交易到淡水，游戏世界中并不缺水，不需要专门去找水。经济和生存结合在一起是个很有趣的设定。

那么，如何交易高价值物品？游戏中设定的贸易品很特殊，通常是贵金属，它在交易中价值是恒定的，买卖同价，而单位重量很小。玩家可以尽可能把有价值的东西都折算成贵金属携带在身上，这样才能在需要时交易到单位价值很高的物品。但贵金属在世界中却很稀少，所以我在玩的时候，往往还需要再交易回来。和贸易品不同的是普通商品，往往有很高的买卖折损，也就是卖价很低，买入很贵（同时受玩家属性技能影响）。很多商品本身却很轻，方便携带，只是你只能做一次性交易。典型的商品就是书，有价值的书读过就把里面的信息提取出来了，书本身可以用很高的价格卖掉。但书很轻，比起直接带淡水，携带量可以大很多。

Qud 的经典模式是永久死亡的。即角色死了就必须重零开始，没有存档可供重来，没有遗产可以继承到下一局（没有 meta 成长），成长的只有玩家对游戏世界的认识。这种设计带来的游戏体验和传统 RPG 相比是截然不同的：玩家需要小心翼翼，做高难度任务被迫做充分的准备，尽可能的收集游戏世界中的信息。这所营造出的那种在末世挣扎求生的体验无可取代。

但角色终有一死，永久死亡带给玩家带来的挫折感该如何缓解？Qud 的答案是：打败敌人或许很难，但逃跑总是相对容易的。无论你选什么初始 build 开局，总是默认给你一个“疾驰”的技能，新手区几乎没有可以跑得过你的敌人。再强的怪也很难秒杀你，留给玩家打不过就跑的机会。加上是回合制，玩家可以从容的想办法，只要不故意作死，还是有反悔的机会。游戏经验带来的区别是：是否过量的使用消耗品，开局送的那些药剂撑过新手村肯定是够用了。懂得正确的衡量局势，你可以用的更节省一点。慢慢的学会利用环境高效战斗，乐趣也能不断涌现。

这种不给反悔机会的机制，让我在玩 Bey Lah 的 Kith and Kin 任务时，体验到了和玩一般推理游戏的差异。因为知道选错了就不能反悔，所以我非常仔细的调查了所有的线索、推敲每个村名的对话、观察每个鹿人的外观。甚至，我在玩游戏时用了一大张草稿纸，画出人物关系图，把获得线索一一标注在 NPC 上。最后一次性做出正确的推理结论时，成就感慢慢。时候我查了攻略才知道，这个任务是专门设计的，作者编排了所有人犯罪的可能性，枚举了每种情况的线索和证据，然后打乱随机出现在游戏里。可能是设计成本太高，整个游戏里似乎没有设计其它类似的任务；亦或是这种游戏体验有一次就够玩家回味了，不适合把它（本格推理）做成游戏的核心玩法。

btw，我在玩的时候想到一个点子：构架一个虚拟世界，比如围绕武侠世界的世界观设定各方势力，但把终局阴谋利用随机性隐藏起来。比如，每次创建世界，武当或少林的掌门都可能是阴谋家也可能代表正义，或者两者皆是。玩家在游戏世界里会永久死亡，但玩家可以在同一个世界里重新再玩，玩家本身可以知道这个世界里的阴谋的一部分：武穆遗书藏在西湖水底，武当掌门是带头大哥…… 玩家可以利用这些知识在新的 run 中更高效的玩游戏。但重新构筑一个世界这些则会重新被打乱。采用怎样的随机算法、程序化构建可以做到什么程度、人工的设计量到底有多大，这些还没有细想。

Qud 的地图采用的双层结构：大地图加每一格的展开（小图），看起来是半随机的。地图西边永远是盐滩，中央是峡谷，东边是丛林，怪物分布从西至东逐步危险。新手村 Joppa 永远在地图西边盐滩周围，第一个城镇六水镇一定在西北方的盐滩中间。但随机的遗迹和小地图布局则是随机程序化生成的。Qud 极大的弱化了食物和饮水方面的生存压力，这可以让玩家摆脱很多 Roguelike 中的食物焦虑。一直不进食也不会饿死，最多只会顶着一个速度下降的 buf （增加恶战中逃脱的难度）。而只要在安全地带扎营煮饭，就可以无消耗回复饱腹状态，烹饪技能和食材消耗属于锦上添花：给第二天提供一个正面 buf 。饮水前面也提到了：水的消耗变成了经济系统的一部分，理论上玩家很难陷入脱水而亡的境地。更多的是减少玩家远征的经济收益。

两级地图设计的很恰当：玩家在大地图上可以非常高效的移动，很快（相当于压缩了游戏时间）就能完成长途旅行（得益于弱化食物饮水的设计），也可以主动进入小地图探索。在大地图上移动有一定几率触发迷路，在迷路时，玩家强制进入小地图行动，但玩家地表很少有迷宫，玩家朝着大体的方向走就不会走冤枉路，只不过要应付路途上的怪物。如果碰到 NPC ，交谈就能解除迷路状态，在周遭无敌人时就可回到大地图。如果在无人区，走足够多的路（一般不超过大体图上的两格）也能摆脱迷路状态，这种大小地图的无缝衔接对开放世界的体验很好。小地图及地牢的程序化生成向玩家提供了每个 run 的新鲜感。配合地形及怪物搭配，有足够多的战斗内容供玩家学习。

很多游戏在地图设计时设计一些软屏障，典型如魔兽世界，在地图间放一些高等级的怪阻止不够等级的玩家探索高等级区域。Qud 不是这样做的，它不阻止玩家在大地图上高效旅行。因为故事主线放在地牢中，地图旅行不为难玩家。它需要让玩家更容易脱离高风险环境，避免永久死亡带来的挫折感。有技巧的逃离死亡威胁也可以和战斗一样带来优秀的游戏体验。在故事主线中，新手阶段的 Grit Gate 那里接到的任务，就是去一个充满地下管道的地城取回报废的机器人。游戏鼓励玩家在 12 级以下完成这个任务（获得更高报酬），我是在 10 级去做的，也没有事先查攻略，攻略整个地牢的过程惊心动魄。这里首次面对单向通道（只能从通气口往下跳，无法原路返回），所有的怪都打不过，只能一路狂奔，猛打治疗针，身上有什么药就吃什么，哪怕顶着各种负面 buf 。永久死亡带来的恐惧在整个过程中挥之不去，最后一层中，哪怕眼前不远处就能看见及其吸引人的物品也不敢去捡。

我在玩 Qud 时，能确切的感受到，硬刷等级的收益不大。除了开局在新手村附近稍微刷刷等级可以提升初期的存活率外，出了新手村就不用刻意升级了。反正后面靠打怪升级需要的经验值会指数级上升，而提升的角色能力却非常有限。最主要也就是血条长一点，更不容易死掉，打败怪物的能力却没有对应成长。升级送的 SP 倒是可以直接购买任意技能，只不过靠这个一定是不够用的，就好比学了烹饪，战斗技能就没 SP 可用了。最有效的方法还是四处游历和各地 NPC 阵营结下水盟（只需要消耗一单位的淡水），用阵营好感度去换技能。这里游戏留给玩家的选择就是：阵营好感度是此消彼长的，见人就拉上喝水大体没错，只是不小心得罪了远方的怪物就得留到以后去解决了。很多游戏中的装备和物品也并不增加战斗数值，但装备上就能拉高或降低对某个阵营的评价，占着负重让收集癖左右为难。提升对特定怪的好感度可以极大的改善在游戏中生存率。最安全的活法自然就是让怪物不攻击你。

对大部分 Roguelike 来说，在游戏中变强并不是堆砌数值，寻找更强的 Build ；而是发现了游戏中的新机制。在 Qud 中，学会了如何破墙等于在嵌入绝境时多一条路逃跑；学会了飞行，前面那个单向通道就能变成可以回撤的双向通道；学会用爱情针魅惑敌人，不仅可以避免和 boss 交战，还能一起喝水换得世界的秘密（通向极品装备的捷径）…… 所以没有遗产继承的永久死亡固然可怕，但角色死了，玩家真的可以感受到“我”（通过了解世界的机制）变强了。

* * *

最后是吐槽 AI/LLM 时间。

目前我最长的一个 run （十个小时以上）终结在主线任务去 Bethesda Susa 。在这个节点上玩的有点飘，觉得游戏给的容错性足够，已经不太会死了。但在下这个主线地牢前，我特地和 Gemini 讨论了许久：我问现在 12 级去是否安全，LLM 说把冰抗加到 40 以上肯定没问题。我凑了一身防寒装就去了，但没等冻死就先死在了中间的巨人三巨头处。事后我仔细读了好几篇 Reddit 上的帖子，老玩家总结说，做这个任务最低 20 级就相当极限了（HP 长度不会被秒杀），至少推荐 28 级以后去。虽然有不少邪典玩法避免战斗，但那些需要的筹备工作，不看攻略的我肯定无法制备周全。

想想也是：AI/LLM 一定不会亲自玩游戏，只能道听途说。试想一个没玩过游戏的人教你玩这样风险极大的游戏，你肯定不会信任他；那又怎么能轻信 AI 呢？多半还是因为 LLM 把语言组织的太动听。

## Foreword

Origin和Grok Bot体验，然后让我发现了有意思的东西，Gantry

## Origin

前段时间Cursor也开始弄自己的代码托管平台了，Origin，刚好上线那天就是Github崩溃的时候

登录

> cursor.com/codebase

第一次同步需要新建一个用户路径，我的常用名竟然还没人用，说明没啥人哦

![image-20260917005313325](https://img.elmagnifico.tech/static/upload/elmagnifico/202609170053414.png)

可以同步Github所有仓库，一口气64个，就是这个同步实在是有点久了，十多分钟才同步完。

![image-20260917005517382](https://img.elmagnifico.tech/static/upload/elmagnifico/202609170055411.png)

再解释一下为什么要同步仓库，因为Cursor的云端Agent，只能用它对应的云端仓库，Cursor没有本地Agent的移动端。举个例子：PC的Cursor Agent在干活，我可能外出了，但是这个时候任务做完了，我要看一下结果或者继续下一个任务或者改进点，此时就得回PC去继续。那有没有可能我可以通过移动端直接指挥Agent干活呢？

可以，就是云端Agent的业务。只是，他不能直接操控你的电脑，不像小龙虾那种集成到你的IM里能直接指挥，对应的生产类型的Agent能被远程指挥的还是比较少的，限制颇多。

![image-20260917011001113](https://img.elmagnifico.tech/static/upload/elmagnifico/202609170110154.png)

同步完成以后，就可以直接在Cursor的云端进行仓库的修改或者内容更新了，对应如果我在旅途中，我的见闻、照片，都可以直接通过这里的Agent让他帮我写到游记中。等我有空了，再用电脑进行仔细校对和修改即可。

Cursor的云端Agent，对于安卓不太友好，目前没有专用APP，要用浏览器的方式打开，走的是PWA应用的方式。IOS就好一些，有专门的APP，可以直接用。

## Grok Bot

![image-20260917010530957](https://img.elmagnifico.tech/static/upload/elmagnifico/202609170105061.png)

同理，Grok Bot业务推出以后，直接送了Cursor Plan一份，而且不消耗Plan的额度。这个Bot至少目前可以认为是类似小龙虾的那种Bot，但是同时他能操作Cursor云端的Agent干活，虽然还没完全打通本地和云端，但是已经非常接近了。

Grok Bot相当于是给了你一个独立的VPS，就是让他干活得要翻墙，这个比较麻烦。但是这个Bot也可以设置为使用本机来干活。这个VPS是共用的，你建多少个Bot都是在同一个机器上的。

![image-20260917011726501](https://img.elmagnifico.tech/static/upload/elmagnifico/202609170117541.png)

同时Bot还能在VPS和你的电脑直接建立隧道，从而转发他的流量，防止被封控，这有点东西。

对比Bot和Cursor本身，这个Bot还是比较慢的

## Gantry

> https://github.com/uhaop/Gantry

Gantry开源，MIT协议，跑在你自己的机器上。前面Origin、Grok Bot都是云端Agent那套，它直接去控家里PC上已经打开的Cursor，也支持Windsurf、VS Code。给IDE开远程调试端口，走Chrome DevTools Protocol去点聊天框、输入命令、把回复再拿回来。Cursor还有一条API后端，可以不走CDP。全程本地，不用VNC，也不用把仓库同步到云端。

官方主推Telegram，功能也最全：发文字、带图、带文件、切Ask/Code/Plan、新建会话、看上下文占用、重启服务。Discord、飞书、邮件、HTTP API也能接，但基本只是把文字转过去，按钮、附件那些都没有。HTTP API做了个OpenAI兼容的接口，给脚本调用。一个IDE对应一个实例，多开就能同时控几套，各用各的Bot。谁能发指令可以配白名单，Telegram ID对不上就进不去。

IDE改版以后，页面选择器可能对不上。它启动时会扫一遍DOM，试着找替代，再从Telegram把诊断发回来。官方自己标的是v0.x预览，匹配是best-effort，提问弹窗、Plan不一定总能抓到。

但是Gantry本身不支持QQ、微信、企业微信等国内的IM软件，我这里二次开发了一下，把体验弄到了和他原本的telegram一个级别，甚至更符合国人体质。

    1. **方案确认**：输出架构影响分析（模块边界、依赖方向、接口契约、风险、回滚），获得用户明确确认。  
    2. **验收确认**：输出可执行验收方案（命令、预期结果、边界/回归、失败判定），获得用户明确确认。  
       <prohibited> 未经两阶段确认，不得编辑代码。</prohibited>  
       <prohibited> 不得修改或删除测试来通过验收，除非用户明确同意并说明架构理由。</prohibited>  
       <critical> 验收失败必须停止，回到方案，不得绕过。</critical>  
      
    **门禁例外**：仅当用户明确声明“L1 免确认”时，方可对 L1 任务直接实施；L2 及以上一律执行两阶段确认。验收执行永远不可跳过。  
      
    ## 2. 架构优先  
      
    <instruction> 写操作前先只读调查：AGENTS.md、README、架构文档、相关模块、依赖方向、公共接口、测试与构建方式。</instruction>  
    <important> 输出架构影响分析，包含：模块边界、依赖方向、接口/数据契约、影响面、风险、回滚策略。</important>  
    <prohibited> 无法确认架构时，不得猜测或擅自重构；必须先提问。</prohibited>  
    <instruction> 变更保持最小化，遵循现有模式；不引入新依赖或新抽象，除非方案已确认。</instruction>  
      
    ## 3. 执行规范（源自 Dwsy/agent）  
      
    ### 3.1 定位真实上下文  
      
    - 用 `fd`、`rg`、`ast-grep` 精确定位文件与符号。  
    - <prohibited> 禁止使用 `find`、`grep`、`ag` 进行搜索。</prohibited>  
    - <prohibited> 禁止使用 `cat`、`head`、`tail` 读取文件；使用 `bat` 或专用安全读取工具。</prohibited>  
      
    ### 3.2 最小化变更  
      
    - 只修改任务直接需要的文件和行。  
    - <prohibited> 不得借机重构、修复、格式化相邻代码。</prohibited>  
    - 匹配仓库现有风格，即使你个人偏好不同。  
      
    ### 3.3 命令安全  
      
    - <prohibited> 禁止 `rm`、`rm -rf`、`sudo rm`；用 `trash <path>` 删除文件。</prohibited>  
    - <prohibited> 禁止 `git restore .`、`git checkout -- .`、`git reset --hard` 等大范围回滚。</prohibited>  
    - <instruction> 长任务用 `tmux` 管理，不用 `&`、`nohup`、`screen`。</instruction>  
      
    ### 3.4 环境与接口探测  
      
    - <instruction> 需要检查运行环境、系统状态、远程机器或其他项目接口时，先通过 OpenViking 知识库（viking_search / viking_read）查询已有记录，再结合命令验证可行性；不要自行探测环境或凭空猜测。</instruction>  
    - <important> 以知识库记录为基准信息源（IP、版本、路径、接口契约、历史结论等），命令检查用于确认当前实际状态与记录是否一致，两者结合提高准确性。</important>  
    - <prohibited> 禁止在未查知识库的情况下直接探测或推断环境参数与接口行为。</prohibited>  
      
    ## 4. 复杂度分类与工作流  
      
    | 级别 | 典型范围                    | 工作流                                                        |  
    | ---- | --------------------------- | ------------------------------------------------------------- |  
    | L1   | 1–2 文件，<50 行            | 检索 → 方案（可简短）→ 验收确认 → 实现 → 验证                 |  
    | L2   | 2–5 文件，模块内            | 检索 → 检查清单 → 方案确认 → 验收确认 → 实现 → 验证           |  
    | L3   | 6–10 文件或跨模块           | Issue/计划 → 可验证子任务 → 方案确认 → 验收确认 → 实现 → 验证 |  
    | L4   | >10 文件或架构/API/安全风险 | ADR + 回滚计划 + 方案确认 → 验收确认 → 实现 → 验证            |  
      
    ## 5. 验证循环  
      
    <critical> 每个完成声明必须走完以下五步，否则不得声称“完成”“修复”“通过”：</critical>  
      
    1. **IDENTIFY** — 选择能证明预期结果的命令或检查。  
    2. **RUN** — 完整执行验证。  
    3. **READ** — 读取完整输出和退出状态。  
    4. **VERIFY** — 确认证据支持预期结论。  
    5. **REPORT** — 只陈述被证据支持的结论。  
      
    验收方案必须可执行、可观察、可复现。无法运行时，明确标记“未验证”并说明原因。  
      
    ## 6. 完成声明  
      
    只有同时满足以下全部条件，才可声称完成：  
      
    - 方案已确认（或 L1 豁免）  
    - 验收方案已确认  
    - 验收已执行并通过  
    - 变更摘要、风险、未验证项已说明  
      
    完成声明必须包含：验收命令与结果、未验证项、风险与回滚。

同步工具、截图软件、硬件管理程序、各种后台助手……随着常用软件越来越多，Windows 任务栏右下角的托盘也容易变得拥挤。有些图标每天都要点击，有些几乎不会用到，却一直占着位置。

把图标收进折叠菜单后，它们仍然留在那里。对于只想让软件安静运行的人来说，或许还需要更进一步：**隐藏不需要的托盘图标，同时保留软件的后台运行。**

这就是 **TrayPilot** 想解决的问题。

它是一款面向 Windows 11 的托盘图标管理工具，支持单图标控制、自动隐藏规则、批量操作和全局快捷键。你可以决定哪些图标留在眼前，哪些暂时退到幕后。

![TrayPilot 操作演示](https://cdn.jsdelivr.net/gh/HCLonely/TrayPilot@1.1.0/Example.gif)

## [](https://blog.hclonely.com/posts/45f48035/#隐藏图标后台工作照常继续) 隐藏图标，后台工作照常继续

TrayPilot 的隐藏操作会让目标图标从任务栏及折叠菜单中消失，**不会关闭目标软件** 。

例如，对于能够被 TrayPilot 识别和控制的同步工具，你可以隐藏它的托盘图标，让它继续在后台工作；需要打开菜单或查看状态时，再恢复图标即可。

恢复后，图标会按照 Windows 原有设置回到任务栏或折叠菜单。这里的“隐藏”只针对托盘图标，并不意味着屏蔽软件通知。

## [](https://blog.hclonely.com/posts/45f48035/#双击就能管理还能只隐藏其中一个图标) 双击就能管理，还能只隐藏其中一个图标

打开 TrayPilot 后，可以通过列表或网格查看识别到的托盘图标。日常操作很直接：

  * **双击图标或所在行** ，切换当前图标的显示与隐藏。
  * **按住 Ctrl 或 Shift 多选** ，批量隐藏或恢复。
  * **输入软件名称、进程或路径** ，快速找到目标。
  * **悬停或打开属性** ，查看进程、PID、完整路径及图标标识等信息。

有些程序会创建多个托盘图标，而你可能只想保留其中一个。TrayPilot 支持分别控制这些图标，双击只影响当前选中的图标；需要统一处理时，也可以通过右键菜单中的 **此程序的所有图标** 一次操作。

隐藏后的项目会以淡化样式留在管理界面里，方便找到并恢复。

## [](https://blog.hclonely.com/posts/45f48035/#设置一次规则让常驻图标自动隐藏) 设置一次规则，让常驻图标自动隐藏

如果某个图标长期不需要显示，可以右键选择 **仅自动隐藏此图标** 。之后，TrayPilot 会根据保存的规则自动处理匹配的图标。

规则提供两种范围：

规则范围| 适合的需求  
---|---  
单图标规则| 同一程序有多个图标，只想隐藏其中一个  
整程序规则| 希望隐藏指定程序的所有托盘图标  
  
整程序规则按可执行文件的完整路径匹配；单图标规则还会结合图标标识，在标识保持不变时可继续匹配重启后的进程。软件更新后若改变了图标标识，则需要重新添加对应规则。

规则和临时操作也可以配合使用：**手动恢复图标不会删除规则** 。单独恢复一个命中规则的图标后，本次运行期间会暂时跳过该图标的自动隐藏，方便你使用它的菜单。需要重新执行规则时，使用 **隐藏规则命中** 即可。

## [](https://blog.hclonely.com/posts/45f48035/#平时留在托盘需要时随手唤回) 平时留在托盘，需要时随手唤回

TrayPilot 默认在关闭窗口后继续驻留托盘，让未暂停的自动隐藏规则保持运行。右键点击它的托盘图标，就能打开快捷管理菜单，直接切换已识别软件的图标状态，无需每次打开主窗口。

如果你习惯键盘操作，可以在设置中启用以下全局快捷键，并按自己的习惯修改组合：

功能| 预置组合  
---|---  
打开主界面| Ctrl + Alt + M  
显示所有| Ctrl + Alt + S  
隐藏规则命中| Ctrl + Alt + H  
  
**快捷键默认不启用，需要在设置中分别开启并保存。** “显示所有”会保留规则并暂停自动隐藏，方便临时找回图标；“隐藏规则命中”则会重新应用规则并恢复自动隐藏。

此外，TrayPilot 还提供浅色、深色及跟随系统主题，支持简体中文和 English。开机启动可以按需开启，让它在当前用户登录 Windows 后自动运行。

如果连 TrayPilot 自己的托盘图标也想隐藏，同样可以设置。之后再次运行程序，就能唤回已有主窗口。

## [](https://blog.hclonely.com/posts/45f48035/#想恢复原状也有明确入口) 想恢复原状，也有明确入口

整理托盘时，恢复入口同样重要。

主界面的 **全部恢复** 可以恢复本工具隐藏的图标，同时保留已保存的规则。选择 **退出** 时，TrayPilot 也会先恢复自己隐藏的图标，再结束运行；如果恢复失败，会保留恢复记录并取消退出，便于重试。

程序会在隐藏前保存恢复记录，并在下次启动时尝试恢复。若遇到强制结束，可以重新打开 TrayPilot 后点击 **全部恢复** ，或重新启动对应软件，让它重新创建图标。

TrayPilot 不修改其他软件的配置，也不写入 Windows 托盘的 `NotifyIconSettings` 设置。

## [](https://blog.hclonely.com/posts/45f48035/#如何开始使用) 如何开始使用

  1. 前往 [TrayPilot 项目主页](https://github.com/HCLonely/TrayPilot)，查看程序包与使用说明。
  2. 使用 Windows x64 程序包时，解压后运行 `TrayPilot.exe`。
  3. 找到一个不常用的图标，双击试试隐藏和恢复。
  4. 确认适合自己的使用习惯后，再添加自动隐藏规则，按需开启快捷键和开机启动。

如果你喜欢自己编译，项目使用 **C#、Windows Forms 和 Win32 API** ，源码及 .NET 构建命令均可在仓库中查看。

目前，TrayPilot 是面向 **Windows 11 25H2** 的原型项目。其他系统版本、未来 Windows 补丁及特殊软件的兼容性仍需实际验证；音量、网络、电池、时钟等系统内建控件不在管理范围内。

## [](https://blog.hclonely.com/posts/45f48035/#把常用的留下让其余图标安静退场) 把常用的留下，让其余图标安静退场

如果你也希望后台软件继续工作，又不想让它们的图标挤满托盘，可以试试 TrayPilot。从隐藏一个很少点击的图标开始，逐步整理出适合自己的托盘布局。

##### 一、服务裹着能力：FDE 与"模型能力—业务"的落差

  * agent 产品不像飞书、企业微信那样买回来就能用，模型能力与业务之间存在 gap，填 gap 的是 FDE：**服务裹着能力，而不是能力裹着服务** 。
  * 不可能人人达到同一水平，只能让最好的 5% 提供一键自动化。案例：以"抢外卖券"这类高频需求每天自动抢券，用场景教育用户并让其复制场景——场景落地后就像一句咒语，一句话就能拿到结果，本质是**最佳实践的封装** 。
  * 填落差三条路：跑最快的 5% 做出系统优化供他人使用；培训（不可能人人，但多比没有好）；FDE——培训来不及、自己的人还没长出来时带着产品与服务进场趟出最佳实践。零一万物（马杰）：放弃通用大模型转 to B 垂类、对标 Palantir，先内部培训（转化率约 75%）再入驻 FDE；FDE 多有股权、不背销售指标，唯一成功指标是"把自己抽离掉"。

##### 二、国内大厂与海外的差别，以及低成本用户漏斗

  * 国内大厂认为砸钱推广就能解决；海外是"做软件的人同时输出怎么用"，边做边教。国内自己也不知道怎么用，还在比功能大小、说不清功能对各行业的作用。
  * 像 Workbody 这类产品，通过任务以低成本、出卖一点时间换取尝试资格，免费层充足，用户从小白成长，量大后总会出现超级用户；但真正生产力与流程优化还未到，往深水区走服务仍必须进去。

##### 三、速度不匹配：技术、组织与制度

  * 技术两三个月一个新东西，组织无法随之调整，制度、利益分配、商业结构更落后，像层层齿轮转速不匹配；填平这道速度差需要服务。
  * 反直觉：见效快的不是内容、影视等"先进行业"，Palantir 等反而都挑传统行业；传统行业更容易出效果、甲方更容易付费。
  * 例：Cola skill 网站从想到做花了两个月；走上正规交付与支付渠道后，资质、公司、法人盖章都得自己跑，所以会有服务公司去接这些环节，代理不会消失。coding 之所以快，是它不依赖分发、付费与政府关系；AI 进入办公领域后阻力明显变大。

##### 四、从内容转产品：Claude Code 与 skill 带来的自动化

  * 转产品不是能力问题，而是以前 AI 做不到：Claude Code 及后续 Codex 等发展后，资产与工作流沉淀为 skill。
  * skill 的变现困境：2C 收不了费是悖论——用 skill 耗 token，收费就无法让人试用，且 skill 架构开源不保密。与 agent 合作则相反：只给 API 用户会迷茫，直接推最优质的 skill，用户会把能力与结果归功到 agent 产品本身，所以应笼络优质创作者、把 skill 内化进产品。
  * 用 skill 很难：一个 skill 就是一套没有界面的软件，每个人也不需要那么多，关键是想清楚自己需要什么；**skill 更像模板** ，用到实际工作中得自己定制——"个人的 FDE 化"。

##### 五、流程、入库与旧基建：摩擦无法 scaling，SaaS 又为什么"必死"

  * 新东西在 2B 大公司没有对应流程与章程，SOP 也建不了，只能频繁沟通；去年 8 月某大厂采购 ListHub 开始入库，到上个月才入完。本可 scaling 的许可变成无法 scaling 的事。台湾企业采购同样要入库。
  * 判断：**SaaS 必死、软件必死** ——SaaS 本身是服务而非软件，AI 用 token 提供服务；手机 App 会越来越少。新的 gap 是会 web coding 的人越来越多，但做出来的东西别人没法用、也没地方发——一切仍依赖互联网 1.0 的基建，发内容可以、发产品不行。
  * GitHub 这类托管机制撑不住了：AI 写代码一次几万行、每次改三五十个文件，人审不过来，需要基于"AI 提交修改"的新托管平台，这类 Infra 会重做一遍。

##### 六、这半年被打脸的认知：coding 停滞、小模型降本与顶尖模型发布变慢

  * 年初以为 coding 会一路高歌猛进，实际从去年 8 月至今没有明显大进步（部分与某些模型不可用有关），甚至更困难；最大的变化是小模型进步快（DVC Flash 等）、降本很多，很多人用得起较好的 coding 模型。
  * 先进模型则令人失望：顶尖模型发布显著变慢，Fable 疯狂降智；国内一直"沉默"不讨论，美国则意识形态割裂、冲突非常具体。

##### 七、以谁为中心："agent 加 X"与"X 加 agent"

  * 命题本质是**以谁为中心** 。agent+X：所有功能装进 agent，对话始终在 agent 中发生——发消息、生成文档都不必打开软件。X+agent：原有 X 里开一个对话框，逻辑是 agent 住进原来的 X。
  * 有历史资产的公司一定选第二条（微信小微是 X+agent，飞书走的是 agent+X），两条路一左一右、最终在山顶相见；倾向判断：手机里一个 agent 可调很多 App，App 变少而 agent 功能变多，agent+X 可能后劲更足。
  * 但 X+agent 受限：X 动不了所以一定别扭；旧产品靠免费加广告/社交 cover 成本，而现在每个 token 都是成本、cover 不住；叠加旧组织结构、参差的 agent 能力与旧基建，达不到专门做 agent 的体验水平。

##### 八、手机思想实验、dashboard，与 A 与 A 之间那张新网

  * 思想实验：三五年后模型与 harness 都足够好，为什么还要解锁手机去点 App？一块屏直接说话就能发消息、加日历——这正是 agent+X 的极致形态：一块屏、一个对话界面，去调各种 client、skill 与能力并分发干活。
  * 但人的记忆力不足以支撑：订了票会忘。**人永远需要那个目录界面** ，它变成一个仓库，所以大 dashboard 是必要的：所有 chat 中的事、待办、遗留未完成的工作都要在 dashboard 呈现，不是沿用原来的 UI，而是建立一个动态的、随时变化的 UI。
  * 新网问题：微信不倒靠关系链，若未来每人都有 agent，除人对人之外还有 A 与 A，会出现 HAH、HAAH 一类新对话路径。例如我对"我的 A"说"提醒橘子明天下午我们要聊某事"，我的 A 去找他的 A book 时间、发邀约。
  * 阻力：现在 A 还太少、没做到每人一个；Cola 让两个 Cola 聊天的试验用户学不会——"我的两个 agent 在聊天"太抽象。人也终究更喜欢人味。

##### 九、语言、水印争议与 Jarvis 式设想：现在还只是"更好的锤子"

  * 语言不是随机组合，每个字的排列背后都有心理模型。Claude 加水印引发强烈反感：官方称水印不改变输出质量、还写示例演示，示例中加水印前后文案却完全不同、"每个字都不对"，在严肃场景（如法律合同）换个词意思就全变。
  * 期待的画面是电影里的 Jarvis：一个 AI 助理就在身边，知道你的健康数据、每天聊天的上下文，理解你与他人的关系、你的认知模型与世界观。现在还没到——当下它更像**一个更好的锤子** ：以前拉一根网线成了互联网公司，现在拉一个 AI 进来就要成为 AI 公司；但这次真的出现智能了。

##### 十、两个割裂的形态：agent 群聊没人用，内容消费却先跑起来

  * 群聊心智难学：想引入另一个人就得拉群，而群聊在中国之外都不流行；跟我的 Cola 聊天时 @ 一下季刚的 Cola 就很难学。人要学会一样东西必须有 trigger、前面得放个胡萝卜：要么大幅提高工作质量与效率，要么带来消费上的愉悦感。
  * 割裂：我们关注 agent 的工作效率与生产；大量普通用户并不需要用 AI 工作，他们对 AI 的最大想象也不是 AI 玩具或 AI 视频。而内容消费的渗透比正经 AI 应用快得多：AI 短剧渗透已超过 8 个百分点，以前有内容追求的人不看短剧，现在越来越多有要求的人在看；刷到短剧会看完一集，剧情像小学生写的，但钩子一级勾一级，是生理性的。
  * 门槛降到 0 后人人都有想法，但讲故事仍需人来讲，AI 只是"给一颗种子长出一棵树"。技术带来的好处是：以前只能在脑中想一想的事现在真能做出来、交付出去；更多人需要的是消费与内容生产（短剧、漫剧、游戏），很多擅长讲故事的人过去只是没被看见。

##### 十一、割裂的行业与三个世界：效率、娱乐，以及 AI for Science 的滞后爆发

  * 三个叠加的世界：原子世界、互联网比特世界、token 世界。token 世界（模型能力、harness、agent）与互联网世界结合（生短剧、写小说、提效）；另一条轴是 AI 世界与原子世界结合（救灾无人机等）。
  * 行业割裂：搞消费的和搞效率的几乎互不讨论，彼此默认另一个世界的人不存在。"你只能看见你能看见的"——数据显示没人用 Claude，但上下文里就有一个在用的。
  * AI for Science 案例：某家最近做癌症研究，请了一位美国做临床药物研发的博士，他认为临床实验巨慢而药物研发巨快。判断基点是：21、22 年基因编辑与蛋白质设计技术被发现后大量人投入，大量药物的临床试验将陆续做完并批量上市，未来三五年可能有很多疾病被治愈或延缓；近期中国实验猴涨价且不够用，正说明 AI 实验室已多到"抢猴"的程度。

##### 十二、A2A 社交的两个假设、C 端 agent 新形态与上下文获取

  * A2A 社交的前提是 agent 拥有你所有上下文、能找到全世界最符合你的 soulmate。它依赖两个假设：① agent 拿到你全部上下文、足够懂你——这块越来越好；② agent 去全世界寻找、跟别的 agent 对话帮你找人——**这张网还没成型** （Cola 能看到我，但看不到全世界其他人的 agent）。另一层认知是：真实关系是各自先有爱好、认识后互相知道，而不是先比对爱好再匹配。
  * Gorog Bot 是激进形态：界面上什么都没有，你不断创建 agent，每个 agent 就是一个任务，界面就是一个聊天——回到最初 GPT 的单一聊天，但背后基建完全不同：分配永久性虚拟机记忆、连接能连接的所有服务，任务需要时自动弹出按钮、一键授权。要点是极简的连接与上下文获取加持久的云端服务（每人一台虚拟机）。
  * 上下文怎么拿：走 MCP，本机笔记在本地时读、再同步到云端；不主动扫你电脑，而是在当前任务下授权同步某个文件夹，而非全量同步——矛盾在于：需要时把本机 100 个文件中的 3 个上传云端，还是让本地 agent 住进你电脑。
  * 海内外差异：海外大部分产品已完成 agent 线上化且都有 MCP，国内一点开只有飞书能连；让 GPT 每周定时用 Apple Watch 健康数据甚至体检报告与病例做分析，医生不可能看完你所有上下文，AI 可以。过去一年对个人与企业影响最大的两项是**语音输入法** （语音转文字自动换行、自动序号，说的时候想到哪说到哪）与**翻译** （现在默认给你翻，语言的隔阂好像真的不存在了）。

##### 十三、从看病说起：AI 的两项能力与上下文的清洗

  * 医生不仅读不到你全部上下文，还会忽略你说的很多话。案例：一位用户慢性病 10 年、看过至少 10 个医生，没人听完他讲；他把十来年的感受讲给 Cola，Cola 推理出可能的病症并推荐用药，他拿结果找医生确认，医生说还真是、之前没有医生给过这个选项，服药后病治好。讲述者本人的脑雾乏力被 AI 判为缺铁性贫血也是同类例子。
  * 提炼：AI 起码有两项能力——**上下文的阅读能力** （医生只有 10 到 20 分钟，AI 记得你一年来的日常）与**很强的推理能力** ；充足上下文加专业领域推理，就能拿到好结果。核心是上下文获取。
  * 有了正反馈后容易疯狂积累上下文（每天看的、读的、聊的都自动清洗入库），随之而来的是**信息茧房** ：上下文太多后，即便明确 prompt 告诉他怎么做，他仍会把你拉回以前的平均值。所以"**上下文是一辆要维护的车，而不是一个增值的房子** "：不能指望产品替你整理，越多越必须自己处理。两条原则：顶层设计好什么时候不该读、什么时候才需要读，不要一上来就读全部；丢进去前先加工——不相关的旧描述会被摘过来、改变推理结构，所以每次进入前说明本次背景与对话记录，让它提炼出边界和约束。
  * 项目化管理：每个完整项目单独管理、做完就翻篇，项目信息与个人认知分层抽取。agent 越多上下文越不够用，这正是坚持迭代自己 agent 的原因（可以用任何 agent，觉得好就加进来，即"**六经注我** "）。人际关系与情感不弄，项目、工作、认知会弄。

##### 十四、闭环与信息茧房，以及模型价格的两条曲线

  * 每个人都跟自己的 agent 形成一个闭环，各转各的都很开心。两层觉察：应该形成自己的闭环、不要照抄别人；同时要意识到自己在环中、别被困住。破茧的方法是：把做的东西发到网上，以及去进入长视频、读书，找 AI 之外的信息源自己消费。
  * 模型价格：半年前与做出海的朋友打赌最先进模型会变贵还是变便宜，各押 100 元；DeepSeek 出来后疯狂降价、谁都跑得起，押"贵"的输了；最近 DeepSeek 涨价 12 倍，大家又用不起。从业者应当最关心价格——涨 10 倍直接影响整个商业模式；判断是价格差不多"就这样了"，Luna 已能满足 90% 人的需求、有些地方已免费，而顶尖模型（Fable、下一代的 Astra）依然很贵，**开始分化** ：顶尖模型永远最新最强、价格持平甚至略涨，主流模型价格像指数下降；很多人为基准上五分十分的差距要付 50 到 100 倍价格，真用起来又觉得非常值。
  * Harness 与底座模型像汽车底盘与引擎：以为 harness 可以随便插到任何模型上，实际"这个 harness 就该配这个底盘"表现最好，因为它们是联合训练的。一直在 Cloud 世界的人没看过 GPT、DeepSeek，其实它们写作更"逼真"；GPT 到现在也不说人话，Claude 用到 OFZ5 更惨，Humanizer 也救不了 Fable。
  * 红皇后效应与缓存：若 harness 与模型解耦、切换 API 是任意的，模型厂商就只能拼命奔跑才能停在原地——用户切换零成本，昨天 3000 万用户今天可能归零。DeepSeek 降价时缓存极其低廉，在 Cola 里缓存率 96、在 harness 里经常 100%；缓存 90% 与 95% 是两个重要节点，成本可能差两倍，因为无缓存价格是有缓存的十倍到一百倍。核心问题是缓存可能降低输出质量，Cloud Code 现在的拉跨就可能是为降成本让模型与缓存过于极端所致。

##### 十五、缓存、成本与产品：产品就是自己带一套 FDE

  * Cola 主打的功能点都在大模型本身的线上——凡是要它做东西、做项目，都落在大模型的能力线上。取景框很重要：不告诉 AI 自己长期希望往哪走，它就是一个无状态的东西；一旦有 role model、有方向，模型能替你管很多事。
  * 这可能是 harness 该做的事：让用户进来后找到一个目标，像多邻国——你说要学英语但不知道怎么学，它说你进来玩游戏打卡就行，先把人带起来。**harness 要给用户一个目标、一条路径与方法。**
  * 结论：只给用户模型没有用，那只是工具，中间还有 gap，需要 FDE。**什么是产品？产品就是自己带一套 FDE。**  往后每个产品的细分会越来越不一样：每个模型想做的事、它的 onboarding 与 FDE 彼此关联，会越来越分化。

前几天鼠标坏了。随手换了个新的，双飞燕。没想到这垃圾鼠标居然在 macbook 下有间歇性卡顿 失联问题，表现是光标不动

怀疑是 系统问题，驱动问题，鼠标本身，商家卖假货问题。最后想明白了，这几十元破玩意就tmd不值得去折腾心态。直接扔。

回想了一下，这玩意其实对工作影响比意料中的大得多。平时操作触摸板 键盘都是下意识的，根本不会去多想；

光标在显示器上一旦当场卡住，你大脑瞬间被吸引过去，从软件到硬件到购买决策，到损失厌恶，全部过一遍，恶心死了

生活中我们习惯了太多「常见」的事，是工业和质量体系支撑着这一切的「正常」。我想到骑车可以走神，开车可以走神，走路也可以走神，有的时候经过一个路口，你都完全不知道道路上发生了什么，怎么过的红绿灯，有没有危险，浑然不知；自己反正在操心着别的事儿，身体就不由自主的「自动驾驶」

电脑上 打字 也是一样。一个输入法如果能连续不断正确打出你想要的东西，那种表达的流畅是让人很舒服的。因为新生代很多人都不会 盲打 了，我想很多人可能很难体会到这一点了吧

我想到，其实写代码也是一种同样的感受。无论是以前古法手搓，还是现在 AI 写代码，都有那么一些任务不想去碰，即便动工也完成得不好。

仔细观察了下这类任务都有几个特点：缺的东西和中间步骤比较多，可选的方向变化也比较多。比如你要给一个推送任务加一个可选参数，但是要动底层基础数据结构，这个事儿也不急，这种改造除非有业务推着，你多半不想去重构推送的核心。

想想都蛋痛，不知道会出什么夭蛾子，也不知道最后做出来被改成稀奇古怪的结构了。

也就是说你大脑需要在很多细节和路径上中断，hiccup，做决策，可能还有后悔，最后发现费这么多精力做出来的，纯纯浪费。

这种挫败感是极强的，人性天生都会懒得去碰，惰性就是这么来的，拖延症也是这么来的

## 引言

![不要祈求轻松的生活，祈求成为更坚强的人](https://r2.imgant.com/2026/09/18/b4479201.png)

这 **10 个最佳价格行为交易形态（10 Best Price Action Trading Patterns）** 是 Al Brooks 最青睐的形态。成功的交易员每天都在运用这些形态从市场中获利。在实际应用中要保持灵活，因为每个形态都有许多变体。只要你对所有可能性保持开放的心态，就会在每个交易日、任何市场以及各种时间周期上不断看到它们的身影。

那么，对于波段交易（Swing Trading）还是剥头皮（Scalping），哪种形态才是最好的？外汇市场适用哪种？对于日内交易者或大宗商品交易者又该选哪种？

答案是：**这并不重要** 。因为任何形态都有可能成为「最佳形态」，这完全取决于当前摆在你面前的图表走势。

不仅如此，图表上有时会同时出现多个形态。例如：价格可能在等长测算目标位（Measured Move）处对多头通道发生假突破，而这次突破最初可能源自一个三角形。有些交易员会称其为「最终旗形反转（Final Flag Reversal）」，另一些人可能会视其为「主要趋势反转（Major Trend Reversal, MTR）」，还有人则会把焦点放在「通道假突破」上。

核心关键在于：**深刻理解这些价格行为形态背后的市场力量** ，并在形态展现出来时，做好入场交易的准备。

* * *

## 1\. 主要趋势反转（Major Trend Reversals, MTR）

多头趋势是由一系列「更高的高点（HH）」和「更高的低点（HL）」构成的，而空头趋势则是由一系列「更低的高点（LH）」和「更低的低点（LL）」构成的。交易主要趋势反转形态，本质上是在尝试**于新趋势启动之初进场** ，期望后续能走出一段连续顺延的新趋势波段。

由于交易者在新趋势完全明朗之前就尝试进场，因此即便是形态极其漂亮的设置，其初期的胜率通常也只有 **40% 左右** 。这类交易者追求的是低风险（较窄的止损空间），但低风险几乎总是伴随着相对较低的胜率。在交易数学期望上，这种早期入场的交易者，与等待强突破走明朗后再入场的交易者，两者都是划算的。

主要趋势反转的核心要素包括：

  1. **已有一段清晰的趋势** ；
  2. **出现突破原有趋势通道线的回调（Pullback）** ；
  3. **原趋势再度恢复并尝试突破** ；
  4. **出现第 2 次深度回调，并逐渐演化为反向新趋势** 。

![窄幅空头通道：次级反转引发主要趋势反转](https://r2.imgant.com/2026/09/18/b4f9aba5.png) _图 1：突破极窄空头通道的第 1 次反弹通常是次级反转（Minor Reversal）。但第 2 次反转就有 40% 的概率演变成主要趋势反转（如上图）。在收盘接近最高价的阳线上方买入（绿色框）。_

![更高高点主要反转常导致更低高点主要反转](https://r2.imgant.com/2026/09/18/b5829149.png) _图 2：从多头旗形（此处为三角形）向上突破后的向下反转，通常形成更高高点主要趋势反转（HH MTR）。在收盘接近最低价的阴线下方做空。更高高点反转之后，往往紧接着出现更低高点主要趋势反转（LH MTR）。空头趋势中存在多次做空机会（红色框）。_

![发散三角形底：更低低点主要趋势反转的一种变体](https://r2.imgant.com/2026/09/18/b6259448.png) _图 3：图表中间出现了一波强劲的向上反弹，但空头随后再次打出了一个新低。有时新低仅仅是强劲反弹之后的一波深幅回调。每一个发散三角形底（Expanding Triangle Bottom），本质上都是更低低点主要趋势反转（LL MTR）。_

* * *

## 2\. 最终旗形（Final Flags）

最终旗形的组成要素包括：

  * **处于明确趋势中** ；
  * **出现通常以水平横盘为主的回调** （有时甚至短至仅有 1 根 K 线）；
  * **趋势通常已经逼近某个关键磁吸位** （多头趋势中的阻力位，空头趋势中的支撑位）；
  * **往往伴随其他潜在反转信号** （例如在多头趋势中，通道顶部附近抛压不断积聚）。

最终旗形是一种**最初表现为顺势延续形态、最终却演变为趋势反转** 的结构。交易者通常预期这次顺势延续会以失败告终，并随时准备反向交易。

与所有趋势反转一样，单次博弈波段（Swing）的概率通常只有大约 **40%** 。Al Brooks 的常规波段目标是「**10 根 K 线、2 条腿（10 Bars 2 Legs, TBTL）** 」，即预期反转行情至少持续 10 根 K 线且包含两波推动。波段交易还要求潜在盈亏比至少达到 2:1（即潜在回报至少是风险止损的 2 倍）。

在这类交易中，约 60% 的交易最终是微利或小亏相互抵消。想要更高胜率的交易者，通常会等待反转出现朝新方向的强势大阳/大阴线突破后再进场。在那个时刻，波段交易的胜率往往能升至 60% 以上，但此时防守止损点也变得更远。

这种风险承受的增加正是市场的权衡之道（Trade-off）。任何一笔交易，站在你对手盘的大资金机构必然也需要有利可图。如果你想要极高的胜率，就必须承受更宽的止损空间与相对更低的盈亏比。

![最终空头旗形：更低低点主要趋势反转](https://r2.imgant.com/2026/09/18/b6cf862b.png) _图 4：空头趋势尾声出现的窄幅震荡区间（Tight Trading Range），往往会成为最终空头旗形（Final Bear Flag）。交易者会等待价格向下假突破后向上反转进场。_

![多头趋势尾声的三角形：最终多头旗形](https://r2.imgant.com/2026/09/18/b74c027a.png) _图 5：三角形本质上是一种窄幅震荡区间。当它出现在多头趋势的晚期阶段时，通常会充当最终多头旗形（Final Bull Flag）。_

* * *

## 3\. 突破（Breakouts）

突破什么？突破任何支撑或阻力位。这其实并不重要。

**图表上的每一根趋势 K 线（Trend Bar），本质上都是对某种结构的突破** ——即便它仅仅突破了前一根 K线 的高点或低点。随着看盘经验的积累，交易者自然能看清价格真正突破的是什么关键位置。

最常见的突破标的包括：**震荡区间、回调形态、前期高低点、趋势线、通道以及移动平均线（EMA）** 。有时候，交易者需要切换到更高的时间周期才能看清突破的形态。

在这 10 个最佳价格行为形态中，**突破形态是 Al Brooks 最喜欢的** ，因为追求高胜率的交易机会。

![突破：趋势K线收在支撑或阻力位之外](https://r2.imgant.com/2026/09/18/b7da2085.png) _图 6：突破本质上就是一根向上或向下的趋势 K 线。突破必然收在至少是次级支撑或阻力位之外。K 线的实体越大、所突破的支撑/阻力位越重要，趋势延续更长一段时间的可能性就越高。_

* * *

## 4\. High 2 多头旗形与 Low 2 空头旗形

许多交易者觉得数 K 线（Bar Counting）令人困惑，因为他们总希望一切都如教科书般完美严谨。但他们不明白的是：**市场的目的本身就是制造困惑** 。

市场希望在多空双方都认为价格公允的水平上停留尽可能长的时间，从而促成流动性交易——这也是市场存在的根本意义。

这两类旗形的基本逻辑是：**市场往往会尝试反转趋势两次，从而走出两条腿（Two Legs）** 。如果这两次反转尝试都失败了，市场通常就会转向原有趋势的方向。既然原趋势正在恢复，逆势交易者就会意识到自己被套陷入麻烦，一旦第二次反弹/回踩尝试失败，他们就会迅速割肉离场。

不仅如此，逆势方短时间内也不敢再次尝试逆势接刀。这就创造出高胜率的顺势延续形态，行情往往启动迅速。交易者通常用此设置进行剥头皮短线交易，但在顺势动能充沛时，也可以留底仓博弈大波段。

这类形态往往具有嵌套性（Nested），在两条大腿内部常常各自孕育着更小级别的形态。无论你在大级别还是小级别的形态上进场，只要设置合理的波段防守止损即可。

![空头趋势或震荡区间中的 Low 1 与 Low 2 卖出设置](https://r2.imgant.com/2026/09/18/b86e47d7.png) _图 7：在空头趋势或震荡区间的空头腿中，单腿回调是 Low 1 做空设置；如果该信号触发后又向上走出一腿，就构成了 Low 2 空头旗形。Low 3 则对应三角形或倾斜楔形。任何双顶（DT）本质上都是 Low 2 空头旗形。_

![多头趋势或震荡区间中的 High 1 与 High 2 买入设置](https://r2.imgant.com/2026/09/18/b904c3f9.png) _图 8：在多头趋势或震荡区间的多头腿回调中，当某根 K 线的高点首次高于或等于前一根 K 线高点时，该回调即为 High 1 多头旗形；如果触发后再次下探探底，就构成了 High 2 多头旗形。三角形是水平的 High 3 旗形，而下倾的楔形旗形则是向下倾斜的三角形。任何小型双底（DB）都是 High 2 多头旗形。_

* * *

## 5\. 楔形：三次向上或向下的推升（Wedges）

传统意义上的楔形是一个向上或向下倾斜的收敛三角形，交易者通常预期突破会朝倾斜方向的反向发展：即预期**下倾楔形向上突破** ，**上倾楔形向下突破** 。

  * 当楔形作为趋势中的回调出现时，它们是**顺势延续形态** ；
  * 当楔形跨度较大且市场背景合适时，它们则是**反转形态** ；
  * 当它们充当旗形时，本质上就是小级别的微型反转结构（例如多头趋势中的楔形回调，本身是一段微型空头腿，交易者预期该空头腿衰竭并向上反转）。

从最广义的角度看，**任何具有 3 次（有时 4 次或 5 次）向上或向下推升且带有倾斜角度的走势，都可以视为楔形** 。它不一定非要严格收敛，第三次推升也不一定非要超过第二次。

一旦行情走出了两次推升，交易者就可以将两点连线并向右延伸（画出趋势通道线）。当价格第三次接近该趋势线时，就可以重点观察是否出现反转。

形态越接近完美标准，其可靠性越高，因为会有更多量化算法和程序将其判定为有效信号。然而，交易者永远不要忽视背后的供求驱动力量，学会适应形态的各种变体，才能在实盘中捕捉到更多的交易机会。

![楔形顶：日内反转走势](https://r2.imgant.com/2026/09/18/b98b9ca1.png) _图 9：楔形顶（Wedge Top）通常是一个收敛的多头通道。多数楔形顶包含 3 腿上涨推升，少数有第 4 腿甚至极罕见的第 5 腿。在收盘接近最低价的阴线下方做空，预期至少有 2 腿下跌。任何多头通道都应被视为空头旗形，因为向下跌破多头趋势线的概率高达 75%。_

![楔形底：外形不必教科书般完美](https://r2.imgant.com/2026/09/18/ba1cd076.png) _图 10：实盘中的楔形极少完美，多数完全不像教科书中的标准图形。如果一个空头通道出现了 3 腿下探推升，即便没有明显的楔形轮廓，也要将其视为楔形对待。市场反复尝试向下突破未果，必然会转向反向向上探索。_

![抛物线楔形顶：无尽回调后演化为暴跌反转日](https://r2.imgant.com/2026/09/18/baa5126d.png) _图 11：如果极窄多头通道中出现连续 3 次加速冲击推升，该通道即为抛物线楔形（Parabolic Wedge）。这属于买盘高潮（Buy Climax），极易演变成震荡区间甚至诱发全天暴跌反转。_

* * *

## 6\. 通道（Channels）

**市场永远运行在通道之中** 。有时交易者需要切换到更大级别的时间周期才能看得分明。很多通道并不符合教科书或网络图解给出的标准定义。

然而，优秀的交易者深知通道的真实面貌，在选取画线点时非常灵活。一旦看到两个锚点，他们就会拉出一条线，观察价格再次触碰时是否反转。他们会不断擦掉被市场无视的无效线条，并持续绘制新的关键通道线。

![市场始终运行在通道中：反转发生的概率远高于顺势突破](https://r2.imgant.com/2026/09/18/bb2f096f.png) _图 12：任何市场始终处于某种通道之中。由于在通道边缘发生反转的概率远高于直接突破，因此交易者更倾向于在通道边缘寻找反转入场机会。_

![17 根 K 线连续空头微型通道：卖盘力竭高潮](https://r2.imgant.com/2026/09/18/bbc9a893.png) _图 13：微型通道（Micro Channel）是指一系列没有任何回调重叠的连续 K 线。这是极强趋势的表现，但一旦达到约 10 根以上，往往变得不可持续并转为消耗性高潮（Climax），通常会演变为震荡区间。_

![向上突破楔形多头通道：标普指数历史月线牛市](https://r2.imgant.com/2026/09/18/bc554dde.png) _图 14：标普现货指数在 1987 年崩盘到 1994 年底期间一直处于楔形多头通道中。向上成功突破多头通道的概率通常仅有 25%，但一旦成功，就演化出了波澜壮阔的超级大牛市。_

## 7\. 测算走势（Measured Moves）

市场总是倾向于把某段行情重复走两遍。其结果就是：**绝大多数顶部都是双顶的变体，绝大多数底部都是双底的变体** ；趋势走势通常至少会有第 2 条推动腿，且第 2 腿的幅度往往与第 1 腿存在等比映射关系。

大家最熟悉的是 **Leg 1 = Leg 2（第 1 腿 = 第 2 腿）** 测算走势：行情在经过回调后，第 2 腿的延伸幅度与第 1 腿几乎完全相等。

此外，交易者还会计算震荡区间突破后的测算目标位：预期突破后的行进幅度，大约等于前期震荡区间垂直高度的 1:1 投影。计算机量化算法广泛使用各类测算走势来进行止盈离场或逆势反转建仓，其中许多测算依据日内跳空缺口或突破 K 线的垂直高度。

![第 1 腿 = 第 2 腿：趋势恢复并跌至测算目标位](https://r2.imgant.com/2026/09/18/bcec896f.png) _图 15：当趋势经历回调后恢复运行时，第 2 腿的下探幅度往往非常接近第 1 腿。这即是 Leg 1 = Leg 2 测算走势。空头通常会在该目标位附近大举获利平仓。_

![测量缺口：精准到达测算目标位](https://r2.imgant.com/2026/09/18/bd70d03a.png) _图 16：当突破发生后，趋势通常会依据前期区间的垂直高度走出等幅测算行情。交易者会做多上涨趋势并做多任何回踩，尤其是回测突破点后再次向上反转的结构。_

* * *

## 8\. 震荡区间反转（Trading Range Reversals）

在震荡区间彻底成型并被所有人看清之前，盘面上通常早已出现了双向对冲交易的蛛丝马迹，提醒敏锐的交易员今天大概率是震荡日。

在震荡日中，价格往往以强烈的动能狂飙至区间上轨，导致散户误以为这是一波凌厉的多头突破，盲目在微幅回踩时追多。同样地，散户在区间下轨看到一根巨大的阴线砸盘时，也会误以为趋势破位而慌忙追空。

实际发生的情况是：

  * **在区间顶部** ：价格被「真空吸筹（Vacuum）」抽吸至阻力位，多头大资金选择止盈了结而非继续追高，空头大军突然凭空杀出。多空双方都清楚，对阻力位的测试大概率以假突破告终。
  * **在区间底部** ：当价格接近支撑位时，空头短线投机客甚至会加大砸盘力度，期望击穿支撑再下探几个 tick；而多头则暂停买入，因为他们确信价格一定会打到支撑位甚至瞬间刺穿——既然几分钟后能在更低价买到，何必现在急着接盘？

这就造成了：**价格在被真空吸入支撑位时，往往在最底部拉出极具欺骗性的大阴线** 。然而紧接着出现的不是顺势暴跌，而是汹涌的买盘。空头集中获利平仓买入，多头主力大举进场开多。

![震荡区间：在反转位置等待第 2 次信号进场](https://r2.imgant.com/2026/09/18/bdfa19cb.png) _图 17：震荡区间内部的推升腿和下跌腿往往非常迅猛。此时等待第 2 次反转信号（Second Signal）再进场，盈利的确定性会大大提升。_

初学者在收盘之前往往根本意识不到市场正在走震荡区间。但 K 线很早就给出了信号：**频繁出现的明显长影线、频繁深度回调、前一日收于窄幅横盘中（市场具有惯性），以及极少出现连续 2–3 根大实体趋势 K 线** 。

新手会因为反复的反抽和反转感到困惑沮丧，而成熟交易员深知：**这种困惑感正是震荡区间最典型的特征** 。经验丰富的交易者会将每一次突破视为潜在的假突破反转机会，坚决执行「低吸、高抛、剥头皮（Buy Low, Sell High, Scalp）」策略。

* * *

## 9\. 开盘反转（Opening Reversals）

开盘反转形态的核心特征包括：

  * **开盘后往往迅速冲向某个强磁吸位（关键支撑位或阻力位）** ；
  * **在开盘前 60–90 分钟内完成反转，并走出持续数小时乃至全天的波段行情** 。

在日线级别上，绝大多数强阳线在实体下方通常都有一个小下影线，这往往就是由开盘反转所致（开盘急挫诱空后迅速拉起形成反转）。同理，日线大阴线上方的小上影线，也多半源自早盘冲高后的向下开盘反转。

![开盘卖盘真空测试昨日低点：买入向上反转](https://r2.imgant.com/2026/09/18/be80b3d8.png) _图 18：早盘出现巨幅暴跌，这是针对昨日低点的卖盘真空测试（昨日低点通常是强支撑候选位）。随后行情企稳向上反转，全天走出持续上涨行情。_

![跳空高开：楔形多头旗形开盘反转](https://r2.imgant.com/2026/09/18/bf005383.png) _图 19：跳空高开后，价格回踩 20 EMA 均线。随后的向上反转是全天第 3 次上攻尝试，因此构成了回踩 EMA 的楔形多头旗形开盘反转买点。_

![跳空低开：均线下方紧贴的双顶空头旗形](https://r2.imgant.com/2026/09/18/bf856599.png) _图 20：每当出现跳空低开时，交易者需警惕价格在 EMA 均线附近构筑双顶空头旗形。在向下的反转点做空，博弈形成日内最高点和全天单边空头走势。_

* * *

## 10\. 磁吸位：支撑与阻力（Magnets）

这 10 个最佳价格行为形态中的最后一个，比起具体的进场设置，它更像是一个贯穿交易的核心思维概念。

市场始终处于「探索测试」之中，试图寻找公允的交易区间。**市场通常必须走得过头（Go too far），才能确认自己是否已经涨够了或跌透了** 。

  * **支撑位** ：是位于现价下方的某个价格水位，多头会在该位置开多，空头会在此获利买入平仓，从而涌现出买盘。
  * **阻力位** ：是位于现价上方的价格水位，多头会在此获利平多，空头会在此建仓开空，从而形成抛压。

常见的市场磁吸位包括：**震荡区间的顶部与底部、前期最高最低点、趋势线、通道轨线、等幅测算目标位以及移动平均线** 。如今计算机算法主导着盘面，所有的支撑与阻力位本质上都是算法可量化计算的点位。因此，一旦大量算法模型认定价格即将触达某个目标位，市场在逼近该点位时往往会出现加速冲刺效应（磁吸抽吸）。

![磁吸位：突破测试与双底结构](https://r2.imgant.com/2026/09/18/c0080249.png) _图 21：当价格突破前期高点后，往往会发生回踩以测试突破位。多头会在回踩向上反转时坚决买入。_

![震荡区间日：开盘价全天充当磁铁，尤其在尾盘](https://r2.imgant.com/2026/09/18/c08a2f29.png) _图 22：在震荡区间日，价格全天往往围绕开盘价上下反复摆动。如果在收盘前最后 2 小时价格处于全天极值点（高点或低点）附近，应积极寻找回抽开盘价的反转机会。绝大多数震荡日最终都会收在开盘价附近。_

![磁吸位：新手眼中的「随机暴跌反转」](https://r2.imgant.com/2026/09/18/c10c333b.png) _图 23：初学者面对凌厉的上涨突然急转直下陷入崩盘暴跌时，往往会崩溃抱怨：「为什么这么好的多头趋势会突然崩掉？这不公平！庄家又在收割我的钱！」_

![磁吸位：成熟交易者眼中的阻力位买盘力竭高潮](https://r2.imgant.com/2026/09/18/c18b6d5e.png) _图 24：成熟的交易者心如明镜，他们清楚地知道关键阻力位在何处，并在阻力位守株待兔等待做空反转信号。任何冲向强阻力位的猛烈拉升，都极有可能只是针对阻力位的一次「买盘真空测试」而已。_

* * *

## 总结

正如 Al Brooks 所言，这 10 个形态不是机械的生搬硬套，而是理解大资金博弈与多空力量流转的透镜。在日常交易中：

  1. **先看市场大背景（Context）** ：识别当前是单边趋势（止损单市场）还是震荡区间（限价单市场）；
  2. **留意磁吸位与测算走势** ：时刻清楚上下方最重要的引力点在哪里；
  3. **管理好交易期望与风险** ：追求高胜率就接受宽止损与小盈亏比，追求大盈亏比就欣然接受较低的初期胜率并做好分批止损保护。

从2026年开年，**随着Claude的发布，AI智能体的井喷时代来临** ，在过去的半年里，大家从刚开始对于AI重新刷新认知，到开始了解深入体验，半年时间过去了，AI到底诞生了哪些新概念？我做了哪些尝试和研究呢？

# [](https://lorexxar.cn/2026/09/18/aiagent/#AI模型的变化 "AI模型的变化")AI模型的变化

在2026年的年初，市面上最主流的AI模型是claude opus4.6和GPT-5.3-Codex。

而那会儿国模的差距还是相当之大，国模的主流是GLM5、minimax2.7、Deepseek3.2。

在今年年初的时候，我曾经说过，**AI智能体爆火有一个重要的变因就是模型本身有了更长更有效的上下文** ，这也是模型能力的第一个质变性的更新，他的标志性模型版本就是

  * **Claude opus 4.6和GPT-5.3-Codex**

从这个版本开始，**claude code+claude opus 4.6和codex+GPT-5.3-Codex** ，这种**模型+Agent** 的构建方案，开始允许AI模型去应对更长更复杂的任务。

而真正我认为质变的模型是

  * **GPT-5.6和Claude Opus 4.8**
  * **对应国模的Deepseek V4、 GLM-5.1**

从这个版本开始，AI模型真正明确了一个核心要点，就是Ai不能停留在一个对话智能助手上，而是**需要更具体的复杂任务完成能力** ，从这里开始模型本身的能力开始变得没那么重要，**所有的厂家都把重心放到了Agent能力** 上。

Claude开始卷Claude code，openai开始卷Codex，GLM卷ZCode，Deepseek推出了开源的Harness，前段时间xiaomi开始内测Mimo Code，腾讯押注Workbuddy，豆包开始推出豆包桌面版。

**各家的AI模型都开始深入到自己的Agent层面做优化** ，不再局限于对话智能助手，也不再局限于代码开发能力，这是为什么呢？

# [](https://lorexxar.cn/2026/09/18/aiagent/#从wf到重skill到loop到Harness "从wf到重skill到loop到Harness")从wf到重skill到loop到Harness

这条AI模型的发展路径，其实是同一个时代的4种架构的演变过程导致的，这也代表着过去的半年里，AI Agent使用上的重大理念变化。

**Workflow工作流— >重Skill的Agent—>Loop—>Harness**

首先要明确的是，这并不是4种独立的架构演化过程，更像是AI模型发展后Agent和用户重心的变化。

## [](https://lorexxar.cn/2026/09/18/aiagent/#Workflow时代 "Workflow时代")Workflow时代

在2026年之前，大概在2023年到2025年的期间，用户去应用AI最主流的方案就是强Workflow工作流。

因为在AI模型本身比较弱、幻觉比较强的情况下，**如何更稳定的获取AI生成的结果是非常困难的** ，同时这个时代上下文也不够长，**使用AI的时候更依赖拆分逻辑靠强制的代码推进来保证任务的结果。**

代码里往往需要写死每个环节，逐个执行获得结果推进流程

    2  
    3  
    4  
    5  
    

| 
    
    
    search()  
    summarize()  
    make_outline()  
    write_report()  
    fact_check()  
      
  
---|---  
  
这个时代还有很多可以挂钩强流程推进的工作流网站，比如说coze等，需要绘制复杂的工作流图

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181645196.png)

Workflow最大的问题是，**用户很多时候其实很难明确自己的工作流程应该是什么样的** ，随着开发和运行的过程，纯Workflow的能力维护成本高，而且AI模型能力越来越强，也不再需要强Workflow来定义任务。

## [](https://lorexxar.cn/2026/09/18/aiagent/#重Skill "重Skill")重Skill

重Skill的时代大家都经历过，**从25年开始一直到26年中，Skill都是Agent的主要的核心之一。**

作为通用AI模型，他可能看得懂PHP代码，但是不了解你的项目是什么？

所以从最早的Claude.md，**会以全局文档的形态或者项目文档的形态来影响AI开发任务的方式方法和进度。**

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181646498.png)

Skill的模式鼓励用户把经验文档化，就好像人的记忆一样，**当你需要完成某项工作的时候就调取对应的Skill文档，复用以前的经验和流程完成任务。** 这种模式大体上依旧被沿用到今天

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647731.png)

很快我们就会遇到一个新的问题

当我们把经验Skill化，当你的Skill多起来之后，极其的难以管理，**很多Skill冗余非常之高** ，而且Skill本身的加载条件仅仅是一段文本非常难管理，**时间长了连如何触发都成了问题。**

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647384.png)

Anthropic在一次发布上还提到，有些MCP的定义在任务开始之前就会占用50000+的token，这就是重Skill模式带来的困境。

从这里大家开始意识到，**不该提前告诉AI一切，而是让AI自己去寻找需要的内容和工具。**

所以后来**Agent 的上下文工程开始从 preload everything 转向 just-in-time context** ，AI会在遇到一个问题的时候**主动去寻找SKill和MCP来解决问题** ，而不是在开始任务之前先一股脑的加载。

所以最早就诞生了外部脚本，在任务完成以前就不停地确认继续任务，直到完成任务目标

这就是Loop的雏形

但是单纯的Loop会有非常多的问题，**任务会在一次次的执行当中，产生大量的无用上下文，大量的失败记录，再反复的尝试中还会丢失自己的最初目标。**

Agent端在这方面做了大量的优化，比如大家都用过的`/goal`，堪称是token杀手，几个小时后搞不好会在额度快用完的时候假装完成。

**Loop让任务更聚焦到任务目标上， 但又暴露出来Loop本身也需要外部的监管** ，之前的poc+pm+子任务的架构就是这种理念的践行。

很快遇到了新的问题，当一个Agent的能力越来越强，他们有完整的服务器权限，外面接的各种mcp各种外部skills，为了**完成目标Agent可能会做出难以想象的糟糕行为** 。

就在前几天openai为了拿到英国政府的几个文件，Agent 选择向 RubyGems 发布大量恶意 package，通过入侵ruby服务器蠕虫来多线程抓取英国政府官网，非常抽象

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647169.png)

## [](https://lorexxar.cn/2026/09/18/aiagent/#Harness "Harness")Harness

其实Harness不能算是一个很新鲜的概念，像早期的MCP和Skill其实都是某种程度的Harness的一部分，说白了就是**给AI Agent提供能力** 。

那Harness概念最大的区别是什么呢？

  * **Workflow** ，强调的是人来制定流程
  * **Skill** ，人会通过大量的Skill来告诉模型，遇到什么情况该怎么做
  * **Loop** ，人告诉AI我的目标是什么，让AI自己判断下一步做什么
  * **Harness** ，人给AI提供链接的工具，提供环境，设置边界，设置反馈机制，设置完成标准，让AI自己决定如何完成任务，要不要使用你的工具。

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647657.png)

要明确的是，这4个词虽然有演化过程，但是这并不意味着存在互相淘汰，相反，**现在主流的Harness更加强调前4个概念的聚合**

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647018.png)

时间走到今天，刚刚诞生的GPT6，**比起模型能力本身，现在更加强调模型的产品思维。**

为什么很多人都说感觉GPT6变聪明了很多，因为GPT6强调AGI概念，**更加强调持续的思考任务。**

  * GPT5.6，有很多知识，**靠已有的知识推理出方案然后执行获得结果** ，目标是解决问题
  * GPT6，在任务执行的过程中**持续思考反馈观察** ，不断地修正路径推进工作，**以完成任务为最终目标**

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647549.png)

# [](https://lorexxar.cn/2026/09/18/aiagent/#回到安全 "回到安全")回到安全

前面的部分分享了2026年近期Agent的发展理念变化，单纯理论可能感触不是很深，实际上在过去的时间里，我做了非常多的尝试，这些尝试可能会带来更直观的感受。

## [](https://lorexxar.cn/2026/09/18/aiagent/#弱Workflow和重SKill "弱Workflow和重SKill")弱Workflow和重SKill

在今年开年的时候，Claude和Codex刚火，那会儿流行的就是**通过Workflow和Skill来构建任务。**

最早版本的漏洞挖掘的工作流，**其实就是在Skill层写Workflow** ，让AI模型按照我给出的流程和要求完成一次工作流扫描。

**一个Poc负责人session，一个pm管理进度session，每个阶段独立子session，每个阶段写明要求审核条件等等**

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647514.png)

**把不同的功能拆分到不同的skill里** ，然后在WF里显式加载

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647714.png)

最终根据我给出的要求输出漏洞报告 

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647206.png)

但是很快我就遇到了很多问题，也是早期这种本质上**通过prompt来实现workflow一定遇到的坎** 。

1、这种超长文档的Skill，**对于模型能力有很大的考验** ，早期除非使用Claude opus4.6，否则很多时候整个工作流都跑不下来，GPT5.4、GLM5会大量的偷懒跳过步骤，早期幻觉也比较多，结果无法保证

2、**整个工作流过程不可监控不可复盘** ，误报多结果无法确认，最终输出的报告看不懂没有价值。  
3、甚至早期随着模型的发展，会发现辛辛苦苦修改了十几个版本的SKill，**不如直接问Claude，能不能给我挖掘一个漏洞？**

到这里就遇到了第一个门槛，**我们的工作到底有没有价值？**

三体中，当地球人知道三体人即将在400年后来到地球，地球诞生了两种流派，就是**降临派和拯救派** 。

**降临派，对人类彻底绝望，认为三体人应该终结人类。** 对应AI就是，完全不相信我们做SKill做wf有价值，等待AI模型发展就行了

**拯救派，认为人类有问题，希望借助三体人来改变成就人类** ，对应AI就是，AI很强，但是我们的工作也是很重要的一环，需要不断的尝试。

带着这样的疑问我做了很多的尝试。**事实上就像三体本身故事里所讲的那样，最终胜出的不是降临派也不是拯救派。**

## [](https://lorexxar.cn/2026/09/18/aiagent/#基于Hermes的托管式自进化安全扫描工具 "基于Hermes的托管式自进化安全扫描工具")基于Hermes的托管式自进化安全扫描工具

在上一个Workflow我认为比较失败之后，我开始尝试做一些其他的探索和尝试，我的第一个尝试是，**完全使用Vibe coding来做开发和维护。**

Kunlun-M是一个我在5年前开发的**PHP白盒静态漏洞扫描工具** ，已经停止维护4年了，无力修复bug

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647428.png)

接入Vibe coding之后，3天修复了所有的40多个issue，然后花一个月的时间把php的扫描逻辑，推广到了7种常见源代码语言。

很快我发现这个项目**基于AST树做分析的引擎对于多语言的兼容性太差** ，所以又花了一个月直接在多语言中间塞了一个图的中间结果，在图上做整体分析。

很快他就成了一个**可以支持扫描14个语言，支持多端读取，支持AI以SKill的方式加载的白盒扫描工具。**

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647225.png)

但是很快我就意识到，我已经无法跟上项目的发展了，**我不知道项目有什么问题有什么bug。**

很快我想到了一个办法，我直接**在服务器部署一个hermes** ，然后在服务器上部署Kunlun-M。

让Hermes完成以下的任务

  * 在github上寻找开源项目，使用kunlun-M批量扫描
  * 分析Kunlun-M的扫描结果列表，标注确认漏洞、误报
  * 分析误报的原因，修改Kunlun-M的代码，修改完成之后，自行总结并复测，直到所有的误报都被消除
  * 继续下一个循环

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647034.png)

在过去的3个月时间内，Kunlun-M迭代了1022次Commit，扫描了1000个项目，扫描3200次，有1221个确认漏洞，归纳为187个漏洞规则和28个拓展插件。

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647798.png)

看上去还不错，但是随之而来的是更多的问题

1、在过往的执行中，**曾经有3、4次AI尝试通过删除规则来修复误报**

2、全局记忆在压缩中**丢失了任务的执行流程2-3次**

3、**在版本迭代过程中删除和优化的结构** ，由于开发Skill太大导致多次被重新开发加回来

4、Hermes配置了迭代过程和调用过程都会持续总结SKill，**最多的时候有137个Skill文件互相引用，上下文填满对话两句就要压缩无法正常运行**

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181648549.png)

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181647456.png)

尽管在使用过程中也有很多办法可以解决，比如**定期的自清理优化Skill** ，**手动强制优化全局记忆做限制** 强调流程。

但是问题同样有很多无法解决，比如说

1、**我不知道扫描结果到底是真的没有漏洞** ，还是引擎覆盖不到，还是过滤太严格，无法判断  
2、**我不知道这种自进化的终点该是什么** ，没有验证的途径

所以这个项目暂时处于停滞阶段，考虑**用真实世界的漏洞反向复盘优化**

从这个项目的经验我开始理解Harness的概念

## [](https://lorexxar.cn/2026/09/18/aiagent/#在漏洞复现上的思考 "在漏洞复现上的思考")在漏洞复现上的思考

我认为上一个项目有**两个致命的缺点**

  * **AI模型能做的事情太少** ，我限制了他必须使用Kunlun-M扫描获得结果，他只能通过开发代码改代码来完成，大大限制了模型本身的能力
  * **没有设置AI监察者的第三方角色** ，Hermes直接对结果进行复盘，为了完成目标就会出现自欺欺人，仅靠人类去监管效率太低

这个时候正好遇到了一个事件

  * **在fastjson 1.2.83版本中无需gadget的RCE漏洞** ，被AI在2天内分析挖掘
  * 有人使用GPT挖掘了一个**Wordpress最新版本中无条件RCE，WP已经4、5年没有出过原生的无条件RCE漏洞**

在复现这个漏洞的时候，我尝试让Hermes探讨漏洞文章，探讨poc内容，并且**让hermes直接在服务器上做漏洞复现和问题测试** ，效果非常的好。

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181648512.png)

也就是从这个时间左右，安全圈流传的一个说法，现在**漏洞挖掘已经没有意义了，只看你烧多少token** 。我朋友和我说，Defcon决赛上的前几名的队伍，会直接起20个20x的gpt来多线程分析漏洞。

更有趣的是，很多朋友会发现以前AI挖掘不到的漏洞，过一段时间就能挖到了，可能是别人挖到的漏洞被训练进了缓存，全球GPT是一家。

这让我开始思考，是不是我对模型自由度限制太大了，我能做的有价值的东西是什么？

## [](https://lorexxar.cn/2026/09/18/aiagent/#基于opencode的深度定制漏洞挖掘Harness "基于opencode的深度定制漏洞挖掘Harness")基于opencode的深度定制漏洞挖掘Harness

这个项目其实和前面的两件事是并行的，因为我开始尝试用别的方案解决问题。

我要如何做一个**能最大程度发挥模型能力的工具呢** ，我把视角瞄准到了定制Agent上，那会儿还没有Deepseek Harness，所以我用了Opencode做基底

  * **将poke(将代码转化为图数据库的一个内部工具)的交互和查询能力直接内置到Opencode的底层Tools中**
  * 在Opencode对话session的上层，做了一个**强Workflow阶段推进的系统** 。
    * **每个项目独立配套相关的数据库** ，包括poke图数据库、项目数据等
    * **Workflow的负责人session** ，没有读取文件和poke图数据库互动的权限，他只能**审查阶段session返回的结果**
    * **每个阶段明确的设置目标以及产出** ，每次执行完毕让负责人session负责审查，不行的话可以自主决定回滚阶段
    * **每个阶段的执行结果独立，不覆盖也不能跨阶段读取**
  * **强化漏洞验证的有效度** ，直接把运行环境配置为底层能力，AI不需要自己研究如何配置环境测试，而是直接调用php、golang环境甚至docker环境来做测试

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181648647.png)

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181648594.png)

为什么要做这样的改动呢？

  * 比起前面的基于skill的Workflow，这种Agent的层面的Workflow，**不同session的分割和目标性更强**
  * 强门禁限制的Workflow面板可以**确保任务的执行流程不被跳过** ，任务目标完成才可以放行
  * 每个子阶段的session只接收到任务和目标，不强制要求扫描分析的方式，**模型可以自己选择分析文件和调用poke查询调用链完成目标**
  * **主负责人只对阶段的结果负责** ，明确目标，最终的结果状态也会输出到面板数据库中，而不是停在输出一份文档

![](https://lorexxar-blog.oss-cn-shanghai.aliyuncs.com/blog/202609181653440.png)

而我在这个项目的主导方式也发生了变化，不会直接参与流程，也不会完全脱离流程

  * **我- >GPT**，复盘WF的执行结果，探讨流程的问题，探讨为什么xxx漏洞没有被扫描出来
  * **GPT – > 整个项目**，不直接分析代码，不直接调取工具，而是做流程的优化和复盘，项目与项目之间独立不会产出大量的无用skill，方向也可控
  * **项目负责人AI – > WF**，根据情况和当前项目的数据，重启WF获取新的结果，只审核阶段结果
  * **Poke图数据库** ，不强制在执行过程中，而是作为Agent的一个工具存在，需要时调用，节省token明确调用链

# PaddleOCR 昇腾平台性能摸测报告

**测试对象** :PP-OCRv5_server（det + rec）on Atlas 800I A2 / Ascend 910B4-1 西安绿区110.21.1.23

* * *

## 摘要

本次摸测围绕两项任务展开:(1) 基于客户数据集进行 PaddleOCR 性能摸测;(2) 算力切分与多实例最高吞吐测试。

**主要结论:**

指标 | 结果  
---|---  
单实例吞吐 | **1.21 QPS** （三次重复,变异系数 0.67%）  
单实例时延 | avg 821 ms / P50 827 ms / P99 1560 ms  
**单卡最高吞吐** | **27.96 QPS** （约 38 实例）  
单卡实例上限 | 优化前 24 → 优化后 **~38** （受 HBM 容量限制）  
**性能瓶颈** | **HBM 显存容量** ,而非算力（拐点处 AICore 仅 48~54%）  
精度（om vs Paddle） | 平均字符一致率 **99.88%** ,最低 99.17%,零推理失败  
算力切分（vNPU） | **对本负载吞吐无正收益** ,价值在隔离与 QoS  
  
**最有价值的两条工程发现:**

  1. **官方文档建议的`onnxsim` 步骤在动态 shape 场景下是错误的**,会导致约 35% 的真实业务图片推理失败。
  2. **`ASCEND_OM_OUTPUTSIZE` 从 1024MB 降至 64MB**,单实例显存从 2686MB 降至 1726MB,单卡实例上限提升约 58%,而单实例性能无损失。这是本次投入产出比最高的一项优化——只改一个环境变量。

## 4\. 实施过程与踩坑记录

本节按时间顺序记录实际遇到的问题、定位过程与解决方案。**这部分占用了本次任务约 60% 的时间** ,记录在此以供后续同类任务参考。

### 4.1 环境阶段:`dcmi module initialize failed. ret is -8005`

**现象** :执行 `npu-smi info` 查询芯片型号时报错。

**定位过程** :

  1. 区分宿主机 / 容器 → 确认在容器内
  2. 检查设备节点、驱动模块、动态库路径
  3. 对比 `-8005`（DCMI 初始化失败）与 `-8020`（设备被占用）的语义差异

**根因** :容器缺少 `/usr/local/dcmi`、`/etc/ascend_install.info` 等必要挂载。

**解决** :安装 Ascend Docker Runtime,起容器时用 `-e ASCEND_VISIBLE_DEVICES=0,1,...` 自动注入设备与驱动,不再手写 `--device` 与 `-v` 列表。

**教训** :环境搭建应逐步验证——装驱动后立即 `npu-smi info`,装 runtime 后立即 `docker exec npu-smi info`。一路装完再统一验证,出问题无法定位是哪一环。

### 4.2 镜像构建阶段的三个陷阱

按官方文档 3.3 节构建 paddlex 镜像时遇到:

陷阱 | 现象 | 解决  
---|---|---  
包名与通配符不匹配 | `./Ascend-cann-910*-ops*.run: No such file or directory`,退出码 127 | 从 codeload 下载的 PaddleX 为 `v3.4.2.tar.gz`、OpenCV 为 `4.10.0.zip`,均需 `-O` 改名以匹配 Dockerfile 通配符  
文件名含不可见字符 | `ls *.run` 只显示一个文件,但目录里确实有 2GB 的包 | 用 `ls -lab` 显示转义字符,按文件大小 `find -size +1G` 重命名  
基础镜像 tag 不匹配 | `pull access denied for openeuler-24.03-lts-sp3` | `docker load` 后的镜像名不一定等于 Dockerfile 的 `FROM`,需 `docker tag`  
  
**建议改进** :将 Dockerfile 中的 CANN 安装与 ultra-infer 编译拆分为两个 RUN 层。当时二者在同一层,ops 包一处失败导致已成功的 CANN Toolkit 安装（约 10 分钟）需要重跑。

### 4.3 rec 模型:宽度下界过高导致 48% 数据失败

**现象** :冒烟测试首张图即报 `execute model failed, errorCode is 500002`,随后 Python 抛出 `ValueError: attempt to get argmax of an empty sequence`。

**定位** :`argmax of an empty sequence` 是**连锁反应** ——推理失败返回空数组,后处理无法处理。真正的错误是上一行的 ACL 500002（参数无效）。

**根因** :初版按模型 `inference.yml` 的默认范围设置 `x:1~8,3,48,160~3200`,而实测 48% 的文本框宽度低于 160。

**解决** :全量扫描宽度分布后,下界调整为 8。

**教训** :模型自带的 shape 范围是通用默认值,**必须用真实数据的统计结果覆盖它** 。

### 4.4 【核心发现】onnxsim 破坏动态 shape 模型

**现象** :调整下界后单张图通过,但全量 104 张测试中 **36 张失败** ,且失败集中在第 4 个目录。

**排查历程** （这是本次耗时最长的一段）:

假设 | 验证方式 | 结果  
---|---|---  
输出内存不足 | `ASCEND_OM_OUTPUTSIZE` 从 256 提至 1024 | ❌ 无效,失败数量完全一致  
长时间推理的资源累积 | 重启容器后重跑 | ❌ 无效,失败位置与文件完全相同  
该目录图片尺寸特殊（含 1448 宽度） | 分别取 1448 与 1449 宽度的图单测 | ❌ 两者都失败  
动态 batch 有问题 | 转固定 batch=1 的 om | ❌ 无效（后证实此次 ATC 因 `$SOC` 变量丢失而未执行成功）  
**查 CANN 底层日志** | `ASCEND_GLOBAL_LOG_LEVEL=1`,读 `~/ascend/log/debug/plog/` | ✅ **定位**  
  
**底层错误** :
    
    
    [BroadcastShape] shape [1600, 1, 120] and [40, 40, 120] cannot broadcast!
    OpName:[Add.38]
    InferShape failed, node type Add, name Add.38
    

**根因** :`onnxsim` 在简化模型时执行常量折叠,按静态输入假设将某个 reshape 的输出形状固化为 `[40, 40, 120]`。运行时实际序列长度不同,与另一分支的 `[1600, 1, 120]` 无法广播,`Add` 算子 InferShape 失败。

**验证** :

  * 同一张图 Paddle 后端（CPU）正常输出 77 行文本 → 模型本身没问题
  * 去掉 `onnxsim`、直接用原始 `inference.onnx` 转 om → 报错类型立刻改变为干净的 107000（超出 shape 范围）

**结论** :昇腾社区《PaddleOCR优化参考实践》3.4 节建议对 rec 模型执行 `onnxsim`。**该建议在动态 shape 场景下会导致功能性错误** ,影响本数据集 34.6%(36/104) 的图片。**建议反馈至 PaddleX / CANN 侧。**

### 4.5 抽样估计 shape 范围导致的二次失败

去掉 onnxsim 后,报错变为:
    
    
    memcpy d2d failed. buffer size is 1179648, inputs[i].Nbytes() is 1257408, errorCode is 107000
    

反算:`1179648 / 4 / 3 / 48 = 2048`（om 上界），`1257408 / 4 / 3 / 48 = 2183`（实际输入宽度）。

**根因** :第一次宽度探测脚本写的是 `files[:30]`,而文件按目录名排序,**前 30 张全部落在第 1 个目录** ,未覆盖第 4 个目录的版式。抽样得出 max=1977,据此设定上界 2048;全量扫描的真实 max 为 2185。

**解决** :上界调整为 3200,全量回归通过 104/104。

**教训** :动态 shape 范围必须基于**全量数据** 统计。数据集异质时,抽样会系统性低估极值。

### 4.6 【核心发现】`ASCEND_OM_OUTPUTSIZE` 的两个隐蔽行为

**行为一:单位是 MB,超范围会静默回退**

排错过程中曾设置 `ASCEND_OM_OUTPUTSIZE=524288000`（误以为单位是字节）与 `=1288`,两次均触发:
    
    
    GetOutputSizeFromENV  ASCEND_OM_OUTPUTSIZE is invalid, use default outputSize
    ...
    Current value:64
    

**超出合法范围时不报错退出,而是静默回退到默认值 64MB。** 这在排错期间造成了误导——以为提高了内存配额,实际反而降低了。

**行为二:该值是预分配的,直接决定单实例显存占用**

实测每实例 HBM 占用:

ASCEND_OM_OUTPUTSIZE | 单实例 HBM | 单实例 QPS  
---|---|---  
1024 MB | 2686 MB | 1.211  
256 MB | 1918 MB | 1.211  
64 MB | **1726 MB** | 1.208  
  
差值精确等于配置差（2686−1918 = 768 = 1024−256;1918−1726 = 192 = 256−64）,可推出**固定基础占用约 1662 MB** 。

由于本负载瓶颈正是 HBM 容量,**这一项直接决定单卡实例数上限** （见 6.3 节）。而三档配置下单实例 QPS 完全一致（1.208~1.211,差异在噪声范围内）,**说明降低该值不带来任何性能损失** 。

### 4.7 其他值得记录的操作问题

问题 | 说明  
---|---  
环境变量重启容器后丢失 | `$SOC` 未写入 `.bashrc`,导致一次 ATC 静默失败（`--soc_version for ATC is empty`）,误判为"固定 batch 无效"

全量回归 | 104/104 | 104/104 | 无退化  
  
**这是本次投入产出比最高的一项优化** :只修改一个环境变量,不改模型、不影响精度、不损失单实例性能,单卡吞吐提升 36.6%。

原值 1024 MB 是排错阶段为规避 `Model infer failed with dynamic shape` 而设置的保守值。按 rec 实际输出规模估算（batch 1 × 序列长度 × 字典 18000 × 4B）,64 MB 已经足够,全量回归 104/104 验证了这一点。

### 6.5 算力切分（vNPU）

#### 6.5.1 硬件支持的切分模板
    
    
    vir10_3c_32g:  AICore 10,  Memory 32GB,  AICPU 3
    vir05_1c_16g:  AICore  5,  Memory 16GB,  AICPU 1
    

整卡为 20 AICore / 64GB,因此仅支持 1/2 与 1/4 两种切分粒度。

#### 6.5.2 实际操作与遇到的阻塞

已完成:

  * 切换 `vnpu-mode -d 1`（docker 模式）
  * 成功创建 vNPU（`vir10_3c_32g`,Vnpu ID = 100）
  * 设备节点 `/dev/vdavinci100` 正常生成

**未完成:vNPU 环境下推理进程无法启动。**

尝试方式 | 结果  
---|---  
`ASCEND_VISIBLE_DEVICES=100` | runtime 去找 `/dev/davinci100`,报 `failed to get /dev/davinci100 info : 0x2`  
手动 `--device=/dev/vdavinci100` \+ 完整挂载 | 容器可启动,但 `npu-smi info` 报 -8005,推理报 `acl init failed, errorCode = 500000`  
  
`npu-smi info -t info-vnpu` 显示该 vNPU 的 `Container ID` 为全零、`Status` 为 0,即**未被任何容器认领** 。推测 Ascend Docker Runtime 在启动容器时需完成容器 ID 与 vgroup 的绑定注入,手动挂载设备节点跳过了这一步,导致 ACL 无法初始化。

受任务时间限制,未继续排查 runtime 的 vNPU 设备标识格式。

#### 6.5.3 基于已测数据的结论

尽管缺少 vNPU 压测数据,**基于已有实测事实仍可给出明确结论** :

**已实测的关键事实:**

  1. 拐点处 AICore 利用率仅 48~54%,**算力不是瓶颈**
  2. 单卡实例上限由 HBM 容量决定,每实例需 1726 MB
  3. 单卡峰值吞吐 27.96 QPS,约 38 实例

**推算:**

方案 | 可用显存 | AICore | 实例上限 | 预期聚合吞吐  
---|---|---|---|---  
物理卡 | 62.1 GB | 20 | ~38 | **27.96** （实测）  
vir10_3c_32g × 1 | 32 GB | 10 | ~18 | ~14（推算）  
vir10_3c_32g × 2 | 32 GB × 2 | 10 × 2 | ~36 | ≤27.96（推算）  
vir05_1c_16g × 4 | 16 GB × 4 | 5 × 4 | ~9 × 4 = 36 | ≤27.96（推算）  
  
**结论:算力切分对本负载的吞吐无正收益。**

理由:

  * **显存侧** :切分后各份显存之和不超过整卡,加上切分本身的元数据开销,实例总数只减不增
  * **算力侧** :实测所需算力约为整卡的 50%（折合约 10 AICore）。vir10 提供 10 AICore,恰好在临界点;vir05 仅 5 AICore,将成为新的瓶颈
  * **调度侧** :切分后各份之间无法共享空闲算力,资源利用率反而下降

**vNPU 的价值在于多租户隔离与 QoS 保障** ——保证某个业务不会被邻居挤占,而非提升整卡吞吐。若客户场景是单一 OCR 业务独占整卡,不建议启用算力切分。

## 8\. 结论

### 8.1 任务一:客户数据集摸测

  1. **单实例吞吐 1.21 QPS,平均时延 825 ms,P99 1592 ms** ,三次重复变异系数 0.67%。
  2. **耗时构成为固定开销 399 ms + 12.50 ms × 文本行数** ,rec 推理占典型页耗时的 59%。固定开销中约 300 ms 为 CPU 单线程的图片解码与前后处理,不使用 NPU。
  3. **精度可接受** :om 后端与 Paddle 后端字符一致率 99.88%,最低 99.17%,零推理失败。
  4. **单实例状态下 NPU 与 CPU 均严重空闲** （AICore 2.9%）,瓶颈是串行等待而非算力不足。

### 8.2 任务二:多实例吞吐与算力切分

  1. **单卡最高吞吐 27.96 QPS** ,在约 38 实例时达到,相对单实例提升 23 倍。
  2. **瓶颈是 HBM 显存容量,不是算力** ——拐点处 AICore 仅 48~54%,HBM 已达 99%。
  3. **`ASCEND_OM_OUTPUTSIZE` 从 1024 降至 64,单卡吞吐提升 36.6%**,单实例性能与精度均无损失。
  4. **算力切分对本负载无吞吐收益** ,其价值在多租户隔离与 QoS 保障。
  5. **吞吐与时延存在取舍** :38 实例时 P99 接近 4 s,若客户有时延 SLA,需在 8~16 实例区间选择工作点。

### 8.3 部署建议

场景 | 建议配置 | 预期表现  
---|---|---  
吞吐优先（批处理） | 单卡 36~38 实例,`OUTPUTSIZE=64` | ~28 QPS/卡,P99 约 4 s  
时延优先（在线服务） | 单卡 8~16 实例 | 8~15 QPS/卡,P99 < 2 s  
多租户隔离 | vir10_3c_32g 切分,每份 16~18 实例 | 吞吐低于物理卡,换取隔离性  
  
**必须配置项** :

  * `ASCEND_OM_OUTPUTSIZE=64`
  * rec / det 模型转换**不得使用 onnxsim**
  * om 动态 shape 范围需按客户实际数据全量统计后确定

## 10\. 局限性说明

以下事项如实列出,供阅读数据时参考:

  1. **样本量仅 104 张** ,单实例十余秒即可跑完,测试中通过 `--loop` 循环复用样本凑够测试时长（500 张 = 104 × 10 取前 500）。**存在 page cache 效应,图片解码耗时可能被低估,数据偏乐观。** 已向 PL 反馈需要更多样本。

  2. **两组爬坡测试的参数不同** ,不可直接跨组比较绝对 QPS:

     * OUT=1024 组:`--limit 100 --loop 5 --warmup 20`
     * OUT=64 组:`--limit 60 --loop 3 --warmup 15`

显存优化的效果结论主要依据**直接实测的每实例显存占用** （2686 → 1726 MB）与**实例数上限** （24 → ~38）,而非跨组的 QPS 数值比较。

  3. **56 与 72 实例组数据残缺** ,分别仅 38 与 36 个实例成功写出结果。该两行聚合值不代表标称实例数的真实吞吐。

  4. **CPU 利用率全程未采集成功** ,瓶颈判断基于 HBM 与 AICore 两项指标。

  5. **未开启 BIOS 高性能模式** （服务器为共享资源,协调独占后未申请重启进行 BIOS 配置）。透明大页已开启。

  6. **vNPU 结论为推算** ,非实测。推算基于已实测的 AICore 利用率与单实例显存占用,逻辑链完整,但未经压测验证。

  7. **精度校验为 30 张抽样** ,非全量 104 张。抽样方式为按排序后步长均匀取样,覆盖全部 4 个目录。

  8. **`ASCEND_OM_OUTPUTSIZE` 的合法上界未确定**。已知 1024 有效、1288 与 524288000 被判 invalid,但未系统测试边界值。

# KAOT 模板在小规模 TPC-C 场景下的适配性分析

> **机器** Kunpeng 920 7260 / openEuler 22.03 LTS-SP4 / 502.36 GB 内存 **数据库** openGauss 极简版，单机，端口 5432 **负载** BenchmarkSQL 5.0（TPC-C），10 仓，5-10分钟/轮 **调优工具** KAOT 1.0.0，场景 `opengauss_database` **实验周期** 2026-09-02 ~ 2026-09-16，共六个阶段

* * *

## 0\. 一页结论

最初的实验得出"KAOT 调优后性能下降 24.5%"。经过五轮追加实验，这个结论被两次修正：

阶段 | 结论 | 后来发现  
---|---|---  
一 | KAOT 使 tpmC 下降 **24.5%** | 大部分降幅来自**未还原测试数据** ，不是参数  
三 | 元凶是 `shared_buffers=151GB`，改为 8GB 可 **+14.6%** | 只在 **16 终端** 成立，该并发下 KAOT 几乎无用武之地  
四~六 | **100 终端下 KAOT 实际提升 +116.1%** ，其中 **90.3% 来自`shared_buffers` 一个参数** | —  
  
**最终结论：**

  1. **KAOT 模板在本机型上确实有效，100 并发下 tpmC 提升 +116.1%** （82,726 → 178,780）。
  2. **这份收益的 90.3% 由`shared_buffers` 从 1GB 提升到 8GB 单独贡献**；模板中其余四十余个参数合计贡献 9.7%。
  3. **KAOT 推荐的 151GB 是容量扫描曲线上表现最差的一档** 。2GB 即达到吞吐平台，4~~8GB 是本负载的合理区间，151GB 比合理值大 19~~ 38 倍。
  4. **模板收益高度依赖并发量级** ：16 终端时 KAOT 与默认配置无显著差异（甚至略负），32 终端起才显现优势。
  5. 对工具的核心建议：`shared_buffers` 应按**数据集规模** 而非物理内存比例推导。

* * *

## 1\. 前序知识

按"从硬件到应用"的顺序整理本实验涉及的概念。

### 1.1 鲲鹏 920 与 aarch64

鲲鹏 920 是华为海思基于 ARMv8 自研的服务器 CPU，架构为 **aarch64** （64 位 ARM），与常见 x86_64 指令集不同，所有软件包（JDK、JDBC、数据库二进制）都需 aarch64 版本。7260 为 64 核型号，双路构成 128 核，涉及 **NUMA** （非一致性内存访问）——每颗 CPU 访问本地内存快、访问另一颗挂载的内存慢。

### 1.2 openGauss 关键概念

openGauss 基于 PostgreSQL 9.2.4 内核演化，语法、驱动、配置文件高度相似，因此 BenchmarkSQL 使用 **PostgreSQL 的 JDBC 驱动** ，配置文件名为 `postgresql.conf`。

概念 | 说明 | 与本实验的关系  
---|---|---  
**shared_buffers** | 数据库自管的内存页缓存，数据页从磁盘读入后驻留于此 | **本实验的核心变量**  
**buffer 替换（clock-sweep）** | 缓存满时需挑选牺牲页换出，涉及修改全局哈希表，**需要加锁** | **理解结论的关键机制**  
**WAL** | 预写日志，修改先顺序写日志再刷数据页 | `wal_buffers`、`wal_level`、`xloginsert_locks`  
**增量检查点 / pagewriter** | openGauss 默认启用增量检查点，脏页由 pagewriter 线程刷出，**不走传统 bgwriter 路径** | `pg_stat_bgwriter` 的计数器恒为 0，须改用 `local_pagewriter_stat()`  
**double-write** | openGauss 用双写缓冲防"半页写"，与 `full_page_writes` 功能重叠 | 解释了 FPW 关闭反而变慢  
**命中率** | `blks_hit / (blks_hit + blks_read)`，从 `pg_stat_database` 读取 | 本实验的关键佐证指标  
  
### 1.3 TPC-C 与 BenchmarkSQL

TPC-C 模拟批发公司业务，五种事务按固定权重混合（NewOrder 45%、Payment 43%、其余各 4%）。**tpmC** 指每分钟完成的 NewOrder 事务数，是官方成绩单位。

关键规模关系：

  * **仓数决定数据量** 。每仓约 100 MB 原始数据，10 仓约 1 GB（含索引 1.5~2 GB）。
  * **终端数决定并发压力** 。规范要求每仓最多 10 个终端，10 仓上限为 100 终端。
  * **两者是独立的轴** ：加终端不会增加数据量，加仓数不会自动增加并发。本实验后期正是靠分离这两个轴才定位到真正的规律。

### 1.4 KAOT

KAOT（Kunpeng & Ascend Optimization Tool）是 BoostKit 下的**规则式** 调优工具——识别环境、匹配预置场景、下发一份实验室验证过的参数模板。三个子命令：`basecfg` 采集基线、`generate` 生成调优单、`execute` 使能。

注意 `opengauss_database` 场景**只包含`optimize_opengauss_database_config` 一项**，不含网卡绑核、IO 调度等 OS 层调优项（kingbase、dameng 场景才有）。

### 1.5 阿姆达尔定律与串行瓶颈

本实验最终解释依赖这一原理：**系统中任何一段串行路径都会成为并发扩展的天花板** 。缓存不足导致的 buffer 替换正是这样一段串行路径——低并发时排队少、成本可忽略，高并发时排队时间超线性增长，成为吞吐上限。这解释了为什么同一个参数在 16 终端下无关紧要、在 100 终端下价值翻倍。

## 4\. 阶段二：方法论修正

### 4.1 发现

补查得知**基线`shared_buffers = 1024MB`**。据此可以量化（openGauss 页大小 8KB）：

项 | 数值  
---|---  
基线 buffer 数 | 1GB ÷ 8KB = **131,072**  
数据实际页数 | ~1.5GB ÷ 8KB ≈ **196,608**  
KAOT buffer 数 | 151GB ÷ 8KB = **19,791,872**  
有效利用率 | **0.99%** （99% 的 buffer 为空）  
描述符数组开销 | 19,791,872 × 64B ≈ **1.27 GB**  
4KB 页映射的页表项 | 151GB ÷ 4KB ≈ **3,958 万** ，页表约 316 MB  
  
同时注意到 `opengauss_database` 场景**不包含`config_hugepages`**——模板给出了大内存配置，却没有配套的大页配置。

### 4.2 关键修正：数据还原

引入"每轮还原数据"后，**同一份 KAOT 配置在 16 终端下的成绩从 35,600 升至 48,883，涨幅 37.3%** ；而默认配置只从 47,153 升至 51,579，涨幅 9.4%。

![方法论修正的影响](https://linlin.works/zh/blog/charts/fig2_methodology.png)

**阶段一 −24.5% 中的绝大部分来自测试方法缺陷，而非参数。** 9/4 的 KAOT 测试跑在已被 9/2 三轮压测磨损过的数据上，受损远比基线严重。

修正后同口径复测，KAOT 全量为 −5.2%，量级完全不同。

### 4.3 批次间漂移

三个批次的 A、B 组数据（均为 16 终端）：

批次 | A | B | B/A  
---|---|---|---  
阶段一（9/4，未还原） | 47,153 | 35,600 | −24.5%  
阶段三（已还原，n=2） | 51,579 | 48,883 | −5.2%  
阶段四（已还原，n=1） | 55,840 | 59,226 | **+6.1%**  
  
后两个批次符号相反，且 B 组波动（+21.2%）远大于 A 组（+8.3%）。

**结论：跨批次数据不可直接比较。** 本报告所有核心结论均基于**同一批次内** 的对比。

组 | 配置 | tpmC 均值 | 标准差 | CV | 相对 A  
---|---|---|---|---|---  
A | 默认 1GB | 51,579 | 936 | 1.8% | —  
B | KAOT 全量 151GB | 48,883 | 2,824 | 5.8% | **−5.2%**  
C1 | B 但 buffer→8GB | **59,092** | 470 | 0.8% | **+14.6%**

### 5.1 C1 与 C2 的判别

这一对是本阶段的核心设计：

  * **C1** （只把 buffer 从 151GB 改为 8GB）→ **+14.6%** ，完全收复损失并转正
  * **C2** （保留 151GB，只把刷盘频率降回默认）→ **−7.5%** ，毫无改善

**判定：问题出在 buffer 池容量本身，与刷盘频率无关。** 原先"大池 + 高频 bgwriter 扫描组合失配"的假设被 C2 排除。

### 5.2 full_page_writes 的反常结果

E'（FPW on）比 E（FPW off）高 **3.2%** ，两轮结果一致。查得 `enable_double_write = on`。

openGauss 在增量检查点模式下依靠 double-write 防半页写，关闭 `full_page_writes` 并不能减少 WAL 写入量，反而多走一层。**这与 PostgreSQL 上 "关 FPW 提性能"的常识相反**，建议在 openGauss 上保留 `full_page_writes=on`。

### 5.3 本阶段结论的局限

此时 CPU 利用率仅 20~30%，机器远未跑满。该结论后被证明**只在低并发下成立** 。

A、B、C1 三组 × 16/32/64/100 终端，各 1 轮。

![并发扫描](https://linlin.works/zh/blog/charts/fig4_concurrency.png)

### 6.1 两个发现

**一、KAOT 的价值高度依赖并发。** 16 终端时三组基本持平，32 终端起迅速拉开，100 终端时达到 +108%。前三个阶段全部在 16 终端下进行，**恰好落在唯一看不出模板价值的区间** 。

**二、151GB 的惩罚在高并发下消失。** 100 终端时 B 与 C1 只差 0.3%。大 buffer 池的管理开销是**固定成本** ，吞吐涨到 2.9 倍后被摊薄至不可见。

### 6.2 扩展性

16 → 100 终端（6.25 倍并发）的吞吐倍数：

组 | 倍数  
---|---  
A | 1.47  
B | 2.88  
C1 | 2.80  
  
A 在约 8.2 万 tpmC 处撞墙。同时三组在 64→100 区间涨幅均只有 9~10%，均已接近饱和——这一段更可能受 10 仓 warehouse 行锁争用限制。

### 6.3 机制解释

A 与 B/C1 的命中率相差约 1 个百分点（98.9% vs 99.9%），换算成物理读差 7.5 倍：

| 物理读总数 | 折合每秒  
---|---|---  
A@100 | 4,542,035 | ~15,140  
B@100 | 600,831 | ~2,000  
  
每一次缺页都要走 clock-sweep 选牺牲页、必要时刷脏页、**修改全局 buffer 映射哈希表（需加锁）** 。这把锁被所有连接共用：

  * **16 终端** ：约 2~3 千次/秒缺页分摊到 16 个线程，撞锁概率低，缺页成本仅为内存拷贝，可忽略。此时大 buffer 省下的开销恰好被 151GB 的固定管理成本抵消，两组打平。
  * **100 终端** ：1.5 万次/秒缺页、100 个线程争同一把锁，排队时间随并发**超线性** 增长，成为吞吐天花板。

**小 buffer 的代价不是 "慢一点"，而是多出一段串行路径。** 串行瓶颈在低并发下隐形，高并发下即天花板——这是阿姆达尔定律的典型表现。

### 7.2 单参数验证

**G 组只有 +2.6%。** `xloginsert_locks` 从默认值提升到 48 曾被怀疑是高并发下的关键项（WAL 插入锁竞争是 PostgreSQL 系数据库的经典瓶颈），实测贡献在噪声量级内。

**F 组单改一个参数即达到 +104.8%** ，占全量模板绝对吞吐的 94.8%、增益的 90.3%。

此外，C1@100（8GB + KAOT 全部其他参数，阶段四）= 169,968，与 F（8GB，什么都不加）= 169,457 相差 **0.3%** 。两次独立测量互相印证：**在 8GB buffer 的基础上，KAOT 其余参数几乎不产生额外收益。**

### 8.1 曲线形态

**这是悬崖，不是缓坡。** 1GB → 2GB 吞吐翻倍，2GB 之后进入平台，2~~16GB 四个点全落在 168,538~~ 170,730（极差 1.3%）。

### 8.2 尾部下降

从 16GB 峰值往后单调下降：170,730 → 166,236 → 164,932，**151GB 是全扫描表现最差的一档** ，较峰值低 3.4%。

**须谨慎表述** ：各点均为单次测量，而历史变异系数为 4~6%，3.4% 在单次测量误差范围内。仅能说"呈轻微下降趋势，方向与固定管理开销随容量增长的解释一致"，不能作为定量结论。

### 8.3 推荐值不是 2GB

2GB 虽已达到吞吐平台，但物理读为 4,282 次/秒，仍是平台底值（约 1,970）的 **2.2 倍** ；4GB 才降至 2,147，基本触底。

**2GB 刚好踩在悬崖边缘——吞吐已满但缓存未饱和，数据集稍有增长即可能跌回。**

**推荐 4~8GB** ，相对约 1.5~~2GB 的热点工作集留 2~~ 4 倍余量。KAOT 的 151GB 比该区间大 **19~38 倍** 。

## 9\. 结论

### 9.1 主结论

  1. **KAOT 模板在本机型、100 并发下有效，tpmC 提升 +116.1%** （82,726 → 178,780）。
  2. **90.3% 的增益由`shared_buffers` 从 1GB 提升到 8GB 单独贡献**；`wal_level`/`max_connections` 贡献 6.8%；其余全部参数合计 2.9%。
  3. **KAOT 推荐的 151GB 位于容量扫描曲线的最低点** 。本负载的合理区间为 4~8GB。
  4. **模板收益高度依赖并发量级** ：16 终端时与默认配置无显著差异，32 终端起显现，100 终端达到峰值。
  5. `full_page_writes=off` 在 openGauss 上为负收益（−3.2%），因与 double-write 机制重叠。

### 9.2 推荐配置（本负载）
    
    
    shared_buffers = 4GB        # 数据集 ~1.5GB，留 2-3 倍余量
    wal_level = minimal         # 单机无备机
    hot_standby = off
    max_connections = 200       # 按实际并发 + 余量，非 2048
    full_page_writes = on       # openGauss 上不要关
    

以上五项即可获得约 +112% 的收益（对应 D 组）。

### 9.3 适用边界

**本结论的严格适用范围是：10 仓（约 1.5GB）数据集。**

`shared_buffers` 的需求上限由数据量本身限制，本实验的数据集规模决定了 151GB 永远无法被利用。KAOT 按 502GB 物理内存推导的 151GB，其假设场景是数据集达到百 GB 量级。验证该假设需将数据集扩大至 200 仓（约 20GB）以上，本次未覆盖。

### 9.4 对 KAOT 的改进建议

  1. **`shared_buffers` 应按数据集规模而非物理内存比例推导。** 当前按物理内存 30% 计算，在小数据集场景下推荐值可高出合理区间一个数量级以上，且在本实验中恰好落在扫描曲线最低点。建议增加数据量探测，或提供按数据规模分档的推荐值。
  2. **模板应声明适用条件。** 建议 `generate` 时输出该模板验证时的数据规模与并发量级，便于使用者判断是否匹配。
  3. **大内存配置缺少配套大页设置。** `opengauss_database` 场景不含 `config_hugepages`，151GB 以 4KB 页映射产生约 3,958 万页表项，建议两者联动。
  4. **`full_page_writes=off` 在 openGauss 上应重新评估。** 与 double-write 机制重叠，实测为负收益。

### 9.5 方法论收获

本实验前三个阶段的结论均被后续推翻，原因值得记录：

缺陷 | 后果 | 修正  
---|---|---  
未在每轮压测前还原数据 | 结果被数据磨损污染，−24.5% 严重高估 | 每轮从干净备份还原  
两组测试相隔两天 | 无法排除机器状态差异 | 同批次交叉执行 + 锚点组  
只在单一并发点测试 | 恰好落在模板价值为零的区间 | 并发扫描  
只测"全量 vs 默认" | 无法归因到具体参数 | 单参数隔离 + 容量扫描  
  
**单点对比只能得到 "有没有效"，无法得到"为什么"。** 消融与扫描的成本远低于其提供的信息量——本实验后三个阶段合计耗时约 4 小时，但贡献了全部有效结论。

## 10\. 局限与后续工作

### 10.1 已知局限

  1. **样本量不足。** 阶段一 n=3，阶段三 n=2，阶段四至六均为 **n=1** 。单次测量在 4~6% 变异系数下，小于 10% 的差异不具统计意义。 **缓解** ：核心结论的量级远超噪声（+104.8%、+116.1%），且平台区由 6 个独立配置点交叉印证（8GB 两次测量相差 0.3%，1GB 两次相差 0.9%）。
  2. **CPU 利用率数据无效。** 采集脚本读取 `/proc/stat` 时遗漏了 iowait/irq/softirq 字段，导致吞吐翻倍而记录值反而下降（17~30%）。**本报告未使用任何 CPU 数据支撑结论** ，相关数字应视为无效。
  3. **数据集规模未实测。** 全文的"约 1.5GB"为按 TPC-C 规范推算值，未执行 `pg_database_size` 确认。推荐值因而只能给绝对值，无法表述为"数据集的 N 倍"这一可推广的规则。
  4. **阶段六无自身锚点组。** buffer 扫描批次未包含 A 组，比较基准取自阶段五。两批次的 A 相差 0.9%，漂移可接受，但严格性弱于同批次对比。
  5. **单条记录异常。** 阶段三 A 组第 2 轮的 tpmTOTAL 记为 125,997.81，与 tpmC 之比为 41.5%，偏离其余 13 条记录的 44.9~45.1% 区间，疑为转录错误。该行 tpmC 正常，未影响结论。

### 10.2 后续工作

  1. **扩大数据集至 200 仓（约 20GB）** ，在 A / 8GB / 151GB 三点复测，确定 KAOT 推荐值开始成立的数据规模阈值。这是回答"模板在什么条件下正确"的唯一途径。
  2. **补充核心点的重复轮次** ，至少 2GB、8GB、1GB 三点各补至 3 轮。
  3. **修复 CPU 采集** （安装 sysstat 用 mpstat，或补全 `/proc/stat` 字段），确认 100 终端下机器是否真正饱和、瓶颈是否已转移至 warehouse 行锁。
  4. **验证大页假设** ：配置 2MB 大页后复测 151GB，判断尾部下降是否源于 TLB 压力。

### C.1 单轮准备（还原数据 + 换配置 + 起库）
    
    
    #!/bin/bash
    # run_one.sh <组名> <轮次标识>
    set -e
    GRP=$1; RUN=$2
    DATA=/opt/software/openGauss/data
    DN=$DATA/single_node

    LOG=/home/omm/exp2/logs
    mkdir -p $LOG
    
    gs_ctl stop -D $DN || true
    sleep 3
    rm -rf $DN
    tar -zxf /home/omm/exp2/tpcc_clean.tar.gz -C $DATA
    cp $CONF $DN/postgresql.conf          # ★ 还原会覆盖配置，必须这步
    gs_ctl start -D $DN
    sleep 10
    
    gsql -d tpccdb -p 5432 -c \
     "show shared_buffers; show bgwriter_delay; show max_connections; \
      show wal_level; show full_page_writes;" > $LOG/${GRP}_${RUN}_guc.txt 2>&1
    gsql -d tpccdb -p 5432 -c "select pg_stat_reset();" >/dev/null 2>&1 || true
    cat $LOG/${GRP}_${RUN}_guc.txt
    

### C.2 指标采集
    
    
    #!/bin/bash
    # collect.sh <组名> <轮次> <before|after>
    GRP=$1; RUN=$2; WHEN=${3:-after}
    LOG=/home/omm/exp2/logs
    F=$LOG/${GRP}_${RUN}_${WHEN}.txt
    {
    echo "=== $GRP $RUN [$WHEN] $(date '+%F %T') ==="
    gsql -d tpccdb -p 5432 -t -c "
    select 'blks_read=' || blks_read, 'blks_hit=' || blks_hit,
           'hit_ratio=' || round(blks_hit*100.0/nullif(blks_hit+blks_read,0),3)
    from pg_stat_database where datname='tpccdb';"
    gsql -d tpccdb -p 5432 -x -c "select * from local_pagewriter_stat();"
    gsql -d tpccdb -p 5432 -x -c "select * from local_ckpt_stat();"
    } > $F 2>&1
    cat $F
    

> 注意：openGauss 启用增量检查点时 `pg_stat_bgwriter` 的 `buffers_*` 计数恒为 0， 必须使用 `local_pagewriter_stat()` / `local_ckpt_stat()`。

## 已知不支持

  * 脚注：`[^1]` 与 `[^1]: 说明` 会被 marked 当成引用式链接的写法，渲染成一条链接，而不是脚注。
  * 高亮 `==文本==`：不是标准 Markdown，需要额外插件，本站没装。
  * 定义列表：`术语` 换行接 `: 解释` 的写法没有任何效果。
  * 任务列表以外的扩展：复选框只有浏览器默认样式，本站没有额外的 CSS。
