## Context

早期实现把代码、渲染输出和运行时状态混在 `main` 与 `gh-pages` 两个分支中：

- `main` 既放代码，也由 CI 直接提交 `feeds.toml`；
- `gh-pages` 同时存放 `output/`、`state.json`、`articles.json` 和旧版 `cache.json`；
- `actions/cache` 使用固定 key `rss-state`，可能恢复过期状态，形成隐藏的第二份数据源；
- CI 用 `git worktree` 在分支之间搬运文件，恢复失败时容易丢失状态，或把运行时文件重新写回渲染分支。

这些做法导致职责重叠、并发运行时互相覆盖、恢复逻辑脆弱，并且 `gh-pages` 的历史同时包含站点和状态两种完全不同的数据。

## Decision

### 1. 分支职责

| 分支 | 允许的内容 | 写入方式 |
|------|-----------|----------|
| `main` | 代码、`config.toml`、`feeds.toml`、文档、测试 | 普通提交；feed 同步由独立 workflow 提交 |
| `data` | `state.json`、`articles.json`、`status.json` | 每次采集一个 snapshot commit，force-push |
| `gh-pages` | `output/` | 每次采集一个 snapshot commit，force-push |

约束：

- 运行时状态只能出现在 `data`，不能出现在 `main` 或 `gh-pages`。
- `gh-pages` 只保存渲染后的站点快照，不保存 `state.json`、`articles.json`、`status.json`。
- `main` 不保存任何运行产物。
- GitHub Pages 仍然从 Actions artifact（`upload-pages-artifact` + `deploy-pages`）部署，`gh-pages` 只是持久化/可浏览快照，不是 Pages 的部署源。

### 2. Snapshot + force-push

每个采集周期的流程是：

1. 从 `data` 以 `--depth 1` 恢复运行时状态；
2. 从 `gh-pages` 只恢复 `output/`；
3. 运行 fetch / classify / cleanup / report / check；
4. 把当前状态写成一个 commit，force-push 到 `data`；
5. 把当前 `output/` 写成一个 commit，force-push 到 `gh-pages`。

force-push 是有意为之：这两个分支是 CI 派生出来的状态，不是多人协作的分支，不需要 merge。每次运行只产生一个 snapshot commit，避免 merge commit 和冲突处理逻辑。GitHub 仍会在服务端保留一段时间的旧对象，但不能把历史提交当作运行时数据源。

### 3. 保留策略

- `data`：只有最新 tip 是有效状态。`articles.json` 仍按 14 天窗口清理；`status.json` 表示最近一次运行。
- `gh-pages`：只有最新 tip 是有效站点快照。`output/` 遵循 ADR-003 的 append-only 语义：历史行不删除，过去日期的文件除幂等追加/修复外不重写，同一天的文件可以扩展。
- 迁移脚本生成的 `backup/*` refs 用于回滚，确认稳定后由维护者手动删除。
- 不依赖分支历史做恢复；需要恢复时使用最新可用的 `data` commit、迁移备份或重新 bootstrap。

### 4. Bootstrap

`data` 或 `gh-pages` 不存在时，工作流不能失败：

- `data` 拉取失败：警告并以空状态继续；本次运行成功后创建 orphan `data` 分支。
- `gh-pages` 拉取失败或没有 `output/`：警告并以空输出继续；本次运行成功后创建 orphan `gh-pages` 分支。
- 持久化时如果 `state.json` 或 `articles.json` 缺失，跳过 `data` push，避免用不完整快照覆盖已有状态。

首次部署新工作流时，`collect.yml` 会在 `data` 缺失或缺少 `state.json` / `articles.json` 时回退读取旧 `gh-pages` 中的运行时文件，因此不会因为迁移顺序造成状态重置。仍然建议在稳定期执行一次迁移（见下节），把旧文件从 `gh-pages` 清理掉，避免长期依赖兼容路径。

### 5. 迁移

`scripts/migrate_branches.sh` 是手动、一次性的迁移工具：

- 默认只打印计划，不修改远端；
- `--apply` 才会先把旧分支备份到 `backup/gh-pages-<timestamp>` / `backup/data-<timestamp>`，再创建只含运行时状态的 orphan `data`，并把 `gh-pages` 重写为只含 `output/`；
- 脚本在临时目录中操作，不修改本地分支或工作区；
- 输出备份与回滚命令。

迁移前必须确认 `origin/gh-pages` 中存在 `state.json` / `articles.json`（或旧 `cache.json`）。迁移完成后，`gh-pages` 不再包含运行时文件。

## Consequences

优点：

- 每个分支只有一种职责，恢复和持久化路径清晰；
- 去掉 `actions/cache` 后不再有隐藏的过期状态源；
- force-push snapshot 避免并发 merge 冲突，失败时最多丢掉一次运行的增量；
- `gh-pages` 体积只随渲染输出增长，不混入运行时文件；
- 分支缺失时可以安全 bootstrap。

缺点：

- `data` / `gh-pages` 的历史不能直接用于回滚业务状态，需要显式备份；
- force-push 会覆盖远端分支，必须避免人工在这些分支上直接提交；
- 迁移需要一个一次性手动步骤；
- 首次运行新工作流前如果忘记迁移，会丢失旧 `gh-pages` 中的运行时状态。
