## Context

ADR-016 把 `articles.json` 的正文留在 Actions cache，只在 `data` 分支保存每日元数据。这控制了仓库体积，但也意味着：

- 用户要求**保留文章原文**，而不是只保留标题/链接/摘要；
- cache 随时可能被 GitHub 驱逐，正文一旦丢失就无法从 git 恢复；
- 仓库是公开的，归档内容必须经过清洗，不能直接保存 feed 提供的任意 HTML；
- 需要按 feed 聚合，且能快速读取单篇正文，而不是每次加载整份大 JSON；
- 希望按天分文件（`archive/YYYY/MM/DD.md`）、append-only、diff 可读；
- 站点和 JSON Feed 应从归档派生，而不是把渲染结果当作事实来源。

因此需要一个新的长期存储形态：**清洗后的 Markdown 正文进入 git，按天追加，并用字节偏移索引文章**。ADR-016 的“正文只进 cache”决定被本 ADR 取代。

## Decision

### 1. 每日 Markdown 归档

归档文件固定为：

```
archive/
  2026/
    05/
      01.md
      02.md
```

- 按文章的发布日期（UTC；缺失时用 `fetched_at` / `cached_at`）分天；
- **append-only**：只追加新记录，不重写历史；重复运行不能删除已有记录；
- 文件内容是清洗后的 Markdown，所有 HTML 在写入前经过与抓取相同的 sanitizer；
- 文件名和目录结构是稳定的，渲染器和索引重建都依赖它。

单条记录的格式：

```markdown
<!-- rss-aggr:article v1
{"v":1,"guid":"tag:example.com,2026:1","feed_id":"example.com-1a2b3c4d5e6f","feed_url":"https://example.com/feed.xml","site_url":"https://example.com/","link":"https://example.com/post/1","title":"An example post","author":"Alice","published":"2026-05-01T08:00:00Z","fetched_at":"2026-05-01T09:12:00Z","body_len":42,"body_sha256":"<sha256 of the body bytes>"}
-->
Body **Markdown** goes here.

<!-- /rss-aggr -->
```

约定：

- 头部第一行固定为 `<!-- rss-aggr:article v1`，第二行是紧凑 JSON，随后是 `-->\n`；
- 头部 JSON 中的 `--` 会转义为 `\u002d\u002d`，避免提前结束 HTML 注释；
- 正文之后是 `<!-- /rss-aggr -->\n`；如果正文本身不以换行结尾，会在正文和 footer 之间补一个 `\n`；
- `v` 是记录版本，目前为 `1`；
- `body_len` 是正文的 **UTF-8 字节数**，`body_sha256` 是正文字节的 SHA-256；
- 读取时以 `body_len` 定界，而不是按空行或 footer 搜索，因此正文中出现 `<!-- /rss-aggr -->` 也不会破坏 framing；
- 偏移量全部是文件内的 **UTF-8 字节偏移**，不是字符数。中文、emoji 等多字节内容不会导致错位。

### 2. 偏移索引

读取单篇正文不需要扫描整个文件。索引记录保存：

| 字段 | 含义 |
|------|------|
| `file` | 归档相对路径，例如 `archive/2026/05/01.md` |
| `offset` | 记录起始字节偏移 |
| `length` | 整条记录（header + body + footer）的字节长度 |
| `body_offset` | 正文起始字节偏移 |
| `body_len` | 正文字节长度 |
| `sha256` | 正文 SHA-256，用于校验 |
| `guid` / `link` / `title` / `published` | 检索和渲染所需元数据 |

验证一条记录时使用 `offset` + `length` 读取、按 `body_len` 切出正文，并比对 `sha256`。任何长度或摘要不匹配都视为归档损坏。

### 3. 每 feed JSONL 索引

```
feeds/
  example.com-1a2b3c4d5e6f.jsonl
```

每个文件第一行是 feed header，之后只追加 article / annotation 记录：

```jsonl
{"v":1,"kind":"feed","feed_id":"example.com-1a2b3c4d5e6f","feed_url":"https://example.com/feed.xml","site_url":"https://example.com/","title":"Example"}
{"v":1,"kind":"article","feed_id":"example.com-1a2b3c4d5e6f","file":"archive/2026/05/01.md","offset":0,"length":312,"body_offset":210,"body_len":42,"sha256":"...","guid":"tag:example.com,2026:1","link":"https://example.com/post/1","title":"An example post","published":"2026-05-01T08:00:00Z"}
{"v":1,"kind":"annotation","guid":"tag:example.com,2026:1","file":"archive/2026/05/01.md","offset":0,"category":"Tech","summary":"A short summary","score":8,"classified_at":"2026-05-01T10:00:00Z"}
```

- `feed_id` 由 canonical feed URL 派生，格式为 `<host slug>-<12 hex>`，稳定且适合做文件名；
- article 记录按 guid / canonical link 去重；同一 feed 重复抓取不会产生重复索引；
- annotation 记录 append-only，读取时“最新一条胜出”；重新分类不会覆盖旧记录；
- 索引是**派生数据**：删除 `feeds/*.jsonl` 后可以从每日 Markdown 归档重建；
- 重建会丢失历史 annotation（分类/摘要/评分），因为归档只保存原文，不保存分类结果。重建前应尽量保留现有索引。

### 4. `article_state.json` 保存待分类元数据

文章处理状态写入 `article_state.json`，不再使用旧的 `articles.json`。文件是带版本的对象：

```json
{"v": 1, "articles": [ ... ]}
```

每条记录只保存：

- 14 天窗口内的 pending / failed / classified 元数据；
- 归档引用：`archive_file`、`archive_offset`、`archive_length`、`archive_body_len`、`archive_sha256`；
- 分类状态、失败次数、feed 元数据和 canonical link；
- `indexed` 标志：是否已写入对应的 `feeds/<feed_id>.jsonl` article 记录。

分类时按偏移从归档 hydrate 正文到内存，写回时再次剥离正文；`save_articles` 会做最后一道 `content` / `content_length` 剥离。`data` 上的 `article_state.json` 永远不包含原文；原文只在 `archive/`。

`article_state.json` 与 feed 抓取状态分离：`feed_state.json` 记录每个 feed 的 `last_attempt`、ETag、失败计数、`retry_at`、`disabled`，由 `src.feed_state` 管理；`article_state.json` 只记录文章处理进度。旧的 `state.json` / `articles.json` 仅作为 legacy fallback 被读取，不再写入。

### 5. 渲染与发布

归档是站点唯一的事实来源：

```bash
python -m src.render --site _site --archive archive --feeds feeds --feed-config feeds.toml
```

渲染结果：

- `<site>/YYYY/MM/DD.html`：每日文章页，正文从归档记录读取；
- `<site>/archive/YYYY/MM/DD.md`：每日 Markdown 的公开副本，供 Range 请求读取；
- `<site>/feeds/<feed_id>.json`：JSON Feed 1.1，包含 `id`、`title`、`url`、`date_published`、`summary`、`tags`、`_score`，以及用 `summary`（没有时用 `title`）填充的 `content_text`；`_archive` 给出 `file` / `body_offset` / `body_len` / `sha256`；
- `<site>/feeds/<feed_id>.html`：轻量 HTML 壳，JS 加载同名 JSON，再按 `_archive` 坐标对 `.md` 发 HTTP Range 请求，只取目标正文；
- `<site>/index.html`：日期和 feed 索引。

渲染只读 `archive/`、`feeds/*.jsonl` 和当前的 `feeds.toml`，不读 `output/` 或 `article_state.json`。`feeds.toml` 在渲染时叠加当前 feed 的 `title` / `site` / `feed_url`；JSONL header 仍保持 append-only 的历史值，只作为 fallback。输出文件名来自索引里的 `feed_id`（经过 slug 化和重名后缀处理），不一定与索引文件名逐字相同。

JSON Feed 是供其他系统消费的元数据/摘要/坐标索引，不是全文副本；全文只在 `archive/YYYY/MM/DD.md`（以及页面上的日视图）中。Range 请求返回 `206` 时直接使用；服务器忽略 Range 返回 `200` 时，前端取整文件后按字节切片兜底。

Pages 使用 Actions artifact（`upload-pages-artifact` + `deploy-pages`）发布，不再使用 Jekyll，也不再写 `gh-pages`。

### 6. 存储角色

| 位置 | 内容 | 角色 |
|------|------|------|
| Actions cache | `archive/`、`feeds/`、`feed_state.json`、`article_state.json`、`output/` | 热副本，加速运行，不是事实来源；不保存派生报告 `status.json` |
| `data` 分支 | `archive/`、`feeds/`、`feed_state.json`、`article_state.json`；`archive/`、`feeds/` append-only；旧 `output/` 可能残留但不更新 | 持久归档和运行状态，cache miss 的恢复源；不含 `status.json` |
| 工作区 | `status.json` | 本轮 `--report` / `--check` 从 `feed_state.json` + `article_state.json` 现算的派生报告，不持久化 |
| `main` | 代码、配置、文档、workflow | 不含运行时数据 |
| Pages artifact | 渲染后的静态站点 | 可重建的派生产物 |

文件职责：

- **`feed_state.json`**：每 feed 的运行状态（`last_attempt`、ETag、失败计数、`retry_at`、`disabled`）。fetch 前按 `feeds.toml` 对账，删除不再配置的 URL；`skip = true` 的 feed 仍在配置里，因此保留；需要显式清除时用 `python -m src.feed_state --forget URL`。
- **`article_state.json`**：文章处理状态和待分类队列，包含归档坐标和 `indexed` 标志；不保存正文。写索引失败的记录保留 `indexed=false`，下一轮 fetch 从归档补写。
- **`status.json`**：仅派生报告。它不是运行输入，不进 data 快照，也不进 cache；丢失或过期不影响下一轮采集。
- **`output/`**：给人看的人工摘要。它不参与 fetch/classify 去重，也不是归档；旧 `data` 上的副本会保留，但新快照不再写入。
- **`state.json` / `articles.json`**：旧布局名字，只作为迁移输入和 loader fallback；`src.migrate_state` 拆分后，下一份 data 快照会删除。

cache 命中时优先使用热副本；cache 未命中时从 `data` 恢复完整归档和索引，再设置 `RSS_FORCE_FETCH=1` 刷新窗口。cache 不再是正文的唯一副本。快照会整体替换 `feed_state.json` / `article_state.json`，但 `archive/` / `feeds/` 只允许增长；`status.json` 若在远端出现会被拒绝。

### 7. 迁移与回填

旧布局（ADR-016）使用 `state.json` / `articles.json`，其中 `articles.json` 还可能含原始 HTML。迁移分两步。

**状态文件名迁移**：先运行一次性命令，把旧文件拆成新文件：

```bash
python -m src.migrate_state
# 确认新文件正确后，可同时删除旧名
python -m src.migrate_state --remove-legacy
```

它写出 `feed_state.json` 和版本化对象 `{"v":1,"articles":[...]}` 的 `article_state.json`；文章行会被规范化为 metadata-only（剥离 `content` / `content_length`），归档正文不受影响。`collect.yml` 在恢复数据后、任何归档操作前都会自动执行这一步；loader 也会在新文件缺失时 fallback 到旧名。

**正文回填**：如果旧 `articles.json` 含原始 HTML，用旧文件作为输入：

```bash
python -m src.backfill \
  --articles OLD_ARTICLES_JSON \
  --root . \
  --feeds feeds \
  --out article_state.json
```

回填会：

1. 清洗旧 `content` 为 Markdown，追加到 `archive/YYYY/MM/DD.md`；
2. 创建/扩展 `feeds/<feed_id>.jsonl`；
3. 写出 metadata-only、带归档偏移的 `article_state.json`。

回填是幂等的：已在 feed 索引中的 canonical link / guid 不会重复写入。`collect.yml` 在 cache miss 且归档缺失时自动执行一次回填；成功后可删除旧 `gh-pages`。

旧 ADR-016 的 `archive/YYYY-MM-DD.jsonl` 是元数据归档，不是新 Markdown 归档。快照步骤会删除这些根级 `.jsonl` 文件，只保留 `archive/YYYY/MM/DD.md`。

迁移后如果索引缺记录，优先用非破坏性的补全：

```bash
python -m src.md_archive --repair-indexes archive --feeds feeds
```

它只追加缺失的 article 记录，保留已有记录和 annotation；`--rebuild-indexes` 才是全量重建并会丢失 annotation。

### 8. 体积与增长

- 归档保存的是**清洗后的 Markdown 正文**，直接进入 git 历史；
- 按当前抓取量估算，年增量在**数百 MB/年**量级；这是为保留原文付出的成本；
- git 自身的 delta/zlib 压缩对 Markdown 有效，文本 diff 可读；不使用 gzip/SQLite，因为二进制会破坏 delta 和可读 diff；
- `data` 每天最多一次快照，普通 push；`archive/`、`feeds/` 只追加，`feed_state.json` / `article_state.json` 整体替换；`status.json` 是派生报告，不进入 `data`，`output/` 也不更新；
- 仓库是公开的，所以只保存 sanitized Markdown；不保存原始 HTML、脚本或未清洗的 feed 内容；
- 迁移前的 `gh-pages` / 旧 `data` 历史可能仍含旧正文。如果仓库体积或版权清理是硬要求，需要重写历史，而不是只改当前 tip。

### 9. 失败与恢复

- **尾部截断**：`python -m src.md_archive --repair ARCHIVE_ROOT` 只截断不完整/不可解析的尾部记录，保留之前所有完整记录；随后 `--validate ARCHIVE_ROOT` 必须返回成功，否则 CI fail closed；
- **索引偏移失效**：冷启动时运行 `python -m src.md_archive --reconcile-indexes ARCHIVE_ROOT --feeds feeds`，逐条校验 offset/length/sha，删除失效 article 及其 annotation，并清空 `article_state.json` 中对应归档引用，让 fetch 重新归档；
- **索引缺记录**：优先运行 `python -m src.md_archive --repair-indexes ARCHIVE_ROOT --feeds feeds`，只补缺失 article 记录，保留 annotation；fetch 也会在下一轮修复 `indexed=false` 的行；
- **索引损坏/丢失**：`python -m src.md_archive --rebuild-indexes ARCHIVE_ROOT --feeds feeds` 从归档重建；annotation 会丢失，需要重新分类或从旧索引人工恢复；
- **分类写入失败**：先追加 annotation，再写 `output/`，最后标记 `classified`；任一失败都会把行退回 pending 并在下一轮重试，不会提交没有 annotation 的 `classified` 状态；
- **cache 驱逐**：从 `data` 恢复 `archive/`、`feeds/`、`feed_state.json`、`article_state.json`，正文不再依赖重新抓取；`status.json` 会重新生成；
- **归档引用失效**：分类时按偏移读取失败会保留 pending 元数据并记录 `archive_error`，不会静默删除；下一轮 fetch 可以重新归档；
- **快照失败**：数据分支不被半成品覆盖；修复后手动触发 `snapshot=true`；
- **push 被拒**：普通 push 后执行一次 `pull --rebase` 重试；并发修改 `feed_state.json` / `article_state.json` 通常无法自动 rebase，此时保持远端不变并报错，需要人工处理。不要 force-push。

## Consequences

优点：

- 原文永久保留在 git，cache 驱逐不再丢正文；
- 按天 append-only，diff 可读、可只 checkout 部分历史；
- 偏移索引让分类和渲染只读取需要的单条记录；
- feed 索引支持按源聚合和 JSON Feed，且可以从归档重建；
- `main` / `data` 职责清晰，Pages 只依赖可重建的渲染产物。

缺点 / 风险：

- 仓库会以数百 MB/年的速度增长，clone 和 fetch 成本上升；
- 公开仓库意味着所有归档正文都公开，必须持续保证 sanitizer 覆盖；
- `data` 每日快照之间仍依赖 cache；cache 在两次快照之间被驱逐时，最近不到 20 小时的正文可能需要重新抓取；
- 当前 cache 保存完整 `archive/` + `feeds/` 作为热副本，archive 达到数百 MB 后，每轮 restore/save 的传输量和 10GB cache 配额会成为瓶颈；下一阶段应改为只缓存最近窗口/增量渲染，或把旧归档移到对象存储；
- annotation 是派生状态，索引重建会丢失分类历史；
- 旧的 `gh-pages` / ADR-016 历史不会自动缩小，需要时另行清理。
