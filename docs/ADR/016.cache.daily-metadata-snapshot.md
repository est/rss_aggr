## Context

ADR-015 把运行时状态和渲染输出拆到 `data` / `gh-pages` 两个分支，并去掉了旧的固定 key `actions/cache`。但每次采集都 force-push 完整运行时状态到 `data`，对长期仓库体积和写放大没有约束；同时 `gh-pages` 与 Pages artifact 部署重复，已经没有存在必要。

本 ADR 基于仓库体积基准重新划分长期存储与短期状态：

| 存储内容 | 估算体积 | 说明 |
|----------|----------|------|
| 含正文的 `articles.json`（raw `content`） | ~300 MB/年 | 每 6 小时覆盖提交，且正文很少变化，git 历史仍会保留旧 blob |
| 仅元数据的每日快照 | ~14 MB/年 | 每天一个 commit，去掉正文后单日增量很小 |

如果将来确实要把正文放进 git，按天拆分的 plain JSONL（`archive/YYYY-MM-DD.jsonl`）优于单个大 JSON：每天一个文件、append-only、diff 可读、可只 clone 部分历史。对比之下：

- gzip 在 git 中几乎不减少长期体积：git 自身已做 delta/zlib 压缩，压缩后的二进制还会破坏 delta 和可读 diff；
- SQLite 是单文件二进制数据库，每次提交都是新的 blob，无法按天增量，合并/冲突不可读；
- 缩短 `articles.json` 的保留窗口不会缩小历史。14 天清理只影响当前 tip，被删除的记录仍留在旧 commit 中。

因此长期体积由“提交进 git 的数据形态”决定，而不是由当前工作区保留多少天决定。

## Decision

### 1. 原始正文只进 Actions cache

`articles.json` 中的 raw `content` 只保存在 `actions/cache`：

- 每次运行用 `actions/cache/restore@v4` 恢复 `.runtime/`；
- 运行结束后用 `actions/cache/save@v4` 保存 `state.json`、`articles.json`、`status.json`、`output/`、`archive/`；
- cache 是热数据，不是事实来源；允许被 GitHub 在长期未使用或容量压力下驱逐。

cache key 为 `rss-runtime-${run_id}`，通过 `restore-keys: rss-runtime-` 恢复最近一份。key 每轮唯一，避免不可变 cache 被覆盖；`cache-hit` 只表示精确命中，日常运行通常通过前缀恢复，因此恢复逻辑以 `.runtime/` 中实际文件及其 JSON 校验结果为准。

### 2. `data` 分支保存每日元数据快照

`data` 分支不再是每 6 小时的完整状态镜像，而是**每天最多一次**的元数据快照：

```
data/
  state.json          # feed 健康、ETag、失败计数
  articles.json       # 14 天窗口元数据，去除 content
  status.json         # 最近一次运行报告
  output/             # 渲染输出（append-only）
  archive/            # 可选，按天 JSONL：archive/YYYY-MM-DD.jsonl
```

- 快照由 `python -m src.archive --snapshot DEST` 生成；该 CLI 只写元数据，不写 raw content。
- 如果将来 `archive/` 需要记录正文，仍使用按天拆分的 plain JSONL（`archive/YYYY-MM-DD.jsonl`），不使用 gzip 或 SQLite。
- 到点条件：`data` 最后一次 commit 超过约 20 小时，或手动触发时 `snapshot=true`。
- 提交信息固定为 `data: snapshot YYYY-MM-DD`。
- 使用正常 push，不再 force-push；被拒绝时执行一次 `git pull --rebase` 后重试。因为快照会整体重写 `state.json` / `articles.json`，真正的并发冲突通常无法自动 rebase，此时保持远端不变并报错，等待下一次快照或人工处理。
- `data` 只由 CI 写入，内容必须严格限制在上面的路径集合内。

### 3. 不再使用 `gh-pages`

Pages 从 Actions artifact（`upload-pages-artifact` + `deploy-pages`）部署，`gh-pages` 不参与部署，也不再保存站点或运行时快照。迁移完成后可以删除远端 `gh-pages`；`backup/*` refs 按需保留一段时间。

### 4. 恢复与 bootstrap

每次 `collect` 的恢复顺序：

1. 优先恢复并校验 `.runtime/`（state + articles 均为合法 JSON）；
2. cache 缺失或损坏时，从 `data` 恢复 `state.json` / `status.json` / `output/` / `archive/`；
3. `data` 不存在时，允许一次性从旧 `gh-pages` 迁移 `state.json`、`output/`，并把旧 `articles.json` / `cache.json` 剥离正文后保留 pending 元数据；
4. `data` 已存在但缺少 `output/`（ADR-015 布局）时，冷启动从旧 `gh-pages` 补一次 `output/`，保留历史页面；
5. 两者都不存在时以空状态启动，首次成功运行后创建 `data`。

cache 未命中时，`data` 的 `articles.json` 是元数据-only，不能直接作为可分类的正文缓存。工作流保留这些元数据记录，设置 `RSS_FORCE_FETCH=1`，让 fetch 忽略 ETag 和抓取间隔、重新抓取完整的 14 天窗口；抓到的正文按 canonical link 回填到对应 pending 记录。源已经不再暴露的正文无法恢复，但标题/元数据保留，文章仍会继续分类或标题-only 输出。

恢复失败（`data` 存在但取不到、文件缺失或 JSON 损坏）必须让 job 失败，并禁止写 `data` 快照。工作流用 `.restore-data-ok` / `.cache-save-ok` 标记记录成功路径；任何未标记成功的运行都不会覆盖 `data`。

### 5. Cache 驱逐与恢复

- cache 被驱逐：下一次运行走 `data` 恢复 + 全量 14 天重抓，然后重新保存 cache；
- cache 损坏：与驱逐相同，记录 warning，绝不把损坏内容写回；
- cache 保存失败：下一次可能恢复到较旧的 cache；`data` 快照必须从当前工作区、经过 `.restore-data-ok` / `.cache-save-ok` 和 JSON/archive 校验后才会写入，不能把失败缓存当成事实来源；
- `data` 快照失败或 push 被拒：下一次运行仍从 cache 恢复，快照在 20 小时窗口后重试；
- 人工需要恢复旧状态时，从 `data` 历史 commit 或 `backup/*` 恢复 `state.json` / `output/`，然后等待下一轮冷启动重建 `articles.json`。

## Consequences

优点：

- git 年增量从约 300 MB 降到约 14 MB；
- 正文不进入新的长期历史，仓库不会因每 6 小时的完整状态提交持续膨胀；迁移前的 `gh-pages`/旧 `data` 历史仍可能包含正文。如果仓库体积或版权清理是硬要求，需要重写/重建那些历史，而不是只改当前 tip；
- `data` 每日一次、普通 push，历史可读且可回滚；
- 只有一个派生分支，删除 `gh-pages` 后分支职责更简单；
- 恢复路径有明确优先级和失败保护。

缺点 / 风险：

- cache 是热数据，不是事实来源；生产状态最多回退到最近一次 `data` 快照；
- pending 元数据会保留在 `data`，但正文只存在于 cache。cache 驱逐时需要从 feed 重新抓取正文；源已经不再暴露的正文无法恢复，对应文章会退化为标题/元数据分类；
- 每日快照意味着 `data` 的 `state.json` 可能比当前运行旧最多约一天；
- 首次迁移依赖旧 `gh-pages` 的 state/output，迁移完成后旧分支即可删除；
- `data` 历史仍会随 `output/` 增长，但增长速度与站点输出一致，不再包含正文；
- `archive/` 的去重范围是目标日期文件；同一链接如果因为 `cached_at` 变化被重新归档到另一天，可能出现跨天重复。`archive/` 是追加日志，不是权威去重源，去重仍以 `output/` 和 `articles.json` 为准。
